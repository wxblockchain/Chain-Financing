# 面客消息中心 · 功能与业务规则

2026-10-15｜面客端：资产方、资金方｜需求评审稿

本模块共三册：本册写功能、业务规则、字段规则与交互逻辑；[流程图与状态机](./02-面客消息中心-流程图与状态机.md)画出主要流程与状态；[验收](./04-面客消息中心-验收.md)供测试使用。各模块统一按 01 功能、02 流程、03 消息通知、04 验收编排；本模块自己不发送任何消息，所以没有 03 册，并非缺失。

编号说明：功能编号 `F-NC-*` 只标在章节标题上，供验收追溯；文中其余编号都是其他模块或原型会引用的（如 `IF-NC-01`）。编号沿用原值，已删除的条目不再占号，所以编号不连续，缺号不代表遗漏。

<a id="design-boundary"></a>
本册只定义信息需求与业务行为；页面布局、组件形态、层级与视觉由 Hallmark 设计决定。本册措辞与设计稿冲突时以设计稿为准，业务口径仍以本册为准。

## 1. 模块是什么

面客消息中心是借贷平台面客端的**本人站内信箱**。资产方、资金方的业务中发生需要本人知道的事情时，由对应的业务模块发出一条站内信。消息中心负责让本人：

1. 在任何已登录页面看到未读数；
2. 打开消息列表，按分类和已读状态筛选；
3. 打开一条消息读完整内容，读完自动变为已读；
4. 需要时从消息前往原业务查看或办理，再回到列表原来的位置。

三条基本原则：

- **消息中心自己不发消息。** 发什么、何时发、发给谁、写什么，都由来源业务模块决定，并在各自模块的消息通知册中维护。本册只定义消息中心的通用框架，来源模块增减或修改消息时，本册不需要随之修改。
- **读消息不等于办业务。** 已读不代表已确认、已付款或已处理，办理始终在原业务页面完成。
- **消息记录的是当时的事实。** 原业务之后发生的变化，不改写旧消息里的金额、时间和原因。

**一个完整的例子。** 以放款为例：资金方登记了一笔放款 → 放款模块按其通知规则，向这笔业务的资产方发出一条消息 → 资产方在任意页面看到消息入口的未读数加 1 → 打开消息列表，点开这条消息；详情展示成功后，这条消息自动变为已读，未读数减 1 → 资产方从详情前往这笔放款 → 办完后返回，回到原来的消息列表位置，筛选条件不变。（例子只说明消息中心的处理过程；具体发什么消息、去向哪里，以放款模块的消息通知册为准。）

### 1.1 本期不做

- 不发送、编辑或撤回消息，不维护消息模板。
- 不提供删除、归档或清空，消息长期保留。
- 不提供逐条“标为已读”和“标为未读”：打开详情即已读，另有“全部已读”。
- 不提供通知开关或偏好设置。
- 不汇总其他平台或运营端的消息，也不合计它们的未读数。
- 消息不直接跳转到其他平台。
- 正文只支持纯文本，不支持富文本或可执行内容。

<a id="same-system"></a>
### 1.2 与运营端消息通知的关系

本模块与[运营端消息通知](../../运营端/07-运营端消息通知/01-运营端消息通知-PRD.md#same-system)是同一套站内信能力在两个端的实现。消息归属、未读数、最近预览、列表取数、已读与全部已读、同一事实只收一条、前往原业务、登录失效等规则，按设计两端相同，各自在本端册内写明。按设计，两端的差异只有下表三项：

| 项目 | 面客端（本模块） | 运营端 |
| --- | --- | --- |
| 谁收消息 | 只有收件人本人 | 另有“全体运营”共享的消息 |
| 谁能进入 | 已登录且已判定为资产方或资金方 | 按运营端功能权限 |
| 打开原业务时按什么判断权限 | 借贷平台面客端的业务权限 | 运营端权限矩阵 |

任何一端修改共同规则时，须同批核对另一端。

## 2. 术语

| 术语 | 含义 |
| --- | --- |
| 面客端 | 借贷平台中资产方、资金方使用的一端，与运营人员使用的运营端相对 |
| 来源模块 | 发出消息的业务模块，例如放款、还款模块；它对消息内容和收件人负责 |
| 原业务 | 消息所说的那一笔具体业务，例如某个项目、某笔报价、某笔放款的某一期 |
| 原动作 | 消息提示可以去做的那个办理动作，例如“确认到账”；原业务往下推进后，它可能已经不适用 |
| 未读数 | 本人仍在有效期内、尚未读过的消息条数 |
| 最近消息预览 | 从消息入口打开、展示最近 10 条的简要列表 |
| 壳层 | 平台所有页面共用的外框，包括账号菜单；消息入口由它提供 |
| 消息有效期 | 来源为某条提醒设的截止时点；过期后不再计入未读数，消息仍可查看。是否设有效期由来源决定，没有设的消息一直有效 |
| 共享登记 | 各来源统一登记消息类型、分类和文案的地方，两端共用同一份。完成登记并验证真实送达，该来源才算“已适配”；未完成前为“待适配”。登记放在哪里、如何实现由研发小队确定 |

<a id="f-nc-01"></a>
## 3. 谁能看到哪些消息（F-NC-01、F-NC-02、F-NC-05）

| 访问者 | 消息入口与未读数 | 能否读消息 |
| --- | --- | --- |
| 游客（未登录） | 不展示 | 不能。从链接直接打开列表或某条消息时，先登录，成功后回到原列表或原消息 |
| 已登录资产方 | 展示 | 只能读本人作为资产方收到的消息 |
| 已登录资金方 | 展示 | 只能读本人作为资金方收到的消息 |
| 登录未绑定角色 | 不展示 | 不能；此状态下不产生站内信，也没有消息入口 |
| 运营人员、SPV | 不进入面客消息 | 不能；运营端有自己的消息 |

- 每条消息只属于一个收件账号，只在借贷平台面客端可见。
- 本期一个企业只有一个员工账号，这个账号就是该企业的收件人。资产方与资金方是两个不同的收件人：同一笔业务需要双方都知道时，各收一条、各自已读。
- 同一钱包下的资产方身份和资金方身份是两个账号，彼此的消息互不可见。
- 收件人只认本平台账号，不按邮箱、钱包地址或其他平台的身份判断。
- 打开他人的消息与打开不存在的消息，看到的结果完全相同，不透露这条消息是否存在；猜测编号或批量访问也取不到他人消息。
- 运营端消息和其他平台的消息不进入本模块，也不计入未读数。
- 资产方认证不足只限制相关业务的办理，不影响阅读本人消息。
- 收到消息不代表获得原业务的查看或办理权限；前往原业务时按当前权限重新判断（见[第 8 节](#f-nc-23)）。

<a id="f-nc-06"></a>
## 4. 消息从哪里来（F-NC-06～F-NC-09）

每条消息都由一个来源模块发出。来源模块在自己的消息通知册中写明在哪个功能、哪个环节发出、发给谁、写什么、打开后去哪；本模块不罗列各来源的具体消息，只规定所有消息共同遵守的规则（4.1、4.2）、来源接入时要登记的信息（4.3）和统一的消息分类（4.4）。

### 4.1 一条消息包含的信息

| 信息 | 规则 |
| --- | --- |
| 收件人 | 必须是确定的本平台账号。无法确定时不发送，不用企业、邮箱、钱包、最近操作人或全体成员代替 |
| 分类 | 按 [4.4 节统一分类](#categories)展示，每条消息归入一类。分类无法识别时显示“其他 / Other”，消息照常展示 |
| 标题与正文 | 中文、英文各一套完整文本。当前语言缺失时显示另一种语言；两种都无法展示时，用分类、发生时间和通用标题“通知 / Notification”展示这一条，不影响其他消息。正文是纯文本，不出现模板占位符或技术标识 |
| 发生时间 | 业务事实发生的时间。重复送达、阅读、切换时区都不改变它 |
| 原业务名称与编号 | 来源提供时展示，编号可复制；不用其他业务的信息补位 |
| 金额与币种 | 取事件发生时的金额与币种；之后汇率或计划变化，不改写旧消息。未知时不显示为 0 |
| 业务日期与时刻 | 业务日期按 UTC；具体时刻按用户偏好的时区展示并标明时区，无偏好时按 UTC |
| 原因 | 来源提供的原因原文完整展示；用户自己填写的原因不做翻译 |
| 打开后去哪 | 三选一：原业务、本平台的某个固定页面、不跳转（见[第 8 节](#f-nc-23)） |
| 消息有效期 | 可选，只有来源明确规定时才设 |

- 切换界面语言后，历史消息的标题和正文随之切换，金额、时间、期次等事实不变。
- 同一事件按收件角色或结果有不同文案时，每个收件人只按条件选用其中一套，不因为有两套文案而多收一条。
- 来源要求逐项对照的消息（例如分期计划的预计与定稿对照），所有条目在同一条消息中完整给出，不拆成多条，也不能只写“去详情查看”。

<a id="if-nc-10"></a>**敏感信息（IF-NC-10）。** 消息标题和正文中不得出现：私人邮箱、完整钱包地址（质押链上的代币持有地址和结算收款链上的收款地址都适用）、证件号、IP 地址、完整的银行账户或凭证内容；也不出现客服邮箱。消息只展示来源已经授权的必要业务名称、金额和编号，不复制对方的完整档案或私人联系方式。

<a id="if-nc-01"></a><a id="q-nc-04"></a>**送达时效（IF-NC-01）。**

- 业务事件发生后 60 秒内，消息出现在列表中，未读数同步更新。60 秒从业务事件发生时起算，不从系统延后处理完成时起算。
- 由时间到点触发的事件（例如到期、逾期），从应到的时点起算，**最晚 6 分钟内**可见：来源判定最多用 5 分钟，消息展示最多再用 60 秒。来源模块的判定延迟须控制在 5 分钟以内，否则不能满足这一承诺。（此条是原待确认事项 `Q-NC-04` 的结论。）

### 4.2 同一件事只收一条

- 同一收件人的同一业务事实只有一条消息。重复送达、重试、刷新、重新登录都不新增消息，也不改变这条消息的排序位置、发生时间和已读状态。
- 已经读过的消息，再次收到同一事实，仍是已读。
- 同一笔业务上发生了新的真实事实（新的一期、新的一轮、新的一次操作），各自是一条新消息。
- 来源对同一事实补充信息时，在原消息上补齐；补齐不倒退事实，也不让消息重新变为未读。
- 只有来源明确规定合并时才合并（例如一次操作同时产生两个结果，来源规定只发一条合并消息）。本模块不按同一天、同一项目或同一个人自行合并。

### 4.3 来源接入时需要登记的信息（RG-NC-01～RG-NC-12、RG-NC-14）

供各来源模块接入时对照填写。编号沿用原值（不连续，见本册开头的编号说明）。

| 编号 | 登记内容 | 要求 |
| --- | --- | --- |
| `RG-NC-01` | 业务类型标识 | 三段式“业务域.对象.动作”，动作里的下划线不算分段；登记后不再改名 |
| `RG-NC-02` | 分类 | 从 [4.4 节统一分类](#categories)中选一个；来源不能自造分类 |
| `RG-NC-03` | 平台与端 | 固定为借贷平台面客端 |
| `RG-NC-04` | 收件人 | 按 4.1 的收件人规则 |
| `RG-NC-05` | 发送来源 | 唯一负责发送的业务模块；其他模块不发同义消息 |
| `RG-NC-06` | 打开后去哪 | 原业务、固定页面、不跳转三选一 |
| `RG-NC-07` | 原业务定位 | 指向原项目、原申请、原业务，以及必要的原期次或原动作；写明原业务状态变化后用户能看到什么。固定页面须是本平台已登记的页面 |
| `RG-NC-08` | 查看与办理条件 | 谁能查看原业务、谁能办理 |
| `RG-NC-09` | 同一事件的区分依据 | 收件账号 + 原业务 + 事件，以及必要的次数、期次或节点 |
| `RG-NC-10` | 中英文文案 | 每种角色或结果一套完整的标题和正文 |
| `RG-NC-11` | 消息有效期 | 可选，见 4.1 |
| `RG-NC-12` | 适配状态 | 默认“待适配”；共享登记、收件账号、文案与真实送达都验证完成后才是“已适配” |
| `RG-NC-14` | 合并规则 | 有同次结果合并时，写明合并条件以及保留哪些事实 |

<a id="categories"></a><a id="q-nc-01"></a>
### 4.4 消息分类（与运营端统一）

面客端与运营端使用同一套消息分类（此节是原待确认事项 `Q-NC-01` 的结论）。每条消息由来源按下表定义归入其中一类。

| 分类 | English | 归入什么消息 | 适用端 |
| --- | --- | --- | --- |
| 业务办理进度 | Business progress | 某项业务有了办理结果或进入下一步，例如审核有了结论、对方已处理、业务已完成 | 两端 |
| 业务提醒 | Business reminders | 业务状态本身没有变化，但需要用户注意，通常由时间或条件触发，例如即将到期、已逾期、条件不足或已恢复 | 两端 |
| 认证与合规 | Verification & compliance | 认证、资格或合规状态发生变化，例如认证通过、驳回、失效、权限暂停 | 两端 |
| 账户安全 | Account security | 账户本身的安全相关变化，例如联系邮箱或密码变更、账户停用或恢复 | 两端 |
| 审核任务 | Review tasks | 有新的事项等待本端人员审核处理 | 运营端 |
| 运营告警 | Operations alerts | 平台定时或自动处理的结果需要运营人员知悉，尤其是失败或被撤销 | 运营端 |

- 消息列表的分类筛选只显示本人实际有消息的分类，所以面客端用户通常只看到前四类。
- “其他 / Other”只是分类无法识别时的兜底，不是可选的分类。
- 新增或调整分类时，须同时修改本表和运营端消息通知册中的同一张表。

<a id="f-nc-11"></a>
## 5. 消息入口、最近预览与未读数（F-NC-03、F-NC-11～F-NC-13）

**入口。** 已登录资产方、资金方在平台每个页面都有消息入口并显示未读数；账号菜单里也有“消息中心”。游客和登录未绑定角色的用户都看不到消息入口。从消息入口打开最近消息预览；从账号菜单直接进入完整消息列表（不带筛选）。

**最近消息预览。**

- 展示最近 10 条，已读和未读都包括；每条可看到标题、摘要、分类、时间和是否已读。
- 只打开预览不会让消息变为已读；点某一条进入它的详情。
- “查看全部”进入完整消息列表。
- 预览里不提供“全部已读”，避免误以为只处理这 10 条。
- 没有消息时明确说明还没有消息。

**未读数。**

- 等于本人有效且未读的消息条数，全部分类合计；列表中的未读状态与未读数一致。
- 过了有效期的消息不计入未读数，但仍可在列表和详情中查看，并标示“已过期”。
- 原业务已办完、原业务不可访问、消息类型尚未登记，都不影响计数：只要消息有效且未读，就计入。
- 为 0 时不显示数字；超过 99 时显示“99+”。
- 读取失败时保留上一次的数字，不清零。
- 新消息到达时，未读数和列表一起更新，不打断用户当前的操作。在一个浏览器标签里读了消息，同一账号的其他标签也随之更新。

<a id="f-nc-14"></a>
## 6. 消息列表与筛选（F-NC-04、F-NC-14～F-NC-17）

**列表。** 消息列表（页面编号 `P-F-MC-01`）有独立网址，可以直接打开和刷新，范围是本人的全部消息，不受预览 10 条的限制。消息长期保留，不会被自动清理；已过期的消息仍在列表中。每条可看到标题、摘要、分类、时间和是否已读，点击即进入详情。

**筛选。**

- 分类：“全部”加上本人实际有消息的分类；无法识别分类的消息归入“其他”。
- 阅读状态：全部、未读、已读，默认“全部”。
- 两个条件同时生效。刷新页面后筛选保持不变；修改筛选后从第一条重新开始。

**排序。** 按消息创建时间从新到旧；同一时间的顺序固定。重复送达不改变顺序，读过也不重排。在“未读”筛选下读过的消息，仍留在当前结果中，重新筛选或刷新后才按新条件移除。

**加载。** 每次加载 20 条，“加载更多”把结果追加到已加载内容之后；没有更多时明确提示。不提供页码跳转，也不显示包含已读在内的消息总条数。

**新消息。** 有新消息到达时，符合当前筛选条件的自动插入列表顶部，不需要用户操作，也不改变用户当前的阅读位置；不符合当前筛选的不插入，切换到对应筛选时才能看到。自动插入只增加新消息，不重新筛选已加载的结果，所以在“未读”筛选下读过的消息不会因此被移走。已加载和后续加载的结果不重复、不遗漏。

**空列表。** 从未收到过消息时，说明还没有任何消息；筛选后没有结果时，说明当前筛选下没有消息，并可一键清除筛选。两种情况须能区分。

**加载失败。** 第一批加载失败时可以重试；“加载更多”失败时，保留已加载的内容和所在位置；加载过程中不显示为空列表；某一条内容异常只影响这一条，其他消息照常展示。

<a id="f-nc-18"></a>
## 7. 消息详情、已读与全部已读（F-NC-18～F-NC-21）

**详情。**

- 消息详情（页面编号 `P-F-MC-02`）有独立网址，可以直接打开和刷新，刷新后仍是同一条消息。
- 展示完整标题、分类、带时区的发生时间、完整正文、来源提供的业务信息，以及前往原业务的入口（如有）。
- 返回：从列表进入的，返回后回到原来的列表，筛选条件、已加载的批次和所在位置都保持不变；刚读过的消息在列表中原地变为已读，不移动位置。直接从链接打开、没有列表可回的，返回到不带筛选的消息列表。从原业务页面后退，可以回到这条消息。

**自动已读。**

- 详情内容展示成功后，这条消息自动变为已读，未读数同步减少。
- 详情加载失败时，不算已读。
- 已读保存失败时：消息仍显示为未读，正文照常可读，并提供“重试”；重试只处理已读，不会重新发送消息，也不会执行业务。
- 已读的消息再次打开，不重复扣减未读数。只打开预览、滚动经过或复制编号，都不改变已读状态。

**全部已读。**

- 作用范围：当前筛选条件下本人全部未读的消息，包括还没有加载出来的部分。
- 执行前须确认。确认时写明当前筛选条件，以及将被标为已读的未读条数：“将把当前筛选下的 {count} 条未读消息标为已读。”／“Mark {count} unread message(s) under the current filter as read.”
- 取消时，所有消息保持不变。
- 成功后，范围内的消息全部变为已读，未读数同步更新。失败时全部保持原状，可以重试；不会出现只成功一部分的情况。
- 当前范围内没有未读消息时，不提示“已清除”其他消息。确认之后新到的消息不在本次范围内，仍为未读。
- 全部已读只改变阅读状态，不代表相关业务已经完成。

<a id="f-nc-23"></a>
## 8. 前往原业务（F-NC-23～F-NC-26）

**去向。** 每条消息打开后去哪由来源决定，三选一：原业务、本平台的某个固定页面、不跳转。不接受站外地址。

- 前往原业务时，必须定位到消息所说的那一笔（包括那一期、那一次动作），不换成最新一笔、下一期或当前默认选中的业务。
- 消息中心本身不办理业务；查看和办理都在原业务页面完成，由用户主动操作。

**进入详情时按原业务当前情况处理。** 进入详情时，按当前权限检查原业务能否查看、能否办理；列表中不逐条检查。检查超过既定的等待上限（3 秒）或检查失败时，仍允许用户前往，由原业务页面重新判断权限。

| 原业务当前情况 | 用户能做什么 | 消息本身 |
| --- | --- | --- |
| 有权查看，消息提示的动作仍可办理 | 前往原业务查看或办理 | 正常展示；未读时计入未读数 |
| 有权查看，但消息提示的动作已办完或已不适用 | 前往查看这一笔的当前结果；不再提供旧动作，也不换成其他业务 | 正文保留当时的事实 |
| 消息已过有效期，原业务仍可查看 | 可以查看原业务；原业务还能不能办理，以原业务当前状态为准（提醒过期不代表业务不能继续办理） | 标示“已过期”，不计入未读数 |
| 原业务不存在，或本人无权查看 | 不能前往；统一显示“相关内容暂不可访问 / The related content is unavailable”，不区分是不存在还是无权 | 正文照常可读；仍有效且未读时计入未读数 |
| 消息类型尚未登记，或来源设为不跳转 | 没有前往入口，也不提示错误 | 正常可读、正常计数 |

**从链接直接打开本平台页面。**

- 本平台已登记的页面：直接打开原目标。未登录时先登录，成功后回到原目标。
- 已登录但无权查看：按平台统一的权限不足引导处理，不展示私有内容。
- 不认识的平台或页面：进入平台默认的资产广场，不出现空白页。
- 本期消息不跳转到其他平台；来源业务自身已确认的外部办理路径不受影响。

<a id="f-nc-27"></a>
## 9. 登录状态与安全（F-NC-27、F-NC-28）

- 退出登录或登录失效时，消息入口、未读数、预览、列表和详情同时清除。必须真正清除，不能只是遮住而数据仍可取到；之后迟到的数据也不再显示。
- 任何一处读取消息时发现登录已失效，都按失效统一处理。
- 自动更新消息不算用户活跃，不延长登录有效期。

<a id="console-boundary"></a>
## 10. 与我的控制台的分工

- 消息记录已经发生的事；我的控制台显示业务当前的状态。
- 读了消息不影响控制台上的业务提醒；业务办完也不会把消息改为已读。
- 控制台不发送消息。控制台的[待办](../09-我的控制台/01-我的控制台-PRD.md#todo)由业务事实产生，与消息未读数互不代替：读信不消除待办，办完待办不把消息标为已读。
