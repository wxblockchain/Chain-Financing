# 放款与放款确认 · 消息通知

2026-09-24｜配套当前 PRD。

本册只定义通知的事件、收件范围与内容；通知的承载形式与视觉由设计决定（见[统一条款](01-放款与放款确认-PRD.md#design-boundary)）。事件、收件账号、时间和双语文案以本册为准；完整业务见[PRD](01-放款与放款确认-PRD.md)，同序验收见[主册验收](01-放款与放款确认-PRD.md#acceptance)，流程见[图册](02-放款与放款确认-流程图与状态机.md)。

**本模块发送两类关键站内信：放款记录已提交、资产方已确认到账。** “报价已接受／进入待放款”由 L6 发送，L7 不重发。本批（2026-09-24）随盖章件核验、要求重传、暂不放款、放款前终止与放款确认时限取消，原临期提醒、确认超期、要求重传、放款前终止四类站内信及其模板与规则一并废止，见[第 8 节](#retired-notify)；本模块不新增运营广播。

<a id="events"></a>
## 1. 哪个环节发送站内信

`N-LN-01` 与 `N-LN-04` 为本文件现行通知编号。每条都识别原融资申请 `FP-28` 和融资业务 `FD-01`；成功登记放款才有放款编号 `LN-01`。一个申请可先后出现不同 `FD-01`，消息不能改投该申请的“最新一笔”。

| 编号 | 发送节点与条件 | 收件人及次数 | 告知内容与下一步 | 业务依据 |
| --- | --- | --- | --- | --- |
| <a id="n-ln-01"></a>N-LN-01 | 资金方放款记录正式提交成功，生成 `LN-01` 并从 `S-FD-3` 进入 `S-FD-4` | 本笔资产方收件账号，一次 | 哪家资金方登记了哪笔放款、币种金额与提交时间；自行核实到账后确认，未到账不要确认。**不含确认截止或剩余时限** | F-LS-49/52 |
| <a id="n-ln-04"></a>N-LN-04 | 资产方确认到账正式成功，`FD-35` 与两维度金额转移成立，进入 `S-FD-6` 并触发计划生成 | 本笔放款登记资金方账号，一次 | 已确认到账、确认时间及真实计划进度；前往同笔还款信息查看，不能将生成触发说成生成完成 | F-LS-52/55、E-LN-13、L8当前计划规则 |

所有消息均以正式业务事实为依据；点击、文件上传完成、提交中或结果未知不构成成功通知。`N-LN-01` 不另给资金方发送提交回执；`N-LN-04` 不另给资产方发送本次确认回执。

<a id="excluded"></a>
### 1.1 三方中哪些场景不发

| 场景 | 本期处理 |
| --- | --- |
| L6 接受报价、进入待放款 | 由 L6 唯一发送；放款清单入列不是第二个通知事件 |
| 资金方暂时不付款、长期停留在待放款 | 本批取消暂不放款动作，没有可登记的处置事实，不发信、不催办 |
| 合同版本或条款争议 | 盖章件与重传已取消，争议线下解决，平台不发相关站内信 |
| 待放款阶段不再继续 | 没有终止动作，也没有对应通知；业务停留在待放款是既定后果，见[主册 7.2](01-放款与放款确认-PRD.md#limits) |
| 资产方长期未确认到账 | 确认时限取消，不再有临期提醒、超期通知或周期催办；等待事实在业务页面中性可读 |
| 阅读、下载、填写账户、上传凭证 | 在办理或详情中反馈；无平台审核消息 |
| 有效质押额不足、项目期限变化、代币事实变化 | 额度与项目事件归 L5；L7 不复制。同笔 `S-FD-3/4` 不因此被自动失效或终止 |
| 表单失败、凭证格式错误、资料缺失、通知失败 | 原场景说明原因与恢复路径，不虚构成功事件或新增失败广播 |
| 还款计划生成中、生成恢复 | L7 不补发第二次确认到账。L8 向资产方发送其计划定稿通知；资金方从 `N-LN-04` 查看同笔实际进度，L8 不再给资金方重复发定稿提醒 |
| 运营管理人员日常查看、客服邮件往来 | 没有本模块新审批、裁决、代确认或强制终止职责，不自动生成运营通知或把面客事件抄送全体运营 |
| SPV机构 | P04 已明确与运营人员一致，本期无资金动作、审批或代确认权，不接收本模块通知；不另设 SPV 通知 |

## 2. 收件账号与跨模块发送归属

### 2.1 企业业务权限不等于全员收信

<a id="n-ln-r01"></a>N-LN-R01：消息属于借贷平台面客端的自然人账号。本期**一个企业只有一个员工账号**（用户 2026-09-24 裁定），该账号即该企业在本模块的收件归属；不开放员工管理，也不按企业名、邮箱、钱包地址或另一平台账号代替收件归属。原多成员责任账号待定项 `Q-LS-N01` 随之闭合。

| 角色 | 本模块收件范围 |
| --- | --- |
| 资产方 | `N-LN-01` 发送给本业务已明确关联的资产方企业账号 |
| 资金方 | `N-LN-04` 发送给本笔成功提交放款记录的本平台账号，依 `LN-14` 确定，属于本笔报价机构 |
| 运营管理人员 | 两类事件均不接收。业务可见权及既有线下职责不因此扩大；无运营全员、角色组或指定运营账号的新模板 |
| 游客、其他机构 / 资产方、其他端或同钱包的另一身份 | 不接收、不共享该条消息。同一人若有两种平台身份，按本次业务对应的账号及端隔离 |

收件归属缺失不能以当前登录者补位。账号停用、失去目标访问资格不自动改投他人；历史消息也不随另一人后来办理转移所有权。

<a id="ownership"></a>
### 2.2 每个事实只有一个发送模块

| 事实 | 唯一归属与边界 |
| --- | --- |
| 报价被接受、进入待放款 | L6。L7 不另建“已进入放款流程”事件，不将其说成已放款 |
| 登记放款、到账确认 | L7 `N-LN-01`、`N-LN-04`；清单、控制台及消息中心只承接，不另发同义信 |
| 覆盖不足造成需求与待接受报价失效 | L5 合并通知；已接受的 `S-FD-3/4` 不适用这条失效 |
| 到账确认与还款计划 | L7 向放款登记资金方发 `N-LN-04`；L8 向资产方发计划定稿通知。计划尚未完成时，L7 不等计划成功才承认到账，也不告知已生成；之后不向资金方再发同义“确认完成／计划已生成” |
| 还款登记、还款确认、逾期、结清 | L8 定义其通知。融资放款清单确认到账后固定显示“已放款”，不随还款状态变化再次发 L7 消息 |
| 线下客服处理 | 客服邮箱是业务页面上的线下联系入口，不是本期新增邮件推送、运营站内待办或平台介入事件；本批后客服邮箱不再进入任何通知正文 |

## 3. 防重复与真实结果

<a id="n-ln-r05"></a>N-LN-R05：同一面客账号、同一 `FD-01`、同一通知事件只收一次。同一事实重复到达不产生第二条、不重新置顶、不恢复未读、不改发生时间；不同真实节点不合并覆盖。`FP-28` 相同但新 `FD-01` 的新业务独立通知。

<a id="n-ln-r06"></a>N-LN-R06：消息保留事件发生时的金额、机构与时间；标题“已提交”仅表示平台登记，不代表资金已到账、已由平台核验或已上链确认。`N-LN-04` 仅在确认及本笔金额转移成功后发送；计划是否定稿采用实际进度选择完整模板，不能靠修改状态词拼接。读信、全部已读、打开旧目标不代替确认或还款。

<a id="n-ln-r08"></a>N-LN-R08：通知失败不回滚已提交 / 已确认事实，不重置额度；业务页面仍可查询准确状态和时间。条件、账号、模板齐备后沿面客消息中心 IF-NC-01 要求，业务事件后 60 秒内在消息列表及未读数一致可见。本模块已无任何到期判定指标，原“超期判定目标 ≤1 分钟、最坏 ≤5 分钟”与 60 秒可见的冲突随时限取消而消失，不需要再做联验裁决。

## 4. 登记输入与完整中英模板

<a id="registration"></a>
### 4.1 两个既有事件标识

两个既有业务标识如下，包含 `financing.deal.confirmed`。下表与本章共同提供面客消息中心 RG-NC-01～12 所需业务登记输入，状态均为“待适配”，不代表共享登记已经完成。无需报文或技术分册。

| 通知 | 原业务类型标识 | 分类语义 | 模板 | 去重业务范围 | 消息自身失效时点 |
| --- | --- | --- | --- | --- | --- |
| N-LN-01 | financing.disbursement.submitted | 业务办理进度 | T-LN-01 | 本账号＋FD-01＋本次放款提交 | 不设失效；业务无确认时限，随时可核实后确认 |
| N-LN-04 | financing.deal.confirmed | 业务办理进度 | T-LN-04A / 04B 按真实计划进度择一 | 本账号＋FD-01＋本次到账确认 | 不设失效；计划生成恢复不重发 |

共同登记项：平台与端为“借贷平台·面客端”，触发方为 L7；收件人依第 2 章；跳转形态均为本平台业务对象，落点见第 5 节，均需按当前身份与业务状态预判。`P-LS-08` 是既有办理承载编号，不为本模块另申请新的消息目标。分类只给用户语义，正式取值待核对，不能将旧 `business_progress` 自动当作新平台全部分类的已确认值。

模板命名沿 `msg.<业务类型标识>.title` / `msg.<业务类型标识>.body`；`T-LN-*` 为本文完整文案引用号，04 的条件变体不新增事件、也不形成双份消息。条件变体登记由面客消息中心适配。所有结果消息长期保留沿框架；本模块不再有“消息临期已过期”一类时间语义。

<a id="variables"></a>
### 4.2 模板业务信息与校验

| 信息变量 | 含义与适用条件 |
| --- | --- |
| demand_id / business_id | `FP-28` 融资申请编号、`FD-01` 融资业务编号，所有模板必有；始终识别原笔，不换成最新业务 |
| disbursement_id | `LN-01` 放款记录编号，三个模板均必有 |
| institution_name | 本笔资金方企业可展示全称，`T-LN-01` 必有；不以操作员工姓名、邮箱或钱包代替 |
| amount / currency | 本笔 `LN-04` 放款金额和 `LN-03` 币种，`T-LN-01` 必有；USD/USDT/USDC 与报价固化数值一致，不用实收额代替，按 L6 固定 1:1:1 与本笔锁定值复用，不取行情、不重算 |
| submitted_at | `LN-06` 成功提交时间，`T-LN-01` 必有。业务日期按 UTC；具体时刻按收件人偏好时区展示并标注，无偏好沿平台规则，不得取送达时间重算 |
| confirmed_at | `FD-35` 正式确认时间，`T-LN-04A/04B` 必有；不是实际发放、上传或计划恢复时间 |

变量只放上述业务值；不放账户号、钱包地址、凭证 / 协议正文、交易标识、内部备注或任意链接。**本批后模板中不再出现 deadline、剩余时限、处置原因或客服邮箱变量**——原 `deadline`、`request_reason`、`termination_reason`、`support_email` 随对应事件废止，见[第 8 节](#retired-notify)。中英模板变量名称与数量一致，金额币种、时间等采用平台统一展示；无缺值时不得出现空白必需信息或裸占位符。

缺失必需事实或可靠账号时，不能以猜测、假值或转发给别人补齐，相关场景不判验收通过。单条异常按消息中心既有降级隔离，不使其他消息不可读；通用降级不等于本业务完整通知合格。

## 5. 落点、历史消息与权限

| 通知 | 准确业务落点 | 当前事实已经变化时 |
| --- | --- | --- |
| N-LN-01 | 本项目、原 `FP-28/FD-01/LN-01` 的到账确认办理场景 `P-LS-08`；仅该资产方且仍 `S-FD-4` 可办理 | 已确认则展示同笔放款结果，不再次打开确认；消息不会因时间经过而失效，资产方随时可从现行业务入口确认 |

## 7. 依赖与跨模块边界

### 7.1 未定项与框架差异

| 项目 | 影响及承接要求 |
| --- | --- |
| Q-LS-N01（已闭合） | 多成员资产方的收件归属随“一个企业一个员工”消解，不再作为未决项；后续如恢复多员工，须先在登录与企业账户模块定义责任账号，本册不自行挑选 |
| Q-LN-01（沿用，范围收窄） | 真实客服邮箱及线下承接安排未提供。本批后该邮箱只出现在办理视图与放款详情，不再进入通知正文；阻塞的是业务页面的客服出口验收，不阻塞本册两类通知 |
| 历史目标与未登记降级 | 面客消息中心对状态流转可能禁用跳转，而 L7 要求旧入口仍可查原笔结果。建议区分“失效动作”与“可读对象”，最终核对落点映射；未登记保持其现行可读降级，不为对齐伪造跳转地址 |
| 同事实重复恢复未读 | 面客消息中心功能 §11.5 允许去重合并后恢复未读；本模块沿用户少干扰要求及 L5/L6 边界，同一事实不置顶、不恢复未读，由面客消息中心统一核对 |
| 分类与条件模板登记 | 两个标识、三对模板及业务落点已给出，正式分类值、04 计划进度变体与共享登记仍待面客消息中心适配，不单方面改旧标识或宣称已登记 |
| 事件删除的下游同步 | 面客消息中心与控制台须同步移除已废止的四类事件及其待办、未读与历史入口映射；历史已送达消息的处理方式由消息中心统一决定，本册不单独定义补偿动作 |
| 原业务规则与剩余依赖 | UTC、固定折算、付款用途完整读取和额度结论未知不放款已定。仅实收范围、数币精度、掩码细则、企业账户字段与按链格式（主册 Q-L7-08）及真实供给联验继续依主册第 7 章 |

### 7.2 跨模块承接

- [授信报价](../v1.0-借贷广场-授信报价与接受拒绝/01-授信报价与接受拒绝-PRD.md)负责接受报价通知，本模块不重发；其本批修订须同步取消盖章件相关文案与事件。[项目与质押](../v1.0-借贷广场-融资需求与代币质押/01-融资需求与代币质押-PRD.md)负责项目与额度事件，已接受业务不据此自动失效。
- [还款模块](../v1.0-借贷广场-还款计划与还款确认/01-还款计划与还款确认-PRD.md)负责资产方计划定稿告知及后续还款事件。资金方只收本模块到账确认信，计划恢复不重发；仍可从原笔查看实际进度。
- 面客消息中心承接两个事件、三对模板、条件变体、本人账号隔离、历史落点、去重及可见时效；运营消息中心不新增本模块通知，SPV 与运营一致。
