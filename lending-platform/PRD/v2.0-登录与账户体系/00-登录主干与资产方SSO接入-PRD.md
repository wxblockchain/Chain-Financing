### 2.2 本 PRD 不做什么

| # | 不做 | 归属 / 理由 |
| --- | --- | --- |
| 1 | **资金方登录、机构注册、账户体系的功能正文** | **WS-349**（用户 2026-09-18 明确的产出边界）。本 PRD 只定义两类角色共用的状态语义与组件，**资金方分支的取值与流程一律不在本 PRD 展开** |
| 2 | 资金方机构认证的**审核端**流程 | 运营端，Stage 3「资金方机构认证审核」 |
| 3 | **资产可信平台授权中心自身怎么做、对外用什么形式提供信息** | 授权中心（A2）为新增模块，形式未定。本 PRD 只写**本平台这一侧必须保证的结果**，见 `Q-L01` |
| 4 | 本平台为资产方提供的任何**自有账号、密码、验证码或兜底登录入口** | 「已确认登录口径」明确否决：资产方唯一登录方式是第三方授权登录 |
| 5 | 各业务能力的**字段级脱敏梯度** | 由各展示类功能按主干的 `X-L1` 自行定义；矩阵只定到「该能力在该档下是脱敏的」 |
| 6 | 矩阵中标 ⬜ 的行的取值 | 归各业务需求 / 资金方域填，本 PRD 只登记行与归属 |
| 7 | 技术架构、接口实现、协议参数与校验算法、表结构、开发任务清单、详细测试执行用例 | 不属产品需求范围。**本 PRD 写「什么情况下用户被判定为登录失败、他看到什么、还能做什么」，不写用什么手段达成** |

**邮箱发码要求的承接位置**：WS-349《05-资金方登录与账户体系-功能需求说明》3.3 `F-L59`（注册联系邮箱）、7.3 `F-L74`（修改联系邮箱）及 M8 `EV-L47`（验证码邮件触发）；《06-资金方登录与账户体系-验收需求说明》3.3、7.2；独立《07-资金方登录与账户体系-流程图与状态机》的邮箱验证流程。本 issue 不展开这些功能正文；资产方仍只读上游邮箱，主干与 SSO 无本地邮箱验证流程。机构注册多附件、预览与下载亦继续由 WS-349 承接。

### 2.3 既定约束与外部依赖

资产方仅通过资产可信平台授权中心登录；本平台只读消费身份及认证结论。OIDC 与跨系统 back-channel logout 沿用 WS-348 issue「已确认登录口径」「重构要点」的明确约束；三平台域名精确白名单沿用同一来源。协议参数、通知传输和校验实现不在本 PRD 展开，联调未定项见第 8 章。权限矩阵、安全结果及本轮未变的时效沿用当前六册，不以原型演示替代。

## 3. 业务角色

| 角色 | 定义 | 身份权威 | 登录方式 |
| --- | --- | --- | --- |
| **游客** | 未登录的访问者，两类角色的共同起点 | — | 无。平台默认游客态，可直接浏览 |
| **资产方** | 持有应收账款、来本平台发起融资的企业用户 | **资产可信平台**（上游） | **第三方授权登录**，唯一第三方为资产可信平台授权中心。本平台无自有凭据、无兜底入口 |
| **资金方** | 提供资金、参与出资的机构用户 | **本平台** | **仅钱包地址登录**（连接钱包 + 签名）。邮箱为资金方独有，在机构注册流程中填写 |

| 角色 | 与本 PRD 的关系 |
| --- | --- |
| **展示类功能**（资产列表、资产详情、我的融资 / 我的出资……） | 契约消费方：读主干第 6 章的四字段、按矩阵判定，**不自读原始状态字段** |
| **各业务需求** | 矩阵的填表方：只填自己那几行 |
| **WS-349 资金方域** | **状态语义与编号的引用方**：状态名、四字段枚举、矩阵列与取值语义一律取自本 PRD，不另造一套 |

| 账户身份（SSO 4.1） | 同一上游账户对应同一本平台资产方身份，历史记录不分裂，不同账户资料不混用；企业、邮箱、钱包不代替账户身份 | 可稳定识别账户的信息及其对应关系；参考 WS-366 的不可变账户标识，不指定本地存储或接口字段名 | 无法可靠确认身份时不得建立该次登录；不能退而用邮箱或钱包拼凑身份 |
| 账户、个人与企业资料（SSO 4.2、9.4） | 只读、不重复采集；个人、企业基本资料仅本人可见，业务必要信息自动获取并按该业务既有角色展示；加载失败、未提供、确认删除须区分 | 四项账户资料和两组基本信息的实际供给、字段对应、适用模板与缺失含义；业务所需信息的可用性与有效主体对应；获取及更新方式由开发设计 | 缺失可选资料沿用空态；业务必要信息不足时仅限制依赖该信息的动作并说明原因，不要求本地补填。不得把失败当删除、待审主体当有效主体；新增字段或敏感授权变更须产品确认，接口有值不等于可公开 |
| 有效企业关联（SSO 4.2、9.3） | 企业信息对应当前有效归属，待审核的新企业或草稿不能覆盖有效主体；不新增多成员或企业切换功能 | 如何取得当前有效企业及对应资料，如何区分待审核申请与有效关联 | 无法区分时不得把最新提交企业当作有效主体；将供给差异反馈产品，不自行决定企业生效条件 |
| 有效综合认证结论（SSO 7） | 只消费上游当前有效综合结论；已认证为 L3，其余为 L0；不自行组合个人、企业审核状态 | 哪些实际取值表示当前有效已认证、如何取得最新结论并满足既定复核要求；区分申请进度与有效认证 | 上游规则不能直接推导出实际接口能力；不能凭单项通过、资料齐全或待审核状态自行放行。若未提供有效结论，反馈依赖缺口 |
| 授权、会话与回跳（SSO 3、6；主干 3） | 保留已确认的授权登录、安全回跳、失效表现和时限；资产方无本地兜底登录 | 登录复用、账户可用性、认证变化与登出联动的实际支持范围及对接方式；具体开发方案由开发确定 | 免二次输入不支持时沿用完整登录；安全回跳未确认按既有规则兜底。其他能力缺口影响既定时效、权限或业务结果时反馈产品，不自行降低要求 |

**确认权限与验收边界**：字段命名、接口对应、调用及同步实现属于开发设计；功能范围、字段业务含义、展示权限、认证放行条件和时效的变化属于产品决策，重大变更再由用户裁定。无需因普通技术选型暂停已确认功能。开发完成对接核实不代表 `Q-L01` 整体关闭；实际供给与剩余证件脱敏口径仍需落实；已确认的本人可见及业务展示原则不再重复待决。受影响的真实联调验收见验收册第 15 章。
