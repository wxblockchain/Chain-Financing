# 授信报价与接受拒绝 · 消息通知

配套[主 PRD](01-授信报价与接受拒绝-PRD.md#notifications)。本册只定义通知的事件、收件范围与内容；通知的承载形式与视觉由设计决定（见[统一条款](01-授信报价与接受拒绝-PRD.md#design-boundary)）。本册集中三类事件的触发、收件、文案及验收；业务步骤读主 PRD，需求终结连带失效的协作见[图册](02-授信报价与接受拒绝-流程图与状态机.md#fl-cr-03)。本批随报价有效期取消废止两个事件，清单见[第 8 节](#retired)。

<a id="events"></a>
## 1. 哪个环节发送站内信

N-CR-01、N-CR-04、N-CR-05 为本文件现行通知编号；N-CR-02、N-CR-03 已废止（见[第 8 节](#retired)）。融资申请编号为FP-28；每次成功报价的融资业务编号为FD-01。同一申请先后有多笔报价时，每笔均用自己的FD-01识别，不把“最新一笔”当作消息对象。

| 编号 | 发送节点与成立条件 | 收件人 | 必须知道什么 / 下一步 | 唯一发送归属 |
| --- | --- | --- | --- | --- |
| <a id="n-cr-01"></a>N-CR-01 | 报价提交成功，本笔进入待接受S-FD-1，金额与锁定已成立 | 该融资申请的资产方收件账号，归属约束见2.1 | 融资申请编号、业务编号、报价机构、金额；报价没有到期时刻，须由本人查看后决定接受或拒绝，不处理就一直待接受 | L6 |
| <a id="n-cr-02"></a>N-CR-02 | **本条废止**（编号保留、不再发送） | — | 报价有效期管控取消，不存在临期节点；模板 T-CR-02 一并作废 | — |
| <a id="n-cr-03"></a>N-CR-03 | **本条废止**（编号保留、不再发送） | — | 报价不会自行到期；需求因项目关闭/项目到期/覆盖不足终结时的连带失效，统一由L5按[需求终结通知](../v1.0-借贷广场-融资需求与代币质押/03-融资需求与代币质押-消息通知.md)合并发送。模板 T-CR-03A / 03B 一并作废 | — |
| <a id="n-cr-04"></a>N-CR-04 | 资产方正式接受成功，本笔进入待放款S-FD-3 | 原报价资金方账号 | 本笔已接受、接受时间；到融资放款清单的同笔FD-01办理放款，无合同盖章件可查、也无放款时限 | L6 |
| <a id="n-cr-05"></a>N-CR-05 | 资产方正式拒绝成功，本笔进入已拒绝S-FD-2，机构在途报价金额释放等结果一致 | 原报价资金方账号 | 哪笔被拒、拒绝时间、完整拒绝原因、本笔在途报价金额已释放；查看对应报价历史 | L6 |

报价成功、接受和拒绝均以正式业务结果成立为准。用户发起操作、提交进行中或操作结果未知，均不构成发送依据。N-CR-01不另给资金方发送“提交成功”回执；N-CR-04/05不另给刚操作的资产方发送回执。

### 1.1 不发送的环节

核定/追加/重新核定/授信到期、上传授信协议、账户选用、草稿与失败、报价浏览/复制/下载/切换历史均只保留现场反馈；不新增授信、过程、失败或运营消息。**报价没有有效期，因此没有任何临期、催办或到期消息**，也没有周期锁定与多档提醒；长时间待接受不触发提醒，长时间待放款同样不触发。项目关闭、项目到期或覆盖不足使需求终结时由L5合并发送，L6不重复。外部行情、参考币种、授信摘要变化不发信、不重算金额；放款/还款节点归所属模块。

## 2. 三方接收范围与跨模块发送归属

### 2.1 从业务角色落实到本人账号

| 角色 | 接收范围与限制 |
| --- | --- |
| 资产方 | 本申请所属企业已明确关联的本平台资产方账号。本期一个企业只有一个员工，该账号即唯一收件人，原Q-LS-N01多成员归属问题随之关闭；仍不向管理员、最近查看者或其他企业投递 |
| 资金方 | N-CR-04/05发送给本笔成功提交报价的本平台资金方账号，属于原报价机构；与L5“相关业务登记账号”衔接。不向该机构其他成员、曾报价但不是本笔的机构、浏览者或全体资金方广播；机构名不代替账号归属 |
| 运营管理人员（含SPV） | 授信与报价没有新增运营审核或处理职责；本模块三类事件均不抄送运营，也不设置每次接受/拒绝的全员播报。已有业务只读、监控及后续审核权限保留；待办存在不自动等于需要站内信 |
| 游客、其他平台、同钱包的另一身份 | 不是本笔收件人。借贷平台面客账号独立归属，同钱包或同邮箱不串信；管理端与面客端不共池 |

<a id="n-cr-r01"></a>
N-CR-R01：账号须可由本笔可靠确认，消息归该自然人；缺归属不由管理员或当前登录者补位，停用/换角色/失权不自动转同事，历史不随后来办理者改投。本期一企一员工，收件归属可直接验收，不再有多成员未决分支。

<a id="ownership"></a>
### 2.2 同一事实由一个模块发送

| 事实 | 唯一发送方 | 相邻模块承接 |
| --- | --- | --- |
| 成功报价、接受、拒绝 | L6发送N-CR-01、N-CR-04、N-CR-05 | L5、控制台和消息中心展示业务事实，不额外发同义消息 |
| 需求因项目关闭、项目到期或覆盖不足终结，连带本轮待接受报价失效 | L5按N-LS-05 / financing.demand.coverage_invalidated向相关双方各发一条，正文同时告知报价失效；L6不再向任一方发送任何报价失效消息 | L6仍负责报价落S-FD-11及本笔机构在途释放，历史详情提供FD-01、实际终结时间、具体原因与释放结果；不因合并通知取消业务处理 |
| 先拒绝报价，之后需求另因项目关闭/到期/覆盖不足终结 | 两次真实事实分别按其归属处理：拒绝由L6发N-CR-05，需求终结由L5发N-LS-05；不是把同一事实重复发两遍 | L5只按需求终结时的真实受影响范围通知；已被拒绝、没有在途报价的原资金方不因历史报价再获需求通知 |
| 需求终结与接受/拒绝竞争 | 以业务裁定的本笔唯一最终结果和原因通知，不同时宣告已接受、已拒绝和已失效 | 需求终结成立则由L5发，接受或拒绝成立则由L6发。补处理不创造第二个报价终结结果 |
| 接受报价、随后放款流程 | L6仅告知“报价已接受，待放款” | L7不再为同一次接受补发“进入待放款”消息；真正新增放款/到账事件由L7定义，不能把接受当作已放款 |
| 后续还款/结清、项目覆盖与期限 | 各自所属模块发送 | L6不复制；单笔结清不代表整个项目结束 |

状态与金额结果见[主 PRD](01-授信报价与接受拒绝-PRD.md#demand-invalid)和[两类失效图](02-授信报价与接受拒绝-流程图与状态机.md#fl-cr-03)，通知合并不取消业务处理。

<a id="rules"></a>
## 3. 时限、历史语义与防重复

<a id="n-cr-r02"></a>
N-CR-R02：报价没有截止时刻，通知中不出现到期时间、剩余时长或倒计时。业务日期UTC，展示按收件人偏好时区并标注，无偏好沿平台规则。没有临期节点，也没有补发提醒的情形；已终结的笔不补任何催办，历史消息保留但不呈现为当前待办。

<a id="n-cr-r03"></a>
N-CR-R03：待接受不会因时间流逝改变结论，通知也不制造时限。项目关闭或项目到期使需求终结时本笔连带失效，此后不能接受；接受成功即转待放款，待放款同样没有时限与终止出口，消息不引导催办。

<a id="n-cr-r04"></a>
N-CR-R04：同一本平台面客账号＋同一FD-01＋同一事件只一条。重复/补处理不增加、不置顶、不恢复未读、不改发生时间；终态由业务先裁定，不能换事件名双发。同FP-28下新FD是新业务，既不覆盖旧历史也不被旧消息去掉。

<a id="n-cr-r05"></a>
N-CR-R05：保留事件时的机构、金额、时间与结果，乱序到达不恢复待接受。读信/全部已读不是接受、拒绝、还款或签署；点击不代勾选或提交，办理仍需当前权限及账户、文件、声明等条件。

<a id="n-cr-r06"></a>
N-CR-R06：发送失败不回滚业务、不解锁、不重置；用户仍可自行查看本笔结果和可做的动作。账号与模板齐备事件按面客中心IF-NC-01于发生后60秒内在列表/未读数一致可见；实际迟到属未达要求，不改事件时间掩盖。

| N-CR-04 | financing.quote.accepted | 业务办理进度 | T-CR-04 | 本平台面客账号＋本笔FD-01＋本次接受 | 结果消息不另设失效时点 |
| N-CR-05 | financing.quote.rejected | 业务办理进度 | T-CR-05 | 本平台面客账号＋本笔FD-01＋本次拒绝 | 结果消息不另设失效时点 |

登记固定借贷平台面客端、L6触发，收件见第2章，目标为第5章本平台业务对象，需重判当前权限和状态；不另注册新的消息目标，无外部URL。办理类消息在本笔终结后停止引导办理、历史保留；结果类保留沿消息中心规则。

模板标题、正文成对命名为msg.<业务类型>.title / msg.<业务类型>.body。T-CR-*只是本文对完整文案的引用编号；现行模板为 T-CR-01、T-CR-04、T-CR-05 三对，同一账号同一事件不收两封。条件变体的正式登记沿共享框架核对；不为角色变体新增业务事件。

### 4.2 业务变量与校验

| 变量 | 业务含义、必填与校验 |
| --- | --- |
| demand_id | 原融资申请编号FP-28；全部模板必有，不能取同一项目的新申请代替 |
| business_id | 本笔融资业务编号FD-01；全部模板必有。接受时尚未产生LN-01，不用虚构放款编号补位 |
| institution_name | 本笔真实报价机构名称；01必有。沿企业可展示名称，不以用户个人姓名、邮箱或钱包地址代替 |
| amount_usd | 本笔成功报价的融资金额，USD数值、大于0，沿L6金额精度展示；01必有，明确是融资金额，不把USDT/USDC结算金额标成USD |
| ~~expires_at~~ / ~~expired_at~~ | **均废止**：报价没有到期时刻，任何模板都不得出现报价截止、剩余时长或倒计时；需求终结的时刻由L5的需求终结通知承载 |
| accepted_at / rejected_at | 平台确认本笔接受/拒绝成功的真实时刻；04/05分别必有；不取点击时间或页面停留时间 |

金额、名称和时间来自同一本笔业务事实，不用当前汇率重算历史金额；参考币种是需求意向，不影响收件筛选。必要变量或归属缺失不得以演示值、空白消息、假编号或裸占位符补齐；按来源补齐，不能对整列表造成不可用。框架的单行语言降级继续有效。双语模板的变量名称、数量一致；时间和金额按平台统一格式展示，原用户原因纯文本保留，不拼接动态动词或状态片段。

## 5. 消息落点与异常表现

| 消息 | 精确落点 | 当前状态已经变化时 |
| --- | --- | --- |
| N-CR-01 | 借贷平台本项目，定位原FP-28和FD-01；按[业务定位规则](01-授信报价与接受拒绝-PRD.md#navigation)，进入本笔报价接受/拒绝办理场景P-LS-06 | 已接受、拒绝或失效则只展示原报价结果及当前状态，不开启旧操作，不自动切换到同申请的新报价；无权时按框架无权限语义，不泄露私有记录 |
| N-CR-05 | 原融资申请的对应FD-01报价历史，按[本模块历史定位](01-授信报价与接受拒绝-PRD.md#navigation)及L5跨清单定位规则，只读结果 | 原申请即使已重新报价，仍定位原笔；可显示当前业务事实，但不在历史详情提供重报或其他业务的快捷入口 |
| N-CR-04 | 融资放款清单中的本笔FD-01，只读查看；此时可没有LN-01，也没有合同盖章件 | 已推进放款/还款则展示同一笔最新事实，不执行旧待放款动作。需要办理时由现行操作入口重新判资格，不把消息点击当作放款指令 |

<a id="n-cr-r07"></a>
N-CR-R07：消息归本人不等于永久拥有业务资料。每次点击重判本平台身份、归属、对象、状态和文件权限；未登录先登录并保留合法目标，换身份不串信。无权/不存在不泄露存在性；映射未就绪保留可读消息并说明暂不可查看，不猜外部地址或静默跳首页。

返回消息中心保留原阅读上下文；纯结果详情只读，文件仅在双方有权范围查看/下载。消息记录不新增企业全员访问、跨机构授信访问或跨平台消息汇总能力。用户已确定的只读详情与办理归属继续沿用。
