## 1. 模块是什么

运营端消息通知是借贷平台运营端的**站内信箱**。运营工作中发生需要运营人员知道的事情时，由对应的业务模块发出一条站内信。本模块负责让运营人员：

1. 在运营端任何业务页面看到未读数；
2. 打开消息列表，按分类和已读状态筛选；
3. 打开一条消息读完整内容，读完自动变为已读；
4. 需要时从消息前往原业务查看或办理，再回到列表原来的位置。

三条基本原则：

- **本模块自己不发消息。** 发什么、何时发、发给谁、写什么，都由来源业务模块决定，并在各自模块的消息通知册中维护。本册只定义消息中心的通用框架，来源模块增减或修改消息时，本册不需要随之修改。
- **读消息不等于办业务。** 已读不代表已审核、已发布或已处理，办理始终在原业务页面完成。
- **消息记录的是当时的事实。** 原业务之后发生的变化，不改写旧消息中的业务事实。

**一个完整的例子。** 某来源按自己的通知规则，向全体运营发送一条需处理事项的消息 → 运营管理员甲在任一业务页面看到未读数加 1 → 甲打开消息列表，点开这条消息；详情展示成功后，对甲自动变为已读，甲的未读数减 1，同事乙的未读数不变 → 甲前往消息指向的那一次业务记录；若乙已先处理完，甲查看这一笔的当前结果，不再次办理旧动作 → 甲返回原消息，再返回原列表，筛选条件、已加载批次和所在位置保持不变。

### 1.1 本期不做

- 不发送、编辑或撤回消息，不维护消息模板，不提供公告发布或按人群发送。
- 不提供删除、归档或清空，消息长期保留。
- 不提供逐条“标为已读”和“标为未读”：打开详情即已读，另有“全部已读”。
- 不提供通知开关或偏好设置。
- 不发送邮件、短信或其他站外消息；各来源模块自己的邮件不受影响。
- 不汇总面客端或其他平台的消息，也不合计它们的未读数。
- 不提供查看他人阅读情况的功能。
- 不提供待办认领、转派，也不处理业务异常的升级、关闭或释放。
- 正文只支持纯文本，不支持富文本或可执行内容。

<a id="same-system"></a>
### 1.2 与面客消息中心的关系

本模块与[面客消息中心](../../面客端/10-面客消息中心/01-面客消息中心-PRD.md#same-system)是同一套站内信能力在两个端的实现。消息归属、未读数、最近预览、列表取数、已读与全部已读、同一事实只收一条、消息分类、送达时效、前往原业务、登录失效等规则，按设计两端相同，各自在本端册内写明。按设计，两端的差异只有下表三项：

| 项目 | 面客端 | 运营端（本模块） |
| --- | --- | --- |
| 谁收消息 | 只有收件人本人 | 另有“全体运营”共享的消息 |
| 谁能进入 | 已登录且已判定为资产方或资金方 | 按运营端功能权限 |
| 打开原业务时按什么判断权限 | 借贷平台面客端的业务权限 | 原业务所属模块定义的运营端功能权限项 |

任何一端修改共同规则时，须同批核对另一端。

## 2. 术语

| 术语 | 含义 |
| --- | --- |
| 运营端 | 借贷平台中运营人员使用的一端，与资产方、资金方使用的面客端相对 |
| 来源模块 | 发出消息的业务模块，例如资金方登录与账户、运营端协议管理；它对消息内容和收件范围负责 |
| 全体运营 | 一种收件范围：消息对所有有权查看消息的运营人员可见，但每个人各自记录是否已读 |
| 本人 | 一种收件范围：消息只对一个指定的运营账号可见 |
| 消息查看权限 | 运营端功能权限项“运营端消息查看”（`PM-AL-12`），由本模块定义，按[运营端账户与登录的权限组织方式（D-AL-07）](../01-运营端账户与登录/01-运营端账户与登录-PRD.md#d-al-07)授予角色；没有它就不能使用本模块 |
| 首登强制改密 | 运营账号首次登录必须先修改初始密码；完成前不开放本模块 |
| 原业务 | 消息所说的那一笔具体业务，例如某份机构申请的某次提交、某个协议的某个版本 |
| 原动作 | 消息提示可以去做的那个办理动作，例如“审核这次提交”；原业务往下推进后，它可能已经不适用 |
| 未读数 | 本人有权看到、仍在有效期内、尚未读过的消息条数 |
| 最近消息预览 | 从消息入口打开、展示最近 10 条的简要列表 |
| 消息入口 | 运营端所有业务页面共用的外框上提供的消息入口，由运营端外框提供，不由本模块自建 |
| 消息有效期 | 来源为某条提醒设的截止时点；过期后不再计入未读数，消息仍可查看。是否设有效期由来源决定，没有设的消息一直有效 |
| 共享登记 | 各来源统一登记[接入字段](#intake-fields)的地方，两端共用同一份。默认待适配；共享登记、收件范围、文案与真实送达均验证完成后才是已适配。登记放在哪里、如何实现由研发小队确定 |
| SPV | 与运营同一主体的一组职责，不是另一种账号，也没有自己的消息 |

<a id="f-o16"></a><a id="f-o17"></a>
## 3. 谁能看到哪些消息（F-O16、F-O17）

| 访问者 | 消息入口与未读数 | 能否读消息 |
| --- | --- | --- |
| 未登录 | 不展示 | 不能。从链接直接打开列表或某条消息时，先回运营端登录；成功后回到原列表或原消息 |
| 已登录、尚未完成首登强制改密 | 不展示 | 不能。先完成改密，再按当前权限回到原目标 |
| 已登录、有消息查看权限 | 展示 | 能读发给“全体运营”的消息，以及发给本人的消息 |
| 已登录、没有消息查看权限 | 不展示 | 不能。从链接直接打开时按运营端账户与登录的功能拒绝处理；本人其他有权限的业务功能不受影响 |
| 面客端账号、其他平台账号 | 不进入运营端消息 | 不能；面客端有自己的消息 |

**两种收件范围。**

- 发给“全体运营”的消息：所有有消息查看权限的运营人员看到的范围相同；每个人各自记录是否已读，甲读了不影响乙的未读数和已读状态。
- 发给“本人”的消息：只有那一个运营账号可见；其他运营人员都看不到，也不计入他们的未读数。管理员的称谓不带来查看他人本人消息的权限。
- 新账号开通前已经存在的“全体运营”消息，新账号可以查看，但不计入其未读数；他人的本人消息不会因此转给新账号。
- SPV 按同一运营身份查看，不另有一份消息，也不另计已读。
- 只有这两种收件范围；不按角色、岗位或机构另分范围。来源没有写明收件范围的，不猜测发给某个经办人、某个管理员或全体运营。

**归属与隔离。**

- 所有查看、计数和阅读都按实际登录的账号和运营端判断；改写网址中的账号、消息编号或端标识，也取不到他人或其他端的消息。
- 打开他人的本人消息、其他端的消息与打开不存在的消息，看到的结果完全相同，不透露这条消息是否存在；猜测编号或批量访问也取不到。
- 面客端、代币发行平台运营端的消息不进入本模块，也不计入未读数。只有来源明确规定两端分别通知时，两端才各有一条，各自已读。
- 收到消息不代表获得原业务的查看或办理权限；前往原业务时按当前权限重新判断（见[前往原业务（F-O14、F-O15）](#f-o14)）。

**权限变化。** 收回消息查看权限后，再次访问时立即拒绝，不能继续使用此前已打开的内容。重新授予后，按资格恢复可见的历史消息，原来的已读状态不变。授权本身由建设方在运营端账户与登录中配置，本模块不提供授权功能。

<a id="single-role"></a>**本期单一角色。** 按[运营端账户与登录的本期预置角色（D-AL-08）](../01-运营端账户与登录/01-运营端账户与登录-PRD.md#d-al-08)，本期运营端只有运营管理员一个角色，运营端消息查看（`PM-AL-12`）及其他功能权限对每个正常运营账号全部开通。本节“已登录、没有消息查看权限”和上段“权限变化”的规则保留原位，作为后续细分角色时的规则；本期不产生实际分支，相应验收本期不可验。

流程参见[消息准入与目标权限分别判断（FL-O05）](./02-运营端消息通知-流程图与状态机.md#fl-o05)。

<a id="f-o18"></a>
## 4. 来源接入字段要求（F-O18）

本模块定义各来源接入运营端消息通知时要提供哪些信息、何时必填、不满足时如何处理，以及消息的统一承接规则。每条消息具体发什么、何时发、发给谁、写什么、去向哪一笔业务，由来源模块在自己的消息通知册中维护。

### 4.1 本模块与来源模块的分工

| 内容 | 由谁定义 |
| --- | --- |
| 每条消息在哪个功能、哪个环节触发，以及不触发的情况 | 来源模块的消息通知册 |
| 每条消息发给谁、排除谁 | 来源模块的消息通知册，按本节收件范围字段填写 |
| 每条消息的中英文标题与正文、必须出现的业务值、按角色或结果区分的文案 | 来源模块的消息通知册 |
| 每条消息打开后去向哪一笔业务、谁能查看和办理 | 来源模块的消息通知册，按本节去向字段填写 |
| 每条消息归入哪个分类 | 来源模块从本模块的统一分类中选择 |
| 接入字段及其要求、统一分类、同一事实只收一条、送达时效、敏感信息限制 | 本模块（本节） |
| 消息的接收、展示、阅读、全部已读、前往原业务 | 本模块的[消息入口](#f-o01)、[消息列表](#f-o06)、[消息详情与已读](#f-o10)、[前往原业务](#f-o14)及[登录状态与安全](#session) |

- 来源增减消息、修改消息内容或文案时，只修改来源模块的消息通知册，本册不随之修改。
- 本册的规则和验收不以某个来源的具体消息为依据。

<a id="intake-fields"></a>
### 4.2 接入字段

每类消息接入时，来源模块按下列字段在自己的消息通知册中登记，并完成两端共用的共享登记。本节与[面客消息中心的接入字段](../../面客端/10-面客消息中心/01-面客消息中心-PRD.md#rg-nc-01)使用同一套字段含义；平台与端、收件范围、查看与办理条件按运营端取值，不另建一份登记。

**识别与归属**

| 字段 | 是否必填 | 要求 | 不满足时 |
| --- | --- | --- | --- |
| 业务类型标识 | 必填 | 三段式“业务域.对象.动作”，动作里的下划线不算分段；每类消息唯一，登记后不再改名 | 未提供标识时由来源补齐后再发；标识有值但类型尚未登记的消息照常可读、计数，没有前往入口，也不提示错误 |
| 分类 | 必填 | 从[统一分类](#categories)中选一个；来源不能自造分类 | 接入时未提供分类由来源补齐；已收到的消息分类无法识别时显示“其他 / Other”，消息照常展示 |
| 平台与端 | 必填 | 固定为借贷平台运营端 | 不属于运营端的消息不展示、不计数，用链接直接打开也看不到 |
| 发送来源 | 必填 | 唯一负责发送该类消息的业务模块；其他模块不发同义消息 | 由来源在登记时保证唯一，缺失时补齐后再发 |
| 收件范围 | 必填 | “全体运营”或“本人”二选一，必须由来源写明；选“本人”时须确定运营账号。范围和阅读隔离按[谁能看到哪些消息](#f-o16)处理 | 无法确定时不发送，不用邮箱、钱包地址、机构、最近操作人或全体运营代替指定账号，也不猜测收件范围 |

**同一事实与合并**

| 字段 | 是否必填 | 要求 | 不满足时 |
| --- | --- | --- | --- |
| 同一事实的区分依据 | 必填 | 收件范围 + 原业务 + 事件，以及必要的次数、期次或节点；选“本人”时范围包含该运营账号，按[同一件事只收一条](#same-fact)处理 | 缺失时由来源补齐后再发；区分依据相同的重复送达不新增消息 |
| 合并规则 | 来源规定一次操作的多个结果合并为一条时必填 | 写明合并条件，以及合并后的这一条保留哪些事实 | 未登记合并规则时不合并，每个结果各自一条 |

**内容**

| 字段 | 是否必填 | 要求 | 不满足时 |
| --- | --- | --- | --- |
| 标题与正文 | 必填 | 中文、英文各一套完整的纯文本标题和正文；按角色或结果有不同文案时，每套都完整登记，每个收件人只按条件使用其中一套。金额与币种、日期与时刻取事件发生时的值，之后不改写；未知金额不显示为 0。业务日期按 UTC，具体时刻按本人偏好的时区并标明时区，无偏好时按 UTC。不出现模板占位符、技术标识或[敏感信息](#sensitive-information) | 缺少可读的标题和正文时不生成消息；已收到的消息按[内容与去向异常](#intake-fallback)处理 |
| <a id="occurred-at"></a>发生时间 | 必填 | 业务事实发生的时间；到点触发的事件取应到时点。按本人偏好的时区展示并标明时区，无偏好时按 UTC | 缺失时由来源补齐后再发，不用送达时间或阅读时间代替；重复送达、阅读、切换时区都不改变它 |

**去向**

| 字段 | 是否必填 | 要求 | 不满足时 |
| --- | --- | --- | --- |
| 打开后去哪 | 必填 | 原业务、运营端固定页面、不跳转三选一；不接受站外、面客端或其他平台的地址 | 来源未提供时补齐后再发；同时指定多种去向或指定本端以外的地址时不接收该消息。已收到但去向缺失或尚未登记的消息按[内容与去向异常](#intake-fallback)处理 |
| 原业务定位 | 去向为原业务或固定页面时必填 | 指向消息所说的原申请、原提交、原版本等那一笔，写明原业务状态变化后运营人员能看到什么；固定页面须为运营端已登记的页面。可同时提供原业务名称与编号，供详情展示，编号可复制 | 缺少必填定位时补齐后再发；缺少可选名称或编号时不显示该项，不用其他业务的信息补位 |
| 查看与办理条件 | 去向为原业务时必填 | 查看与办理原业务各需要哪项运营端功能权限，按原业务所属模块定义的功能权限项填写 | 缺失时由来源补齐后再发；前往时仍按当前权限重新判断，见[前往原业务](#f-o14) |

**有效期与接入状态**

| 字段 | 是否必填 | 要求 | 不满足时 |
| --- | --- | --- | --- |
| <a id="effective-until"></a>消息有效期 | 可选，只有来源明确规定时才设 | 写明截止时点；过期后不再计入未读数，消息仍可查看并标示“已过期” | 未设有效期的消息一直有效 |
| 适配状态 | 必填 | 默认“待适配”；共享登记、收件范围（本人消息含指定账号）、文案与真实送达都验证完成后才是“已适配” | 未完成验证时保持待适配，不能称已上线 |

- 来源缺少必填信息时，补齐后再发；不发空白消息，不用 0、虚假编号、演示值或其他业务的信息补位。
- 类型有值但未登记、分类无法识别、已收到的消息内容或去向异常，适用本节写明的兼容规则，不一律拒收或隐藏。
- 切换界面语言后，历史消息的标题和正文随之切换，金额、时间、版本和业务编号等事实不变。

<a id="sensitive-information"></a>**敏感信息。** 消息标题和正文中不得出现：账号密码、验证码、完整钱包地址、证件号、IP 地址、材料原件或文件下载地址、完整的银行账户或凭证内容；也不出现客服邮箱。消息只展示来源已经授权的必要业务名称、金额和编号，不复制他人的完整档案或私人联系方式；机构审核员的私人身份按来源的匿名规则处理，不在消息中披露。


<a id="categories"></a>
### 4.3 消息分类（与面客端统一）

运营端与面客端使用同一套消息分类。每条消息由来源按下表定义归入其中一类。

分类名称与含义统一引用[面客消息中心的消息分类](../../面客端/10-面客消息中心/01-面客消息中心-PRD.md#categories)。运营端可承接该表标为“两端”或“运营端”的分类；筛选只显示当前账号实际可见的消息分类。

- “其他 / Other”只是分类无法识别时的兜底，不是可选的分类。
- 分类变更只维护上述统一分类表；本端按适用端和账号范围承接。

<a id="same-fact"></a>
### 4.4 同一件事只收一条

- 同一收件范围的同一业务事实只有一条消息。重复送达、重试、刷新、重新登录都不新增消息，也不改变这条消息的排序位置、发生时间和已读状态。
- 已经读过的消息，再次收到同一事实，仍是已读。
- 同一笔业务上发生了新的真实事实（新的一次提交、新的一次审核结果、新的一次定时处理），各自是一条新消息；不按“同一机构”“同一版本号”把不同的事实合并掉。
- 来源对同一事实补充信息时，在原消息上补齐；补齐不倒退事实，也不让消息重新变为未读。
- 只有来源按[接入字段中的合并规则](#intake-fields)明确规定时才合并。本模块不按同一天、同一业务或同一个人自行合并。

<a id="delivery-time"></a>
### 4.5 送达时效

- 业务事件发生后 60 秒内，消息出现在列表中，未读数同步更新。60 秒从业务事件发生时起算，不从系统延后处理完成时起算。
- 由时间到点触发的事件（例如定时处理到点后的结果），从应到的时点起算，**最晚 6 分钟内**可见：来源判定最多用 5 分钟，消息展示最多再用 60 秒。来源模块的判定延迟须控制在 5 分钟以内，否则不能满足这一承诺。

<a id="intake-fallback"></a>
### 4.6 已收到消息的内容与去向异常

以下规则适用于已进入本人可见范围的消息，不替代来源接入时补齐必填信息的要求。表中计数和已读均遵守[谁能看到哪些消息](#f-o16)及[未读数](#f-o01)规则，包括新账号查看开通前历史消息的限制；他人、其他端或无法确认归属的消息仍按归属与隔离规则处理。

| 情况 | 阅读与计数 | 前往入口 |
| --- | --- | --- |
| 类型标识有值，但业务类型尚未登记 | 正常可读；有效且未读时计数；打开详情按统一规则已读 | 没有入口，也不提示错误 |
| 业务类型已登记，但去向缺失或尚未登记 | 消息不隐藏；正常可读、计数和已读 | 没有入口，不跳默认页或错误页 |
| 来源设为不跳转 | 正常可读、计数和已读 | 没有入口，也不提示无法跳转 |
| 只缺少可选的原业务名称或编号 | 正常可读、计数和已读；缺项不显示，不用其他业务信息补位 | 其他必填定位完整时仍可按登记去向前往 |
| 分类无法识别 | 归入“其他 / Other”，正常可读、计数和已读 | 按已登记的去向与权限处理 |
| 当前界面语言缺失 | 显示另一种语言，正常计数和已读 | 按已登记的去向与权限处理 |
| 中英文内容都无法展示 | 用分类、发生时间和通用标题“通知 / Notification”展示这一条，不暴露内部标识，不影响其他消息；计数和已读按统一规则 | 按已登记的去向与权限处理 |
| 已存在的异常去向混合多种类型，或指向本端以外 | 正文保留；计数和已读按统一规则 | 不提供入口，不前往本端以外或任意地址 |

## 5. 消息入口、最近预览与未读数（F-O01～F-O05）

**入口。** 有消息查看权限、已完成首登强制改密的运营人员，在运营端每个业务页面（总览、机构认证审核、代币准入审核、融资参数配置、项目合约管理、融资台账、协议管理、账户设置和消息页面）都能看到消息入口及未读数；账户菜单里也有“消息中心”。从消息入口打开最近消息预览；从账户菜单直接进入完整消息列表（不带筛选），不先经过预览。各业务页面使用同一批消息和同一份已读状态，不各自计数。

**账户菜单中的本人信息。** 账户菜单中可看到本人当前的工作邮箱和角色：本期只有一个角色，显示“运营管理员 / Operations Administrator”。修改邮箱后显示新邮箱，消息归属和已读状态不变。账户菜单不提供邀请用户、配置权限等人员管理功能。

**最近消息预览。**

- 展示最近 10 条，已读和未读都包括；每条可看到标题、摘要、分类、时间和是否已读。
- 只打开预览不会让消息变为已读；点某一条进入它的详情。
- “查看全部”进入完整消息列表。
- 预览里不提供“全部已读”，避免误以为只处理这 10 条。
- 没有消息时明确说明还没有消息；读取失败时可以重试，不显示为没有消息。
- 打开预览不影响当前业务页面上尚未保存的内容。

**未读数。**

- 等于本人有效且未读的消息条数，“全体运营”和“本人”两种消息、全部分类合计；列表中的未读状态与未读数一致。
- 过了有效期的消息不计入未读数，但仍可在列表和详情中查看，并标示“已过期”。
- 原业务已办完、原业务不可访问、消息类型尚未登记，都不影响计数：只要消息有效且未读，就计入。
- 为 0 时不显示数字；超过 99 时显示“99+”。
- 读取失败时保留上一次的数字，不清零。
- 新消息到达时，未读数和列表一起更新，不打断用户当前的操作。在一个业务页面或浏览器标签里读了消息，同一账号的其他页面和标签最晚 60 秒内随之更新。

流程参见[入口、列表、详情、已读与返回（FL-O01）](./02-运营端消息通知-流程图与状态机.md#fl-o01)。

## 6. 消息列表与筛选（F-O06～F-O09）

**列表。** 消息列表（页面编号 `P-O20`）有独立网址，可以直接打开和刷新，范围是本人可见的全部消息，不受预览 10 条的限制。消息长期保留，不会被自动清理；已过期的消息仍在列表中。每条可看到标题、摘要、分类、时间和是否已读，点击即进入详情。

**筛选。**

- 分类：“全部”加上本人实际有消息的分类；无法识别分类的消息归入“其他”。分类筛选只影响查看，不改变收消息的范围。
- 阅读状态：全部、未读、已读，默认“全部”。
- 两个条件同时生效。刷新页面后筛选保持不变；修改筛选后从第一条重新开始。网址中的筛选条件无效时，按默认条件展示，不显示为没有消息。

**排序。** 按消息创建时间从新到旧，与[面客消息中心](../../面客端/10-面客消息中心/01-面客消息中心-PRD.md#f-nc-14)一致；同一时间的顺序固定。每条消息仍按[发生时间字段](#occurred-at)展示业务发生时间，发生时间不作为排序依据。重复送达不改变顺序，读过也不重排。在“未读”筛选下读过的消息，仍留在当前结果中，重新筛选或刷新后才按新条件移除。

**加载。** 每次加载 20 条，“加载更多”把结果追加到已加载内容之后；没有更多时明确提示。不提供页码跳转，也不显示包含已读在内的消息总条数：还有多少要处理看未读数，全部已读会改变多少条看确认时给出的条数。加载进行中不能重复触发“加载更多”。

**新消息。** 有新消息到达时，符合当前筛选条件的自动插入列表顶部，不需要用户操作，也不改变用户当前的阅读位置；不符合当前筛选的不插入，切换到对应筛选时才能看到。自动插入只增加新消息，不重新筛选已加载的结果，所以在“未读”筛选下读过的消息不会因此被移走。已加载和后续加载的结果不重复、不遗漏。

**空列表。** 以下三种情况须能区分：没有消息查看权限（按[谁能看到哪些消息](#f-o16)的功能拒绝处理）；从未收到过消息，说明还没有任何消息；筛选后没有结果，说明当前筛选下没有消息，并可一键清除筛选。

**加载失败。** 第一批加载失败时可以重试；“加载更多”失败时，保留已加载的内容和所在位置，可以重试；加载过程中不显示为空列表；某一条内容异常只影响这一条，其他消息照常展示，这一条仍能打开详情。

<a id="f-o10"></a><a id="f-o11"></a><a id="f-o12"></a><a id="f-o13"></a>
## 7. 消息详情、已读与全部已读（F-O10～F-O13）

**详情。**

- 消息详情（页面编号 `P-O21`）有独立网址，可以直接打开和刷新，刷新后仍是同一条消息。
- 展示完整标题、分类、带时区的发生时间、完整正文、来源提供的业务信息，以及前往原业务的入口（如有）。正文是纯文本，其中的标签或脚本按文字显示，不会被执行。
- 返回：从列表进入的，返回后回到原来的列表，筛选条件、已加载的批次和所在位置都保持不变；刚读过的消息在列表中原地变为已读，不移动位置。直接从链接打开、没有列表可回的，返回到不带筛选的消息列表。返回地址只能是本端列表，不接受外部传入的地址。
- 从消息前往本人账户设置或原业务后，可以回到这条消息。原业务页面有尚未保存的内容时，按原业务自己的离开提示处理；返回不等于批准或取消业务。
- 登录账号、权限或消息可见性已经变化时，返回后重新判断，不恢复旧内容。

**自动已读。**

- 详情内容展示成功后，这条消息对本人自动变为已读，未读数同步减少。
- 详情加载失败时，不算已读，并说明尚未标为已读，提供重试和返回列表。
- 已读保存失败时：消息仍显示为未读，正文照常可读，并提供“重试”；重试只处理已读，不会重新发送消息，也不会执行业务。
- 已读的消息再次打开，不重复扣减未读数，首次阅读时间不变。只打开预览、滚动经过或复制编号，都不改变已读状态。
- 已读只属于“本人与这条消息”：读一条“全体运营”消息，不改变其他运营人员的已读状态，也不改变原业务的进度。

**全部已读。**

- 作用范围：当前筛选条件下本人全部未读的消息，包括还没有加载出来的部分；不扩大到其他筛选条件下的消息。
- 当前范围内没有未读消息时，这个操作不可用，并说明原因。
- 执行前须确认。确认时写明当前筛选条件，以及将被标为已读的未读条数（包括尚未加载的部分）；具体措辞与确认方式由设计确定。
- 取消时，所有消息保持不变。
- 执行期间不能重复提交。成功后，范围内的消息全部变为已读，未读数同步更新；确认时的条数与实际处理条数因其他页面已读而不同时，按实际处理结果反馈。失败时全部保持原状，可以重试；不会出现只成功一部分的情况。
- 确认之后新到的消息不在本次范围内，仍为未读。在其他页面已读过的消息不重复计算。
- 执行中登录失效时，不提示成功；重新登录后按实际的已读结果展示。
- 全部已读只改变本人的阅读状态，不通知其他运营人员，也不代表相关业务已经完成。

流程参见[入口、列表、详情、已读与返回（FL-O01）](./02-运营端消息通知-流程图与状态机.md#fl-o01)、[全部已读（FL-O04）](./02-运营端消息通知-流程图与状态机.md#fl-o04)、[本人阅读状态（ST-O02）](./02-运营端消息通知-流程图与状态机.md#st-o02)。

## 8. 前往原业务（F-O14、F-O15）

**去向。** 每条消息打开后去哪由来源按[接入字段](#intake-fields)登记，三选一：原业务、运营端的某个固定页面、不跳转。不接受站外地址，也不接受面客端或其他平台的地址。

- 前往原业务时，必须定位到消息所说的那一笔（那一次提交、那一个版本），不换成最新一笔或当前默认选中的业务。
- 本模块不办理业务；查看和办理都在原业务页面完成，由运营人员主动操作。
- 打开原业务时，按原业务所属模块定义的功能权限项，并遵守[运营端账户与登录的按权限收敛入口与越权处理（F-AL-17）](../01-运营端账户与登录/01-运营端账户与登录-PRD.md#f-al-17)，判断本人当前能否查看、能否办理。消息查看权限不带来原业务的权限；没有消息查看权限，也不影响本人从业务页面访问自己有权限的内容。

**进入详情时按原业务当前情况处理。** 进入详情时，按当前权限检查原业务能否查看、能否办理；列表中不逐条检查。检查超过等待上限 3 秒（`N-O05`）或检查失败时，仍允许前往，由原业务页面重新判断权限；超时不放宽任何权限。

| 原业务当前情况 | 运营人员能做什么 | 消息本身 |
| --- | --- | --- |
| 有权查看，消息提示的动作仍可办理 | 前往原业务查看或办理 | 正常展示；未读时计入未读数 |
| 有权查看，但消息提示的动作已办完或已不适用 | 前往查看这一笔的当前结果；不再提供旧动作，不能重开或再次办理，也不换成其他业务 | 正文保留当时的事实 |
| 消息已过有效期，原业务仍可查看 | 可以查看原业务；原业务还能不能办理，以原业务当前状态为准（提醒过期不代表业务不能继续办理） | 标示“已过期”，不计入未读数 |
| 原业务不存在，或本人无权查看 | 不能前往；统一显示“相关内容暂不可访问 / The related content is unavailable”，不区分是不存在还是无权 | 正文照常可读；仍有效且未读时计入未读数 |
| 消息类型尚未登记、去向缺失或尚未登记，或来源设为不跳转 | 没有前往入口，也不提示错误 | 正常可读、正常计数 |

- 来源已明确要求在某种情况下给出特定提示（例如“暂不可查看详情”）时，按来源保留该提示。
- 原业务页面不提供旧材料下载、版本对比或状态回退；消息只指向当时那一笔，不代替原业务的历史记录。
- 前往固定页面时，直接打开该页面，页面仍按本人当前权限判断。

流程参见[前往原业务（FL-O03）](./02-运营端消息通知-流程图与状态机.md#fl-o03)、[消息有效期（ST-O01）](./02-运营端消息通知-流程图与状态机.md#st-o01)。

<a id="session"></a>
## 9. 登录状态与安全

- 退出登录或登录失效（到期、长时间无操作、改密后旧登录失效等，按运营端账户与登录处理）时，消息入口、未读数、预览、列表和详情同时清除，回到运营端登录页。必须真正清除，不能只是遮住而数据仍可取到；之后迟到的数据也不再显示。
- 任何一处读取消息时发现登录已失效，都按失效统一处理，不当作普通的读取失败。
- 自动更新消息不算用户活跃，不延长登录有效期。
- 从链接直接打开消息时未登录：先回运营端登录，完成首登强制改密等必须事项后，按当前权限回到原消息；登录前不展示正文，也不透露这条消息是否存在。登录后发现消息不属于当前账号时，按不存在处理，不提示“登录了错误的账号”。
- 切换账号或退出后，前一个账号的正文、未读数和迟到的操作结果都不会出现在新账号中。
- 修改邮箱不产生新的收件身份，不清空已读，也不把历史消息转给使用该邮箱的其他账号。

流程参见[消息准入与目标权限分别判断（FL-O05）](./02-运营端消息通知-流程图与状态机.md#fl-o05)。

## 10. 待确认事项与依赖

当前没有需要裁定的新业务口径。

<a id="shared-validation"></a>**共享登记与真实送达依赖。** 两端共用同一份登记；来源的逐字段登记结果、收件范围与账号隔离、真实送达和原业务目标仍需完成验证，未完成时保持“待适配”。涉及共享登记一致性、真实送达及目标权限的验收待验，不判通过；本册字段规则本身不代表来源已适配。

依赖：

- 运营端账户与登录：账号与角色、首登强制改密、登录与登录后回到原目标、按角色授予功能权限项（消息查看权限（`PM-AL-12`）本身由本模块定义）与[按权限收敛入口与越权处理（F-AL-17）](../01-运营端账户与登录/01-运营端账户与登录-PRD.md#f-al-17)、语言与时区偏好。
- 研发小队：共享登记放在哪里、如何实现；PRD 只要求两端共用同一份登记、各来源统一登记。
- 各来源模块：按[接入字段](#intake-fields)在自己的消息通知册中登记每类消息，负责触发、收件范围、内容、文案与具体去向，并把到点事件的判定延迟控制在 5 分钟以内；数币精度与尾差等由来源确定，消息只按来源展示。
- 既有性能目标：未读数读取 P95 300 毫秒，列表首批 20 条 1 秒内，预览与详情各 P95 800 毫秒，1000 条以内的全部已读 2 秒内，进入详情时的原业务检查 500 毫秒内；实现与验证归研发、测试。
