<a id="entry"></a>
## 1. 模块是什么

平台预置了若干份协议（例如服务条款、隐私政策一类），面客端任何角色（含未登录的访客）都可以阅读协议文本。本模块让运营人员维护这些协议的**内容**：上传新的协议文件，当天 24:00 自动生效；查看版本历史与操作记录；同时保证面客端随时能取到本平台当前生效的那一版。

协议本身（叫什么、给哪些业务环节用、允许什么文件格式）由平台建设方预置，运营端只读；本模块不创建、不编辑、不下线协议。本平台本期不收取任何协议同意（[登录主干的协议口径](../../面客端/01-登录主干与资产方SSO接入/01-登录主干与资产方SSO接入-PRD.md#agreement)），协议文本只供阅读。

基本原则（用户 2026-10-20 确认）：

- **上传协议，当天 24:00 生效。** 上传成功的文件成为待生效版本，在上传当天 24:00（即次日 00:00）自动生效，替换原来的生效版本。
- **没有生效时间可选，也没有立即生效。** 不提供选择生效时间、立即生效或草稿保存。
- **每次调整都是上传新的协议，把旧的覆盖掉。** 24:00 前再次上传，直接覆盖还没生效的那份文件；被覆盖的文件不保留。
- **一份协议同一时刻最多一个待生效、一个已生效版本。**
- **已生效的内容不能修改，生效过的版本保留并只读。** 新版本生效或协议下线时，原生效版本自动归档，仍可由具协议历史版本读取权限的运营人员查看与下载，不能恢复或删除。
- **下线由建设方执行，重新上线是一份全新的协议。** 下线直接取消尚未生效的上传；重新上线不继承旧协议的任何版本或记录。
- **本平台的协议与另两个平台互不影响。** 同一份规格由运营管理平台、代币发行平台、资产可信平台各自使用，内容、版本与生效各自独立（见[平台独立](#platforms)）。

“24:00”指 UTC 24:00，与平台已确认的“业务日期统一按 UTC”一致；运营人员按个人时区看到对应钟点，例如北京时间为次日 08:00。

**一个完整的例子。** 某份已上线协议当前生效版本是 v2。运营管理员从共享导航进入“协议管理”，在列表中找到它，进入协议详情：基本信息里先是协议定义，后是操作进度。管理员点“更新协议”，上传新文件并提交；系统生成 v3 作为待生效版本，并写明它将在当天 24:00 生效，v2 仍在生效，面客端仍读到 v2；操作进度新增一条“上传”。当天下午发现文件有错字，管理员再点“更新协议”，看到的就是 v3 这份待生效文件，重新上传正确的文件——仍是 v3、仍是当天 24:00 生效，原来那份有错字的文件被覆盖、不再保留，操作进度记下覆盖前后的文件名。当天 24:00，v3 自动生效、v2 自动归档，面客端最迟 5 分钟内读到 v3；全体运营收到“定时生效成功”告警，从告警打开即进入 v3 的版本详情，读完返回原消息。

<a id="out-of-scope"></a>
### 1.1 本期不做

- 运营创建、编辑、下线或删除协议及协议类型；协议定义由建设方预置。
- 选择生效时间、立即生效、草稿保存。
- 在线编辑协议正文、协议正文分语种版本（一个版本只有一个文件）。
- 恢复历史版本、以历史版本为底复制新建、手动归档、删除已生效或已归档版本。
- 审批、复核、双人确认。
- 面客侧的协议同意、同意记录、强制重新同意（本平台本期不收取协议同意）。
- 运营设置“需重新同意”标记（用户 2026-10-20 裁定删除）。后续如需约束重新同意，由研发在代码层面直接约束，界面只做展示，不提供运营设置入口。
- 协议相关的邮件、短信或推送；发给资产方、资金方的协议更新通知。
- 跨平台总控台、在本端切换或批量管理另两个平台的协议。

## 2. 术语

| 术语 | 含义 |
| --- | --- |
| 协议 | 建设方预置的一份协议对象，有固定的协议标识；运营只维护它的内容 |
| 版本 | 协议的一份内容，含一个协议文件；版本号形如 v1、v2，只在本协议内计数 |
| 生效日界 | 每天 UTC 24:00（即 UTC 次日 00:00），所有待生效版本在这一刻生效 |
| 待生效 | 已上传、等待下一个生效日界的版本；同一协议最多一个 |
| 覆盖上传 | 已有待生效版本时再次上传，新文件替换待生效版本中的旧文件；版本号与生效时刻不变，旧文件不保留 |
| 已生效 | 面客端当前读到的那一版；同一协议最多一个 |
| 已归档 | 曾经生效、已被新版本替换或因协议下线而退出的版本 |
| 已取消 | 协议下线时尚未生效的待生效版本所转入的只读终态；与运营“撤销待生效”不同 |
| 撤销待生效 | 运营在生效日界前主动撤回待生效版本，该版本与文件一并移除，当前生效版本不变 |
| 下线 | 建设方停止某份协议的使用；协议转为已下线并只读留存 |
| 重新上线 | 建设方以完整的新定义上线一份新协议；与已下线的旧协议是两个对象 |
| 文件内容指纹 | 标识某个协议文件内容的指纹值，用于核对读到的文件就是这一版（原称“内容凭据”） |
| 操作进度 | 某份协议已发生的全部操作及其结果的记录，即协议操作记录 |

## 3. 通用规则

<a id="entry-order"></a>
### 3.1 功能入口与信息域

- 本模块入口是管理端共享导航中的“协议管理 / Agreements”；入口可见性按[权限](#permissions)判定，导航的承载与样式由设计决定。
- 本期四个信息域：协议列表（P-O-AG-01）、协议详情（P-O-AG-02，含“基本信息”与“版本历史”）、更新协议（P-O-AG-03）、版本详情（P-O-AG-04）。“基本信息”“版本历史”“版本详情”“操作进度”是信息域名称，“更新协议”“上传”“撤销待生效”是业务动作，均与界面上的位置和承载形式无关。
- 办理完成或返回时，回到来源并保留原检索条件、分页与所在位置。

<a id="permissions"></a>
### 3.2 权限与账号准入

- 本期运营端只有运营管理员一个角色（[本期预置角色（D-AL-08）](../01-运营端账户与登录/01-运营端账户与登录-PRD.md#d-al-08)），以下五项协议权限对每个正常登录的运营账号全部开通。
- 五项权限仍分开登记，作为后续细分角色时的授权单位；本期不产生按角色的差异。后续细分角色时，按本节已确认的边界执行：协议历史读取仅运营管理员、操作记录全员可看、维护与发布须配套当前内容查询（见下表）。

| 阅读或动作 | 所需权限 |
| --- | --- |
| 协议列表、协议定义、当前生效版本与待生效版本 | 协议当前内容与工作版本查询（PM-AL-09） |
| 上传与覆盖上传（上传即排定当天 24:00 生效，相当于更新内容并发布） | 协议内容与版本维护（PM-AL-10）与协议版本发布（PM-AL-11），并须同时具备 PM-AL-09 |
| 撤销待生效 | 协议版本发布（PM-AL-11），并须同时具备 PM-AL-09 |
| 版本历史、已归档与已取消版本的查看、预览与下载 | 协议历史版本读取（PM-AL-15） |
| 操作进度 | 协议操作记录查看（PM-AL-16）；不以 PM-AL-09 或运营端消息查看（PM-AL-12）为前提 |
| 协议告警站内信 | 运营端消息查看（PM-AL-12）；按[运营端消息通知](../07-运营端消息通知/01-运营端消息通知-PRD.md)阅读，不替代目标版本的权限 |

- 缺少哪项权限，对应动作就不可用，其余照常；交付配置中维护或发布未配套 PM-AL-09 时，对应动作被拒绝，并说明须由建设方修正交付配置，不静默通过，也不自动补授权。
- 共享账户菜单展示本人当前邮箱与真实角色；展示内容不改变授权。
- 本模块不新增人员或授权管理功能，不按运营机构或本人经办过滤数据。SPV 沿同一运营角色体系，不新增账号类型、机构过滤或跨平台权限。
- 账号未登录、登录失效、待首登改密或已锁定时，不开放任何协议内容与记录，按运营端账户与登录引导；已打开的办理也不能提交。
- 无权访问时不展示对应入口；直接访问被拒绝，不泄露记录是否存在，并可返回原入口。
- 内容查询、历史读取、记录读取分别判定；进入信息域、下载文件、从操作记录或消息跳转都不得绕过。
- 游客、面客账号与另两个平台的账号不属于本端运营人员，不能读取任何管理侧内容；公开读取只有[当前生效版本](#f-o-ag-11)。

<a id="platforms"></a>
### 3.3 平台独立

- 本规格由运营管理平台、代币发行平台、资产可信平台三个平台各自使用；各平台有自己的协议定义、文件、版本、当前生效版本、操作记录与消息，同名协议或相同协议标识不表示共用内容。
- 协议标识只在本平台内唯一；另一平台有相同标识不构成冲突，运营人员无需添加平台前缀，也无需填写或选择平台维度。
- 本端的上传、撤销、到点生效、生效失败或下线，都不改变另两个平台的版本、文件、消息或其面客端读到的内容；反之亦然。
- 本端列表、管理入口与读取只服务本端协议，不提供平台列、平台切换或跨平台批量读取。
- 本端登录或授权不能取得另两个平台的管理权限；SPV 与运营同一主体也不代表跨平台授权。
- 本平台的协议由运营管理平台维护、借贷面客端读取；另两个平台的实际协议清单、角色与信息域由各自登记，见[依赖](#dependencies)。

### 3.4 时间、语言与展示

- 生效日界是同一个真实时刻；所有时点按本人偏好时区展示并标注时区，切换个人时区只改变显示，不改变生效时刻。生效日界按 UTC；例如偏好时区为 UTC+8 的运营人员看到的生效时间是次日 08:00。
- 界面默认英文，支持中英即时切换；切换不清空已选文件与已填内容，也不改变任何协议文件。规则沿三平台共享国际化基线。
- 关键状态的英文名称：Scheduled 待生效、Active 已生效、Archived 已归档、Cancelled 已取消、Unpublished 未发布、Offline 已下线；动作的英文名称：Update agreement 更新协议、Upload 上传、Cancel scheduled version 撤销待生效。字段英文对照见[字段命名与术语对照表](../../00-字段命名与术语对照表.md)第 7 节。
- 长名称、协议标识与文件名的完整值须可获得；文件内容指纹可复制。
- 状态须有文字表达，不只靠颜色区分。
- 操作记录与通知中的人员邮箱按共享脱敏规则展示，不展示完整 IP。

<a id="states"></a>
## 4. 状态

### 4.1 版本状态

| 版本状态 | 允许的业务动作（另需权限，且协议已上线） | 谁能读取内容 |
| --- | --- | --- |
| 待生效 | 覆盖上传，或撤销待生效 | 按 PM-AL-09；不公开 |
| 已生效 | 本版本不能修改；可经“更新协议”上传下一版本 | 按 PM-AL-09；面客端公开读取 |
| 已归档 | 无任何写动作 | 按 PM-AL-15；不公开 |
| 已取消 | 无任何写动作，不能恢复 | 按 PM-AL-15；不公开 |

- 到点生效失败的待生效版本仍是待生效，在状态上附加“生效失败”，不另设版本状态。
- 被覆盖的文件、被撤销的待生效版本都不保留，不是一种版本状态；只在操作进度中留下记录。
- 取消编辑、提交失败都不是版本状态。

### 4.2 协议上线状态与协议状态

协议上线状态（已上线 / 已下线）描述协议对象本身，版本状态描述单个版本，二者是两个量。协议列表展示的“协议状态”由二者组合得出：

| 协议上线状态 | 版本情况 | 协议状态 | 更新协议时上传的结果 | 面客端公开读取得到 |
| --- | --- | --- | --- | --- |
| 已下线 | 任意 | 已下线 / Offline | 不可用 | 协议已下线 |
| 已上线 | 有已生效版本，无待生效版本 | 已生效 / Active | 新建下一编号的待生效版本，当天 24:00 生效 | 当前生效版本 |
| 已上线 | 有已生效版本，也有待生效版本 | 已生效 / Active | 覆盖该待生效版本的文件，版本号与生效时刻不变 | 当前生效版本 |
| 已上线 | 无已生效版本，有待生效版本 | 待生效 / Scheduled | 覆盖该待生效版本的文件 | 暂无生效版本 |
| 已上线 | 无任何版本 | 未发布 / Unpublished | 新建 v1 待生效版本，当天 24:00 生效 | 暂无生效版本 |
| 定义已被建设方移除 | 原有版本全部留存 | 不在当前协议列表中出现，管理侧仍可按原协议定位留存 | 不可用 | 协议不存在 |

- 待生效版本存在时，列表须能获知其版本号与生效时间，但不能把它当作当前生效版本；没有生效版本时“当前生效版本”一栏为“—”。

状态图见[单个版本状态机（ST-O-AG-01）](./02-运营端协议管理-流程图与状态机.md#st-o-ag-01)与[协议对象的上线与下线（ST-O-AG-02）](./02-运营端协议管理-流程图与状态机.md#st-o-ag-02)。

## 5. 协议定义、列表与检索（F-O-AG-01～F-O-AG-03）

适用角色与前提：正常登录的运营人员，具 PM-AL-09；从[功能入口](#entry-order)进入协议列表（P-O-AG-01），从列表中的协议进入协议详情（P-O-AG-02）。

### 5.1 协议详情的组成

- 协议详情包含“基本信息”与“版本历史”两个信息域；版本历史按 PM-AL-15 开放。首次从列表进入默认落在基本信息；重新取数和浏览器前进后退保留当前所在的信息域。
- 基本信息由“协议定义”与“操作进度”构成，二者须同时可得，顺序为先定义后进度。当前版本与待生效计划不另立独立信息域，操作记录也不另设独立信息域。
- 基本信息指当前所选协议的定义，不是某个版本的摘要。
- 当前生效版本与待生效版本须有可达的只读查询入口，按 PM-AL-09 进入版本详情（P-O-AG-04）。
- 更新动作统一叫“更新协议 / Update agreement”；规则见[上传协议](#f-o-ag-04)。

### 5.2 协议定义字段

协议定义全部只读，运营端不提供新增、编辑、下线、删除协议及协议类型的入口。下表的“必填”指协议定义是否完整，不是运营可编辑的内容；没有提供的默认值不能补成真实业务值。

| 业务信息 | 含义与类型 | 必填与校验 | 默认值 |
| --- | --- | --- | --- |
| 协议标识 | 文本；引用该协议的固定标识 | 必填；本平台内唯一；上线后不可变；字符与长度限制（由建设方随协议定义提供，见[依赖](#dependencies)） | 无 |
| 协议类型编码 | 文本；本平台自定义的协议分类编码 | 必填；取本平台定义，不套用他平台类型清单 | 无 |
| 协议类型名称（中／英） | 文本；协议分类的双语名称，列表展示依据 | 两种语言均必填 | 无 |
| 协议名称（中／英） | 文本；按界面语言显示的协议名称 | 两种语言均必填；只表示名称双语，不表示协议文件分语种 | 无 |
| 协议用途说明 | 文本；供运营理解该协议用途的内部说明 | 可选；不对外公开；长度限制（由建设方随协议定义提供，见[依赖](#dependencies)） | 空 |
| 适用业务环节 | 环节清单；每项含编码与中英文名称 | 必填；写明本平台面客端在哪些环节取用本协议；实际清单与字段限制（由建设方随协议定义提供，见[依赖](#dependencies)） | 无 |
| 允许上传格式 | 格式清单；本协议可上传的文件格式 | 必填；按协议逐项明确；适用业务环节需要在线阅读时应选择可在线呈现的格式 | 无全局兜底 |
| 单文件大小上限 | 文件容量；单个文件可接受的最大容量 | 必填；按协议明确数值与单位，上传前须可获知；未明确不得上线 | 无全局兜底 |
| 协议上线状态 | 二值：已上线 / 已下线 | 必填；运营只读；已下线仍保留历史 | 无 |
| 默认排序值 | 数值；协议列表的默认排列依据 | 可选；缺值时的顺序与取值范围（由建设方随协议定义提供，见[依赖](#dependencies)） | 无 |

- 协议定义由研发随既定配置发布提供，本册不展开实现。新定义可用后以“未发布”出现在列表。
- 缺允许上传格式或单文件大小上限的定义不得上线，不作为可用协议出现在列表。
- 协议由系统预置、本模块只维护内容与版本，这一点须在协议列表与协议定义处可获知。
- 已下线与定义被移除的结果见[协议下线、留存与重新上线](#offline)。

### 5.3 协议列表

- 列表只保留核心信息（用户 2026-10-20 确认），每条协议须可得：协议名称与协议标识、协议类型、当前生效版本及其生效时间、待生效版本及其生效时间（如有）、协议状态、最近更新，以及进入协议详情的动作。
- 无当前生效版本、无待生效版本或从未有操作时，对应值取“—”。
- 适用业务环节、版本数等其余信息在协议详情中查看。
- 协议状态按[协议上线状态与协议状态](#states)的组合表判定。
- 列表只含本平台协议；没有新建协议的入口。

### 5.4 检索与分页

| 条件 | 规则 |
| --- | --- |
| 关键词 | 同时模糊匹配协议名称（中英）与协议标识；忽略大小写与首尾空格 |
| 协议状态 | 多选 |

- 两个条件取交集，协议状态多选取并集；“查询”应用条件，“重置”清空条件并回到第 1 页。
- 固定先按默认排序值，再按最近更新时间从新到旧，不提供其他排序。
- 每页 20 条，不提供每页条数切换；重新取数与浏览器前进后退保留筛选与分页。
- 取数进行中须可识别；取数失败可重试并保留条件，不把失败显示成没有协议。
- 两种空结果须可区分：本端尚无协议定义时说明“暂无协议，协议由系统预置”；筛选无匹配时说明没有符合条件的协议并提供重置。两种情形都没有新建协议的入口。

## 6. 上传协议（F-O-AG-04、F-O-AG-05）

适用角色与前提：协议为已上线对象；运营人员具 PM-AL-09、PM-AL-10 与 PM-AL-11。已下线的协议不能再上传；重新上线的新协议从 v1 开始。

### 6.1 更新协议与上传

- 协议详情的“更新协议”进入更新协议（P-O-AG-03）。只有查询权限时不提供该动作。版本历史与版本详情中没有更新入口。
- 更新协议只做一件事：选择一个协议文件（可附变更说明）并提交上传。没有生效方式、生效时间或草稿保存可选。
- 进入时须可获知：当前生效版本（如有）；待生效版本（如有）的版本号、文件与生效时间；以及本次上传成功后的生效时间。
- 上传成功的结果：

| 上传时的协议情况 | 结果 |
| --- | --- |
| 没有待生效版本 | 新建下一编号的待生效版本，生效时间为当天 24:00 |
| 已有待生效版本 | 覆盖上传：新文件替换该待生效版本的文件，版本号与生效时间不变；被覆盖的文件不保留 |

- 上传直接提交，不需要二次确认；24:00 前可以随时再次覆盖上传或撤销。
- 上传成功后回到协议详情的基本信息，操作进度随之更新。
- 不需要第二人复核。

### 6.2 文件规则

- 一个版本只对应一个文件；没有语种选择，也没有正文在线编辑。
- 一次只提交一个文件；未选文件不能提交；一次选多个文件、空文件、改扩展名伪装的文件均被拒绝。
- 格式与大小按本协议定义；大小等于上限可接受，超过才拒绝。错误须说明本协议实际的格式要求或大小上限。
- 已上传的文件须可获知原始文件名、大小、上传时间，并可下载。
- 上传进行中须可识别；上传失败时既有待生效版本与当前生效版本都保持原样，已填内容保留，可重试。

### 6.3 版本字段

| 业务信息 | 含义与类型 | 必填、可编辑与校验 | 默认值 |
| --- | --- | --- | --- |
| 版本号 | 文本，形如 v1、v2 | 系统生成、只读；新建待生效版本时分配更大且从未用过的编号；覆盖上传不改变版本号；被撤销的版本号不复用 | 新建时自动递增 |
| 协议文件 | 文件；协议正文或模板 | 必填；须符合本协议的格式与大小限制 | 无 |
| 变更说明 | 文本；说明这次内容的变化 | 可选；最多 500 字符；覆盖上传时可重新填写 | 空 |
| 生效时间 | 时间点；系统按生效日界给出 | 只读，不可选择；待生效版本取当天 UTC 24:00，按本人时区展示并标注时区 | 系统给出 |

### 6.4 撤销待生效

- 已有待生效版本时，可在生效日界前撤销待生效；须二次确认，确认时展示协议名称、版本号、原生效时间，并说明撤销后该版本与文件将被移除。取消确认时不发生任何变化。
- 撤销后，待生效版本与其文件一并移除、不保留，当前生效版本不变；没有生效版本时协议回到“未发布”。

### 6.5 异常与边界

- 离开更新协议时若已选文件但未提交，须先确认；取消则继续，确认才放弃。
- 提交进行中不重复执行；重复提交不会产生两个待生效版本。
- 两人先后上传同一协议时，以后提交成功的为准，两次上传都记入操作进度。
- 生效日界当刻：以 24:00 那一刻的待生效文件为准生效；24:00 之后提交的上传归入下一个生效日界，不会改写刚刚生效的内容。

流程参见[按对象读取与上传协议（FL-O-AG-01）](./02-运营端协议管理-流程图与状态机.md#fl-o-ag-01)，状态参见[单个版本状态机（ST-O-AG-01）](./02-运营端协议管理-流程图与状态机.md#st-o-ag-01)。

## 7. 到点生效（F-O-AG-06）

| 情形 | 结果 |
| --- | --- |
| 生效日界到达且生效成功 | 待生效版本成为已生效，原已生效版本同时自动归档；实际生效时间为本次生效成功的时刻；不以运营人员是否在线为条件 |
| 首版生效前 | 面客端公开读取为暂无生效版本，直到生效成功 |
| 生效失败 | 待生效版本保留并附加“生效失败”，当前生效版本不变；首版仍无当前生效版本；记录失败并发送站内信。该版本在下一个生效日界再次生效；期间可覆盖上传或撤销 |
| 协议在生效前已下线 | 待生效版本按下线取消，不再生效，不发生效结果告警；见[协议下线、留存与重新上线](#offline) |

- 同一协议任意时刻最多一个待生效、一个已生效版本；替换不得出现同时两份生效或暂时没有生效版本的中间结果。
- 生效时冻结最终生效的文件及其文件内容指纹；已生效、已归档、已取消版本的内容与文件内容指纹固定不变。
- 被覆盖的待生效文件与被撤销的待生效版本都不保留，不能再读取；操作进度只记文件名与变化。
- 重新上线的新协议从 v1 开始，与旧协议同号不代表同一版本。
- 生效时刻按同一真实时刻判断；生效日界为 UTC 24:00。

通知：生效成功、生效失败、撤销待生效三处向全体运营发送站内信，见[消息通知](#notifications)。
流程参见[上传、覆盖与到点生效（FL-O-AG-02）](./02-运营端协议管理-流程图与状态机.md#fl-o-ag-02)。

## 8. 协议下线、留存与重新上线（F-O-AG-06、F-O-AG-07、F-O-AG-09、F-O-AG-11）

适用前提：下线与重新上线由建设方执行（需求方 P12 裁定，开发层面直接取消）；运营端不新增上下线动作、审批或人工撤销步骤。本节只定义运营人员与面客端可观察到的结果。

### 8.1 下线的结果

| 情形 | 结果 |
| --- | --- |
| 下线成功 | 原协议停止对外提供当前内容；待生效版本直接取消，到生效日界也不会生效 |
| 原来有已生效版本 | 转为已归档，保留原实际生效时间、文件与归档时间；这不是运营手动归档 |
| 原来有待生效版本 | 转为已取消；原生效时间与取消原因“协议下线”在版本详情与操作进度中可查；实际生效时间为空，不伪造生效或归档经历 |
| 生效失败后再下线 | 原失败事实保留，待生效版本按下线取消；取消不报告成生效失败或成功 |
| 上传、撤销或到点生效与下线相遇 | 下线成立后，上传、覆盖上传与撤销都不能再成功，并告知协议已下线、可返回；若到点生效先成功，保留这次真实生效记录，再按下线归档；下线后旧内容不会重新成为当前可用版本 |
| 下线结果未成功或未明 | 不展示已下线或已取消；说明结果尚未确认，重新读取可信状态；不把未确认的结果写成记录或通知 |
| 定义被移除 | 保留原协议身份与必要的历史信息；版本历史与操作进度仍可按原协议定位；面客端不再取用原内容，公开读取得到“协议不存在”；不因定义消失删除历史，也不误指新协议 |

- “已取消”只表示因下线而终止的待生效版本，是只读终态；与运营主动撤销待生效不同，后者直接移除待生效版本。
- 下线留存的版本仍按原版本号从新到旧排列。

### 8.2 重新上线

- 建设方提供完整的新定义，成为一份独立的新协议：初始为未发布，无当前生效版本、无待生效版本。
- 首次上传新建 v1，当天 24:00 生效。
- 新协议有独立的协议与版本标识；名称或用途相同也不继承旧协议的文件、版本序列、操作记录或消息归属，不以“恢复旧版”或复制旧版本代替全新上线。

### 8.3 旧地址与留存

- 旧版本、旧操作记录与旧消息仍指向原协议；版本内容按 PM-AL-15 读取，操作记录按 PM-AL-16 读取；无权时说明并可返回。任何情况下都不自动转向同名新协议或其 v1。
- 下线的留痕包括原协议、关联版本（如有）、发生时间、执行方、结果与原因“协议下线”；无版本的定义下线关联版本取“—”，不造 v0 或其他版本。自动取消与自动归档的执行方记为“系统”，不冒记为某位运营人员。
- 旧记录与已归档、已取消版本的文件永久保留、不可篡改；留存不等于公开。用户已下载的文件不在本模块追回范围。
- 重新上线的新协议单独计数，旧记录不混入新协议的操作进度。

流程参见[下线、旧对象留存与全新上线（FL-O-AG-06）](./02-运营端协议管理-流程图与状态机.md#fl-o-ag-06)。

## 9. 版本历史与版本详情（F-O-AG-07）

### 9.1 版本历史

适用角色与前提：具 PM-AL-15 的运营人员，从协议详情的“版本历史”进入。

- 按版本号从新到旧，包含待生效、已生效、已归档与已取消的版本；当前已生效的是哪一条须可识别。被覆盖的文件与被撤销的版本不出现。
- 版本历史只承载辨认版本所需的信息与打开内容的动作，完整信息在版本详情。

| 业务信息 | 取值与空值 |
| --- | --- |
| 版本号 | v{n}，本协议内唯一；待生效版本多次覆盖上传仍是同一条 |
| 版本状态 | 待生效、已生效、已归档、已取消；生效失败的待生效版本附加“生效失败” |
| 生效时间 | 待生效版本取即将到来的生效日界并标明是计划；已生效与已归档版本取实际生效时间；已取消版本取“—”，原生效时间到版本详情查看；均带时区 |
| 可做的动作 | 只有“查看”与“下载协议” |

- 版本历史中没有上传、撤销、删除、手动归档、恢复或“以此新建版本”；持有全部写权限也不改变这一范围。上传回到协议详情的“更新协议”。
- 已生效版本在另一版本生效成功或协议下线时自动归档，没有手动归档入口。

### 9.2 版本详情

适用角色与前提：当前生效版本与待生效版本按 PM-AL-09 读取；已归档、已取消版本按 PM-AL-15 读取。可从协议详情的当前查询入口、版本历史、操作进度或消息进入。

- 版本详情（P-O-AG-04）是独立的只读信息域，有可直接访问的地址，关联指定协议的指定版本；不能用当前生效内容冒替被查看的版本。
- 除查看内容、复制文件内容指纹、下载与返回外，没有写动作。
- 这一版本由谁在何时上传、覆盖或撤销，在[操作进度](#f-o-ag-09)中查看，版本详情不再逐项重复。

| 业务信息 | 含义与取值 |
| --- | --- |
| 协议标识、版本标识与版本号 | 系统提供，必有、只读；必须对应打开的那一版 |
| 版本状态 | 待生效、已生效、已归档、已取消；由[到点生效](#f-o-ag-06)与[下线](#offline)决定，不能手动修改 |
| 文件信息 | 文件实际名称、格式、大小、上传时间；只读 |
| 生效时间 | 带时区；待生效版本为计划生效时间，已生效与已归档版本为实际生效时间，两者明确区分 |
| 归档时间 | 只读；未归档时为空 |
| 取消时间与取消原因 | 只对已取消版本；须有真实取消时点，并保留原计划生效时间 |
| 变更说明 | 只读；未填写时为空 |
| 文件内容指纹 | 对应所展示的协议文件；只读、可复制；待生效版本标明“尚未生效，24:00 前可被覆盖”，已生效与已归档版本固定 |

- 文件可在线呈现时提供预览与下载，不能呈现时说明并提供下载；预览失败可重试或下载。
- 返回时回到来源并保留原筛选、分页与所在位置：从版本历史进入的回到版本历史，从当前查询、操作进度或消息进入的回到各自来源；不能把无历史权限的人带入版本历史。
- 重新取数与浏览器前进后退仍指向原指定版本。
- 取数失败可重试；版本不存在（含已被撤销）或无权限时给出明确说明与可用的返回路径，不默认显示第一条样本。

流程参见[当前查询、版本历史与原来源返回（FL-O-AG-03）](./02-运营端协议管理-流程图与状态机.md#fl-o-ag-03)。

## 10. 操作进度与留痕（F-O-AG-09、F-O-AG-10）

适用角色与前提：具 PM-AL-16 的运营人员；不以 PM-AL-09 或 PM-AL-12 为前提。操作进度位于协议详情的基本信息中，排在协议定义之后。

- 操作进度表达该协议已发生的操作与结果，覆盖全部版本，不只取当前生效版本；不新建审批流，也不虚构完成百分比。
- 不按本人经办或所属机构过滤。

| 业务信息 | 含义与取值 |
| --- | --- |
| 操作类型 | 实际发生的业务动作：上传、覆盖上传、撤销待生效、系统生效、系统归档、到点生效失败、协议下线、关联取消 |
| 关联版本 | 本次动作关联的版本号；版本动作必有；无版本的定义下线取“—”；始终关联原协议，不能只靠 v1 这类同号辨认新旧协议 |
| 操作人 | 实际姓名与脱敏工作邮箱；自动动作记为“系统 / System” |
| 操作时间 | 动作发生的时点，带时区；默认按发生时间从新到旧 |
| 结果 | 成功 / 失败；只打开查看、未提交的选择不记为成功变更；到点生效失败明确为失败 |
| 变更摘要 | 一句话说明实际变化，完整内容须可获得；上传时含文件名与生效时间；覆盖上传时含被覆盖与新的文件名；撤销时说明待生效版本已移除 |

- 记录只读、由系统生成；操作类型、原协议、执行方、操作时间、结果、变更摘要均必有，关联版本按上表条件必有。
- 人工动作以发生时的姓名与脱敏邮箱为归属，之后改邮箱不改写已有记录；系统动作不填造邮箱。来源地点只展示地区摘要，不展示完整 IP。
- 每次覆盖上传都单独留痕；被覆盖的文件本身不保留、不提供读取入口。
- 操作记录中不出现协议正文、附件、文件内容指纹或可取文件的地址；记录只显示脱敏的业务身份，不链接他人账户档案。
- 每页 20 条，不提供每页条数切换；日期排序不因语言或时区改变实际先后。
- 三种情形须可区分：本协议尚无操作时说明“暂无操作记录”；取数失败时只影响操作进度本身、可重试，不当作没有记录；登录失效或账号不正常时按账户准入处理，不伪装成空记录。

**变更约束（F-O-AG-10）：**

- 记录只增不改、永久保留；已生效、已归档、已取消版本的文件永久保留、不可修改或删除。
- 越权、修改协议定义、修改已生效内容、篡改操作记录在实际执行时同样被拒绝，不能只靠不提供入口实现。

流程参见[按对象读取与上传协议（FL-O-AG-01）](./02-运营端协议管理-流程图与状态机.md#fl-o-ag-01)与[上传、覆盖与到点生效（FL-O-AG-02）](./02-运营端协议管理-流程图与状态机.md#fl-o-ag-02)。

<a id="f-o-ag-11"></a>
## 11. 当前生效版本的公开读取（F-O-AG-11）

适用角色与前提：本平台面客端任何角色（含未登录的访客）阅读协议文本时读取；按协议标识读取，也可一次取多份或按协议类型取已上线协议的当前生效版本。本模块只定义取到什么与异常结果；面客侧在哪里展示协议由各消费模块定义。

| 情形 | 结果 |
| --- | --- |
| 已上线，有当前生效版本 | 取得本平台该版本的协议名称、协议标识、协议类型、适用业务环节、版本标识与版本号、文件信息与文件、文件内容指纹、生效与发布时间；版本、文件与文件内容指纹对应同一已生效内容 |
| 待生效版本 | 不作为当前版本返回；直接指定版本或访问文件也取不到未生效内容 |
| 已归档、已取消版本 | 不公开提供；直接指定历史版本或旧文件地址同样不可读，不能借公开读取绕过 PM-AL-15 |
| 协议不存在（未定义或定义已移除）、协议已下线、暂无生效版本（含重新上线后尚未发布）、版本不存在 | 四种结果分别可识别，不表现为成功取得空白文件；暂无生效版本时不从旧协议或另一平台补取 |
| 读取失败 | 明确说明读取失败，不当作没有协议 |
| 另一平台有同名或同标识协议 | 始终取本平台的版本；本平台没有可用版本时不借用另两个平台的版本 |

- 公开内容不含协议用途说明、运营人员身份、操作记录或待生效内容；不提供正文语种切换、在线富文本或平台切换。
- 当前生效版本切换后，面客端最迟 5 分钟内显示新版本（沿协议管理基线）。
- 读取字段映射与文件内容指纹约束沿协议管理基线第 9 节，本册不复制接口、参数或访问路径。

流程参见[公开当前版本读取（FL-O-AG-04）](./02-运营端协议管理-流程图与状态机.md#fl-o-ag-04)。

## 12. 消息通知

- 本模块向本端全体运营发送三类站内信：到点生效成功、到点生效失败、撤销待生效；触发环节、收件范围、内容要点与打开后去哪见[消息通知](./03-运营端协议管理-消息通知.md)。撤销告警是否保留待用户确认（[撤销告警是否保留（Q-O-AG-14）](#q-o-ag-14)），确认前照常发送。
- 上传、覆盖上传、下线及其自动取消、重新上线、操作记录被查看、历史被下载都不发站内信；当次结果由办理结果与操作进度告知。
- 不发邮件、短信或推送，不向资产方、资金方或另两个平台的账号发送。
- 消息的阅读、未读与跳转按[运营端消息通知](../07-运营端消息通知/01-运营端消息通知-PRD.md)执行；从消息进入版本时按目标版本此刻的状态重新判断权限（见[版本详情](#f-o-ag-07)）。

流程参见[事件告知、阅读与目标权限（FL-O-AG-05）](./02-运营端协议管理-流程图与状态机.md#fl-o-ag-05)。

<a id="accepted-limits"></a>
### 13.2 按用户决定保留的业务后果

供研发与测试知悉，不判为缺陷：

1. **上传后最早当天 UTC 24:00 才生效。** 没有立即生效：发现线上协议有错误时，修正版最快在当天 UTC 24:00（北京时间次日 08:00）生效，期间面客端仍读到原版本。
2. **24:00 前的最后一次上传会生效。** 上传不需要二次确认；临近 24:00 上传的文件也会在这次 24:00 生效。
3. **下线没有运营端动作。** 下线由建设方在开发层面执行，运营端看不到也不能发起下线、撤回下线或恢复旧协议；需要恢复时只能由建设方重新上线一份新协议，并重新上传 v1。
4. **本平台本期不收取协议同意。** 协议文本只供阅读；更换协议内容后，平台侧没有用户已阅读或已同意新版本的记录。

<a id="dependencies"></a>
### 13.3 依赖

- **运营端账户与登录**：提供账号、会话、本期单一角色与协议相关权限项（PM-AL-09～PM-AL-11、PM-AL-15、PM-AL-16）及运营端消息查看（PM-AL-12）。
- **运营端消息通知**：承接本模块三类站内信的展示、未读与跳转。本模块的到点生效成功与失败属于到点事件（生效日界），须在 5 分钟内判定，以满足消息框架“从应到时点起最晚 6 分钟可见”的要求；实现与验证归研发、测试。
- **面客端各消费模块**：负责在面客侧何处展示协议文本；本平台本期不收取协议同意。
- **建设方**：随协议定义提供真实协议清单、适用业务环节清单、各协议的允许上传格式与单文件大小上限、协议标识的字符与长度、协议用途说明的长度、默认排序值缺值时的顺序与取值范围（用户 2026-10-20 确认）；提供前按本册已确定的行为设计与开发，演示用的格式与大小（如 PDF、5MB）不是上线配置。另负责执行下线与重新上线，并交付本期运营账号与权限配置。
- **另两个平台**：代币发行平台、资产可信平台按本规格各自建立实例，其协议清单、角色映射与信息域编号由各自登记；三平台互不影响的结果需在各平台实例上分别验证。
- **三平台共享国际化基线**：语言、时区与脱敏口径。
- **协议管理基线**（`cly-V1.0.0` 的 `financial-service-platform/prd/v1.0-协议管理/`，只读）：读取字段映射与文件内容指纹约束（第 9 节）、文件安全与访问约束（第 12.2 节）、协议定义随既定配置发布（第 7.1 节）。文件呈现不能执行文件中的恶意内容，也不能泄露非公开文件；不合法格式不能仅凭改名通过。
- **技术目标**（沿协议管理基线）：生效日界的切换偏差不超过 60 秒；20 条列表首批与版本详情 P95 小于 1.5 秒；面客端当前版本读取 P95 小于 300 毫秒；下载首字节 P95 小于 800 毫秒；支持 Chrome、Edge、Firefox、Safari 最近两个大版本。实现与验证归研发、测试。
