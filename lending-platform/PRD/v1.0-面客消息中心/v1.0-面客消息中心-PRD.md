# 借贷平台 · 面客端 · 面客消息中心 PRD **V1.0**

> **本模块是框架型模块。** 它不生产任何一条业务消息，只做三件事：**持有本平台面客端的消息池**、**提供 `biz_type` 触发登记的规则与表位**、**把消息呈现给资产方与资金方**。
>
> **接入一个新业务的唯一动作是「往触发登记表加一行」，正文零改动。** 这是本册的硬性验收（`AC-NC-01`～`AC-NC-06`），不是愿望。因此本册**正文里不存在任何一条具体业务消息**——不列事件清单、不写发送时点、不写任何一条消息的文案、不出现任何一个具体的 `biz_type` 取值。哪些事会发消息、什么时候发、文案写什么，由各业务模块在**它们自己的 PRD** 里定义并登记。
>
> **本模块为三册 + 一份图册**（章节号连续，同一编号只在一处定义）：
>
> | 文件 | 章节 | 主阅读角色 |

## 3. 背景、定位与目标

### 3.1 背景

借贷平台的面客用户有两类：**资产方**（经资产可信平台授权登录）与**资金方**（本平台账号，以境外机构为主）。他们在平台上办的业务有一个共同特征——**事情先发生在别处，人要被告知**：状态在后台流转、结论在对手方那里产生，而用户无从知晓。没有统一的站内消息入口，用户只能逐个打开业务列表页轮巡。

> **本节刻意不列举任何业务事件。** 哪些事会发消息、什么时候发，由各业务模块在自己的 PRD 里定义——这是本册作为框架的第一条纪律，从背景章节就开始遵守。

三平台独立后，消息能力必须在本平台**自己长出来**：消息池归本平台、登记表归本平台、页面归本平台。而本模块的开工时点**比它的接入方更早**——借贷广场、我的控制台、代币质押等模块还在各自排期。**因此本期交付的是框架，不是成品**：把「收」这一侧的规则、边界与登记方式一次定死，让后续模块接进来时只需往登记表加一行。

### 3.2 产品定位

| 项 | 口径 |
| --- | --- |
| 一句话 | 借贷平台面客用户的**唯一站内消息入口**：知道发生了什么，并能一键到该处理的地方 |
| 主对象 | **一条消息**（不是一笔业务、不是一个待办） |
| 本模块做什么 | **收**：消息池、可见范围、未读计数、列表与详情、已读语义、分类筛选、跳转执行与降级、进度展示、双语渲染、会话失效表现 |
| 本模块**不做**什么 | **发**：哪些业务事件产生消息、什么时点发、每条叫什么 `biz_type`、文案写什么、发给谁——**全部归各业务模块**（4.2） |
| 与「我的控制台待办」的分工 | **消息 = 告知，待办 = 当前状态**（5.6 `B-1`～`B-5`） |
| 与其他平台消息中心的分工 | **各平台各自一个消息中心，本期不合并**（5.1 `D-NC-10`） |
| 产品形态 | Web，桌面 + 移动自适应（借贷平台面客端母版）；**登录后可用，游客不可见** |
| 页面数 | **2**：`P-F-MC-01` 消息中心列表、`P-F-MC-02` 消息详情 |

### 3.3 本期目标

| # | 目标 | 达成口径 |
| --- | --- | --- |
| `G-NC-1` | 已登录用户在**任意页面**都能看到「有几件事需要我知道」 | 顶栏消息入口常驻 + 未读角标（分册 01 11.1） |

## 4. 范围

### 4.1 本期做

- **消息池**：本平台面客端消息的承接范围、可见范围与归属、未读计数口径、保留与清理、异常数据处置（分册 01 第 9 章）。
- **`biz_type` 触发登记框架**：登记表的表位与填表规则（`RG-NC-01`～`RG-NC-12`）、分类框架、未登记时的降级、文案模板与双语规范、增量接入自检（分册 01 第 10 章）。
- **页面与展示**：`P-F-MC-01`、`P-F-MC-02` 与四个组件；入口与角标、快捷面板、列表与筛选、已读语义、详情与进度、跳转与降级、空态与异常、会话失效表现（分册 01 第 11 章）。
- **对消息来源方的业务要求**：`IF-NC-01`～`IF-NC-10`（5.7）。
- **跨平台深链在本平台侧的行为要求**：作为被跳转方与作为发起方（5.8、分册 01 第 12 章）。

### 4.2 本模块只做「收」不做「发」（**红线**）

| 项 | 归属 |
| --- | --- |
| **收**：列表、详情、未读角标、已读语义、分类筛选、加载更多、空态、跳转执行与降级、失效表现、双语渲染、进度展示 | **本模块** |
| **发**：哪些业务事件产生消息、什么时点发、每条叫什么 `biz_type`、文案写什么、发给谁 | **各业务模块**，按分册 01 第 10 章自助登记 |
| 消息内容的编辑、人群圈选、发布与撤回、定时发送 | **不在本模块**，也不在本期 |
| 站外触达（邮件 / 短信 / 推送） | **不在本模块** |
| 通知偏好 / 订阅开关 | **本期不做**（`X-NC-05`） |

`D-NC-07`【红线 · 反向】：本 PRD、原型与实现中**不得出现任何「发消息」「新建通知」「通知设置」「消息偏好」入口**。本模块的全部界面动作**只有六个**：看、筛、加载更多、标已读、跳过去、返回。

### 4.3 本期不做（各有归属，不是遗漏）

### 4.4 本期取舍（代价正面写出来）

| # | 取舍 | 本期结论 | 代价 |
| --- | --- | --- | --- |
| 1 | 消息按自然人账号定向还是按企业主体定向 | **按自然人账号** | 同企业其他成员看不到同一条消息。企业维度的感知由**控制台待办带**承担 |

## 5. 硬口径与红线

> 本章是本册的规则核心。**分册 01 是它的展开，分册 02 是它的验收，图册是它的图示，三处不另造口径。**

### 5.1 承接范围：本模块只承接本平台面客端的消息（**红线**）

| 编号 | 条款 |
| --- | --- |
| `D-NC-08` | 本模块的消息池里**只有借贷平台面客端的消息**，一条都不多。资产可信平台、代币发行平台、本平台管理端的消息**一律不承接**，各自留在各自的消息中心 |
| `D-NC-09` | **跨平台聚合不做、不预留、不开关控制。** 不存在任何形式的跨平台消息聚合、跨平台未读数合计的入口、菜单、开关、配置项或请求参数 |
| `D-NC-10` | **资产方是同一个人，在资产可信平台与借贷平台会有两个消息中心、两套未读数、两份已读状态，本期不合并。** 这是「只承接本平台」的**必然结果，不是漏做**——要合并就是另一个量级的跨平台聚合需求。对客与客服口径应按「各平台各自有自己的消息中心」讲，**不要讲成「正在做合并」** |
| `D-NC-11` | **归属由来源方在提交时决定，本模块不参与路由。** 一条不属于本平台面客端的消息**根本不会进入本模块的池**，不存在「被本模块接收后再过滤掉」这条路径 |
| `D-NC-12` | 本模块的**每一处查询**（列表、详情、未读数、标已读、全部已读、跳转预检）都以「本平台面客端 ∧ 当前登录账号」为强制范围，**忽略请求侧任何形式的范围指定**——包括缺省、空值、数组与多值形态 |
| `D-NC-13` | **异常数据**：若因故障或数据错误，池中出现不属于本平台面客端的记录，本模块**不渲染、不计入未读数、不可经由详情深链打开**，并记录一次数据异常。**不做兼容展示、不做降级展示** |

### 5.2 只做「收」不做「发」

见 4.2 `D-NC-07`。

### 5.3 可见范围与归属（**红线**）

| 编号 | 条款 |
| --- | --- |
| `D-NC-14` | 一条消息的收件人是**一个自然人账号**。可见范围 = **本平台面客端 ∧ 收件人 = 当前登录账号**，不存在第二种可见模型 |
| `D-NC-15` | **归属一律按本平台的账号标识判定。** 不得用邮箱、钱包地址、其他平台的账号原值作为归属依据——同一钱包地址允许同时是资产方与资金方，用邮箱或钱包做归属会让合法的双身份用户**串池** |
| `D-NC-16` | **按人不按企业**：同企业其他成员**看不到**同一条消息。企业维度的感知由我的控制台的待办带承担（`B-5`） |
| `D-NC-17` | 本模块**不得读取账户的原始资质状态**（认证状态、申请单状态等）来推导归属或可见性；展示类功能一律消费登录态已对外给出的账号标识与角色 |
| `D-NC-18` | **越权一律返回「不存在」语义，不返回「无权限」**，且不可与「消息确实不存在」相区分；**消息标识不可枚举**；**不提供批量取消息的入口** |
| `D-NC-19` | 「同企业成员看不到、铃铛为 0 而待办带有事」是**设计上正确的表现**，必须**写明了的正确**（对客文案与帮助中心同口径），否则会被当成缺陷反复上报（`R-NC-01`） |

### 5.4 未读计数口径

| 编号 | 条款 |
| --- | --- |
| `D-NC-20` | 未读数 = **可见范围内的条数 − 该收件人已读的条数**，由服务侧计算，**前端不自行推导** |
| `D-NC-21` | 角标**不分分类**，为全分类合计；分类维度通过列表筛选表达 |
| `D-NC-22` | **不计入**：已过期的消息、已主动失效的消息 |
| `D-NC-23` | **仍计入**：「目标已删除 / 目标状态已流转 / 无权限」三类跳转失效的未读消息（这三类是进入详情时的实时判定结果，不做全量预判）；**业务类型未登记**的消息（未登记不是失效） |
| `D-NC-24` | 超过 `N-NC-03`（99）展示 `99+`，该状态下不展示精确数字；无未读时**不展示角标，也不展示 `0`** |
| `D-NC-25` | 取数失败时角标**保留上一次数值**，**不清零、不弹错误提示**——一次网络抖动把角标清成 0，用户会以为消息被读掉了 |

### 5.5 会话失效一律回落游客态（**红线**）

> 这是面客端与管理端的根本差异：管理端跳走登录页、页面自然卸载；面客端**留在原页**，不主动清就会残留。

| 编号 | 条款 |
| --- | --- |
| `D-NC-26` | 会话失效时，已渲染的**消息列表、详情正文、快捷面板内容、未读角标数字全部从页面移除**，整页替换为游客态视图，**不是用弹层盖住** |
| `D-NC-27` | 顶栏消息入口与账号下拉的「消息中心」条目**随登录态一起消失**；**不得出现「已回落游客态但入口还在」的中间态** |
| `D-NC-28` | 未读数刷新**立即停止**并中止进行中的取数；游客态下**不得发起任何未读数请求** |
| `D-NC-29` | 会话在详情页失效时，详情内容**整页卸载**，不是弹层遮挡——共用办公设备下「弹个框盖住」等于没登出 |
| `D-NC-30` | 游客访问消息中心的任一地址：**不给「不存在」页、不白屏、不静默跳首页**，一律走本平台面客端既定的登录回跳机制，登录成功后**回到原处**（列表回列表，详情回该条详情）。**本模块不自建回跳解析、不自拼回跳参数**（`DEP-NC-02`） |
| `D-NC-31` | **未读数刷新不得用于续期或保活会话**，也不得被计入任何「用户活跃」判定。不写这条，一个后台常驻刷新会把绝对会话悄悄变成滑动会话 |
| `D-NC-32` | 未读数刷新遇到登录态失效**不得静默忽略**，与其他请求一视同仁立即触发统一回落——否则会出现「页面还在、角标还在刷、登录态其实已经没了」的假活状态 |
| `D-NC-33` | 若本平台存在「登录后尚未完成必办前置」的受限会话形态，**消息中心一律不可达**（等同游客处置），**不得因为「消息中心又不是业务」而开口子**——消息内容本身就是业务数据 |

### 5.6 消息与待办的边界（`B-1`～`B-5`，**跨模块引用点**）

> **本节是跨模块引用点。** 我的控制台开工时**直接引用本节**，不重新讨论、不各写一版。

| # | 判据 | 展开 |
| --- | --- | --- |
| `B-1` | **消息 = 告知，待办 = 当前状态** | 消息记录**发生过的事**，读过就完了，读完仍保留在列表里；待办表达**当前还没做完的事**，业务状态一变自动消失 |
| `B-2` | **没有需要用户执行的动作，就不是待办** | 只是告知的事项进消息、不进待办带。判定问的是「用户现在能点什么把它做掉」，不是「用户想不想知道」 |
| `B-3` | **待办由业务状态派生、不留存，不需要已办归档** | 因此**不存在待办的已读、待办的删除、待办的历史**。要回看历史只能看消息 |
| `B-4` | **未读数与待办计数分开显示、分别计数，不合并成一个红点** | 合并后用户清掉红点却发现事情没办完 |
| `B-5` | **两个计数的归属维度不同：未读数按自然人账号计，待办按企业主体计** | 由 `D-NC-16` 直接推出。不点明会产生一类必然客诉（`D-NC-19`、`R-NC-01`） |

**两条互不侵入的边界**：本模块**不产生待办、不计算待办、不渲染待办带**；我的控制台**不自建消息列表、未读角标与已读逻辑**。

### 5.7 对消息来源方的业务要求（`IF-NC-01`～`IF-NC-10`，**契约外移后仍然成立**）

> **本节是本轮裁定 1 的落点。** 跨平台的报文与契约条款不在本册展开，**但对上游的业务要求必须活着**——以业务规则表达、以可验收条款收口。**任何一条都不得因为「契约层未定」而消失或降级为建议。** 逐条验收见分册 02 18.3。

| 编号 | 业务要求 | 不满足会怎样 |
| --- | --- | --- |
| `IF-NC-01` | **可见时效**：一个业务事件发生后，对应消息必须在 **`N-NC-01`（默认 60 秒）内**在本平台面客端可见——未读角标与列表**同时**体现，不存在「角标已加、列表里没有」或反之的中间态 | 用户收到通知却打不开对应内容，或点进列表发现没有那条，判为一次可见性缺陷 |
| `IF-NC-02` | **关键要素缺失即不入池**：一条消息缺少**收件人、业务类型标识、可渲染的文案**任一项时，**本平台不接收、不入池**，并让来源方可感知。**不得以空白标题、空白正文或占位符的形态进入用户列表** | 一条没有任何内容的消息进了用户列表，用户无法判断发生了什么 |
| `IF-NC-03` | **非关键要素缺失照常入池**：缺跳转目标、业务编号、进度步序、失效时点等非关键要素时，消息**照常入池、照常展示、照常计入未读**，缺项按分册 01 的既定降级表现（不渲染跳转按钮、不展示步序等），**不因此丢消息、不因此隐藏整条** | 丢消息比展示不全严重得多 |
| `IF-NC-04` | **重复事件不得产生重复消息**：同一业务事件被重复送达时**只产生一条消息**，用户列表里只出现一条。判重依据是来源方在登记表里声明的**去重标识**（`RG-NC-09`） | 用户被同一件事刷屏，未读数虚高 |
| `IF-NC-05` | **去重标识必须能区分同一对象的不同事件**：来源方声明的去重标识须包含足以区分「同一业务对象的不同事件 / 不同进度节点」的成分。**本模块只按声明的去重标识判重，不自行按「事件类型 + 时间窗」推导** | 复用同一去重标识时，后一条会就地覆盖前一条，**用户永久丢失中间进度**——该后果由来源方承担，本模块不兜底 |
| `IF-NC-06` | **幂等与乱序**：同一条消息重复送达不产生第二条、不改变已有展示；**后到的旧内容不覆盖已有的新内容** | 用户看到状态倒退 |
| `IF-NC-07` | **收件人以本平台账号标识指定**：不得用邮箱、钱包地址或其他平台的账号原值（`D-NC-15`）；一条消息只有一个收件人，多个接收方**各自一条** | 双身份用户串池；或一条消息被当成广播 |
| `IF-NC-08` | **跳转目标必须已登记且属于本平台**：跳静态页面时用带平台标识的本平台页面编号（`D-NC-03`）；跳业务对象时用已登记的业务类型标识。**跳转形态三选一互斥**（业务对象 / 静态页面 / 无跳转），同时声明两种或直接给一个完整外部地址的，**本平台不接收** | 消息实体里存了会过期的地址，或用户被带到不存在的落点 |
| `IF-NC-09` | **文案以模板 + 变量提供，中英齐备**：不得传已经拼好的整句；两种语言的变量集合必须一致。时间传原值不自行格式化，金额传数值与币种不拼成字符串 | 切换语言时静默丢信息；跨境场景下金额与时间格式必错一种 |
| `IF-NC-10` | **消息内容不得携带未脱敏的敏感信息**：完整邮箱、完整钱包地址、完整证件号、完整 IP 不得进入标题、正文或变量 | 站内信成为敏感信息的泄漏面 |

> **这十条不是接口规范，是业务底线。** 它们描述的是「一个业务事件发生后，用户应当在多久内、以什么完整度、以什么唯一性看到它」——报文长什么样、走什么通道，由契约册与研发决定，**本册不写、也不需要知道**。

### 5.8 跨平台深链：本平台的两种角色（**只写本平台行为**）

| 编号 | 角色 | 条款 |
| --- | --- | --- |
| `D-NC-34` | **被跳转方** | 其他平台把用户带到本平台某个页面时，本平台必须按「平台标识 + 页面编号」把用户带到**对应的那个页面**；落点是需要登录的页面而当前未登录时，走本平台既定登录回跳，**登录后回到该落点**，不落首页 |
| `D-NC-35` | **被跳转方** | 落地时**重新判权**：当前身份不具备该页面权限时，落**本平台既定的受限引导**，**不是错误页、不是报错提示** |
| `D-NC-36` | **被跳转方** | 平台标识不是本平台、或页面编号在本平台未登记时：**落本平台面客端首页**并记录一次未知落点，**不给「不存在」页、不白屏、不静默无反应** |
| `D-NC-37` | **发起方** | 本期，需要用户去**其他平台**办的事，本平台产出的消息一律是**「无跳转」**形态：内容照常完整展示，详情页**只留「返回列表」**，**不给任何说明文案**（`D-NC-45`） |
| `D-NC-38` | **发起方** | 将来实现跨平台跳转时，执行**一律复用本平台统一的对端白名单与离站告知机制，本模块不自建一套**（`DEP-NC-03`） |
| `D-NC-39` | **两边都不写** | **解析实现不在本册**：怎么把「平台标识 + 页面编号」路由到具体地址、谁维护映射，属实现与契约层。本册只定义**本平台侧可被观察的行为与结果** |

## 6. 用户角色与场景

### 6.1 角色

| 角色 | 在本模块里是谁 | 可见范围 |
| --- | --- | --- |
| **游客** | 未登录访问者 | **消息中心不可见**：入口不渲染、账号下拉无「消息中心」条目、深链走登录回跳 |
| **资产方** | 经资产可信平台授权登录的本平台面客账号 | 仅自己名下的本平台消息。**与其在资产可信平台的消息中心完全隔离** |
| **资金方** | 本平台面客账号（以境外机构为主） | 仅自己名下的本平台消息 |
| **受限会话用户** | 已登录但未完成本平台必办前置 | **消息中心不可达**（等同游客处置，`D-NC-33`） |

> **本模块不按用户资质档位区分可达性。** 只要是已登录且非受限会话，消息中心一律可达、可见范围一律按 `D-NC-14`。资质档位只影响**跳转落地页**的权限判定（`D-NC-35`）。

### 6.2 用户故事

| 编号 | 作为 | 我想要 | 以便 |
| --- | --- | --- | --- |
| `US-NC-01` | 已登录的面客用户 | 在任意页面的顶栏看到未读数 | 不用逐个打开业务页轮巡也知道有事发生 |
| `US-NC-02` | 已登录的面客用户 | 点开入口快速扫一眼最近几条 | 不打断当前正在做的事 |
| `US-NC-03` | 已登录的面客用户 | 打开完整的消息中心并按分类、已读状态筛选 | 在消息变多之后仍能找到想看的那一类 |
| `US-NC-04` | 已登录的面客用户 | 从一条消息一键到它讲的那件事 | 不用自己回忆该去哪个页面找 |
| `US-NC-05` | 已登录的面客用户 | 看到一笔业务当前办到哪一步、是什么状态 | 不用点进业务详情页才知道进度 |
| `US-NC-06` | 境外资金方用户 | 界面与消息内容都是本人所选语言，切换时历史消息也跟着变 | 不用在两种语言之间猜 |
| `US-NC-07` | 共用办公设备的用户 | 会话一失效，页面上的消息内容立刻消失 | 下一个使用这台设备的人看不到我的业务信息 |
| `US-NC-08` | **业务模块的负责人** | 只读一份登记规则加一张表就能把自己的消息接进来 | 不用等消息模块改代码、不用去改消息模块的 PRD |

### 6.3 典型场景

| # | 场景 | 走到哪 |
| --- | --- | --- |
| 1 | 用户在某个业务页工作时收到新消息 | 角标在下一个刷新周期内（`N-NC-01`）更新；**不打断当前操作、不弹层、不抢焦点** |
| 2 | 用户点入口扫一眼，发现一条需要处理 | 快捷面板 → 点该条 → 详情（该条转已读）→ 跳转 → 目标业务页 |
| 3 | 用户攒了一批消息集中处理 | 账号下拉「消息中心」→ 列表 → 按分类筛选 → 加载更多 → 逐条查看 → 「全部已读」 |
| 4 | 用户从外部渠道拿到一条消息详情链接，当时未登录 | 走登录回跳 → 登录成功 → **回到该条详情** |
| 5 | 用户收到一条指向其他平台事项的告知 | 内容完整展示，**详情页无跳转按钮、无任何说明文案**，只有「返回列表」 |
| 6 | 用户开着标签页离开工位，会话到期后回来 | 页面回落游客态、消息内容从页面清除、入口消失、刷新停止 |
| 7 | 某业务模块刚上线，其业务类型尚未登记到前端 | 消息**正常展示、可点进详情、计入未读**；详情页不渲染跳转按钮、不展示说明文案；记录一次未知业务类型 |

**三段必读的业务说明（图册不重复，正文不省略）：**

1. **「消息可见」有两处同时成立才算数**：未读角标与列表**同时**体现（`IF-NC-01`）。只更角标不更列表，用户点进去会以为消息丢了；只更列表不更角标，用户根本不知道有新消息。
2. **「未登记」与「无跳转」在界面上完全一致**，区别只在是否记录一次未知业务类型（`D-NC-46`）。本平台会长期处于「业务模块陆续接入」的状态，**灰度期出现未登记是预期的**，它应随各接入方登记完成而收敛到零。
3. **所有会话失效路径的终点都是「游客」，没有一条通向登录页**（`SM-NC-03`）。面客端顶栏在游客态仍然存在，所以消息入口必须被**显式清除**，不能指望页面卸载。
