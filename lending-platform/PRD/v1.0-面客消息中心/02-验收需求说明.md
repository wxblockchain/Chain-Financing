# 面客消息中心 · 验收需求说明 V1.1

测试主读。[主册](v1.0-面客消息中心-PRD.md)与[功能需求](01-功能需求说明.md)是完整规则来源；[图册](v1.0-面客消息中心-流程图与状态机.md)表达相同流程；[通知衔接册](03-面客消息中心-消息通知.md)用于核对当前来源。不以本册另立业务口径。

## 14. 共用验收前提

除明确相反场景外，资产方、资金方分别以正常登录账号验收；至少包括同企业另一员工、无关企业、同钱包不同身份、游客及受限会话。消息、业务对象、可办理状态分别准备正常与失效情形。虚构业务验证框架扩展，真实来源验证实际接入，两者不可替代。

列表与角标须一致，业务事件后60秒可见为既有硬要求。原V1.0的读取P95目标（计数300ms、首屏/详情800ms）仅作为原目标引用，不据文档或原型自测宣称已达。真实性能、投递及跨平台结果需实际证据。时效冲突沿第19章保留，不改起点或将来源5分钟与消息60秒相加放宽。

安全与可用性共用条件：本人消息隔离、失效不残留、纯文本安全显示、敏感资料受保护；键盘可开整行、预览可Esc关闭、状态与禁用原因可被读屏理解；375px及桌面宽度能完整阅读和操作，长正文/双语不丢关键内容。具体排版不作为本轮新增业务验收条件。

## 15. 沿用观察指标

M-NC-01消息打开率、M-NC-02业务目标进入率、M-NC-03未登记类型出现率、M-NC-04内容缺失率、M-NC-05全部已读使用率、M-NC-06列表与未读读取表现继续观察。指标用于发现接入缺口和干扰，不凭“打开率低”增加催促，不把正文降级的可读性当作业务完整性合格。

## 17. 依赖交接规则

CR-NC-01沿用lending页面编号作为跨平台输入；CR-NC-02保留IF-NC-01～10结果要求；CR-NC-03承接共享登记位置及适配；CR-NC-04以本批B-1～5与控制台V1.4衔接，无待办区恢复。跨平台契约未编制不能成为丢消息、越权或延迟达标的豁免。

框架功能可独立验收，但本平台全链路通知需要真实来源、收件账号、完整模板、原对象映射和时间结果。某分支依赖未明可记录待验，不把整个模块重新列为业务决策未定，也不把待验标成通过。
