## 3. 背景与目标

### 3.1 背景

资产方在资产可信平台完成应收账款确权并上链存证，经代币发行平台铸造为代币；代币经 `X-03` 同步进**借贷平台的只读代币域**（资产广场模块已落地），资产方本人持有代币，**平台不托管**。此时代币只是一张"已确权债权的凭证"，没有变现通道。

**借贷广场是融资需求的公开撮合场所，也是融资全生命周期的唯一执行场所。本模块是这条链路的第一段**：把代币变成可融资的额度，并把融资需求公开出去。

**心智模型（功能基线沿用）**：**资产方创建的每个融资项目就是一个资产池**——往池里质押代币，平台算出池内资产价值，资金方看到的是"池内资产 + 融资信息"。

**三平台拆分带来的真实变化**：质押这件事从"一个系统内的一次操作"变成了**跨两个平台的一次业务**——**业务决策（谁能质押、进哪个池、算不算数、额度够不够）在借贷平台，链上执行（把代币转进质押合约、转回原地址）在代币发行平台**。两边分家之后，"提交了但还没有结果"这段中间态、"一次提交多张而结果不齐"这件事，都必须在产品上有明确说法——这是本版改写的主线。

### 3.2 产品定位

| 项 | 口径 |
| --- | --- |
| 一句话 | 资产方把只读代币域里属于自己的代币质押成资产池、公开发布融资需求的**面客端执行场所** |
| 主对象 | **融资项目（＝资产池＝广场一行项目记录）**，不是单枚代币；项目内审核与确认清单按代币，不按提交批次组织 |
| 与资产广场的分工 | **资产广场看「张」，借贷广场看「池」。** 资产广场回答"平台上有哪些真实资产、每一张是什么"；借贷广场回答"谁在融资、融多少、池子够不够" |
| **本平台在质押上的角色** | **业务决策方**。判定可不可以质押、进哪个池、算不算进覆盖、额度够不够、结果怎么呈现；**不执行链上动作、不持有代币事实、不托管代币** |
| **代币发行平台的角色** | **链上执行方**。审核通过后由它承担代币转入 / 转出质押合约的链上执行，并把执行结果回写本平台（`X-04`/`X-05`） |
| 运营端质押审核 | **外部输入**。审核动作与界面在 WS-359（本平台运营端），本模块只消费其结论（5.4） |
| 产品形态 | Web 面客端，游客可看、动作需登录；桌面 + 移动自适应，沿用本平台面客端母版与组件规范 |
| 页面数 | **3**：`P-LS-01`、`P-LS-02`、`P-LS-03` |

### 5.1 `D-LS-22` `PS-*` 统一定义（与资产广场同值同义，不重开）

**需求方 2026-09-18 裁定**：`PS-*` 在全平台链路上只有一套定义，权威方＝**借贷平台**。本模块是该状态的**权威方与唯一写入方**，资产广场是只读消费方。

### 5.3 `D-LS-29` 质押的跨系统事务：业务决策在本平台，链上执行在代币发行平台

> `X-04`（质押转入执行与回写）与 `X-05`（解除质押执行与回写）**契约尚未定义**（`GAP-LS-01`）。本节按**业务规则**写死必须成立的结果；协议报文、回调字段、重试与去重机制**不属本 PRD 范围**，由实现方按这份口径自行决定（`IF-LS-*` 见分册 01 第 10 章）。

| 编号 | 条款 | 错了会怎样 |
| --- | --- | --- |
| `D-LS-29`【职责分工】 | **审核通过后的链上执行由代币发行平台承担；本平台只做业务决策与结果消费。** 本平台判定：谁能质押、哪几张、进哪个池、算不算进覆盖、额度够不够、结果怎么呈现。本平台**不执行链上动作、不代持代币、不代资产方签名或付费** | 两边都执行会出现重复转移；两边都不执行则申请通过后无人推进 |
| `D-LS-30`【按张独立结算】 | 资产方可批量提交、运营逐笔审核；每张通过后可独立执行，也可同项目跨提交一同确认。实际执行结果按张：成功且符合资格才计覆盖，明确失败且无占用的张回 `PS-1`、按资格重新申请；无明确结果仍处理中，不当失败。不同张不回滚彼此，批次不设统管结论 | 不能用一张失败覆盖其他张成功，亦不能以未知结果放开重押 |
| `D-LS-31`【费用归属 · 含失败张】 | **gas 由资产方承担，平台不代付、不垫付、不返还，也不额外收取任何服务费。** **执行失败的那一张，已经产生的链上费用同样不退回**——这一点必须在发起前的费用确认里和失败反馈里**都讲清楚**；**审核期内零费用、驳回零费用** | 不提前讲清楚，失败之后资产方第一个问题就是"钱扣了没有、能不能退"，客服答不了 |
| `D-LS-32`【中间态】 | 实际发起后、结果未确认前，该张显示“质押处理中”，不计覆盖、不可再次选入其他池、撤回、提取或重复发起；其余代币及项目动作按各自判据可用。显示等待时长及已知费用，未知费用标待核实。执行等待不套审核 48 小时，不自动判失败或释放；长期无结果提示“执行结果待核实，请联系平台客服人员”；本期不提供异常处置流程（D-LS-63） | 不锁整项目，不把没有结果说成资产已返回 |
| `D-LS-33`【审核 48 小时】 | **从每笔提交成功时点起连续 48 小时，仍无有效通过 / 驳回且未撤回，则自动质押失败（审核超时）并释放该笔申请占用。** 同批各笔继承提交时点；查看、上传或未提交编辑不是有效审核、不重置计时。代币未转入，保持 / 恢复 `PS-1`，本次零费用；记录保留，可按最新资格再次提交至同一或其他项目。只影响未审笔，不等运营补审。48 小时按经过时长，不按自然日或工作日；**不适用于链上执行超时** | 界面明确“48 小时未完成审核”；释放申请占用不等于 X-05 转回，不生成 PS-4 待提取 |
| `D-LS-47`【未知与冲突结果】 | 普通晚到且无跨期/冲突结果按对应单笔实际执行呈现。与原事实冲突的结果保留原记录、关联对应单笔，不自动覆盖新申请或重复计覆盖；沿 E-11 差异标记限制新动作。异常引导联系平台客服，**本期不设计核实工单、人工改判、异常释放或恢复资格流程**（D-LS-63），旧“执行两天自动失败重押”不再作为前提 | 真实未知不能伪装终态，不把审核时限套作执行安全决策 |

`AC-LS-105`【红线】：构造三张均已逐笔通过、一次确认执行结果为"2 成 1 败"的场景——2 张进「已质押」且计入统计区，1 张回到可质押清单且可立即选入另一个池；页面**逐张**给出结果与费用说明；**不出现整单回滚；明确失败且无占用的张可重新选择；未知或差异张按 D-LS-32 / 47 处理**。

### 5.4 `D-LS-34` 质押审核是外部输入，本册不展开

**审核动作与界面在 WS-359（本平台运营端）。** 本模块是审核的**提交方与结论消费方**：

| 本模块做什么 | 本模块不做什么 |
| --- | --- |
| 批量提交（建池首笔 / 追加），每张形成独立审核对象，待审笔可撤回 | 审核队列、审核动作、审核人权限、工作量分配、独立于用户已确认 48 小时规则的时限设定 |

### 5.5 唯一的一套额度口径（沿用功能基线，**不存在第二套公式**）

| 编号 | 条款 |
| --- | --- |
| **`INV-FIN-01`【唯一口径】** | **融资上限 − 项目融资余额 − 项目在途金额 ≥ 0**，即 **有效质押价值 × 80% ≥ 项目融资余额 + 项目在途金额**。任何时刻必须成立；不成立即禁止一切增加占用的动作 |
| `AC-FIN-11`（视角 A · 展示） | `可融金额 = max(0, 融资上限 − 项目融资余额 − 项目在途金额)` |
| `AC-FIN-12`（视角 B · 准入） | 新增占用（发布需求、报价、放款）校验 `可融金额 ≥ 本次金额`；**每次校验都用平台当场重算的数值，不吃缓存** |
| `AC-FIN-13`（视角 C · 撤回） | 按撤回后的池重算：`(有效质押价值 − 拟撤回价值) × 80% ≥ 项目融资余额 + 项目在途金额`；**已失效代币不参与本判定**（`D-FIN-59`） |
| `AC-FIN-22` | **可撤回上限 = 可融金额 ÷ 质押率**。它是 `AC-FIN-13` 的代数变形，不是第二条公式，用途是把"能不能撤"翻译成用户看得懂的一个数 |
| `AC-FIN-23` | **`项目在途金额` 只有"发布占用"一个来源**；报价环节不新增占用 |
| `AC-FIN-25` | 放款确认完成的同一时刻，金额从 `项目在途金额` 移出、计入 `项目融资余额`，**原子、无空档** |
| `AC-FIN-26`（视角 D · 失效） | 逐笔需求的失效判据：按发布时间正序累计已保留的需求金额，对每一笔检验 `融资上限 − 项目融资余额 − 更早已保留需求金额合计 < 本笔需求金额` ⇒ 该笔失效 |
| `D-FIN-54`【估值保守原则】 | **不确定的一律不计入**：① 链上执行处理中（`CT-1`）不预先计入；② 撤回处理中立即预扣、失败回滚才恢复；③ 对账差异项不计入；④ **审核期内与"通过待入池"不计入**（`D-FIN-82`） |
| `AC-FIN-20` | **占用不参与质押价值的计算**：占用只出现在不等式右边，绝不从有效质押价值里扣减 |
| `AC-FIN-14`／`AC-FIN-18` | 单位统一 `USD`、展示保留 2 位小数、计算过程不提前四舍五入；可融金额为负按 0 展示并禁止新增占用 |

**术语口径**（`D-FIN-06` 红线：同一个量只有一个名字，文档中不得出现无限定词的"融资余额"）：

| 术语 | 口径 |
| --- | --- |
| **池内资产总额** | 池内全部代币的代币价值合计，**含已失效代币**；仅展示，不参与任何校验 |
| **有效质押价值** | 池内代币价值合计，需同时满足：① 审核通过；② 链上转入执行成功回写；③ 底层应收账款未失效（取只读代币域的代币状态）；④ 无对账差异、未处于撤回预扣。**一切校验只认这个数** |
| **融资上限** | 有效质押价值 × 质押率（**本期硬编码常量 80%**） |
| **项目融资余额** | 该项目下未偿本金合计（**不得简写为"融资余额"**） |
| **项目在途金额** | 本项目下已发布且未终结的融资需求金额合计 |
| **可融金额** | `max(0, 融资上限 − 项目融资余额 − 项目在途金额)` |
| **可撤回上限** | `可融金额 ÷ 质押率`；仅对未失效代币适用 |

### 5.6 三档质押覆盖状态（沿用 `D-LS-17` 定稿）

| 档 | 判据 | 含义 | 系统行为 |
| --- | --- | --- | --- |
| **① 覆盖有余** | `INV-FIN-01` 成立且可融金额 > 0 | 还有额度可用 | 正常展示与操作 |
| **② 覆盖持平** | `INV-FIN-01` 成立但可融金额 = 0 | 已借的被完全覆盖，但不能再借 | 新增发布不可用；已发布需求的报价不新增项目占用，按既有覆盖条件与L6授信校验办理，不因可融金额为0一概禁报价；可撤回上限为0，不触发债务覆盖不足提醒 |
| **③ 覆盖不足** | `融资上限 < 项目融资余额` | 已发生的债务本身没有被池内价值覆盖住 | 覆盖不足提醒 + 禁止一切新增占用 + 运营待办 |

`D-FIN-55`：**提醒线与准入闸门不是同一条线。** 闸门比较 `项目融资余额 + 项目在途金额`（管"还能不能借"）；提醒只比较 `项目融资余额`（管"已借的还被覆盖得住吗"）。可融金额为0不等于已发生债务覆盖不足，三档仍按各自判据区分；受众与处置动作分别定义、分别呈现。

### 5.7 四条不可削弱的红线

| 编号 | 红线 |
| --- | --- |
| `D-MC-110`/`D-MC-111` | 质押率本期为**固定常量 80%**。页面可以展示这个数，但**不得以任何形式暗示可调**：无输入框、无下拉、无滑块、无"调整质押率"入口与文案 |

### 6.3 典型场景

- **S1 建池与发布**：新建项目 → 填项目名、选代币类型 → 从可质押清单勾 3 张同类型代币（共 100 万 USD）→ **提交质押申请（零 gas，不发生链上操作）** → 项目落 `S-FP-1 草稿`（广场不可见）并直达详情页，统计区五个数与提交前完全一致 → 运营逐张审核通过 → 资产方回来，平台逐张复核资格，在同一容器核对代币与费用并确认后**发起链上执行（由代币发行平台承担，资产方承担 gas）** → 3 张全部成功回写 → 计入有效质押价值 → 在操作区点「发布融资需求」填 50 万并选择参考结算币种 → 项目在途金额 = 50 万，可融金额 = 80 − 0 − 50 = 30 万，项目转 `S-FP-2 募集中`。
- **S2 按张独立结算**（本版新增主场景）：同项目不同提交的 3 张均已逐笔通过，资产方从代币清单一次确认，回写结果 2 成 1 败 → 成功的 2 张进 `PS-2` 并计入覆盖；失败的 1 张回 `PS-1 可质押`，**无占用且最新资格允许时可立即选入本池或另一个池**；页面逐张列出结果与费用说明（失败张的 gas 同样不退）；**项目照常可发布**，校验按实际成功入池后的重算结果。
- **S3 局部审核超时**：批次 A 已通过并执行、B 已驳回、C 待审；提交成功满 48 小时只使 C 质押失败（审核超时），释放 C 的申请占用、零费用、保留记录。A/B 不回退、不改费用；C 按资格可再次质押。执行处理中即使经过 48 小时，也不据此判失败或释放。
- **S4 代币清单与重新提交**：资产方的清单逐张呈现；B 被驳回时仅 B 展示原样原因、解除占用及零费用。重新提交 B 生成新单笔，清单显示 B 当前申请，旧笔进入 B 的历史；不同提交中已通过的 A/D 可一起确认，无需按提交分组逐批操作。
- **S5 撤回还有空间**：池值 100 万、已发布 50 万 ⇒ 可撤回上限 = 30 ÷ 80% = 37.5 万。撤回 30 万放行；再撤 10 万被拒，提示"最多还可撤回 7.5 万 USD"。
- **S6 失效代币**：池内一张 10 万的代币因底层应收账款到期，只读代币域把代币状态推成失效 → 本平台读到结果后把它移出有效质押价值 → 它的撤回**不做任何额度判定，直接放行**。
- **S7 覆盖不足提醒**：项目已放款 50 万，两张代币失效使有效质押价值跌到 60 万 → 融资上限 48 万 < 50 万 → 触发覆盖不足提醒，缺口 2 万、需追加 2.5 万；广场与双方页面同时可见。**提醒文案须说明"追加质押要先过审核、提交不即时生效"**（`R-LS-13`）。
- **S8 释放与提取**：项目结清 → 平台即时解除全部质押占用关系、代币置 `PS-4 已释放 · 待提取` → 资产方自行发起提取（链上执行仍由代币发行平台承担、gas 自付），可批量一次提完。

**三段必要的业务说明**（正文口径，图只表达它）：

1. **撤回判定的顺序不可换**（`AC-FIN-13` 视角 C）：① 已失效的**不做任何额度判定，直接放行**；② 未失效的按 `可撤回上限` 判定，超出即拒绝并给出三个数（拟撤回价值、可撤回上限、差额）与两条出路；③ 通过后发起链上执行，**处理中即按保守口径预扣**，成功移出池、失败预扣撤销并保持在池。
2. **自动失效的粒度与顺序**（`D-FIN-73`）：**最小必要失效 + 按发布时间倒序**，每作废一笔即重算，直到剩余需求全部满足判据；若已无需求可作废而判据仍不成立，**停止动作**、项目留在覆盖不足档走催追加，不空转。
3. **失效与覆盖不足提醒是两条线**：失效走逐笔判据、判定即失效；提醒走档③、管的是已放款债务本身。失效判据**更早触发**——一笔需求可能已失效而项目仍在"正常"档。
