### 13.2 风险

| 编号 | 风险 | 影响 | 应对 |
| --- | --- | --- | --- |
| R-DS-01 | 幂等键选错（来源资产 ID 实际不唯一或会变更） | 清单重复入库或两端追溯主键失效，属本期红线事故 | Q-DS-01 优先确认；唯一约束建在数据层，一旦冲突即按幂等命中处理而非失败 |
| R-DS-02 | 「回执未知」被误判为失败，重推造成重复入库 | 清单统计被污染 | 幂等在接口层强制（11.2），重推天然安全；结果面板明确提示「重推受幂等保护」 |
| R-DS-03 | 无自动重试，运营端短时不可用时大批量条目落 S-DS-2 | 人工重推工作量集中爆发 | P-M-DS-03 支持**按批次一键全量重推**失败条目（7.6） |
| R-DS-04 | **钱包地址取错主体** | 该地址已是必填字段并直接用于**不可逆**的代币铸造（WS-318），取错即铸给错误的收币方且无法回收 | 取值规则已由需求方 2026-09-10 定死：**取该企业下最初完成企业认证的那位成员的地址**，写在 D-DS-05 字段定义里（Q-DS-02 据此关闭）。实现必须严格按该规则取数，**不得退化为「取任一已认证成员」或「取最近登录成员」**；该规则须有单测覆盖 |
| R-DS-05 | **写动作直接落在 WS-305 已定稿的只读页面上**：合页裁定后，上链按钮就在 P-M40 / P-M41 上，与 F-18「服务端对资产管理端账号的一切写请求直接拒绝」正面冲突 | 安全评审口径不一致；更实际的风险是后来者以「这页本来就能写」为由继续往上加写能力，例外被越用越宽 | 主文档 3.1 把例外的边界写死为三条（只开两个权限点、可审计、可单独回收），并明确两个权限点不得合并；DEP-DS-03 要求 WS-305 文档侧补对应说明。**新增写能力必须重新走裁定，不得援引本例外** |
| R-DS-06 | 确权信息快照与源数据后续不一致（源数据被修正） | 运营端看到的是旧值 | 本期明确「快照取推送时刻的值、只存不改」；增量同步在后续迭代（Q-DS-08） |
| R-DS-07 | **漏推在运营侧不可发现**：运营端既不展示失败资产，本期也没有对账视图，运营人员无法判断「我看到的是不是全部」 | 某批资产因失败或漏推没进清单时，只能靠资产管理端主动发现，运营侧的业务判断可能基于不完整的数据 | 这是需求方为控制本期范围主动接受的取舍。**本期缓解**：P-M-DS-01 的「未推送 / 推送失败」筛选是唯一的发现入口，建议在上线运营规范中约定由资产管理人员例行检查。**后续定案（需求方 2026-09-09）**：不做完整的两端对账视图，改为在 P-M-DS-01 增加默认视图「已确权且未推送 / 推送失败」+ 条数角标，**排在代币铸造 issue 之后**作为同步链路的收口迭代（见主文档 2.4）。该方案不需要跨平台拉数与新接口，成本远低于对账视图 |
| R-DS-08 | **上链回执未知导致同一资产重复存证**：超时后人工重新上链，链上可能留下两条存证 | 同一资产存在多份凭证，核查时无法确定以哪条为准 | 7.8.3 的存证幂等：重新上链前先查该资产是否已有有效回执，有则直接落「已上链」而不重复发交易。这条与推送幂等同等重要，**不能只做推送侧** |
| R-DS-09 | **链侧不可用会阻断整条链路**：上链是推送的硬前置，链服务故障期间所有资产都推不出去 | 同步链路整体停摆，且本期没有自动重试兜底 | 这是「推送前必须先上链」这条业务规则的固有代价，本期接受。缓解：失败原因文案明确区分「链服务不可用」（E-DS-07，等一等再试）与「数据问题」（E-DS-09，改了再试）；P-M-DS-03 支持按批次一键重新上链，故障恢复后可批量补 |
| R-DS-10 | **运营端不校验链上真伪，凭证只是「看起来可信」** | 若资产平台伪造一组格式合法的凭证，运营端在系统内看不出来——只有人工去区块浏览器核对才会发现 | 本期取舍（8.1）。凭证的价值在于**可被独立核查**，不在于系统自动挡住伪造；详情页的跳转入口就是为了让这件事有人做得到。若后续要系统级校验，需运营端接链节点或第三方验证服务，属另一量级工作，届时单独立项 |
| R-DS-11 | **存量无地址记录靠重推补不上** | 修订生效前已入库的、钱包地址为空或格式非法的记录，重推会命中幂等，而幂等不更新已有记录的任何字段（AC-DS-29），因此这批脏数据不会自愈 | 只能在上线前做**一次性数据体检清零**（DEP-DS-07）。**不得**为此放宽幂等去更新字段——那会在红线上开口子；也**不得**在运营端加补录入口——运营端只读（AC-DS-43） |
