## 9. 通知消息通用数据契约（交接物，强制条款）

> **本章是平台级契约，适用于任何要发消息的模块**——首批是 WS-301 / WS-302 / WS-303，后续包括尚未立项的融资、放款、还款、额度、票据、结算、运营公告、系统维护等。接入方按本章约定产出消息，本模块保证其能被正确投递、展示、筛选、跳转与切换语言。接入方不需要了解本模块的页面实现，本模块也不需要了解接入方的业务逻辑。
>
> **需要动手接入的人，读 [`04-接入指南.md`](./04-接入指南.md) 即可**（含 Checklist、命名申请、反例与最小完整示例）。本章是规范正文，接入指南是它的操作化版本，两者结论一致，冲突时以本章为准。

### 9.1 消息实体 `Message`

> 只定义业务字段与口径，不指定存储实现。

| 字段 | 类型 | 必填 | 口径 | 说明 |
| --- | --- | --- | --- | --- |
| `message_id` | string | ✅ | 消息唯一标识，不可枚举（如 UUID） | 由本模块生成 |
| `event_id` | string | ✅ | 触发事件的唯一标识，**幂等键** | 由触发方生成；本模块重复收到同一 `event_id` 时丢弃，不产生第二条消息 |
| `end` | enum | ✅ | 四值：`asset` / `admin` / `fs` / `fs_ops`，见下方「四个端」 | 决定消息进哪个消息池；**不存在同时投递多个端的消息** |
| `recipient_scope` | enum | ✅ | 五种接收方范围：`account` / `admin_account` / `admin_all` / `enterprise` / `broadcast` | **完整语义、本期是否实现、新增一种要改什么，见 9.1.1** |
| `recipient_account_id` | string | 条件必填 | `recipient_scope = account` 时必填 | 资产端隔离的唯一依据（`v1.0-消息通知-PRD.md` 8.1.1） |
| **`recipient_admin_id`** | string | 条件必填 | `recipient_scope = admin_account` 时必填 | 管理端个人消息的归属依据 |
| **`recipient_enterprise_id`** | string | 条件必填 | `recipient_scope = enterprise` 时必填 | **本期不实现**，见 9.1.1 |
| **`visible_from`** | datetime (UTC) | ❌ | 受众起算点：只有在该时间点之后**已存在**的接收者才看得到这条消息 | 缺省取 `created_at`。用于 `broadcast` 与 `admin_all`——避免新注册用户 / 新入职管理员一登录就面对全部历史消息（同一机制见 `v1.0-消息通知-PRD.md` 8.2.4） |
| **`subscribable`** | bool | ❌ | 该**站内消息**是否允许用户按 `category` 退订，缺省 `false`（不可退订） | **本期不实现偏好中心**，字段先留位，见 `v1.0-消息通知-PRD.md` 2.5.1。退订只作用于站内消息，与其他渠道无关。安全、账户、认证与合规类**不得**声明为 `true` |
| `category` | string | ✅ | 消息分类，展示层的筛选维度 | 取值见 9.3.1；**代码层定义，新增需研发适配** |
| `biz_type` | string | ✅ | 业务类型标识，跳转映射与业务语义的依据 | 命名规范见 9.3.2 |
| `biz_ref` | object | 条件必填 | `{ resource_type, resource_id }`；跳转目标为**业务资源**时必填 | 跳转形态 1，见 9.4.1。**不得存放 URL** |
| **`page_target`** | string | 条件必填 | 页面编号（如 `P-A11` / `P-A17` / `P-M05`）；跳转目标为**静态页面**时必填 | 跳转形态 2，见 `01-页面与展示.md` 7.6.1 与 9.4.4。与 `biz_ref` **互斥**，两者都不填即「无跳转」 |
| `title_key` | string | 条件必填 | 标题文案模板 key | 与 `title_snapshot_i18n` 二选一必填，见 9.5 |
| `body_key` | string | 条件必填 | 正文文案模板 key | 与 `body_snapshot_i18n` 二选一必填 |
| `summary_key` | string | ❌ | 列表摘要文案模板 key | 缺省时由正文渲染后截断生成摘要 |
| `params` | map<string, string\|number> | 条件必填 | 文案模板的变量取值 | 使用模板 key 时必填模板所需的全部变量；变量命名见 9.5.2 |
| `title_snapshot_i18n` | object | 条件必填 | `{ "en": "...", "zh-CN": "..." }` 成品标题 | 无法模板化时使用，见 9.5.3 |
| `body_snapshot_i18n` | object | 条件必填 | `{ "en": "...", "zh-CN": "..." }` 成品正文 | 同上 |
| `progress` | object | 条件必填 | `category = business_progress` 时必填 | 结构见 9.6 |
| `created_at` | datetime (UTC) | ✅ | 消息创建时间，**列表排序与展示时间的唯一依据** | 展示时按接收者时区渲染（WS-302 `02-页面字段与双语文案.md` 13.4） |
| `expire_at` | datetime (UTC) | ❌ | 有效期截止时间；为空表示永不过期 | 到期后不计入未读角标、列表带「已过期」标签（`01-页面与展示.md` 7.7 第 1 类） |
| `invalidated_at` | datetime (UTC) | ❌ | 触发方主动置为失效的时间 | 用于「业务已被撤销、这条消息不再有意义」的场景；效果同 `expire_at` 已到 |
| `dedupe_key` | string | ❌ | 去重键，构造规范见 9.1.3 | 命中时合并为一条、更新时间、若此前已读则恢复未读（`01-页面与展示.md` 7.5.4） |
| `require_precheck` | bool | ❌ | 跳转前是否需要预检，缺省 `true` | 见 `01-页面与展示.md` 7.6.2 |
| `source_module` | string | ✅ | 接入方模块标识（如 `WS-301`、`financing`） | 仅用于排障与埋点，不在界面展示 |

**本模块自行维护、接入方不得写入的字段**：`message_id`、已读状态（独立实体，见 9.2）、列表排序位置、未读数。

##### `end`：四个端与消息池隔离

平台按仓库 `README.md` 的划分共有**两个平台、四个端**，`end` 必须能唯一标识其中之一：

| 取值 | 端 | 所属平台 | 现状 |
| --- | --- | --- | --- |
| `asset` | 资产端（面客） | 资产平台 | 已用（WS-302 / WS-303 等 13 行登记见 `docs/notification-contract/接入指南.md` 3.4） |
| `admin` | 资产管理端（控制台） | 资产平台 | 已用 |
| **`fs`** | **金融服务端（面客）** | 金融服务平台 | **本轮新增，暂无接入方** |
| **`fs_ops`** | **运营端（控制台）** | 金融服务平台 | **本轮新增**，首个接入方为 WS-309 |

**四个端 = 四个互不混池的消息池**（D-N29）。`end` 的隔离与账号体系是否互通无关——即使某人同时持有两个端的账号，两个端的消息、未读数、已读状态也完全分开；运营端账号与资产管理端账号已由 WS-308 定为完全独立。

**这是一次纯新增的枚举扩展**：`asset` / `admin` 两个原值的语义与拼写**一个字不动**，已入库的 13 行 `biz_type` 登记、WS-302 / WS-303 的事件负载、原型 `registry.js` 全部不受影响。这正是 9.1.1 把 `recipient_scope` 设计成枚举而非布尔的同一条理由——**扩值是这套契约自带的扩展路径**。

> **两处同名字段的区分，务必读清楚**：
>
> | 字段 | 维度 | 取值 |
> | --- | --- | --- |
> | **契约层 `Message.end`**（本节） | **消息池归属**——这条消息进哪个端的池子 | `asset` / `admin` / `fs` / `fs_ops` |
> | **原型层 `registry.end`**（`asset-platform/prototypes/_shared/registry.js`） | **画布形态**——原型用控制台壳还是面客壳 | 只有 `admin` / `asset` 两值，按 `docs/design-system/README.md` 的要求，**新端接入时归入两种形态之一复用现值，不为平台或端本身新增取值** |
>
> 运营端在原型层取 `admin`（控制台形态），在契约层取 `fs_ops`（新增值）。**两者都对、不冲突**，但混为一谈会让人去改错地方。

#### 9.1.1 `recipient_scope`：五种接收方范围

| 取值 | 语义 | 归属字段 | 可见范围 | 已读归属 | 本期 |
| --- | --- | --- | --- | --- | --- |
| `account` | 投递给**指定资产端账户** | `recipient_account_id` | 仅该账户 | 该账户 | ✅ 实现 |
| `admin_account` | 投递给**指定管理员本人** | `recipient_admin_id` | 仅该管理员 | 该管理员 | ✅ 实现 |
| `admin_all` | 投递给**全体管理员**（共享池） | — | 全部管理员 | **每个管理员各自独立** | ✅ 实现 |
| `enterprise` | 投递给**某企业下的全部账户** | `recipient_enterprise_id` | 该企业下的全部关联账户 | 每个账户各自独立 | ❌ 不实现 |
| `broadcast` | **全平台广播**，面向全体账户或某人群 | —（人群条件由服务端的可见集计算解析，本契约不定义人群模型） | `visible_from` 之后存在的全部目标账户 | 每个账户各自独立 | ❌ 不实现 |

> **`admin_*` 里的 "admin" 读作「该端的控制台账号」，不是「资产管理端」专属。** 在四端语境下，`admin_all` / `admin_account` / `recipient_admin_id` 对 `end = admin` 指资产管理端账号，对 `end = fs_ops` 指运营端账号——**语义是「控制台侧的账号」，由 `end` 决定具体是哪个端的**。
>
> **字段名不改**（不改成 `console_all` 之类）：这三个名字已被 WS-303 的定稿 PRD 引用、已落在 WS-302 的事件负载上，重命名收益为零、破坏面很大。这里只做措辞澄清。

**两条贯穿全部取值的规则**：

1. **消息实体只有一条，不为每个接收者物化副本。** 「谁能看到」由服务端的**可见集计算**决定（按 scope + 归属字段 + `visible_from`），不靠给 N 个账户各插一条消息。否则一次广播会在消息表里产生几十万行，且同一条公告的文案修订无法统一生效。
2. **已读记录只记录「读过的人」**（见 9.2），未读数 = 可见集条数 − 该接收者的已读条数。这条对五种 scope 完全一致，因此新增 scope 不改变未读计数的算法。

**`enterprise` 为什么本期不实现**：本期一个账户只对应一家企业（WS-302 的多企业模型为后续迭代），「企业下的多个账户」这个集合在数据上还不存在。契约先留位，避免届时改字段。

**新增一种接收方范围要改什么**（三处，且**只有这三处**）：

| # | 要改的地方 | 说明 |
| --- | --- | --- |
| 1 | 服务端的**可见集计算** | 新增一个分支：给定接收者，判断这条消息是否可见 |
| 2 | 列表与未读数接口的**查询条件** | 沿用同一份可见集逻辑，不另写 |
| 3 | **越权校验点**（`v1.0-消息通知-PRD.md` 8.1.2 的六个接口） | 详情、标记已读、跳转预检需能对新 scope 判定归属 |

**展示层、消息实体结构、已读表结构、跳转逻辑、去重逻辑全部不需要改动**——这是把 scope 设计成枚举而不是布尔标志的收益。

#### 9.1.2 广播消息的连带影响确认表

本期不实现广播，但必须确认现有契约**不会挡住它**。逐项确认如下：

| 影响面 | 现有契约是否已能承载 | 依据 |
| --- | --- | --- |
| 一条消息对应 N 个接收者 | ✅ | 9.1.1 规则 1：消息不物化副本，可见集计算 |
| 已读状态存储量 | ✅ | 9.2：只记录读过的人。一条广播若 1% 的人读过，就只有 1% 的行 |
| 未读角标计数 | ✅ | 未读数 = 可见集 − 已读集，算法与单账户消息一致 |
| **发布后新注册的用户是否看到** | ✅ | `visible_from` 界定受众起算点，与 8.2.4「新管理员的未读起算点」同一机制 |
| 去重键 | ✅ | 9.1.3：广播消息的 `dedupe_key` **不得包含账户标识**，在广播范围内唯一即可 |
| 无跳转目标 | ✅ | 「无跳转」已是合法形态（`01-页面与展示.md` 7.6.4），不会被当成映射缺失 |
| 分类归属 | ✅ | `announcement` 已在 9.3.1 登记 |
| 有效期 | ✅ | `expire_at` 已有；公告过期后不计角标、列表带「已过期」标签 |
| 退订 | ✅ | `subscribable` 字段已留位（2.5.1） |
| 展示层是否要写特殊逻辑 | ✅ **不需要** | 广播消息进入列表后与普通消息完全一致：同样的排序、筛选、已读、角标、跳转 |

**唯一需要新增的能力**是人群圈选（「发给哪些人」），它属于运营后台，不属于本契约——本契约只需要知道「这条消息的可见集怎么算」，人群条件由服务端在可见集计算中解析。

#### 9.1.3 `dedupe_key` 构造规范

`dedupe_key` 相同的消息会被**合并成一条**：时间更新为最新一次，若此前已读则**恢复为未读**（`01-页面与展示.md` 7.5.4）。它防的是**同一个事件被重复触发**（服务重试、消息队列重投），不是「同一业务的不同节点」。

**本模块只以 `dedupe_key` 为去重依据，不做任何兜底推导**——不会按「事件类型 + 时间窗」自行合并。构造错了没有系统侧的安全网。

| 场景 | 构造 |
| --- | --- |
| 一个对象只会发一次 | `{biz_type}:{resource_id}` |
| 同一对象多个节点各发一次 | `{biz_type}:{resource_id}:{node_key}` |
| 同一对象同一节点可能重复发生（重提、重试、多轮） | `{biz_type}:{resource_id}:{node_key}:v{version}` |
| 每个接收者终身只发一次 | `{biz_type}:{recipient_id}` |
| **广播消息** | **不得包含账户标识**，在广播范围内唯一即可 |

**自查方法**：这个对象在它的生命周期里，同一个 `biz_type` 会发生几次？大于 1，键里就必须有区分那几次的东西。漏掉会导致后一次**就地覆盖**前一次且**不报错**——完整反例见 `04-接入指南.md` 5.3。

`dedupe_key` 是选填。事件天然不会重复触发、且 `event_id` 幂等已足够时可以不填，不填等于「每次都是新消息」。**拿不准时不填**：多一条重复消息比少一条真实消息安全。

### 9.2 已读状态 `MessageReadState`

| 字段 | 类型 | 必填 | 口径 |
| --- | --- | --- | --- |
| `message_id` | string | ✅ | 关联的消息 |
| `reader_type` | enum | ✅ | `account` / `admin` |
| `reader_id` | string | ✅ | `account_id` 或管理员账号 ID |
| `read_at` | datetime (UTC) | ✅ | 首次标记已读的时间；重复标记不更新 |

- **已读必须是独立实体，不能是消息实体上的布尔字段。** 管理端共享池要求「一条消息 × N 个管理员」各自独立的已读状态（`v1.0-消息通知-PRD.md` 8.2.2），布尔字段无法承载。资产端虽然是一对一，但为了结构统一，同样走该结构——**这也是广播与企业维度消息将来能直接接入的前提**（9.1.1）。
- **只记录读过的人，不预生成未读记录。** 一条 `broadcast` 或 `admin_all` 消息不会为每个可见者插一行「未读」；未读数由「可见集 − 已读集」算得。这条对五种 `recipient_scope` 一致。
- 已读记录**不可删除**；「标为未读」本期不提供（D-N08）。系统侧的恢复未读（去重合并场景）通过删除该条已读记录实现，属系统行为。

### 9.3 分类与业务类型标识

#### 9.3.1 `category`：消息分类（展示层筛选维度）

`category` 是**面向用户的分类**，用于列表筛选与分类标签展示，也是将来通知偏好退订的最小粒度（`v1.0-消息通知-PRD.md` 2.5.1）。它是一个**在代码层定义的有限枚举**；管理端不提供分类配置界面。

**本轮已按平台通用重新审视。** 首版的取值是从首批三个模块反推出来的，资金财务、运营公告、系统维护这三类平台迟早要有的消息一条都落不进去。**结论：现在就补齐平台通用分类，即使本期没有接入方。**

理由：① 分类是代码层枚举，新增需要研发适配（9.3.3）——等融资模块来了再加，那时要改的是**本模块**，恰好违反「新模块接入不用改本模块」这条底线；② 补一个分类的成本只是一个枚举值 + 一对中英文案 key，几乎为零；③ **定义了但没有消息的分类不会在界面上产生空筛选项**——`01-页面与展示.md` 7.3.2 已定「分类筛选器只渲染当前接收者实际拥有消息的分类」，所以「先定义、后使用」不会给用户看到一堆点进去为空的选项。这三条合起来，先定义是纯收益。

**资产端分类枚举**：

| `category` | 展示名（EN / 中文） | 语义边界 | 可退订 | 本期接入方 |
| --- | --- | --- | --- | --- |
| `security` | Security / 安全 | 账户安全事件：凭据变更、异常登录、会话安全 | ❌ 永不 | WS-302 |
| `account` | Account / 账户 | 账户状态与资料的非安全变化 | ❌ 永不 | WS-302 |
| `compliance` | Verification / 认证与合规 | 认证、合规、资质相关，但**不在业务办理进度轨迹上**的告知 | ❌ 永不 | WS-303 |
| `business_progress` | Business progress / 业务办理进度 | **任意业务线**的办理进度更新（认证审核、融资申请、放款、还款、票据…），必须带 `progress` 结构 | ❌ 永不 | WS-303（本期唯一），后续业务线直接复用 |
| **`finance`** | **Funds / 资金与财务** | **到账、扣款、额度变动、对账、票据结算等资金动向**（与「办理进度」区分：进度是流程走到哪一步，资金是钱发生了变化） | ✅ 部分可 | **本期无，预留** |
| **`announcement`** | **Announcements / 运营公告** | **运营发布的内容**：平台公告、活动、政策变更 | ✅ 可 | **本期无，预留** |
| `system` | System / 系统通知 | **平台自身的技术状态**：维护窗口、版本更新、服务降级 | ❌ 永不 | 本期无，预留 |

**管理端分类枚举**：

| `category` | 展示名（EN / 中文） | 语义边界 | 本期接入方 |
| --- | --- | --- | --- |
| `security` | Security / 安全 | 管理员本人的账号安全事件 | **本期无接入方**（WS-302 已于 `46e1d59` 删除 E-08，管理端本期不产生任何通知）；分类保留，供后续管理端模块使用 |
| `review_todo` | Review tasks / 审核待办 | 需要管理员处理的待办 | WS-303 |
| **`ops_alert`** | **Operations / 运营告警** | **平台运营需要人工介入的异常**（如定时任务执行失败） | **本期无，预留**（WS-301 的 `activation_failed` 是首个候选） |
| `system` | System / 系统通知 | 平台自身的技术状态 | 本期无，预留 |

**为什么把 `announcement` 与 `system` 分开**（两者容易被合并成一个「公告」）：`system` 是平台的技术状态，影响用户能不能正常使用，**永不可退订**；`announcement` 是运营内容，用户有权拒收，**将来可退订**。合成一类，退订开关就没法做——要么把维护通知也关掉（用户在维护期间一脸茫然），要么运营内容也关不掉（骚扰）。这条区分是为 2.5.1 的偏好中心提前铺路。

**三条通用规则**：

- 展示层**不写死这张表**：筛选器选项由服务端返回的分类元数据渲染（含 `category` 值与 `category_label_key`），新增分类不改前端页面逻辑。
- **各端的 `category` 取值空间互相独立**，同一个字符串在不同端可以是不同含义。四个端各有自己的分类集合，本表当前登记的是资产端与资产管理端两组；新端接入时在 `docs/notification-contract/接入指南.md` 4.1 增补自己那一组。
- 遇到**未登记的 `category`**：列表仍展示该消息，分类标签回落展示为「其他 / Other」，**不隐藏消息**（与 `01-页面与展示.md` 7.6.3 同一原则——内容永远优先于分类）。

**新增一个分类要做什么**：在 `04-接入指南.md` 的分类登记表登记 → 研发加枚举值与中英文案 key。**不需要改展示层的任何页面逻辑。**

#### 9.3.2 `biz_type`：业务类型标识

`biz_type` 是**面向系统的类型标识**，决定跳转映射、预检接口与业务语义。

| 项 | 规范 |
| --- | --- |
| **命名格式** | `{domain}.{object}.{action}`，全小写，点号分隔，各段用下划线连接多词 |
| 示例 | `agreement.version.activated`、`account.password.changed`、`verification.personal.rejected`、`financing.application.submitted` |
| `domain` | 业务域，与触发方模块对应（`account` / `agreement` / `verification` / `financing` …） |
| `object` | 业务对象（`version` / `password` / `application` …） |
| `action` | 已发生的动作，**用过去式或状态词**，不用祈使句（是 `rejected` 不是 `reject`） |
| 长度 | 建议不超过 64 字符 |
| 稳定性 | **一经登记不得更名**。`biz_type` 会落在历史消息上，改名会导致历史消息的映射失效 |
| 与接入方 `event_type` 的关系 | 接入方已有的事件类型定义**若已是三段式**（如 WS-301 `agreement.version.activated`、WS-303 `verification.personal.rejected`），**直接复用为 `biz_type`**，不另起一套；**若不是三段式**，由接入方改名后提供——**本模块不再维护任何转换层**（原 9.3.4 的过渡表已随 WS-302 适配完成而移除） |

##### 一级域（`domain`）命名空间规划

首版只列了现有取值，装不下尚未立项的模块。本轮给出**全平台的一级域规划**——新模块从下表挑一个已规划的域，或按「申请流程」新增：

| 段 | 一级域 | 覆盖范围 | 状态 |
| --- | --- | --- | --- |
| **平台基础** | `account` | 账户、凭据、登录、会话、偏好 | 已用（WS-302） |
| | `admin` | 管理端账号自身的事件 | 已用（WS-302） |
| | `agreement` | 协议、条款、版本、同意记录 | 已用（WS-301） |
| | `verification` | 个人认证、企业认证、资质审核 | 已用（WS-303） |
| **链融主业务**<br>（尚未立项，**预留**） | `financing` | 融资申请、授信、合同 | 预留 |
| | `disbursement` | 放款、出账 | 预留 |
| | `repayment` | 还款、逾期、结清 | 预留 |
| | `credit` | 额度申请、额度变更、额度冻结 | 预留 |
| | `invoice` | 票据、发票、单据 | 预留 |
| | `settlement` | 结算、对账、清分 | 预留 |
| **横向域** | `announcement` | 运营公告、活动 | 预留 |
| | `system` | 平台维护、版本、服务状态 | 预留 |
| | `ops` | 运营侧告警与人工介入事项 | 预留 |
| **保留段（禁止业务使用）** | `notification` | **保留给消息模块自身**（如「你有多条未处理消息」这类汇总消息） | 保留 |
| | `platform` | 保留给未来的平台级能力 | 保留 |
| | `test` / `demo` / `tmp` | **禁止进入生产**，服务端在接收时直接拒收 | 禁止 |

> 一级域刻意按**业务域**划分，不按**模块或 issue 编号**划分（不用 `ws301.*`、`kyc_module.*`）。理由：模块会拆分、合并、改名，而业务域相对稳定；`biz_type` 会落在历史消息上且**一经登记不得更名**，绑定到易变的组织结构上迟早出问题。

#### 9.3.3 扩展方式：代码层定义，新增需研发适配（强制条款）

| 项 | 口径 |
| --- | --- |
| 定义位置 | `category` 与 `biz_type` 的取值**在代码层定义** |
| 管理端界面 | **不提供任何业务类型配置界面**——不能在管理端新增、编辑、停用一个业务类型 |
| 新增一类的流程 | 由对应业务需求在 PRD 中登记 → 研发在代码层增加定义与登记表条目 → 随版本发布生效 |
| 与 WS-301 的一致性 | 与 WS-301 M0「协议定义（代码层，管理端只读）」是同一口径：类型的存在与语义属于产品设计的一部分，不是运营可以随手改的配置 |
| 为什么不做可配置 | 一个业务类型不只是一个名字——它必然连带跳转目标、预检逻辑、文案模板、可能的进度节点语义。让运营在界面上「新增一个类型」，只能新增出一个跳不动、没文案的空壳，反而制造故障 |

### 9.4 跳转目标的字段约定

#### 9.4.1 `biz_ref` 结构

| 字段 | 类型 | 必填 | 说明 |
| --- | --- | --- | --- |
| `resource_type` | string | ✅ | 目标资源类型，命名规范同 `biz_type` 的 `{domain}.{object}` 两段，如 `verification.application` |
| `resource_id` | string | ✅ | 目标资源的业务主键 |
| `extra` | map<string, string> | ❌ | 路由模板需要的附加参数（如 `tab=personal`），键名由接入方在登记表中声明 |

**约束**：

- ❌ **不得存放 URL、路径或深链字符串**。前端路由会重构，历史消息不可能批量改写。
- ❌ 不得把多个资源塞进一个 `resource_id`（如逗号分隔）。一条消息只指向一个目标。
- ❌ 不得与 `page_target` 同时填写。一条消息只有一个跳转目标。
- ✅ 跳转目标是静态页面时**不填 `biz_ref`，改填 `page_target`**（见 9.4.4）。
- ✅ 无跳转目标的消息（纯告知类）**两者都不填**，详情页不渲染跳转按钮，这是正常形态、不是缺失（见 `01-页面与展示.md` 7.6.4）。

#### 9.4.2 前端业务类型登记表

登记表是**前端代码中的一张映射表**，每个业务类型一条：

| 登记项 | 必填 | 说明 |
| --- | --- | --- |
| `biz_type` | ✅ | 主键 |
| `route_template` | ✅ | 路由模板，用 `{resource_id}` 与 `{extra.xxx}` 占位，如 `/user-center/verification?tab={extra.tab}&id={resource_id}` |
| `require_precheck` | ✅ | 是否需要跳转预检；消息实体的同名字段可覆盖 |
| `precheck_api` | 条件必填 | 需要预检时必填，由业务方提供 |
| `cta_label_key` | ❌ | 跳转按钮文案 key，缺省为「查看详情 / View details」 |
| `end` | ✅ | 该类型属于哪一端（`asset` / `admin` / `fs` / `fs_ops`），防止某一端的类型被另一端的映射误用 |

#### 9.4.3 登记要求（对各业务需求的硬性要求）

任何需求要新增一类站内消息，**必须在自己的 PRD 中同时给出以下五项**，缺一不可：

1. `biz_type` 标识（符合 9.3.2 命名规范）
2. `category` 归属（复用已登记分类，或说明为何需要新增分类）
3. `biz_ref` 的 `resource_type` 与 `resource_id` 取值口径
4. 目标路由与是否需要预检；需要预检时给出预检接口及其返回的失效原因枚举（`resource_deleted` / `state_changed` / `no_permission`）
5. 文案模板 key 与其变量清单（见 9.5.2）

**未登记的后果是明确的、不是故障**：消息仍会正常投递、正常展示、正常已读，只是不渲染跳转按钮（`01-页面与展示.md` 7.6.3）。本模块不会因为某个业务类型没登记而拒收消息——那会让通知因为一个前端配置缺失而彻底丢失。

#### 9.4.4 `page_target`：静态页面目标

| 项 | 约定 |
| --- | --- |
| 取值 | **页面编号**，取自各需求 PRD 的页面清单（如 WS-302 主文档 5.1 的 `P-A11` / `P-A17` / `P-M05`，本文档 5.1 的 `P-A18`） |
| 落地方式 | 前端维护一张**页面路由表**（页面编号 → 路由），与业务类型登记表并列但相互独立 |
| 是否预检 | **否**。静态页面恒久存在，不存在资源被删除或状态流转的可能 |
| 跨端校验 | `page_target` 的所属端必须与消息的 `end` 一致——资产端消息不得指向 `P-M*` / `P-O*`，运营端消息不得指向 `P-A*` / `P-M*`，四个端两两之间均如此。**服务端在接收时校验，不一致直接拒收**——这是接入错误，放行只会让用户点到一个进不去的页面 |
| 页面编号不存在于路由表 | 按 `01-页面与展示.md` 7.6.3 的映射缺失口径处理：不渲染按钮 + 说明文案 + 上报日志 |
| 为什么不直接用 `biz_ref` 硬套 | 静态页面没有 `resource_id`，硬套会产生 `resource_id = null` 的畸形数据，并强迫每个静态目标都去业务类型登记表里编一条空映射 |

**当前已登记的页面目标**（随接入方增补）：

| 页面编号 | 页面 | 端 | 登记方 |
| --- | --- | --- | --- |
| `P-A11` | 账户设置 | asset | WS-302 |
| `P-A17` | 用户中心 | asset | WS-302 |
| `P-M05` | 管理端账户设置 | admin | WS-302 |
| `P-A18` | 消息中心 | asset | 本文档（供其他消息引用，如「你有多条未处理消息」类汇总消息） |

**与 WS-302 `link_target` 的关系**：WS-302 的 `link_target` 存的**同样是页面编号**（其 `03-流程图与状态机.md` 第 399 行：「页面编号（如 `P-A11`）；无跳转时为空」）——**取值语义与格式与本契约的 `page_target` 完全一致，差异只在字段名**。因此适配项 A-02 是一次字段改名，不涉及取值格式转换，也不需要 WS-302 重新梳理任何一条消息的跳转目标。

### 9.5 多语言文案的承载方式

#### 9.5.1 结论

**主口径：模板 key + 参数（`title_key` / `body_key` + `params`），文案在展示时按用户当前语言渲染。**
**兼容口径：无法模板化的内容使用成品文案快照（`title_snapshot_i18n` / `body_snapshot_i18n`），同时落中英两份。**

渲染优先级：`title_key` / `body_key` 存在 → 用模板渲染；否则 → 用快照；两者都没有 → 走 9.5.4 的降级。

#### 9.5.2 为什么以模板 key 为主

| 理由 | 说明 |
| --- | --- |
| **语言必须能实时切换** | WS-302 D-39 已定：站内信的语言在**展示时**按用户当前语言选取，而不是发送时固定。模板 key 天然满足——用户切到中文，历史消息立刻是中文 |
| **文案可统一修订** | 发现一句文案有歧义时，改模板即可对所有历史消息生效；成品文案落库后只能改新消息，历史消息永远保留错误措辞 |
| **翻译工作可集中** | 所有文案集中在文案资源里，翻译、审校、补齐缺失都在一处，不需要去各业务的触发逻辑里翻 |

**`params` 的命名规范**：
- 使用 `{snake_case}` 占位符，与 WS-302 `05-消息通知与邮件模板.md` 12.5.5 已有的占位符命名保持一致（`{time}`、`{device}`、`{email_mask}`、`{address_short}` 等）。
- **参数值必须是最终展示值或可被展示层格式化的原值**：时间传 UTC 原值（由展示层按接收者时区渲染），金额传数值 + 币种（由展示层按 WS-302 `02-页面字段与双语文案.md` 13.5 格式化），已脱敏的字段由触发方脱敏后传入（本模块不做脱敏判断）。
- ❌ **禁止拼接句子片段作为参数**（如 `{action} 已完成` 里的 `{action}` 传「审核」）。中英文语序不同，片段拼接必然在某个语言下产生病句。需要不同措辞时，用不同的模板 key。

#### 9.5.3 什么时候用成品文案快照

| 场景 | 承载方式 |
| --- | --- |
| 运营撰写的系统公告（每条内容都不同，无法模板化） | 快照，中英两份 |
| 触发方已有成品双语文案且不打算改造 | 快照。**已对着 WS-302 定稿版（`03-流程图与状态机.md` 14.8）逐字段核对：字段名确为 `title_i18n` / `body_i18n`，拆分后未改名，直接映射到本契约的 `title_snapshot_i18n` / `body_snapshot_i18n`，WS-302 无需改造即可接入** |
| 引用了用户提交的原文（如驳回原因中的审核意见） | **混合**：模板 key 承载句式，用户原文作为 `params` 中的一个变量传入。审核意见本身不翻译，原样展示 |

**新接入方的默认要求是模板 key**。快照是兼容通道，不是推荐做法：用快照的消息在用户切换语言后能正确显示（因为两份都存了），但文案修订无法回溯到历史消息。

**快照 + `params` 的渲染顺序（本轮核对补充）**：WS-302 的 `title_i18n` / `body_i18n` 是**变量已渲染完毕**的成品文本，同时它的 `variables` 字段又携带了变量原值，用途正是「供通知模块在需要时重新渲染」。两者并存时本模块的处理顺序是：

1. 默认直接展示快照文本；
2. **但 `{time}` 例外**——快照里的时间是按事件发生时的账户时区渲染的，用户此后若改了时区偏好，快照会显示旧时区的时间。因此当 `params`（映射自 `variables`）中带有时间原值时，**以原值按当前时区重新渲染该占位符**，其余部分仍用快照文本；
3. `variables` 缺失时按快照原样展示，不报错。

这条不需要 WS-302 做任何改动——它已经把变量原值传过来了。

#### 9.5.4 缺失与降级（强制条款）

| 情况 | 表现 |
| --- | --- |
| 模板 key 存在，当前语言的翻译缺失 | **回落英文**，遵循 WS-302 `02-页面字段与双语文案.md` 13.7；构建期报告缺失项 |
| 模板 key 存在，英文也缺失 | 该条消息在列表中降级为「分类标签 + 时间 + `Notification / 消息`」的最小形态，详情页展示同样的兜底文案。**绝不展示文案键名**（如 `msg.verification.rejected.title`）给用户 |
| 模板 key 存在，`params` 缺少某个变量 | 该占位符渲染为空字符串并去除多余空格，不展示 `{xxx}` 原文；服务端记录一次告警 |
| 快照缺少中文 | 展示英文 |
| 快照与模板 key 都没有 | 消息**不投递**——这是触发方的接入错误，服务端在接收时即校验并拒绝，返回明确的错误给触发方。不能让一条没有任何内容的消息进入用户的列表 |
| 富文本 / HTML | 不支持。文案与参数一律按纯文本渲染并转义，见 `v1.0-消息通知-PRD.md` 13.2 |

### 9.6 `progress`：业务办理进度结构

`category = business_progress` 时必填。

| 字段 | 类型 | 必填 | 说明 |
| --- | --- | --- | --- |
| `biz_name_key` | string | ✅ | 业务名称的文案 key（如「实名认证」「融资申请」），作为列表标题位与详情标题 |
| `biz_no` | string | ❌ | 对外可展示的业务编号，详情页展示并支持复制 |
| `node_key` | string | ✅ | 当前节点名称的文案 key（如「材料复核」） |
| `node_status` | enum | ✅ | `in_progress` / `action_required` / `succeeded` / `failed`，**封闭枚举**，见 `01-页面与展示.md` 7.8.2 |
| `node_index` / `node_total` | int | ❌ | 当前第几步 / 共几步；两者同时提供时列表展示「第 2/5 步」，缺任一则不展示 |

- 节点的**定义、顺序、推送时机**由各业务需求负责，本契约只承载「当前是哪一步、什么状态」。
- `node_status` 不得扩展；业务侧的细分状态由 `node_key` 的文案表达。
- **`dedupe_key` 必须包含节点标识**（建议 `{biz_type}:{resource_id}:{node_key}`）。这是硬约束，理由见 `01-页面与展示.md` 7.8.4——复用同一个 key 会让后一个节点的更新覆盖前一个，用户永久丢失中间进度。

### 9.7 职责分界表

本表的「接入方」指**任何一个要发消息的模块**，不特指首批三个。

| 事项 | 接入方（任何要发消息的模块） | 本模块（平台站内消息能力） |
| --- | --- | --- |
| **什么事件触发通知** | ✅ 定义并触发 | ❌ 不定义、不判断 |
| **触发时点** | ✅ 定义（精确到某一步成功之后） | ❌ |
| **消息文案内容** | ✅ 提供模板 key + 参数（或快照双语文案） | ❌ 不写文案，只负责渲染与语言选取 |
| **消息分类归属 `category`** | ✅ 声明 | ✅ 定义平台通用枚举与新增流程（9.3.1） |
| **业务类型标识 `biz_type`** | ✅ 声明并遵守命名规范 | ✅ 定义命名空间、保留段、申请流程与登记表（9.3.2） |
| **跳转目标资源 `biz_ref`** | ✅ 提供 `resource_type` + `resource_id` | ❌ 不知道目标是什么 |

| **有效期 `expire_at` / 主动失效** | ✅ 按业务语义设置 | ✅ 按其执行过期表现 |

| 消息投递与幂等（按 `event_id`） | — | ✅ |
| 谁能看到（`recipient_scope` 与可见集计算） | — | ✅ 定义规则并实现（9.1.1） |
| 未读数计算与角标 | — | ✅ |
| 列表、筛选、分页、排序、空态 | — | ✅ |
| 详情展示形态 | — | ✅ |
| 已读语义（单条 / 全部） | — | ✅ |
| 语言选取与文案回落 | — | ✅ 按**展示时**的用户语言 |

### 9.8 接入 Checklist（接入方自检用）

| # | 检查项 | 通过标准 |
| --- | --- | --- |
| 1 | 事件是否幂等 | 每次触发有稳定唯一的 `event_id`；重试不产生重复消息 |
| 2 | `end` 与 `recipient_scope` 是否正确 | 资产端消息必须带 `recipient_account_id` |
| 3 | `category` 是否已登记 | 已在 9.3.1 表中，或本次 PRD 已说明新增理由 |
| 4 | `biz_type` 是否符合命名规范 | `{domain}.{object}.{action}`，且与自己已定义的事件名一致 |
| 5 | 跳转目标形态是否明确 | 三选一：`biz_ref`（业务资源）/ `page_target`（静态页面）/ 两者都不填（无跳转）。**不得同时填写**，且都**不含 URL** |
| 5b | `page_target` 的端是否与消息一致 | 资产端消息不得指向 `P-M*`，反之亦然（9.4.4） |
| 6 | 是否在登记表中补齐了路由与预检 | 五项登记内容（9.4.3）齐全 |
| 7 | 文案是否用模板 key | 是；使用快照的需说明原因 |
| 8 | `params` 是否完整 | 模板中的每个占位符都有取值，且不是句子片段 |
| 9 | 是否需要有效期 | 有时效的消息设置了 `expire_at` |
| 10 | 去重键是否会误合并 | 不同业务节点使用不同 `dedupe_key`（见 `01-页面与展示.md` 7.8.4） |
| 11 | 进度类消息是否带 `progress` | `biz_name_key`、`node_key`、`node_status` 齐备 |
| 12 | 敏感信息是否已脱敏 | 完整邮箱、完整钱包地址、完整 IP、证件号不得进入 `params` |
| 13 | 管理端消息的投递范围是否正确 | 全员待办用 `admin_all`；**管理员个人的账号安全消息必须用 `admin_account` + `recipient_admin_id`**（`v1.0-消息通知-PRD.md` 8.2.2） |
| 14 | `recipient_scope` 是否用对 | 五种取值见 9.1.1；用到本期未实现的 `enterprise` / `broadcast` 需先确认实现排期 |
| 15 | 是否声明了 `subscribable` | 缺省 `false`；只有运营公告、部分资金类才可为 `true`，安全 / 账户 / 认证与合规**永远** `false` |
| 16 | 是否误把邮件当成本模块的职责 | 本模块只处理站内消息。**邮件由你自己发**，不要期待提交给本模块的消息会产生任何邮件（`v1.0-消息通知-PRD.md` 2.4） |
