### 14.2 节点判定：为什么是这些节点

本节按三个判断维度——事件发生时用户在不在站内、这条消息晚一天看到还有没有用、需不需要一条「攻击者撤不回」的外部通道——逐维度套用到认证链路，得出「哪些节点要通知、走哪些渠道」。**渠道判定由本模块自持**：WS-304 已按「邮件不属于消息通知」的裁定删除其渠道规则一节。

| 维度 | 在认证链路上的回答 |
| --- | --- |
| **① 事件发生时用户在不在场** | 认证链路上只有**提交**这一个动作是用户主动发起、且当场就在页面上；**审核结论全部是异步产生的**——用户提交完就离开了，几小时到几天后才出结论，出结论那一刻他几乎一定不在站内 |
| **② 晚 24 小时还有没有用** | 审核结论**有用且必须尽快知道**：驳回意味着他要动手改材料，早一天知道就早一天解锁业务；提交受理**晚一天就没意义了**（他当场已经从提交结果页看到了） |
| **③ 需不需要攻击者撤不回的外部通道** | 认证链路本身不改凭据，不属于典型的账户接管场景；但**企业重复注册拦截**是例外——如果一家企业被他人抢先注册，真实企业的负责人可能根本不在平台上，站内信他看不到，而邮件是唯一能触达、且平台事后撤不回的凭证 |

**由此得出的三条结论**：

1. **审核结论类节点（通过 / 驳回 / 整体通过）→ 站内信 + 邮件。** 三个维度里前两个都指向"必须有站外渠道"。
2. **提交受理 → 只发站内信。** 用户此刻正看着提交结果页（P-K02），再发一封"我们已收到"的邮件是纯噪声；但站内信要发，它是消息中心里这条业务轨迹的**起点节点**，用户日后回查"我什么时候提交的"要靠它。
3. **企业重复注册拦截 → 站内信 + 邮件。** 虽然用户当场就看到了拦截提示（[`02-企业认证与模板.md`](./02-企业认证与模板.md) 9.4.1），但这条记录**对用户不利且可能引发申诉**：他需要一份自己留存、平台改不了的凭证去找客服；如果是被冒名注册，邮件更是唯一的外部触达通道。这是第③维度的适用场景。

**明确不发通知的情形**（列出以免被当成遗漏）：

| 情形 | 为什么不发 |
| --- | --- |
| 保存草稿、切换步骤、上传成功 | 纯前台交互，用户当场可见，通知只会制造噪声 |
| 申请进入审核队列、审核员领取 / 打开详情 | 平台内部动作，对用户没有可执行的含义；也不该让用户感知到"谁在看我的材料" |
| 审核中的任何中间态、版本号变化本身 | 不构成进度节点。**进度节点＝用户能感知到的状态变化**，不是系统内部的每一次写库 |
| 提交被限频拦截（[`03-流程与状态机.md`](./03-流程与状态机.md) 7.5.4）、被校验拦下 | 当场就有页内提示与 Toast，且没有产生任何审核成本 |
| 企业唯一键的占用与释放（[`02-企业认证与模板.md`](./02-企业认证与模板.md) 9.4.3） | 系统内部状态，用户无从理解也无需理解 |
| 级联驳回的"级联"这一动作本身 | 它已经体现在企业认证的驳回结论里（14.3 的 `verification.business.rejected`），不另发一条 |
| 管理端的"新申请待审核" | 见 14.9 的结论与理由 |

**几条必须写清的口径**：

1. **事件名全部是三段式**（WS-304 9.3.2）。相较本 PRD 上一版，`verification.submitted` / `verification.completed` / `verification.duplicate_blocked` 三个两段式已改为 `verification.application.submitted` / `verification.overall.completed` / `verification.business.duplicate_blocked`。改名后 7 个事件可**直接作为 `biz_type`**，不需要任何转换层。
2. **`verification.business.duplicate_blocked` 归 `compliance`，不带 `progress`**：它是一次提交被当场拦截的即时告知，不在任何一条办理轨迹上——没有"办到哪一步"，也没有后续节点。其余 6 条都在实名认证这一条轨迹上，归 `business_progress` 并必须带 `progress` 结构（14.5）。
3. **提交只发一条消息，用批次号做资源标识**：一次提交同时创建个人与企业两份申请，但 WS-304 契约规定一条消息只能有一个跳转目标（9.4.1）。用 `batch_id` 落到 P-K03 认证详情页（该页本就同时展示两条轨道），比拆成两条时间戳相同、内容雷同的消息更贴合用户"我提交了一次"的心智。
4. **个人线与企业线的结论消息不合并**（WS-304 适配项 B-07）：N-02～N-05 各自独立成条。理由：两条认证各走各的状态机（[`03-流程与状态机.md`](./03-流程与状态机.md) 11.1）；用户对两者的处理动作不同（个人驳回改证件、企业驳回改营业执照）；级联驳回时企业线有独立于个人线的说明要传达。**实现时不得自行合并成一条"认证结论"消息。**
5. **级联驳回不新增事件**：走 N-05，正文使用级联专用文案（14.7），并在 `params` 中带 `is_cascaded = true` 供邮件模板选择措辞。
6. **已通过后更新的结论不新增事件**：仍走 N-02～N-05，但使用**不同的文案模板 key**（14.7.4）——因为"更新被驳回"会导致已认证状态被收回（[`03-流程与状态机.md`](./03-流程与状态机.md) 7.5.3.3），后果与首次驳回完全不同，必须用不同措辞。`biz_type` 不变的理由：`biz_type` 决定跳转与业务语义，二者在这里是一致的；WS-304 允许同一 `biz_type` 使用不同模板 key。
7. **提交给 WS-304 的 `channels` 一律为 `["in_app"]`（含要发邮件的六条）**。用户已裁定邮件不属于消息通知模块，WS-304 不做邮件分发；若在 `channels` 里声明 `email`，要么没有任何一方去执行、要么与本模块自己的发送重复成两封。上表的「邮件」列是**本模块自己的触发口径**，不是 `channels` 字段的取值。
   > 这是本模块与 WS-304 之间唯一一处「声明与事实分离」的地方，因此写在这里而不是藏在实现里。日后若邮件重新收归通知模块统一分发，改动面只有一处：把这六条的 `channels` 改回 `["in_app", "email"]` 并停用 14.8.1 的自发逻辑——**触发时点、文案、去重键、进度映射全部不受影响**。

### 14.4 `dedupe_key` 构造（强制条款）

> WS-304 `04-接入指南.md` 5.3 把「漏掉版本号导致静默数据丢失」写成了反例，而那个反例的原型正是本模块。**消息模块只认 `dedupe_key`、不做任何兜底推导，这一项没有系统侧安全网。**

**构造规则**：

```
{biz_type}:{resource_id}:v{version}
```

| 事件 | `dedupe_key` |
| --- | --- |
| N-01 | `verification.application.submitted:{batch_id}:v{version}` |
| N-02 | `verification.personal.approved:{personal_verification_id}:v{version}` |
| N-03 | `verification.personal.rejected:{personal_verification_id}:v{version}` |
| N-04 | `verification.business.approved:{enterprise_verification_id}:v{version}` |
| N-05 | `verification.business.rejected:{enterprise_verification_id}:v{version}` |
| N-06 | `verification.overall.completed:{account_id}:v{version}` |
| N-07 | `verification.business.duplicate_blocked:{unique_key_hash}:{submitted_at_epoch}` |

**版本号为什么是硬约束（不可省略、不可简化）**

本 PRD 的 [`03-流程与状态机.md`](./03-流程与状态机.md) 11.1 允许 `rejected → under_review` 重新提交并把版本号 +1，[`03-流程与状态机.md`](./03-流程与状态机.md) 7.5.3.3 又允许 `approved → under_review`。因此**同一条申请可以被驳回多次**：v1 驳回、改完 v2 又被驳回、甚至已通过后更新的 v3 再被驳回。若 `dedupe_key` 不含版本号：

| 时间 | 事件 | 结果 |
| --- | --- | --- |
| 周一 | 第 1 次驳回（v1），原因「影像模糊」 | 产生消息 A |
| 周三 | 用户修改后重新提交（v2） | — |
| 周五 | 第 2 次驳回（v2），原因「企业名称不一致」 | 命中消息 A 的去重键，**就地覆盖**：时间变周五、内容变成第二次的原因 |

用户**永久看不到第一次驳回的记录，且全程不报错**——列表里始终只有一条，看上去一切正常。等用户问「你们上次说的是影像问题，怎么又变了」时，记录已经不存在了。所以：

- **版本号必须进 `dedupe_key`**，`{version}` 取该申请本次结论所对应的 `version` 字段（[`03-流程与状态机.md`](./03-流程与状态机.md) 15.1 / [`03-流程与状态机.md`](./03-流程与状态机.md) 15.2）。
- **N-06 的版本号**取整体通过时两条申请的共同版本号（同批次同版本，[`03-流程与状态机.md`](./03-流程与状态机.md) 7.5.3.1）；`{account_id}` 而非申请编号做资源标识，因为"整体通过"是账户级事实。
- **N-07 没有申请编号**（提交被拦截，未创建申请），因此用「唯一键哈希 + 提交时刻」构造：`unique_key_hash` 是企业唯一键的不可逆哈希（**不得放明文唯一键**，避免消息层泄露其他账号的企业标识），`submitted_at_epoch` 保证同一用户反复尝试同一家企业时每次各成一条——他每次尝试都是一次独立的、需要被告知的事实。
- **拿不准时宁可不填**（WS-304 5.4）：多一条重复消息，比少一条真实消息安全得多。本模块的 7 条都能明确构造，不适用该兜底。

### 14.5 进度结构 `progress` 与四态映射

N-01～N-06 六条属于 `business_progress`，必须带 `progress` 结构（WS-304 9.6）。

**固定字段**：`biz_name_key = msg.verification.biz_name`（实名认证 / Identity & business verification）；`biz_no = {batch_id}`（对外可展示的业务编号，详情页可复制）；`node_index` / `node_total` **不提供**——认证不是固定步数的线性流程（两条轨道并行、可重提多轮），给出"第 2/5 步"只会误导。

| 事件 | `node_status` | `node_key` | 节点展示名（EN / 中文） |
| --- | --- | --- | --- |
| N-01 | `in_progress` | `msg.verification.node.submitted` | Submitted · awaiting review / 已提交 · 等待审核 |
| N-02 | `succeeded` | `msg.verification.node.personal_approved` | Identity verification · approved / 个人认证 · 已通过 |
| N-03 | **`action_required`** | `msg.verification.node.personal_rejected` | Identity verification · action required / 个人认证 · 需修改后重新提交 |
| N-04 | `succeeded` | `msg.verification.node.business_approved` | Business verification · approved / 企业认证 · 已通过 |
| N-05 | **`action_required`** | `msg.verification.node.business_rejected` | Business verification · action required / 企业认证 · 需修改后重新提交 |
| N-06 | `succeeded` | `msg.verification.node.completed` | Verification complete / 实名认证 · 全部通过 |

**驳回为什么映射 `action_required` 而不是 `failed`（强制条款）**

WS-304 的 `action_required` 语义是「**需要用户做点什么**」，`failed` 是「未通过或业务终止」。本模块的驳回**明确要求用户修改后重新提交**（[`03-流程与状态机.md`](./03-流程与状态机.md) 11.1 `rejected → under_review`，P-K03 驳回态直接提供重新提交入口），属于前者。若映射成 `failed`，消息列表会显示红色的「未通过」，用户很可能理解成认证被终结、无事可做——而这恰恰是最需要他动手的时刻。

**`failed` 在本模块本期不使用（这是结论，不是遗漏）**：`approved` 不是终态（[`03-流程与状态机.md`](./03-流程与状态机.md) 7.5.3.3 允许更新后重审）、`rejected` 可无限次重提（[`03-流程与状态机.md`](./03-流程与状态机.md) 7.5.4 只限频不封顶），本期的认证链路里**不存在终止性失败**。日后若引入"认证被永久拒绝/账户被停用"这类终止态，才会用到 `failed`。

**已通过后更新被驳回时的 `node_status`**：仍为 `action_required`——用户要做的事没变（改材料重提），变的是后果（已认证状态被收回），后果由文案传达（14.7.4），不由 `node_status` 表达。

#### 14.7.3 驳回原因为什么不整段放进站内信

驳回问题项是一组**双语预置文案**（[`06-双语文案与线框.md`](./06-双语文案与线框.md) 8.7.4）。若在触发时把它们渲染成一段文本塞进消息，这段文本的语言就在**发送时**固定了；而 WS-304 D-39 明确站内信的语言在**展示时**按用户当前语言选取——用户切成英文后会看到一段中文原因，与全站语言切换的行为不一致。

因此站内信只给 `{reason_count}` + 跳转到 P-K03，**完整原因在详情页按当前语言渲染**（[`03-流程与状态机.md`](./03-流程与状态机.md) 7.5.2 已定义字段级回显）。审核员的补充说明是个例外：它是审核员手写的自然语言，本来就没有译文，按 WS-304 9.5.3 的"混合"用法作为变量原样传入。

### 14.8 邮件（本模块自持）

> **邮件不属于消息通知模块**（用户 2026-09-08 裁定）。本节定义的不是"提交给谁去发"，而是**本模块自己的一项功能**：由本模块在同一业务事件上独立触发、渲染并发送。

#### 14.8.1 触发与发送口径

| 项 | 规则 |
| --- | --- |
| 适用节点 | N-02～N-07 六条（14.3 的「邮件」列）；**N-01 提交受理不发邮件** |
| 触发时点 | 与站内信**同一时点、同一事件**（结论写入之后），但**两条分支相互独立**：任一条失败都不影响另一条，也不回滚业务 |
| 与 WS-304 的关系 | 提交给 WS-304 的消息 `channels` 只声明 `["in_app"]`（14.3 第 7 条）；WS-304 不感知、不参与邮件 |
| 收件地址 | 账户当前已验证的邮箱（WS-302 的 `email`） |
| **地址缺失** | **静默跳过，不报错、不记为异常**——纯钱包账户没有邮箱是正常状态（WS-302 的建号路径允许），不是故障 |
| 语言 | **发送时**按接收者当时的语言偏好定语（WS-302 13.2），发出后不再改写；无偏好时用英文 |
| 幂等 | 以事件的 `event_id` 为幂等键：同一结论的重试只发一封；重复触发不产生第二封 |
| **失败不阻断** | 邮件发送失败**不得阻断认证状态写入、不得阻断站内信、不得让审核员的结论操作报错**；失败进重试队列，重试耗尽后记审计 |
| 退信 | 硬退信记入审计并纳入监控（17 章）；**不解绑邮箱、不改账户状态、不影响认证状态** |
| 频控 | 认证结论类邮件按事件触发，天然低频，不额外限频；同一结论不因用户反复刷新而重复发送（幂等保证） |
| 发件域与送达 | 沿用 WS-302 的发件域与 SPF / DKIM / DMARC 配置，不另起一套发件身份 |
| 内容边界 | 正文**不出现证件号码、影像链接、企业注册号原文、他人账号信息**；需要看细节一律引导回站内 |

> 这三条（成功语义、失败不阻断、地址缺失跳过）**由本模块自己定义并执行**。WS-304 曾在其 9.9 定义过同样语义，但该节已随「邮件不属于消息通知」的裁定删除——邮件的规则与执行现在都在本模块，不存在跨模块的假设。

| 判断维度 | 在管理端审核场景下的回答 |
| --- | --- |
| ① 审核员在不在场 | **在场**。审核员的工作方式是上班后打开管理端、看队列、逐条处理；管理端左侧菜单的「个人认证审核 / 企业认证审核」已带**待审数量角标**（[`v1.0-实名认证与审核-PRD.md`](./v1.0-实名认证与审核-PRD.md) 5.1），进门就能看到有多少待办 |
| ② 晚 24 小时还有没有用 | **队列不会消失**。申请一直留在队列里按提交时间排序，晚看到不会丢件；真正的风险是"积压太久"，那属于产能问题，靠 17 章的积压指标监控，不靠给每个审核员发一条消息 |
| ③ 需不需要外部不可撤回通道 | **不需要**。这不是安全事件 |

三个维度都指向"不需要"。另外两条更实际的理由：

1. **量级与噪声**：每一次用户提交都会产生一条 `admin_all` 消息，消息量 = 提交量。所有管理员共享消息池、已读各自独立（WS-304 9.1.1），一个人处理了申请**不会**让其他人的那条消息消失——消息列表会迅速退化成一份没有状态、无法勾销的劣质队列副本，与真正的队列（P-M30 / P-M32）并存且互相矛盾。
2. **没有回收机制**：WS-304 本期没有"待办完成即撤回消息"的能力（`invalidated_at` 需要触发方主动调用，且不改变其他管理员的已读状态）。做一个不能勾销的待办列表，比不做更糟。

**因此本模块不使用 `review_todo` 分类。** WS-304 `02-数据契约与字段.md` 9.3.1 的管理端分类表把 `review_todo` 的本期接入方标注为 WS-303——按本结论，**该分类本期没有生产者**。这不是本模块的遗漏，是判断结果；建议 WS-304 把该行的接入方标注调整为"本期无，预留"，以免被当成缺口去催。

**后续可能的替代方案（本期不做，登记为候选）**：真正有价值的不是逐条待办，而是**积压告警**——例如"待审队列超过 N 条"或"最早一条已等待超过 N 小时"时给管理端发一条聚合提醒。它属于 WS-304 已预留的 `ops_alert` 分类，且量级可控、有明确的处置动作。待产能数据积累后再评估阈值。
