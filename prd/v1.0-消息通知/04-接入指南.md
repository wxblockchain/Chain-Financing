## 1. 你需要知道的四件事

**第一，本模块只做站内信。** 你提交给它的就是一条**站内消息**，它不会、也不能替你发邮件或短信——**站外触达归你自己**（模板、触发、投递、退订都在你那边，见 `v1.0-消息通知-PRD.md` 2.4）。契约里没有任何渠道字段，别去找。

**第二，站内信这一层你只负责「什么时候发、发什么」。** 谁能看到、怎么展示、未读怎么算、已读怎么标、点了跳哪、失效了怎么办——全部由消息模块承担，你不需要实现，也不应该自己实现一套。

**第三，接入不需要改消息模块。** 如果你发现「要接进来必须让消息模块改点什么」，那不是你的问题，是规则没做到通用——**直接提出来**，那属于消息模块的缺陷，不要绕过去自己造一套。

**第四，消息一旦发出就会长期留存。** 本期不做保留期与自动清理（`01-页面与展示.md` 7.10），`biz_type` 一经登记不得更名，历史消息会一直带着你当初填的字段。所以命名与结构值得多想五分钟。

**最小接入路径**：读第 2 章（要提供什么）→ 第 3 章（申请命名）→ 第 5 章（构造去重键，最容易踩坑）→ 第 8 章（对照 Checklist 自查）→ 第 9 章（照着示例填一遍）。

## 2. 你要提供什么

### 2.1 必填字段

| 字段 | 你要提供什么 | 常见错误 |
| --- | --- | --- |
| `event_id` | 本次事件的唯一标识，**幂等键**。重试同一个事件要用同一个 `event_id` | 每次重试生成新 ID → 用户收到多条重复消息 |
| `end` | `asset`（资产端用户看）/ `admin`（管理端看） | 两端都要知道时，**产出两条消息**，不要指望一条能同时投递 |
| `recipient_scope` | 五选一，见 2.2 | 把管理员个人的消息发成 `admin_all` → 泄漏给全体管理员 |
| 接收者标识 | 按 scope 填 `recipient_account_id` / `recipient_admin_id` / `recipient_enterprise_id` | — |
| `category` | 从第 4 章的分类枚举里选，不自造 | 所有消息都塞 `system` |
| `biz_type` | 三段式命名，见第 3 章 | 用单段（`order_paid`）或带模块名（`ws305.order.paid`） |
| 文案 | `title_key` + `body_key` + `params`（推荐），或双语成品快照，见第 6 章 | 传一句拼好的中文字符串，用户切英文后还是中文 |
| `created_at` | 事件发生时间，**UTC** | 传本地时间 → 用户看到的时间错几小时 |
| `source_module` | 你的模块标识 | — |

### 2.2 选哪个 `recipient_scope`

| 你的场景 | 用 | 本期可用 |
| --- | --- | --- |
| 发给某一个用户（绝大多数业务消息） | `account` | ✅ |
| 发给某一个管理员本人（他的账号安全、他的待办） | `admin_account` | ✅ |
| 发给全体管理员（谁都可以处理的待办、运营告警） | `admin_all` | ✅ |
| 发给某企业下的所有账户 | `enterprise` | ❌ 本期未实现，需先确认排期 |
| 发给全平台或某人群（公告） | `broadcast` | ❌ 本期未实现，需先确认排期 |

> **判断 `admin_account` 还是 `admin_all` 的标准只有一条**：这件事**任何一个管理员都可以去处理**吗？可以 → `admin_all`；只跟某个人有关（他自己的密码、他被指派的任务）→ `admin_account`。判断错的代价不对称：错发成 `admin_all` 会泄漏个人信息并污染所有人的未读数，错发成 `admin_account` 只是少了几个人看到。**拿不准时选 `admin_account`。**

## 3. `biz_type` 命名规范与申请

### 3.1 命名格式

```
{domain}.{object}.{action}
```

全小写，点号分隔，多词用下划线连接，建议不超过 64 字符。

| 段 | 含义 | 例 |
| --- | --- | --- |
| `domain` | 业务域，从 3.2 的一级域里选 | `financing` |
| `object` | 业务对象 | `application` |
| `action` | **已发生**的动作，用过去式或状态词 | `approved` |

✅ `financing.application.approved`、`repayment.installment.overdue`、`account.password.changed`
❌ `order_paid`（单段）、`ws305.order.paid`（用模块编号当域）、`financing.application.approve`（祈使句）、`financing.approve_application`（两段）

**一经登记不得更名**——它会落在历史消息上，改名会让历史消息的跳转映射全部失效。

### 3.2 一级域规划

| 段 | 一级域 | 覆盖范围 | 状态 |
| --- | --- | --- | --- |
| **平台基础** | `account` | 账户、凭据、登录、会话、偏好 | 已用 |
| | `admin` | 管理端账号自身的事件 | 已用 |
| | `agreement` | 协议、条款、版本、同意记录 | 已用 |
| | `verification` | 个人认证、企业认证、资质审核 | 已用 |
| **链融主业务** | `financing` | 融资申请、授信、合同 | 预留 |
| | `disbursement` | 放款、出账 | 预留 |
| | `repayment` | 还款、逾期、结清 | 预留 |
| | `credit` | 额度申请、变更、冻结 | 预留 |
| | `invoice` | 票据、发票、单据 | 预留 |
| | `settlement` | 结算、对账、清分 | 预留 |
| **横向域** | `announcement` | 运营公告、活动 | 预留 |
| | `system` | 平台维护、版本、服务状态 | 预留 |
| | `ops` | 运营侧告警与人工介入事项 | 预留 |
| **保留段** | `notification` / `platform` | 保留给平台能力，**业务不得使用** | 保留 |
| | `test` / `demo` / `tmp` | **禁止进入生产，服务端直接拒收** | 禁止 |

> 一级域按**业务域**划分，不按模块或 issue 编号划分。模块会拆分、合并、改名，业务域相对稳定。

### 3.3 申请流程

| 步骤 | 做什么 |
| --- | --- |
| 1 | 在**你自己的 PRD** 里列出要用的 `biz_type` 全集，一级域从 3.2 里选；没有合适的域时申请新增并说明为什么现有域装不下 |
| 2 | 对照 3.4 的登记表自查是否与已有取值重复 |
| 3 | 消息模块的需求负责人合入登记表，研发同批加代码层常量 |

**冲突避免**：一级域**先登记后使用**；同一域下的 `{object}.{action}` 由该域的归属模块自己保证唯一，不需要跨域协调。

**没来得及登记会怎样**：服务端**照常接收并投递**（只记告警），前端因映射表里没有条目而不渲染跳转按钮，消息内容正常展示。**不会丢消息**——登记滞后是流程问题，不该让用户承担。唯一例外是保留段 `test` / `demo` / `tmp`，直接拒收。

## 4. 分类枚举与编号唯一性

### 4.1 `category` 分类枚举

**资产端**：

| `category` | 展示名 | 什么时候用 | 可退订 |
| --- | --- | --- | --- |
| `security` | 安全 | 凭据变更、异常登录、会话安全 | ❌ 永不 |
| `account` | 账户 | 账户状态与资料的非安全变化 | ❌ 永不 |
| `compliance` | 认证与合规 | 认证/合规相关、但**不在办理进度轨迹上**的告知 | ❌ 永不 |
| `business_progress` | 业务办理进度 | **任意业务线**的进度更新，必须带 `progress` 结构 | ❌ 永不 |
| `finance` | 资金与财务 | 到账、扣款、额度变动、对账、结算 | ✅ 部分 |
| `announcement` | 运营公告 | 运营发布的内容：公告、活动、政策 | ✅ 可 |
| `system` | 系统通知 | 平台自身的技术状态：维护、版本、降级 | ❌ 永不 |

**管理端**：`security`（管理员本人的账号安全）、`review_todo`（审核待办）、`ops_alert`（运营告警，需人工介入）、`system`（平台技术状态）。

> **`business_progress` 与 `finance` 怎么分**：进度是「流程走到哪一步」，资金是「钱发生了变化」。放款审批通过 → `business_progress`；款项到账 → `finance`。
>
> **`announcement` 与 `system` 怎么分**：运营内容 vs 平台技术状态。前者将来可退订，后者永不可退订——合成一类，退订开关就没法做。

**新增分类**：在本章登记 + 研发加枚举值与中英文案 key，**不需要改展示层任何页面逻辑**。

## 5. `dedupe_key` 构造规范（最容易踩坑的一项）

### 5.1 它是干什么的

`dedupe_key` 相同的消息会被**合并成一条**：时间更新为最新一次，若此前已读则**恢复为未读**。它的用途是防止**同一个事件被重复触发**（服务重试、消息队列重投）时用户收到两条一样的消息。

**消息模块只认 `dedupe_key`，不会自己推导。** 没有「按事件类型 + 时间窗兜底去重」这种安全网——你构造错了，系统不会替你兜住。

### 5.2 构造规范

```
{biz_type}:{resource_id}:{节点或版本标识}
```

**必须能区分同一对象的不同节点 / 不同轮次。** 具体加哪个后缀由你的业务决定：有版本号加版本号，有节点加节点，有轮次加轮次。

| 场景 | 建议构造 |
| --- | --- |
| 一个对象只会发一次的消息 | `{biz_type}:{resource_id}` |
| 同一对象多个节点各发一次 | `{biz_type}:{resource_id}:{node_key}` |
| 同一对象同一节点可能重复发生（重提、重试、多轮） | `{biz_type}:{resource_id}:{node_key}:v{version}` |
| 每个账户终身只发一次（欢迎、首次完成） | `{biz_type}:{account_id}` |
| 广播消息 | **不得包含账户标识**，在广播范围内唯一即可 |

### 5.3 反例：漏掉版本号导致的静默数据丢失

> **这是真实核对中发现的坑，写在这里是因为它最容易踩，而且踩了不报错。**

某认证审核模块允许「驳回 → 用户修改 → 重新提交 → 再次审核」，重新提交时版本号 +1。它最初打算这样构造：

```
verification.personal.rejected:{application_id}      ← 错误：漏掉版本号
```

会发生什么：

| 时间 | 事件 | 结果 |
| --- | --- | --- |
| 周一 | 第 1 次审核驳回（v1），原因「证件照模糊」 | 产生消息 A |
| 周三 | 用户修改后重新提交（v2） | — |
| 周五 | 第 2 次审核驳回（v2），原因「企业名称不一致」 | `dedupe_key` 命中消息 A，**就地覆盖**：时间更新为周五、内容变成第二次的原因 |

**用户永久看不到第一次驳回的记录**，而且**全程没有任何报错**——列表里始终只有一条消息，看起来一切正常。等到用户问「你们上次说的是证件照问题，怎么现在又变了」的时候，记录已经不存在了。

正确构造：

```
verification.personal.rejected:{application_id}:v{version}   ← 每一轮驳回各自成条
```

**自查方法**：问自己一句——「这个对象在它的生命周期里，同一个 `biz_type` 会发生几次？」答案大于 1，`dedupe_key` 里就必须有区分那几次的东西。

### 5.4 什么时候可以不填

`dedupe_key` 是选填。如果你的事件**天然不会重复触发**、且**上游有幂等保证**（`event_id` 已经足够），可以不填。不填等于「每次都是新消息」，不会被合并。**拿不准时不填**——多一条重复消息，比少一条真实消息安全得多。

## 6. 文案与多语言

### 6.1 两种承载方式，优先用第一种

| 方式 | 怎么填 | 什么时候用 |
| --- | --- | --- |
| **模板 key + 参数**（推荐） | `title_key` / `body_key` + `params` | 绝大多数业务消息 |
| 双语成品快照 | `title_snapshot_i18n` / `body_snapshot_i18n`，中英各一份 | 运营公告等每条内容都不同、无法模板化的场景 |

**为什么优先模板 key**：站内信的语言在**展示时**按用户当前语言渲染。用户切到英文，历史消息立刻是英文；文案写错了改模板即可对历史消息一并生效。快照做不到后者。

### 6.2 `params` 的规矩

- 占位符用 `{snake_case}`，例如 `{amount}`、`{due_date}`、`{business_name}`。
- **时间传 UTC 原值**，不要自己格式化——展示层会按接收者时区渲染。
- **金额传数值 + 币种**，不要自己拼字符串——展示层按平台统一格式渲染。
- **敏感信息你自己脱敏后再传**：完整邮箱、完整钱包地址、完整 IP、证件号**不得**进入 `params`。
- ❌ **禁止拼接句子片段**：不要写 `{action} 已完成` 然后把「审核」传进 `{action}`。中英语序不同，片段拼接必然在某个语言下产生病句。需要不同措辞就用不同的模板 key。

### 6.3 缺失会怎样

| 情况 | 表现 |
| --- | --- |
| 当前语言缺翻译 | 回落英文 |
| 英文也缺 | 降级为「分类 + 时间」的最小形态，**绝不把文案 key 显示给用户** |
| `params` 少了某个变量 | 该占位符渲染为空，不显示 `{xxx}` 原文，服务端记告警 |
| **文案完全没提供** | **服务端拒收**——一条没有任何内容的消息不能进用户的列表 |

## 7. 跳转目标：三选一

| 形态 | 什么时候用 | 怎么填 |
| --- | --- | --- |
| **业务资源** | 跳到某一条具体记录（订单、申请单、账单） | `biz_ref = { resource_type, resource_id }`，并在登记表补路由模板与预检接口 |
| **静态页面** | 跳到一个固定页面（账户设置、用户中心） | `page_target = 页面编号`，不需要预检 |
| **无跳转** | 纯告知，没有可去的地方 | 两个都不填 |

**三条硬规矩**：

1. **绝不存 URL**。前端路由会重构，历史消息不可能批量改写。只存业务类型 + 资源标识，或页面编号。
2. **两者互斥**，同时填会被拒收。
3. **「无跳转」是正常形态，不是缺失**——详情页不渲染按钮，也不会显示任何「暂不支持跳转」的提示。

**关于预检**：跳业务资源时，如果那条记录**可能已经被处理掉、被删除、或用户已无权访问**，就要提供预检接口，返回 `resource_deleted` / `state_changed` / `no_permission` 之一。消息模块会据此禁用跳转按钮并说明原因，而不是把用户带到一个进不去的页面。

> 典型场景：用户一周后才点开「请补充材料」的消息，而该申请已经重新提交并通过了。有预检 → 显示「该业务状态已变更，无需再处理」；没预检 → 用户跳到一个已经不能操作的页面。

## 8. 接入 Checklist

按顺序自查，全部通过再提交接入。

| # | 检查项 | 通过标准 |
| --- | --- | --- |
| 1 | 事件是否幂等 | 每次触发有稳定唯一的 `event_id`，重试不产生重复消息 |
| 2 | `end` 与 `recipient_scope` 是否正确 | 两端都要知道 → 产出两条；管理员个人消息用 `admin_account` 而非 `admin_all` |
| 3 | 接收者标识是否齐备 | 按 scope 填对应字段 |
| 4 | `category` 是否已登记 | 在 4.1 的枚举里；需要新增时说明理由 |
| 5 | `biz_type` 是否合规 | 三段式、一级域已登记、不与现有取值重复、不使用保留段 |
| 6 | 跳转目标形态是否明确 | 三选一，**不得同时填** `biz_ref` 与 `page_target`，且都不含 URL |
| 7 | `page_target` 的端是否一致 | 资产端消息不得指向 `P-M*`，反之亦然 |
| 8 | 需要预检的是否提供了预检接口 | 目标记录可能失效的，必须提供，返回三种失效原因之一 |
| 9 | 路由与预检是否已登记 | 在 3.4 的登记表中补齐 |
| 10 | 文案是否用模板 key | 是；用快照的说明原因 |
| 11 | `params` 是否完整、是否合规 | 变量齐全、时间传 UTC、金额传数值、无句子片段、已脱敏 |
| 12 | **`dedupe_key` 是否会误合并** | 按第 5 章自查：同一对象同一 `biz_type` 会发生多次的，键里必须有区分那几次的标识 |
| 13 | 是否需要有效期 | 有时效的消息设置 `expire_at` |
| 14 | 进度类消息是否带 `progress` | `category = business_progress` 时，`biz_name_key`、`node_key`、`node_status` 齐备 |
| 15 | `node_status` 是否取自四态 | `in_progress` / `action_required` / `succeeded` / `failed`，**不得自行扩展** |
| 16 | `subscribable` 是否声明正确 | 缺省 `false`；安全 / 账户 / 认证与合规**永远** `false`。**只作用于站内消息** |
| 17 | 是否误以为本模块会替你发邮件 | 不会。站外触达归你自己，契约里没有渠道字段 |
| 18 | 敏感信息是否已脱敏 | 完整邮箱、钱包地址、IP、证件号不得进入任何字段 |

## 9. 最小完整接入示例

以一个尚未立项的「放款」模块为例，走完整流程。**示例中的字段取值是虚构的，只用于说明形态。**

### 9.1 场景

放款业务有三个需要通知用户的时点：放款审批通过、款项已到账、放款失败需要用户处理。

### 9.2 第一步：申请命名

一级域 `disbursement` 已在 3.2 中预留，直接使用：

| 事件 | `biz_type` | `category` | 理由 |
| --- | --- | --- | --- |
| 放款审批通过 | `disbursement.order.approved` | `business_progress` | 流程节点 |
| 款项已到账 | `disbursement.order.credited` | `finance` | 钱发生了变化，不是流程节点 |
| 放款失败需处理 | `disbursement.order.failed` | `business_progress` | 流程节点，且需要用户动作 |

在自己的 PRD 中声明这三个取值，交消息模块维护方合入 3.4 的登记表。

### 9.3 第二步：登记跳转

三条消息都跳到放款单详情页，需要预检（放款单可能被撤销）：

| 项 | 取值 |
| --- | --- |
| `biz_ref.resource_type` | `disbursement.order` |
| `biz_ref.resource_id` | 放款单号 |
| 路由模板 | `/financing/disbursement/{resource_id}` |
| 预检接口 | 由放款模块提供，返回 `resource_deleted` / `state_changed` / `no_permission` |
| 页面编号 | 申请 `P-A30` 起的段位 |

### 9.4 第三步：构造一条消息

「放款失败需处理」这条的完整字段：

| 字段 | 取值 | 说明 |
| --- | --- | --- |
| `event_id` | `disb-20260908-000123-failed` | 重试用同一个值 |
| `end` | `asset` | 给用户看 |
| `recipient_scope` | `account` | 单个用户 |
| `recipient_account_id` | 该用户的 `account_id` | — |
| `category` | `business_progress` | 流程节点 |
| `biz_type` | `disbursement.order.failed` | 已登记 |
| `biz_ref` | `{ "resource_type": "disbursement.order", "resource_id": "D20260908000123" }` | 不存 URL |
| `title_key` | `msg.disbursement.order.failed.title` | — |
| `body_key` | `msg.disbursement.order.failed.body` | — |
| `params` | `{ "order_no": "D20260908000123", "amount": 500000, "currency": "USDT", "reason_key": "reason.bank_rejected" }` | 金额传数值 + 币种，不拼字符串 |
| `progress` | `{ "biz_name_key": "biz.disbursement", "node_key": "node.disbursement.remit", "node_status": "action_required" }` | 需要用户处理 → `action_required` |
| `dedupe_key` | `disbursement.order.failed:D20260908000123:attempt3` | **同一放款单可能失败多次，键里带尝试次数** |
| `created_at` | 事件发生时间（UTC） | — |
| `subscribable` | `false`（缺省） | 资金类不可退订 |

> 这条业务同时需要邮件告知？**那是放款模块自己的事**——自行发送，与本契约无关，也不需要在这里填任何字段。
| `source_module` | `disbursement` | — |

### 9.5 第四步：自查

对照第 8 章的 18 项。**重点看第 12 项**：同一张放款单可能失败多次（换卡重试、银行二次拒绝），所以 `dedupe_key` 里带了 `attempt3`——如果只写 `disbursement.order.failed:D20260908000123`，第二次失败会把第一次的消息就地覆盖，用户看不到失败过两次。

### 9.6 用户看到什么

| 位置 | 展示 |
| --- | --- |
| 铃铛角标 | 未读数 +1 |
| 列表项 | `[业务办理进度] 放款 · 当前节点：银行汇款 [待你处理] · 2 小时前` + 正文摘要 |
| 详情页 | 完整正文 + 「查看业务详情」按钮（跳放款单详情，进入详情时预检一次） |
| 一周后再点 | 若该放款单已重新发起并成功，预检返回 `state_changed`，按钮禁用并说明「该业务状态已变更，无需再处理」 |

**放款模块需要实现的部分到此为止**：产出消息 + 提供预检接口 + 提供文案 key。列表、角标、已读、跳转、失效表现全部由消息模块承担，**不需要改消息模块的任何代码或 PRD**。

## 10. 禁止事项

| # | 禁止 | 后果 |
| --- | --- | --- |
| 1 | **在 `biz_ref` 或任何字段里存 URL / 路径 / 深链** | 前端路由重构后历史消息全部跳到死链，且无法批量修复 |
| 2 | **`biz_type` 使用保留段** `test` / `demo` / `tmp` / `notification` / `platform` | 前三个直接拒收；后两个是平台保留域 |
| 3 | **`biz_type` 登记后改名** | 历史消息的映射全部失效 |
| 4 | **自行扩展 `node_status` 四态** | 状态标签是全平台统一的视觉语言，各造一套颜色语义后用户无法建立稳定认知 |
| 5 | **把安全 / 账户 / 认证与合规类声明为 `subscribable = true`** | 用户能关掉安全告警，等于在账户被接管时失去唯一通道 |
| 6 | **把管理员个人消息发成 `admin_all`** | 泄漏同事的账号安全动作，并污染全体管理员的未读数 |
| 7 | **在 `params` 里传完整邮箱 / 钱包地址 / IP / 证件号** | 违反平台脱敏口径 |
| 8 | **拼接句子片段作为参数** | 中英语序不同，必然在某个语言下产生病句 |
| 9 | **自己实现一套消息列表 / 未读角标 / 已读逻辑** | 两套已读状态必然不一致，用户会看到「点开了还是未读」 |
| 10 | **期待本模块替你发邮件 / 短信** | 本模块只做站内信。站外触达归你自己，契约里没有渠道字段，填不进去也不会生效 |
| 11 | **同时填 `biz_ref` 与 `page_target`** | 直接拒收 |
| 12 | **靠消息模块做业务频控**（「同一笔业务每天最多 N 条」） | 消息模块不做这类限流——静默丢弃业务方认为必要的通知比多发几条更危险。频次控制在你自己那边做 |
| 13 | **为了接入去改消息模块的规则** | 如果非改不可，说明规则不通用——提出来，由消息模块修订并对所有模块一体生效 |

## 11. 遇到问题找谁

| 情况 | 怎么办 |
| --- | --- |
| 规则里没写到你的场景 | 提给消息模块。**这是规则的缺陷，不是你的例外**——规则会补充并对所有模块生效 |
| 需要 `enterprise` / `broadcast` 这类本期未实现的能力 | 先确认排期，不要自己变通（例如给企业下每个账户各发一条） |
| 页面编号段位不够用 | 申请新的十位段，更新 4.2 的表 |
| 不确定该用哪个 `category` / `recipient_scope` | 看 4.1 与 2.2 的判断标准；仍不确定时选**更保守**的那个（范围更小、不可退订） |
| 需要邮件 / 短信触达 | **不找本模块**。站外渠道归你自己实现（`v1.0-消息通知-PRD.md` 2.4） |
