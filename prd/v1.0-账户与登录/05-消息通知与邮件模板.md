### 12.5 通知矩阵（供通知投递服务与消息通知模块消费）

本节定义本模块产生的账户与登录类通知：**什么时候发、走哪个渠道、发什么内容、归哪个分类、跳到哪里、重复触发怎么处理**。

> **边界**：站内信的**展示形态**——通知中心页面、铃铛入口、未读角标、单条已读与全部已读、列表筛选与分页——全部归消息通知子需求，本文档不定义。本模块只产出事件与内容。

#### 12.5.1 渠道分工结论

> **判断方法归 WS-304。** 渠道该怎么选——三个判断维度与各场景的默认组合——由 WS-304《消息通知》`02-数据契约与字段.md` 9.9.1「渠道选择原则」统一定义，本模块不再自写一套。本节只给出**本模块各事件套用该方法后的结论**。

**不是所有事件都双发。** 按 WS-304 9.9.1 的判断维度，本模块保留的事件归为两类：

| 事件类别 | 渠道 | 本模块的事件 |
| --- | --- | --- |
| **登录前事件** | 仅邮件 | E-11 账户被锁定 |
| **敏感变更** | 邮件 + 站内信 | E-03 绑定钱包、E-05 密码变更、E-10 邮箱绑定或变更 |
| **敏感变更（无站内可投）** | 仅邮件 | E-09 通知旧邮箱 |

**账户被锁定是典型的登录前事件，站内信在这里没有意义**：用户正因为被锁而进不来，锁定期最长 30 分钟，等他能登录看到站内信时锁早就解了，这条消息只剩考古价值。因此该事件**明确只走邮件，不产出站内信**——这是有意的判断，不是遗漏。

#### 12.5.2 通知矩阵总表

| # | 事件 | 触发时点（精确到某一步成功之后） | 类别 | 渠道 | 分类 | 跳转 |
| --- | --- | --- | --- | --- | --- | --- |
| E-03 | 首次绑定钱包 | 验签通过且签名地址与手填地址一致、绑定关系落库之后 | 敏感变更 | 邮件 + 站内信 | 安全 | P-A11 账户设置 |
| E-05 | **密码变更**（设置 / 修改 / 重置，三种情形合并） | 新密码哈希落库之后、会话批量失效之前 | 敏感变更 | 邮件 + 站内信 | 安全 | P-A11 账户设置 |
| E-09 | 修改邮箱 · 通知旧邮箱 | 邮箱绑定关系落库之后，发往**被替换掉的旧邮箱** | 敏感变更 | **仅邮件**（见 12.5.4） | 安全 | 无 |
| E-10 | **邮箱绑定或变更 · 通知该邮箱**（首次绑定与变更合并） | 新邮箱验证码校验通过、邮箱绑定关系落库之后 | 敏感变更 | 邮件 + 站内信 | 安全 | P-A11 账户设置 |
| E-11 | 账户被锁定 | 失败计数达到 5、`locked_until` 与 `lock_tier` 落库之后 | **登录前** | **仅邮件** | 安全 | 无 |

**不产生通知的事件**（明确列出，避免被当作遗漏）：

| 事件 | 原因 |
| --- | --- |
| 自动建号成功 | 用户就在屏幕前，引导页顶部已有显著的建号确认区块；补齐凭据的提醒由常驻提示条 C-08 长期承担 |
| 凭据补齐完成 | 用户当场补完，界面即刻提示「已完成，你现在可以发起个人认证了」，提示条同时消失 |
| 锁定自动解除 | 时间到期的自动事件，无「是不是你本人」的告警价值；锁定邮件已告知预计解除时间；且对攻击者是「可以继续试了」的提示 |
| 其他设备会话被强制退出 | 总是由用户自己的敏感变更引起，信息并入对应变更事件的正文，不单独成条 |
| 登录成功（常规） | 高频事件，逐次通知是纯噪音；本期无设备识别能力，无法只对"新设备登录"告警 |
| 登录失败、签名地址不一致被拒 | 单次失败噪音大；连续失败会走 E-11 锁定通知 |
| 语言 / 时区偏好变更 | 非安全相关，用户当场就能看到结果 |
| 管理端账号的创建、停用、初始密码重置、首登强制重置 | 管理端本期不产生任何通知 |

#### 12.5.3 站内信文案（中英双语）

变量占位符的取值见 12.5.5。正文均为实际文案，可直接实现。**站内信共 3 条**——只有既是敏感变更、又有站内可投对象的事件才产出站内信。

| # | 站内信标题（EN / 中文） | 站内信正文（EN / 中文） |
| --- | --- | --- |
| E-03 | Wallet linked<br>钱包已绑定 | The wallet address {address_short} was linked to your account on {time}. Your wallet address can't be changed after linking — keep this wallet accessible.<br>钱包地址 {address_short} 已于 {time} 绑定到你的账户。钱包地址绑定后不可修改，请妥善保管该钱包。 |
| E-05 | Your password was {password_action}<br>登录密码已{password_action} | Your password was {password_action} on {time} from {device}. All devices were signed out.<br>你的密码已于 {time} 在 {device} 上{password_action}，所有设备均已退出登录。 |
| E-10 | Email address updated<br>账户邮箱已更新 | This address became your account email on {time} from {device}. {email_change_note}<br>该邮箱已于 {time} 在 {device} 上成为你的账户邮箱。{email_change_note} |

> E-09（通知旧邮箱）与 E-11（账户被锁定）只走邮件，不产出站内信，因此不在本表中。

> **本表只是站内信文案。邮件文案不复用本表，全部单独定义在 12.6「邮件模板」**，包括本表未覆盖的 E-09、E-11 两条只走邮件的事件。两者为什么不能共用一份文案，见 12.5.8。

#### 12.5.4 三条需要明确的判断

**① 修改邮箱的旧邮箱通知只走邮件**

旧邮箱在变更完成后已不再是该账户的邮箱，但它仍是"发现账户被接管"最关键的一条外部通道——如果是攻击者改的邮箱，受害者只能从旧邮箱得知。而站内信是发给**账户**的，账户此刻已归属新邮箱，E-10 那条站内信已经完整覆盖了"邮箱变更了"这件事，再为旧邮箱产出一条站内信既无处投递也无意义。

**② 锁定自动解除不发任何通知**

- 它是**时间到期的自动事件**，不是任何人的操作，没有"是不是你本人"的告警价值；
- E-11 的锁定邮件里**已经写明了本次预计自动解除时间**，用户已经知道什么时候能再试；
- 更重要的是，这条通知对攻击者同样是一次"现在可以继续试了"的提醒，属于负收益。

**③ 会话强制退出并入触发它的变更事件，不单独发**

本模块中，其他设备被强制退出**总是**由用户自己的某次敏感变更引起（改密码、设密码、重置密码、改邮箱）。若在变更通知之外再单独发一条"其他设备已退出"，用户改一次密码会连收两条内容高度重叠的消息。因此该信息**并入对应变更事件的正文**（见 12.5.3 中 E-05、E-10 正文里的"所有设备均已退出登录"一句），不单独成条。

> 若后续引入了非用户自身操作导致的强制下线（例如管理员强制踢出），那属于新的独立事件，届时应单独定义，不适用本条合并规则。

#### 12.5.5 变量占位符取值

| 占位符 | 取值 | 说明 |
| --- | --- | --- |
| `{time}` | 事件发生时间 | 按接收者的账户时区渲染并带时区标注，格式遵循 13.4；存储仍为 UTC |
| `{device}` | 设备摘要 | 取 `Session.device_summary`：浏览器 + 操作系统 + IP 归属地（如 `Chrome on macOS · Shanghai, CN`）。**不含完整 IP** |
| `{email_mask}` | 邮箱掩码 | 按 [12.4](./04-安全与风控.md) 的脱敏规则渲染为 `a***@example.com` |
| `{address_short}` | 钱包地址缩略 | 前 6 位 + `…` + 后 4 位，格式遵循 13.5 |
| `{unlock_time}` | 本次锁定的预计自动解除时间 | 由 `locked_until` 渲染，格式同 `{time}`；仅 E-11 邮件使用 |
| `{password_action}` | 密码变更的具体情形 | E-05 用它区分三种情形：`set / 设置`、`changed / 修改`、`reset / 重置` |
| `{email_change_note}` | 邮箱事件的情形补充 | E-10 合并首次绑定与变更后用它区分：**首次绑定**取 `You can now sign in with an email code, and we'll send security alerts here. / 你现在可以使用邮箱验证码登录，我们也会将安全通知发送至此。`；**由旧邮箱变更而来**取 `All devices were signed out. Sign in with this address from now on. / 所有设备均已退出登录，今后请使用该邮箱登录。` |
| `{action_guidance}` | 「不是本人操作」的处置指引 | 仅邮件使用，按情形取值，见 12.6.2 的 M-04 |

#### 12.5.6 各事件的去重键

> **去重的通用语义归 WS-304**：各渠道独立去重、去重键的构造规范、合并后恢复未读等规则，由 WS-304《消息通知》`02-数据契约与字段.md` 9.9.3「跨渠道去重」统一定义，本模块不再重复。本节只给出**本模块各事件的去重键取值**。

| 事件 | 去重键 |
| --- | --- |
| 通用事件 | `account_id + biz_type + 时间窗`，时间窗取 N-22（默认 5 分钟） |
| 账户被锁定（E-11） | `account_id + locked_until`——按**本次锁定周期**而非时间窗口，同一次锁定只发一封邮件，用户在锁定期内反复尝试不会触发第二封 |
| 首次绑定钱包（E-03） | `account_id`，每个账户**终身只发一条**（钱包绑定后不可修改，只会发生一次） |

#### 12.5.7 各类账户的通知覆盖差异

加入站内信之后，不同凭据组合的账户在通知覆盖上有实质差异，实现与测试时需要按类覆盖：

| 账户类型 | 邮件 | 站内信 | 说明 |
| --- | --- | --- | --- |
| 有邮箱 + 有钱包（`active`） | ✅ 全部邮件事件 | ✅ 全部站内信事件 | 覆盖最完整 |
| **只有钱包**（钱包建号且未补邮箱） | ❌ **无法送达任何邮件** | ✅ 全部站内信事件 | **本轮之前，这类账户收不到任何安全通知**；引入站内信后它们才第一次有了通知渠道。但**登录前事件（E-11 账户被锁定）对它们仍是完全不可达的**——既没有邮箱可发，站内信又看不到。这类账户被锁定时只能从界面上的锁定提示得知 |
| 只有邮箱（邮箱建号且未补钱包） | ✅ 全部邮件事件 | ✅ 全部站内信事件 | 与完整账户一致 |

**实现要求**：账户 `email` 为空时该邮件**静默跳过**，不报错、不阻断触发它的业务操作（例如不能因为发不出邮件而让「设置密码」失败）。这两条属通用投递语义，由 WS-304《消息通知》`02-数据契约与字段.md` 9.9.2 的三条强制规则统一约束，**执行方是通知投递服务**；本模块只需保证 `channel_targets` 为空时如实留空。

#### 12.5.8 邮件与站内信不是同一份文案

**结论：不一致，且不能复用。** 同一个事件在两个渠道上是两种写法，实现时必须各写一份。

| 维度 | 站内信 | 邮件 |
| --- | --- | --- |
| 读者状态 | **已登录、正在站内**，刚做完或刚经历这件事 | **可能几天后才打开**，打开时不在站内，甚至已经忘了上下文 |
| 上下文来源 | 可以短——不懂就点跳转，落到页面上自然明白 | **必须自解释**，邮件里没有可点的账户设置页，看完就得懂发生了什么 |
| 必备信息 | 事件 + 一句结果 | 事件 + **发生时间** + **大致地区 / 设备摘要** + **「不是你本人操作？」的处置指引** |
| 结构 | 标题 + 正文两段 | 发件人显示名 + **主题行** + **预览文本** + 正文 + 行动指引 + **页脚**（合规信息） |
| 语言 | **展示时**跟随用户当前语言，切换语言后历史消息随之变化 | **发送时**固定，已投递的邮件无法改写（见 [13.2](./02-页面字段与双语文案.md)） |
| 隐私约束 | 站内可见范围仅本人，可展示掩码后的邮箱与缩略地址 | 受 12.4 约束更严：**不出现完整邮箱、不出现明文密码、不出现完整钱包地址、不出现完整 IP**，因为邮件可能被转发、被网关扫描、被留存在第三方邮箱服务器上 |
| 覆盖事件 | 见 12.5.3（3 条） | 见 12.6（8 个模板，含站内信没有的 E-09、E-11，以及不属于通知范畴的验证码邮件） |

> 举个具体差别：修改密码这件事，站内信写「你的密码已于 {time} 在 {device} 上修改，所有设备均已退出登录」就够了，用户此刻就在站内、刚做完这个操作；同一件事的邮件则必须再补上「如果这不是你本人的操作，请立即重置密码并检查邮箱账户是否安全」以及页脚的客服联系方式——因为收到这封邮件的人可能正是那个"账户被别人改了密码"的受害者，他此刻登不进去，邮件是他唯一的线索和求助入口。

### 12.6 邮件模板

本章定义本模块发出的**全部邮件**的可实现模板。分三组：与站内信同源的敏感变更类（M-02、M-04、M-07）、只有邮件没有站内信的（M-08、M-09）、验证码类（M-10～M-12）。

变量占位符沿用 12.5.5 的体系，不另起一套；品牌与合规类占位符集中在 12.6.5，需由需求方提供实际值。

#### 12.6.1 通用结构与规范

##### 12.6.1.1 邮件的六个组成部分

| 部分 | 规范 |
| --- | --- |
| 发件人显示名 | `{product_name}`（见 12.6.5）。安全类邮件统一使用同一个显示名与发件地址，不因事件类型变化——变化会削弱用户对"什么样的邮件是真的"的判断 |
| 主题行 | 统一格式 `{product_name} · <事件短语>`。**带产品名前缀**：安全邮件带品牌名有助于用户辨别真伪，也降低被误判为钓鱼的概率。长度建议：中文 ≤ 20 字、英文 ≤ 50 字符（超出部分在移动端收件箱列表会被截断） |
| 预览文本 | 收件箱列表中紧跟主题行显示的一行摘要，长度建议中文 ≤ 30 字、英文 ≤ 90 字符。**不得把验证码放进预览文本**（理由见 12.6.4.1） |
| 正文 | 实际文案，见各模板 |
| 行动指引 | 「不是你本人操作？」该怎么做。**每封安全类邮件都必须有**，且指引必须是当下真的做得到的事 |
| 页脚 | 公司主体、客服联系方式、隐私政策链接等，见 12.6.5 |

##### 12.6.1.2 HTML 与纯文本双版本

- 每个模板必须同时提供 **HTML 版本**与**纯文本兜底版本**，以 `multipart/alternative` 发送。
- 纯文本版本不是把 HTML 标签去掉了事：链接要写成 `文字（完整 URL）` 的形式，排版靠空行与短横线分隔。
- 判断依据：部分企业邮箱网关会剥离 HTML，纯文本版本是这些用户唯一能看到的内容。本文档在每个模板中给出 HTML 版正文，纯文本版按同一文案去除样式、按上述规则处理链接即可，**文案内容不得删减**。

##### 12.6.1.3 邮箱与敏感信息的呈现

| 信息 | 规则 |
| --- | --- |
| 邮箱 | 正文中提及邮箱一律用掩码 `{email_mask}`（`a***@example.com`）。**唯一例外**：收件人本人的地址出现在收件人字段是必然的，正文中不再重复完整地址 |
| 钱包地址 | 用 `{address_short}`（前 6 后 4） |
| IP | 只给 `{device}` 中的地区摘要，**不出现完整 IP** |
| 密码 | 任何情况下不出现明文密码，也不出现密码提示 |
| 验证码 | 只出现在正文，不出现在主题行与预览文本 |

##### 12.6.1.4 语言

邮件语言在**发送时**按接收者当时的账户语言偏好固定；未设置偏好时用英文（默认语言，见 [13.1](./02-页面字段与双语文案.md)）。已投递的邮件不因用户后续切换语言而改写——这与站内信相反，站内信在展示时跟随当前语言。

##### 12.6.1.5 退信后的界面提示

> **退信的通用处理语义归 WS-304**：软退信不另行重试、硬退信记入审计但不解绑邮箱不改账户状态、任何渠道的失败都不阻断业务操作、地址缺失静默跳过——这四条由 WS-304《消息通知》`02-数据契约与字段.md` 9.9.2「各渠道的投递成功语义」统一定义，**执行方是通知投递服务**，本模块不再重复。

本模块只定义退信在**自己页面上**的表现：

| 情况 | 本模块的处理 |
| --- | --- |
| 硬退信累计达阈值（N-23，默认 3 次） | 在 P-A11 账户设置的邮箱条目下展示一条提示：`We can't deliver emails to this address. / 我们无法向该邮箱送达邮件。` |

> **这条提示只能是告知，给不出解法。** 因为修改邮箱必须先验证旧邮箱（见 [7.6.3](./01-模块详情.md)），而旧邮箱恰恰是送达失败的那个——用户看到提示也改不了。这是 7.5.4 已经写明的产品事实在邮件侧的一个具体表现，不是本章能解决的问题。文案上因此不要写"请更换邮箱"这类做不到的引导。

#### 12.6.4 第 3 组 · 验证码邮件模板

验证码邮件严格说不属于"通知"，是事务性邮件，因此不在 12.5 的通知矩阵内；但它是全系统发出量最大的一类邮件，且带有一条硬约束，故在此定义。

##### 12.6.4.1 三条共同约束

**① 文案不得透露该邮箱是否已有账户**（见 [7.2.1](./01-模块详情.md) 与 AC-13）。

**结论：按用途分三个模板，但同一用途内的文案恒定不变。** 理由：

- 泄漏与否的判定标准是——**同一个入口下，已注册邮箱与未注册邮箱收到的内容是否不同**。只要同一用途的模板对所有人完全一致，就不泄漏。
- 而不同用途之间的差异不构成泄漏：用户点的是哪个入口是他自己选的，他本来就知道。攻击者把受害者邮箱填进「登录」入口，无论该邮箱是否注册，收到的永远是同一封登录验证码邮件——不可区分。
- 反过来，如果三个用途共用一套完全相同的文案，用户在同时进行多个操作时（例如先试了登录、又去改邮箱）会收到两封一模一样的邮件，无法分辨该用哪个码，反而制造实际的使用故障。

**② 不得在邮件中放一键登录链接，只给验证码数字。** 理由：magic link 被转发、被企业邮箱网关预取扫描时会造成账户被接管；且一键链接绕过了本模块「验证码 + 滑块 + 限频」的整套防护模型（见 [12.3](./04-安全与风控.md)），等于开了一个不受这些约束的旁路。

**③ 验证码不出现在主题行与预览文本中。** 理由：主题行与预览文本会出现在手机锁屏通知、邮件客户端列表中，旁人无需解锁设备即可看到。这对一个金融资产平台是不可接受的肩窥面。代价是用户必须打开邮件才能看到验证码，这是有意的取舍。
