# M10 消息中心 · 运营端原型

依据 [`PRD/两端共用/M10-消息中心/`](../../../PRD/两端共用/M10-消息中心/01-消息中心-PRD.md)（提交 `c44f233a`；画面结构首次按 `e5dbee4b` 出屏），页面结构参照代币发行平台 M7 消息通知原型。消息标题与正文取自来源模块现行 03 消息通知册：M7b（NT03）、M8（NT01～02）、M9（NT03）、M15（NT01）。组件规范与本轮 UI 变体见下文。

原型只用于评审页面、字段和主流程；规则、校验与异常分支以 PRD 为准。企业、编号、金额、VIN、时间、调整原因与失败原因均为演示数据；预警、规则、接口与 M8、M15 原型的演示数据一致。

## 打开与路径

双击 [`消息中心.html`](消息中心.html)，或使用离线单文件附件。默认进入消息列表；侧栏底部「画面目录 · 演示数据」默认关闭，可到达全部 51 屏，并提供「主流程下一屏」。

- 入口：右上角账号入口展开后“账户设置”下面的“消息中心”（侧栏不设消息菜单，按 M2 F-OP-08），以及每个运营端页面顶栏的铃铛与未读数。
- 主流程：顶栏铃铛 → P01 最近消息 → 查看全部消息 → L01 消息列表（第一批 20 条）→ D10「有新的确权申请待运营审核 · AP-DEMO-0024」（打开即已读，未读 6 → 5）→ 面包屑回 L12（该条原地变为已读）→ A02 全部已读确认 → A04 处理中 → A06 成功。
- 运营端只有“全体运营”一种收件范围：同一批消息每人各自记录已读；全部已读确认中写明只改变本人的阅读状态。
- 原动作已办完的消息（已由其他运营管理员处理的预警、已审核或已到期关闭的申请）仍可前往，只能查看当前结果。详情中的申请编号、预警编号、规则编号、接口名称是前往原业务的入口，经[仓库联看](../../README.md#仓库联看)进入 M9 申请详情、M8 预警详情或规则详情、M15 接口调用记录；来源模块未画出的一笔提示“该入口尚未纳入原型。”。
- 顶栏铃铛同时接入其他运营端模块；首登改密等受限登录画面不显示。

## 本期不做与未出屏

- 按 PRD 本期不做：发送、编辑、撤回消息与模板；站外消息；删除、归档；逐条标为已读 / 未读；通知开关；发给某一位运营管理员本人的消息与账户安全类消息；查看他人阅读情况；两端未读合计。
- 未单独出屏（以 PRD 为准）：未登录打开消息链接、首次改密后回到原消息、登录失效、新消息自动插入、多标签页同步、新开通账号看到的历史消息直接为已读、分类无法识别归入“其他”。

## 本轮 UI 深化（2026-11-25，WS-683）

产物类型：existing-system adaptation；现有系统桌面控制台。原型代码基线 `096030bc`，结合最新 PRD `647b90c0`（包含 `025bf9d3` 的行为口径）。上游已说明这两次 PRD 修订不需新增画面；本轮只调整呈现，不补写排序、已读保存、登录回跳或消息服务逻辑。

### 设计变化

- 列表按“标题 → 分类及业务识别 → 单行摘要”扫描；未读同时用字重、圆点、文字状态及浅底区分。时间列固定阅读空间，日期与时分分两行；列表保留整行进入详情，不增加统计与查询步骤。
- 详情使用“分类 → 完整标题 → 时间与时区 → 正文 → 相关业务”的阅读顺序；正文在上、相关业务及原业务入口在下，所有宽度纵向排列（2026-11-26 用户裁定替代原宽屏分栏）。完整正文保留换行；业务编号 / 名称沿用原链接，增加下划线和方向图标辨识。
- 顶栏预览沿用最近 10 条，标题两行、摘要一行；时间与已读状态共用弹性行。筛选、数据、原入口和已读 / 未读行为继承原型。
- 全部已读流程统一 600 px 弹窗，范围条件独立浅底分组；原条数、说明、处理中与失败分支继承。列表空、筛选无结果及失败区保留各自反馈和操作。
- 实现与尺寸集中在共享源码，由 `data-module="messages"` 限定 M10 页面；共享预览使用 `.dd.inbox`，不复制共享层。规范见[组件规范的本轮说明](../../_shared/design-system/组件规范.md#m10-消息中心-ui-深化ws-6832026-11-25)。

## 详情上下布局修订（2026-11-26，WS-683）

现有系统桌面控制台的局部呈现修订；基线 `eae0b7fc`，本轮 PRD 最新仍为 `647b90c0`。按本 issue 最新派发，替代上一轮宽屏左右布局：正文在上，相关业务与原入口在下；所有宽度一行一个信息分区，不在宽屏恢复并排。分区内短字段两列、规则名称等长文本通栏，≤900 px 单列；标题、字段与正文的左缘对齐，内边距由原 32 px 收为 24 px（窄屏 20 px）。正文维持完整文本、换行和原阅读宽度，不新增折叠、分区导航或演示状态。

仅改 `_shared/components.css` 的 M10 限定样式，移除 `tokens.css` 无消费者的侧栏宽度 token，并更新两端 README 与组件规范的 M10 条目；通用上下布局规范由 M7b 维护，本轮不代改。已核查 `inbox-pages.js` 的消费者只有 M10 两端；该脚本与消息数据、排序、已读、权限、路由、列表及共享预览均未修改。

本轮实测（Chromium / Playwright）：

- `D01–D24` 与 `S01–S05` 共 29 屏，中英文 × 768 / 1024 / 1280 / 1440 / 1920 px。两端合计 45 屏、450 次检查；其中 41 屏正文 / 相关业务版式修改，4 屏读取失败 / 消息不存在画面继承回归。宽屏始终为正文上、相关业务下，两区等宽且内容左缘对齐；窄屏字段单列，字段标签位于值上方。未发现脚本错误、整页横向溢出、正文 / 业务链接裁切或分区遮挡。
- 双语实测列表键盘焦点 / Enter 进入详情、面包屑返回；企业端 D04 → M7b，运营端 D01 / D03 → M8、D08 → M15、D10 → M9 的原业务入口通过键盘点通。原已读保存失败、内容损坏、原业务无权画面保持，S05 仍无前往入口。列表、最近预览和确认框另作基本打开与溢出回归。

- 本模块为纯文本消息，没有业务表格、附件分区或分区导航；本轮未增加这些内容。未验证：768 px 以下、其他浏览器、屏幕阅读器、真实消息服务及未修改模块的业务流程。上一轮 850 次检查是历史记录，不计入本轮实测。
