# M3 应收账款与发票 · 运营端原型

依据 [`PRD/两端共用/M3-应收账款与发票/`](../../../PRD/两端共用/M3-应收账款与发票/01-应收账款与发票-PRD.md)，最新需求提交 `1707c18`；申请状态名称与进度条环节按 M7a 应收查看与确权申请；车辆的履约进展、付款情况、收款情况按 M5、M4、M6 原样展示。组件规范 v1.28。

原型只用于评审页面、字段和主流程；规则、校验及异常分支以 PRD 为准。企业、编号、金额、VIN、日期、银行账号和文件均为演示值；Carloha Holding / Carloha Nigeria 不代表实际业务主体。

## 打开与路径

双击 [`应收账款与发票.html`](应收账款与发票.html)，或使用离线单文件附件；无需服务。左侧菜单“资产数据 / 应收账款”进入列表。侧栏底部“画面目录 · 演示数据”默认收起，列出全部画面和“主流程下一屏”。

列表编号或右侧“查看”进入演示详情：AR-DEMO-0012 / 0019 / 0021 / 0008，其他演示行提示“演示仅提供部分应收账款的详情画面。”。申请编号、风控入口，以及车辆信息明细中的 VIN、外采订单号、销售合同号经[仓库联看](../../README.md#仓库联看)进入 M9 / M8 / M5 / M4 / M6 已有画面；对方模块尚未画出的记录（如 PO-DEMO-047、PO-DEMO-044、SC-DEMO-2039、VIN LDEMOVIN000000012）提示“该入口尚未纳入原型。”。单文件附件中跨模块入口统一给范围提示。

主流程：O1 列表 → O5 详情 → O6 差异待核实 → O7 记录核实 → O8 核实已记录。

## 详情结构

0. **页头**：债权人 → 债务人企业名称为首要信息；应收账款编号、发票号码与时区在其下的说明行。
1. **应收账款概要**（页头下方）：应收账款金额、应收账款到期日（ERP 时区跟随日期）、账款起算日、天数；右侧到期状态、回款状态、预警信息。企业名称已在页头，不重复。核心资料状态不单独展示，差异明细在底部“资料追溯”。
2. **确权与审核进度**：紧接概要。发起申请 / 债务人确认 / 运营审核三环节，状态与环节对应按 M7a；申请编号旁显示申请状态。
3. 发票信息与附件 → 4. 车辆信息明细 → 5. 合同信息 → 6. 回款信息（先统计、后 ERP 收款明细）。

车辆信息明细每车一行：VIN（下方履约进展，进入 M5 车辆履约详情）、车型、单价、外采订单号（下方付款情况，进入 M4 采购交易详情）、销售合同号（下方收款情况，进入 M6 销售交易详情）。多笔采购 / 多笔销售逐条列出；“买方不一致 / 卖方不一致”进入 M4 / M6 的按应收账款追溯；“未找到上游采购 / 暂无下游销售”不可点击。不展示车辆数量、明细合计与车辆明细附件。演示号码与状态取自 M4、M5、M6 现有画面；O11（AR-DEMO-0008）沿用 AR-DEMO-0012 的车辆演示数据。
7. **资料追溯**（仅运营）：核心资料差异、核实记录、关联风控预警。资料按 ERP 最新内容展示，不提供补充记录（PRD 94ccac6 §4.3）。

预警信息为“有”的口径（未处理的 M8 预警含回款预警，或核心资料差异待核实）以 PRD 为准，原型只展示结果。

## 待确认与未覆盖

- “运营审核通过”只改变进度条文字（运营审核：通过），版式与其他进行中状态相同，未单独出屏。出库环节待 M9 定义后接入进度条。
- 跨模块真实入口、并发核实、提交失败等以 PRD 为准；未将静态页面当作真实服务。
- ERP 回款八列表格在 1440 px 以下宽度于表内横向滚动（沿用既有下限 1240 px）。

## 实际核验（v1.28）

Chromium / Playwright，中英文 × 1280 / 1440 / 1920 px：11 屏无脚本错误、无整页横向溢出，英文模式无未翻译文案。仓库联看中实测 VIN → M5（v-delivered、v-hints）、订单号 → M4（d-detail）、合同号 → M6（d-detail）、买方 / 卖方不一致 → M4 / M6 追溯（t-trace-multi）均到达对应画面，未画出的记录给范围提示。单文件附件在独立目录断网打开，样式与主流程正常、无外部请求。其余 13 个模块在两种语言、三档宽度回归加载、脚本错误与整页溢出；未重跑其业务流程。未验证 1280 px 以下、屏幕阅读器与真实服务。
