**关键阻断项**（单列，不计入平均分，任一失败即不能发布）：

- B1 首次改密前进入平台，或绕过入驻步骤访问业务或账户信息接口（AC-12、27）。
- B2 账号枚举：登录、找回、发码时，有效邮箱和无效邮箱的提示、表现、等待与限额或响应快慢可以区分（AC-09、18）。登录时，格式不正确的邮箱同样不能与不存在的邮箱区分（01 册登录邮箱的输入规则）。
- B3 跨企业取得账户信息、组织资料或联系信息，或“不存在”和“无权查看”能区分（AC-39、43）。
- B4 钱包被更换、解绑、重复绑定，或用不一致的地址或签名完成绑定（AC-30、32～34）。
- B5 邮件、页面提示或安全记录中出现明文密码、验证码或签名原文（AC-06；03 册“不得出现”）。
- B6 应当结束全部登录的事件发生后，任一设备或标签页仍能取得受保护数据。事件以 01 册 M1-F11 表为准，共 8 种（AC-14、16、24、46、51、52、53、54、58）。

**跨模块文档不一致（登记，不作为挂起理由）**

- 原 Q1 已确认：M1 相关 Case 一律按 M1 判定。
- M2 现行文本（`3d79991a` 中的 M2 01 册）仍与 M1 不一致，有两处：
  - “开发人员更正登录邮箱”一节写两种情况处理结果相同：都重新生成初始密码、发企业邀请邮件、须改密。
  - 相邻模块一节（第 690 行）写“密码状态回到待首登改密”。
- M1 现行口径：已完成首次改密的账号，由开发人员线下提供新邮箱和新密码，不发邮件，密码状态不变，直接登录。
- M2 也没有写入 M1 新增的登录邮箱输入规则（全角空格、零宽字符、不支持国际化域名）。
- 处理方式：
  - 这两点由 WS-672 同步。在 M1 Eval 中只登记，不影响 M1 的判定和发布门槛。
  - 运营端的展示和操作记录不在本 Eval 判定，归 M2 Eval。

## 2. Case 数量与覆盖

**规模**

- 计划数量（本文没有生成完整用例集）：
  - 启动集约 205 条原子 Case。由 53 条 AC 拆分得到：一条 AC 中的每个场景、每个样本值拆成一条可单独判定的 Case。`3d79991a` 在 AC-08、09、19、31、37、45、47、55、57、58 中补充了样本，拆分时一并纳入。
  - 另加约 35 条 PRD 有规则、但 AC 没有单列的补充 Case，标为“PRD 派生”。
- 实际生成数量：本文只给出下表 30 条代表性 Case，其余由测试小队按扩充规则编写。
- 稳态规模：每个维度 50～200 条。D1、D3 优先扩充：每次评审变更或线上缺陷至少补 1 条回归 Case。

  - 删去账户信息的更正提示；

- 风险覆盖集和统计集分开管理：上表是风险覆盖集，有意加重了对抗类比例，只用于判断能否发布，不用来推断真实用户体验。真实体验看第 5 节的 L3 线上指标。

## 3. 通过线

以下数值都是**建议、待业务确认**。依据如下：

- M1 是规则明确的确定性功能，任何偏离都是缺陷；
- 错误成本高：钱包地址是外部代币发行平台和借贷平台识别企业身份的依据；
- 兜底手段有限：钱包绑定后不能更换，账号被冒用后只能靠开发人员线下更正邮箱。

**统计与随机性**

- 确定性 Case 每次执行一次。失败后在干净环境重跑 1 次，用来排除环境问题；重跑通过时仍记为“不稳定”，要排查原因，不能直接算作通过。
- 时限类 Case 一律用时间控制注入平台时间，不用真实等待。“恰好到达”按平台时间判定，页面上的倒计时只作为展示检查。
- 并发和竞态类 Case（C-D1-10、C-D2-02，以及 AC-34、57）：每条重复 n 次，建议 n ≥ 50。零失败只说明失败率较低，**不能证明没有竞态**。零失败时，95% 单侧上界约为 3／n（n = 50 时约 6%）。比例指标用 Wilson 区间报告。
- 响应快慢不可区分（B2 和 C-D1-01）：
  - 每类邮箱（不存在、格式不正确、运营账号、企业邮箱加错误密码）各请求至少 200 次，交替执行，并固定网络环境；
  - 两两比较，用 Mann-Whitney U 检验加中位数差判断；
  - 显著性水平和可接受的中位数差见 Q3。
- 签名失败降速（C-D2-08）：等待时长由研发确定，不设数值门槛。只做二元判定：超过 20 次后出现提示，不封禁、不锁账号，不影响其他网络地址，等待结束后可以继续。
- 版本比较按同一 Case ID 配对，看 Case 在新旧版本之间从通过变失败、从失败变通过的情况，不只比较总通过率。
- 本文没有执行数据，所以不填写任何区间、通过率或显著性结论。

**失败兜底**（发布判断之外的处置，建议）

- 阻断项失败：不能发布，由安全评审确认修复后，重跑该维度的全部 Case。
- 邮件投递类失败：PRD 规定投递失败不回滚变更。评估只检查“不回滚”和“不虚报已发送”这两点，投递成功率本身看 L3 监控。

**待确认（本节）**

- Q3【归测试与研发（安全）确定，PRD 不写数值】“响应快慢不能区分”的量化方法。
  - 本文建议：中位数差 ≤ 50 ms，且 Mann-Whitney U 检验在 p < 0.01 下不显著。
  - 在测试与安全确定前，C-D1-01 和 B2 的耗时部分只记录数据、不出通过结论，提示与表现部分照常判定。
- 发布门槛的具体数值（P1 98%、P2 95%）由产品和测试负责人确认。
- 已按 `3d79991a` 关闭：
  - Q4：长度按看到的字符计数；

**L3 线上验证**（上线后，只看真实流量，和风险覆盖集分开统计）

- 观察指标，阈值都待业务确认：
  - 首次改密完成率；
  - 入驻漏斗：设置密码 → 绑定钱包 → 提交资料，各步的流失和失败原因分布；
  - 钱包绑定失败原因分布：地址不一致、拒绝签名、网络不对；
  - 签名失败超限提示的出现次数；
  - 找回密码成功率；
  - 锁定触发率；
  - 验证码投递失败率；
  - 越权拒绝次数；
  - 开发人员更正登录邮箱的次数。
- 关于开发人员更正登录邮箱：
  - 线下交付的新密码不经过强制改密，可以一直使用。PRD 输出已在本次提交中提示这一风险。
  - L3 只观察这类账号此后自行修改密码的比例，作为风险参考，不作为 M1 的发布门槛。
  - 是否要求改密，由业务方决定。
- 这些都是线上代理指标，只说明“流程是否通畅”，不等于入驻资料真实有效。PRD 本身不审核资料内容。
- 越权拒绝次数突增、同一 IP 发码或签名失败激增，作为安全告警的信号交给运维，不在 Eval 中处理。
