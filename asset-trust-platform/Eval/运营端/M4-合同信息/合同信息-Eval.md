## 1. 评估维度（3–5 个）

**评估范围与前提**

- 被评对象是 M4 合同信息模块本身：运营端只读页面，包括三个页签的列表和详情、执行进度的计算与展示、跨模块的取值与跳转。M4 不含模型能力，所以本 Eval 以确定性判定为主，人工评审只用于图表和展示。
- 不在范围内：M3、M5、M8、M11、M14 自身的规则正确性（只核对 M4 取值与它们是否一致）；ERP 的取数接口；原型画面（PRD 写明原型不作为验收依据）；性能和并发（PRD 没有要求）。
- 本 Eval 不改写 PRD 的 43 条验收，而是按“产品是否合格”把它们重新分组，并补上验收没有覆盖的组合、随机和真实数据核对。每个维度注明来源章节，可以追溯到 PRD。

**已确认口径（E-Q1～E-Q5 在 PRD 提交 `412cd389` 中关闭；M4-Q17 在 `28dddb06` 中关闭，E-Q6、E-Q7 在 `d82c7d21` 中关闭；PRD 现在没有待确认事项）**

- **E-Q1 已售怎么判断**：按车辆履约（M5）的当前物流节点判断，节点为“已外销出库”才算已售。销售退库后节点回到“已入库”，不算已售；再次出库后重新计入。终端回款仍只看最近一份外销合同。如果最近一份合同先收了款、还没出库，只计回款、不计已售，这是有意的设计（01 §2、§7.2；AC-M4-71）。
- **E-Q2 多次出库**：按辆计，只算 1 辆。外销合同的已出库还要同时满足两个条件：本车最近一条外销出库记录属于本合同，且当前节点为“已外销出库”。车辆清单中的出库日期仍然全部列出（01 §7.2、§12.2；AC-M4-72）。
- **E-Q3 M3 对账**：M4 合同的终端回款金额不要求等于 M3 各内销发票的终端回款之和，D3 不做这项检查。原因是未开票的车辆不在 M3 中，而且 M3 的计入方式以 M3 为准（01 §7.2）。
- **终端回款的计入（M4-Q17，用户 2026-11-25 确认按外销单价占比，PRD `28dddb06`）**：零售合同的收款全额计入。批售合同的收款按外销单价比例分摊：收款 × 本合同车辆在该批售合同中的外销单价合计 ÷ 该批售合同的外销合同金额，不按辆数均分。批售合同只含本合同车辆时比例为 100%。同一份外销合同只计一次。批售合同的外销合同金额为 0 或取不到时显示“-”。分摊值只用于计算终端回款，车辆清单仍不展示单车收款和分摊值（01 §7.2）。
- **E-Q6 N 怎么数（PRD `d82c7d21`）**：“含 N 份批售合同按外销单价比例分摊”中，N 只数分摊比例低于 100% 的批售合同。比例为 100% 的批售合同（只含本合同车辆）不计入 N，也不单独注明。没有比例低于 100% 的批售合同时，进度下方不出现这句说明（01 §7.2；AC-M4-68 场景 3）。
- **E-Q7 分摊分子算哪些车（PRD `d82c7d21`）**：分子只计“最近一份外销合同就是这份批售合同”的本合同车辆。之后已按其他外销合同再次销售的车辆，不再计入原批售合同的分子（01 §7.2；AC-M4-68 场景 5）。
- **E-Q4 时效**：没有时效要求。D1、D3 只检查最终一致：平台取得变化后，运营再次查看时看到最新结果（01 §3.1、§14.1）。
- **E-Q5 名称**：终端回款进度的未完成值叫“终端未回款金额（美元）”，小于 0 时为 0.00 USD；终端销售进度的已完成、未完成分别叫“已售车辆数”“未售车辆数”（01 §7.2；AC-M4-43）。

**已知的跨模块差异（不计为 M4 缺陷）**：M3 目前还有两处与 M4 口径不同，PRD 已在 WS-682 留言：一是 M3 把“M5 中有任一外销出库记录”算作完成销售，M4 按当前物流节点判断；二是 M3 按整份外销合同全额计入终端回款，M4 对批售合同按比例分摊。WS-682 结论出来前，D3 不比较 M3 与 M4 的这两项结果。

**业务门槛**：用户已于 2026-11-25 确认按建议值采用第 3 节各维度门槛和真实数据对账样本量（300 份，0 份不一致时 95% 上界约 1.26%）。

**仍待确认**：只剩 L3 上线后核对的具体指标，需业务方在上线前给出（第 5 节）。

## 3. 通过线

**单条 case 怎样算通过**：case 中列出的每个预期值都符合，并且没有出现任何“禁止行为”。一条 AC 有多个场景时，全部场景都满足才算通过，与验收册的规则一致。

| 维度 | 指标（分子／分母） | 门槛 | 依据 | 确认状态 |
| --- | --- | --- | --- | --- |
| D1 | 通过的 case 数／D1 的 case 数 | 100% | 归集错一次，一份合同的金额就会全部错 | 已确认（用户 2026-11-25 按建议采用） |
| D2（关键） | 通过的 case 数／D2 的 case 数；随机计算集：与预期值不一致的合同份数 | 规则集 100%；随机计算集 0 份不一致 | 这个模块是资产可信平台的“交易依据”，金额和进度会被运营和风控（M8）直接引用。没有人工兜底，算错就会被当作事实采信 | 已确认（用户 2026-11-25 按建议采用） |
| D3 | 取值一致：一致的字段数／比较的字段数；跳转：落点和返回都正确的路径数／路径数 | 取值一致 100%；PRD §15.2 列出的全部路径 100% | 不一致会让运营在两个模块看到两个数，无法判断以哪个为准 | 已确认（用户 2026-11-25 按建议采用） |

| D5（阻断） | 越权访问成功或信息泄露的次数 | 0 | 交易商业信息和个人信息泄露，没有事后补救手段 | 已确认（用户 2026-11-25 按建议采用） |

**阻断项**：任意一项发生即不能发布，不与其他维度平均。

- D2 中任一金额或比率与预期值不一致。
- D5 中任一越权或泄露。
- 加载失败被显示成 0.00 USD、0.00% 或“无”。

**排除规则**

- PRD 已没有“待验，不判通过”的场景。E-Q1～E-Q7 和 M4-Q17 都已确认，相关 case（包括 E-07、E-22）正常计入，目前没有排除的 case。
- WS-682 结论出来前，M3 与 M4 在已售口径和终端回款计入方式上的差异，不计为 D3 失败（见第 1 节）。

**整体发布门槛（已确认（用户 2026-11-25 按建议采用））**：

- D1～D5 全部达到上表门槛，没有阻断项。
- 真实数据对账集 300 份已完成，每一处差异都查明原因：是 M4 的缺陷、来源数据问题，还是口径问题。
- 属于 M4 缺陷的差异必须为 0 份。这类差异同时按 D2 阻断项处理，修复后重新核对受影响的合同。来源数据问题和口径问题单独登记，不计为 M4 的不一致，但发布前要有结论。

**统计与不确定性**

- 规则集是确定性判定，100% 只表示“这些 case 都对”，不代表没有其他缺陷。所以 D2 另用随机计算集补充覆盖面。
- 真实数据对账集按比例统计，用 Wilson 区间报告不一致率的上界。已确认样本量为 300 份：0 份不一致时，95% Wilson 上界约为 1.26%（这是计算方法，不是结果）。以后如果要求上界低于 1%，样本至少要约 381 份。
- 对账中出现不一致时，按实际的不一致份数重新计算上界并如实报告，不能用“0 份”时的 1.26% 代替。
- 版本对比用同一批合同、同一个 M11 汇率快照配对比较，避免汇率变化被误判为版本差异。
- 本文档没有执行任何评测，不包含通过率、分数或通过结论。

## 4. 标注方法

**预期值怎样产生**：D1～D3 不需要人工给出主观标签。预期值的来源分三种：

- 验收册写好的预期值，直接使用（例如 E-05）。
- 测试小队按 PRD 口径独立实现的计算，用于随机计算集。必须由不参与 M4 开发的人编写，避免开发和测试犯同一个口径错误。
- 真实数据对账集：由财务或运营人员从 ERP 原单据手工核算。

| 阶段 | 做什么 | 角色 | 产物 |
| --- | --- | --- | --- |
| 启动 | 编写 63 条 case 的前置数据和预期值；产品复核每条 case 是否符合 PRD 口径 | 测试小队编写；PRD 负责人复核口径 | 启动集 v1，每条 case 标注来源 AC 和复核状态 |
| 扩展 | 独立实现预期值计算；先用启动集中 D2 的 27 条校准，结果与验收册全部一致后，才用于随机计算集 | 测试小队（非 M4 开发） | 预期值计算口径说明及校准记录 |
| 真实对账 | 抽样合同，双人独立核算，结果不一致时由第三人仲裁 | 财务或运营 2 人核算；PRD 负责人仲裁口径 | 对账表：每份合同的 M4 值、核算值、差异和结论 |
| 持续 | 每个线上问题和每次需求变更都转成 case；每季度重新复核 10% 的旧 case 是否仍符合当前 PRD | 测试小队；PRD 负责人 | 新版本的 case 集及变更说明 |

**D4 人工评审 rubric**：每项只判“是”或“否”，由 2 人独立评审，不一致时由产品仲裁。

| 检查项 | 通过（是） | 不通过（否） |
| --- | --- | --- |
| 四个值都能看到 | 每项进度的已完成、总量、未完成、比率都以文字显示 | 某个值只能从图形长度推断，或要悬停才能看到 |
| 图表与数值一致 | 进度条长度与比率一致；超过 100% 时能看出超出部分和总量的位置 | 101.35% 被画成满格，看不出超出 |
| 缺失与零值可以区分 | “-”与 0.00%、0.00 USD 在图形上明显不同（例如虚线空框与空进度条） | 总量为 0 和比率为 0 画成同样的图形 |
| 成本对照不是进度 | 两个值用同一比例尺并列，没有比率，也没有高低提示 | 出现百分比、颜色警示或“超出”字样 |
| 不出现风控判断 | 字段旁和概要中没有本模块自己判定的提示 | 出现“价格倒挂”“未收回”之类的提示 |

- 评审人先用 3 张正例截图和 3 张反例截图对齐标准，再正式评审。正反例截图取自原型，作为锚点，不作为验收依据。
- 本模块不建议用 LLM-as-judge 作为主要判定。如果以后用模型预筛截图，要先用人工结果校准；校准用的截图和正式评审用的截图分开，校准前不能把模型结果当作通过依据。

**L3 上线后核对（方案）**

- 运营在日常使用中发现 M4 数值与 ERP 或 M3 不一致时（终端回款不与 M3 对账，见 E-Q3），按“合同号、字段、M4 值、预期值”登记，作为线上问题回流。

**失败回流与版本管理**
