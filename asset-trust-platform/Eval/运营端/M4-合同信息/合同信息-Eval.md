## 1. 评估维度（3–5 个）

**评估范围与前提**

- 被评对象是 M4 合同信息模块本身：运营端只读页面，包括三个页签的列表和详情、执行进度的计算与展示、跨模块的取值与跳转。M4 不含模型能力，所以本 Eval 以确定性判定为主，人工评审只用于图表和展示。
- 不在范围内：M3、M5、M8、M11、M14 自身的规则正确性（只核对 M4 取值与它们是否一致）；ERP 的取数接口；原型画面（PRD 写明原型不作为验收依据）；性能和并发（PRD 没有要求）。
- 本 Eval 不改写 PRD 的 44 条验收，而是按“产品是否合格”把它们重新分组，并补上验收没有覆盖的组合、随机和真实数据核对。每个维度注明来源章节，可以追溯到 PRD。

**已确认口径（E-Q1～E-Q5 在 PRD 提交 `412cd389` 中关闭；M4-Q17 在 `28dddb06` 中关闭，E-Q6、E-Q7 在 `d82c7d21` 中关闭；M4-Q18 在 `42029246` 中关闭，E-Q8、E-Q9 在 `9e60f477` 中关闭；PRD 现在没有待确认事项）**

- **E-Q1 已售怎么判断**：按车辆履约（M5）的当前物流节点判断，节点为“已外销出库”才算已售。销售退库后节点回到“已入库”，不算已售；再次出库后重新计入。终端回款仍只看最近一份外销合同。如果最近一份合同先收了款、还没出库，只计回款、不计已售，这是有意的设计（01 §2、§7.2；AC-M4-71）。
- **E-Q2 多次出库**：按辆计，只算 1 辆。外销合同的已出库还要同时满足两个条件：本车最近一条外销出库记录按 M5 对应到本合同，且当前节点为“已外销出库”。外销合同车辆清单只列对应到本合同的出库日期，本车在其他外销合同下的出库不列（01 §7.2、§12.2、§12.3；AC-M4-72；`fefd721f` 起）。
- **E-Q3 M3 对账**：M4 合同的终端回款金额不要求等于 M3 各内销发票的终端回款之和，D3 不做这项检查。原因是未开票的车辆不在 M3 中，而且 M3 的计入方式以 M3 为准（01 §7.2）。
- **终端回款的计入（M4-Q17，用户 2026-11-25 确认按外销单价占比，PRD `28dddb06`）**：零售合同的收款全额计入。批售合同的收款按外销单价比例分摊：收款 × 本合同车辆在该批售合同中的外销单价合计 ÷ 该批售合同的外销合同金额，不按辆数均分。批售合同只含本合同车辆时比例为 100%。同一份外销合同只计一次。批售合同的外销合同金额为 0 或取不到时显示“-”。分摊值只用于计算终端回款，车辆清单仍不展示单车收款和分摊值（01 §7.2）。
- **E-Q6 N 怎么数（PRD `d82c7d21`）**：“含 N 份批售合同按外销单价比例分摊”中，N 只数分摊比例低于 100% 的批售合同。比例为 100% 的批售合同（只含本合同车辆）不计入 N，也不单独注明。没有比例低于 100% 的批售合同时，进度下方不出现这句说明（01 §7.2；AC-M4-68 场景 3）。
- **E-Q7 分摊分子算哪些车（PRD `d82c7d21`）**：分子只计“最近一份外销合同就是这份批售合同”的本合同车辆。之后已按其他外销合同再次销售的车辆，不再计入原批售合同的分子（01 §7.2；AC-M4-68 场景 5）。
- **E-Q4 时效**：没有时效要求。D1、D3 只检查最终一致：平台取得变化后，运营再次查看时看到最新结果（01 §3.1、§14.1）。
- **E-Q5 名称**：终端回款进度的未完成值叫“终端未回款金额（美元）”，小于 0 时为 0.00 USD；终端销售进度的已完成、未完成分别叫“已售车辆数”“未售车辆数”（01 §7.2；AC-M4-43）。

**v1.1 同步的 PRD 变化（`fefd721f`、`42029246`）**

- **收付按分配金额计入**：外销收款记录列的是登记到本合同的分配金额，外销已收款、终端回款都按分配金额合计；一笔收款登记到多份合同时，每份合同各列一行，不按全额重复计入（01 §4.2、§13；AC-M4-59 新增 RC-7900）。外采付款同理（AC-M4-52、53 改用 PAY-0305：共 140,000.00，分配到 PPI-0301 40,000.00）。
- **M4-Q18 逐笔美元值与合计（用户在 WS-668 裁定）**：
  - 付款记录、收款记录的逐笔金额（美元）取 M14 已确定的值，按收付日期当日汇率，之后不随 M11 变化；M14 注明“暂计”或显示“-”时，M4 同样展示。
  - 合同和发票层面的外采已付款、外销已收款按原币计入；收付币种不同时，用 M14 所用的收付日期汇率换算成发票或合同币种。按币种合计后，再按查看时的当前汇率折算美元，旁注“按当前汇率”。
  - 因此同币种付清时比率为 100%，不随汇率变化；逐笔美元值相加可能不等于合计（01 §3.3；AC-M4-73）。
- **内销未收款**：统一为“内销已开票 − 内销已收款，小于 0 时为 0”。某张发票多收时，可能小于发票清单中各张待收款之和（01 §7.2；AC-M4-44 场景 5）。
- **外销出库对应的合同**：引用 M5 §4.3：取合同日期不晚于出库日期、日期最近的一份外销合同；没有对应合同的出库不归入本模块（01 §4.2、§12.2、§12.3）。
- **个人客户名称不脱敏**：用户在 WS-674 裁定，按 ERP 原值完整展示，不展示名称以外的个人信息（01 §12.1；AC-M4-57 场景 1）。v1.0 中 D5 的“只显示脱敏名称”已反转。
- **不再写“由 M8 判断”**：主体比对、VIN 不一致、“出库时未收款”等，本模块都不提示；风控判断以 M8 风控规则目录为准（01 §1.2、§4.2、§12.2）。
- **样本变化**：RC-7781 改为 2026-11-03、30,000,000.00 NGN（20,000.00 USD），SO-2045 外销单价改为 39,600,000.00 NGN（26,400.00 USD）。由此 SC-0008 终端回款进度 31.33% → 23.33%，SO-2045 收款进度 100.00% → 75.75%，AC-M4-68 各场景随之重算。下方 case 的预期值已按新样本复算。

**跨模块核对结果**

- **M3（`dc67846b`）已与 M4 一致**：已售按当前物流节点判断；批售合同按外销单价占比分摊，N 只数比例低于 100% 的批售合同。v1.0 登记的两处 M3 差异已消除。M4 与 M3 的终端回款仍按 E-Q3 不对账。
- **M3 文档内的旧写法（不影响 M4 判定）**：M3 01 的依赖一节仍写“终端回款按整份外销合同计入”，与 M3 正文的分摊规则不一致；M3 用“当前有效外销合同”（Q-M3-14 待验证），M4 用“最近一份外销合同”。由 M3 在 WS-682 处理。
- **样本未完全对齐（影响联调）**：VIN-A 的内销合同号、外采单价、内采单价，M3、M4 用 SC-0008、PI-0012，M5 仍用 CT-0012、INV-0012。PRD 建议由 M5 向 M3、M4 对齐。对齐前，用同一套数据联调 D3 时，这几项的差异按样本问题登记，不计为 M4 缺陷。
- **M8（`53371ee0` 起）**：仍引用 M4 的开票、外采付款、外销收款与出库，所以 M4 的分配金额和原币合计规则会传到 M8 的规则判断。这一点只影响 L3 上线后核对，不影响 M4 判定。

**业务门槛**：用户已于 2026-11-25 确认按建议值采用第 3 节各维度门槛和真实数据对账样本量（300 份，0 份不一致时 95% 上界约 1.26%）。

**E-Q8、E-Q9 的结论（PRD `9e60f477`）**

- **E-Q8 分配金额的逐笔美元值**：PRD 没有采用 v1.1 的建议（用 M14 的两位小数值按比例计算），而是用 M14 为该笔收付确定美元值时所用的同一汇率换算分配金额：USD 收付的美元值就是分配金额；NGN 收付为分配金额 ÷ 该汇率。按未取舍的值计算，展示时四舍五入到两位小数。各单据的美元值相加可能与 M14 相差 0.01 USD，不调整尾差。只对应一张单据时，结果与 M14 完全相同（01 §3.3；AC-M4-73 场景 4）。
  - 例：一笔 46,500,000.00 NGN 收款，汇率 1,528.50，M14 为 30,421.98 USD，分配 6,500,000.00 和 40,000,000.00 NGN 到两份合同，得 4,252.54 和 26,169.45，合计 30,421.99。按 M14 两位小数值按比例算出的 4,252.53 判为失败。
- **E-Q9 暂计的收付怎样计入合同合计**：收付币种与发票或合同币种不同时，按 M14 暂计所用的汇率换算后计入，合计旁注明“含暂计”；收付日期当日结束、M14 确定美元值后，按确定时所用的汇率重新计入，“含暂计”消失。币种相同时按原币计入，不受暂计影响（01 §3.3；AC-M4-73 场景 3）。

**待用户确认**：只剩 L3 上线后核对的指标 U-1、U-2，见第 5 节，按编号回复即可。PRD 已说明这两项不在 PRD 范围内。

**统计与不确定性**

- 规则集是确定性判定，100% 只表示“这些 case 都对”，不代表没有其他缺陷。所以 D2 另用随机计算集补充覆盖面。
- 真实数据对账集按比例统计，用 Wilson 区间报告不一致率的上界。已确认样本量为 300 份：0 份不一致时，95% Wilson 上界约为 1.26%（这是计算方法，不是结果）。以后如果要求上界低于 1%，样本至少要约 381 份。
- 对账中出现不一致时，按实际的不一致份数重新计算上界并如实报告，不能用“0 份”时的 1.26% 代替。
- 版本对比用同一批合同、同一个 M11 汇率快照配对比较，避免汇率变化被误判为版本差异。
- 真实数据对账按 M4-Q18 分开核对：逐笔金额（美元）与 M14 比较；合同和发票层面的已付款、已收款先按原币核对，再核对按当前汇率折算的美元值。只有美元值因汇率快照不同而不一致的，不计为 M4 的不一致。
- 本文档没有执行任何评测，不包含通过率、分数或通过结论。

## 4. 标注方法

**预期值怎样产生**：D1～D3 不需要人工给出主观标签。预期值的来源分三种：

- 验收册写好的预期值，直接使用（例如 E-05）。
- 测试小队按 PRD 口径独立实现的计算，用于随机计算集。必须由不参与 M4 开发的人编写，避免开发和测试犯同一个口径错误。
- 真实数据对账集：由财务或运营人员从 ERP 原单据手工核算；逐笔收付的美元值以 M14 已确定的值为准，不按当前汇率重算（M4-Q18）。

| 阶段 | 做什么 | 角色 | 产物 |
| --- | --- | --- | --- |
| 启动 | 编写 68 条 case 的前置数据和预期值；产品复核每条 case 是否符合 PRD 口径 | 测试小队编写；PRD 负责人复核口径 | 启动集 v1，每条 case 标注来源 AC 和复核状态 |
| 扩展 | 独立实现预期值计算；先用启动集中 D2 的 32 条 case 校准，结果与验收册全部一致后，才用于随机计算集 | 测试小队（非 M4 开发） | 预期值计算口径说明及校准记录 |
| 真实对账 | 抽样合同，双人独立核算，结果不一致时由第三人仲裁 | 财务或运营 2 人核算；PRD 负责人仲裁口径 | 对账表：每份合同的 M4 值、核算值、差异和结论 |
| 持续 | 每个线上问题和每次需求变更都转成 case；每季度重新复核 10% 的旧 case 是否仍符合当前 PRD | 测试小队；PRD 负责人 | 新版本的 case 集及变更说明 |

**D4 人工评审 rubric**：每项只判“是”或“否”，由 2 人独立评审，不一致时由产品仲裁。

| 检查项 | 通过（是） | 不通过（否） |
| --- | --- | --- |
| 四个值都能看到 | 每项进度的已完成、总量、未完成、比率都以文字显示 | 某个值只能从图形长度推断，或要悬停才能看到 |
| 图表与数值一致 | 进度条长度与比率一致；超过 100% 时能看出超出部分和总量的位置 | 101.35% 被画成满格，看不出超出 |
| 缺失与零值可以区分 | “-”与 0.00%、0.00 USD 在图形上明显不同（例如虚线空框与空进度条） | 总量为 0 和比率为 0 画成同样的图形 |
| 成本对照不是进度 | 两个值用同一比例尺并列，没有比率，也没有高低提示 | 出现百分比、颜色警示或“超出”字样 |
| 不出现风控判断 | 字段旁和概要中没有本模块自己判定的提示 | 出现“价格倒挂”“未收回”之类的提示 |

- 评审人先用 3 张正例截图和 3 张反例截图对齐标准，再正式评审。正反例截图取自原型，作为锚点，不作为验收依据。
- 本模块不建议用 LLM-as-judge 作为主要判定。如果以后用模型预筛截图，要先用人工结果校准；校准用的截图和正式评审用的截图分开，校准前不能把模型结果当作通过依据。

**L3 上线后核对（方案）**

- 运营在日常使用中发现 M4 数值与 ERP 或 M3 不一致时（终端回款不与 M3 对账，见 E-Q3），按“合同号、字段、M4 值、预期值”登记，作为线上问题回流。
- 离线 Eval 只证明“按 PRD 口径算对了”，不能证明运营据此做出了正确判断。上线后另看两件事，具体指标**待用户确认**，下面是推荐：

| 编号 | 看什么 | 推荐做法与指标（建议，待确认） | 理由 | 责任 |
| --- | --- | --- | --- | --- |
| U-1 | 运营是否还要回 ERP 或 M14 手工核对 | 上线后前 4 周，每周按三类合同的实际数量比例抽 20 份合同。运营只看 M4 完成核对，再与 ERP、M14 比对。指标一：由 M4 缺陷造成的差异为 0（与 D2 阻断项一致）。指标二：运营认为“必须回 ERP 才能确认”的合同不超过 10%，超过时逐份记录原因，判断是缺字段还是展示问题 | 指标一延续离线门槛；指标二衡量的是信息是否够用，不是计算对错，所以给容忍度。10% 是起步值，没有历史数据，4 周后按实际情况调整 | 运营负责人；测试小队整理 |

**失败回流与版本管理**

- 每个线上问题和每次口径变更都转成至少一条 case，并标注来源（线上问题编号或 PRD 提交号）。
- 规则集、随机计算集的生成规则、真实对账样本分别管理版本，并记录对应的 PRD 提交号（当前为 `9e60f477`）。真实对账集用于统计整体不一致率，规则集和随机集用于发现缺陷，两者的结果不混在一起报告。
- PRD 口径变更时（例如 M5 对齐样本），先改相关 case 的预期值，再重新运行受影响的层级。
