## 1. 评估维度（3–5 个）

**评估范围与依据**

- 需求来源：M17 PRD 三册，基线 `cly-v6.0.0` @ `317e877f05485e1cd939129c40b1b77dfb5262c2`（PRD 无待确认事项），包括 [01 功能与业务规则](../../../PRD/运营端/M17-运营端首页/01-运营端首页-PRD.md)、[02 流程图与状态机](../../../PRD/运营端/M17-运营端首页/02-运营端首页-流程图与状态机.md)、[04 验收](../../../PRD/运营端/M17-运营端首页/04-运营端首页-验收.md)（26 条，按场景拆分共 51 个）。下文用 `§x.x` 指 01 册章节，用 `AC-xx` 指 04 册的 `AC-M17-xx`。Q-M17-01～11 已由用户裁定；v1.0 提出的 E-Q1～E-Q5 已由 PRD 在 `317e877f` 定稿。
- 被测对象：首页的研发实现，包括取数、计算、展示，以及加载、刷新和失败时的表现。原型只用来对照页面，不作为判定依据，这一点与 04 册一致。
- 判定方式：首页的数字由确定的规则计算得出，不包含模型生成的内容，因此**不使用 LLM-as-judge**。数值和规则类判定全部用 code-based 方式：测试按 PRD 口径独立实现一份重算程序（下称 oracle），与页面展示值逐项比对。状态画面、文案和可读性由人工按二元 rubric 判定。
- 判定口径：按展示精度比对，不设容差。金额保留两位小数，天数保留一位小数，百分数向零截取后保留两位小数（§3.4）。“-”与 0 不能互相替代。
- 不在范围内：§1.1“本期不做”的内容；响应时间和性能（§13 写明产品不设目标，由研发评估、测试验证）；M2、M3、M5、M11 自身的规则（只评首页的汇总结果与来源模块的现行值是否一致）；原型本身。

**阻断项**（不参与任何维度的平均，任意一条出现即判定不通过）

- B1 首次加载失败、刷新失败或单板块失败时，显示 0、0.00 USD 或 0.00%（§3.5）。
- B2 把旧数据当作最新数据展示：刷新失败后数据更新时间变成当前时间，或者刷新时失败的板块没有提示“本板块更新失败”（§3.5）。
- B3 企业账号、锁定账号或待首登改密账号能取到首页的任何数据（§3.1）。
- B4 无法折算的金额按 0 计入合计，或者合计中有无法折算的项却没有注明（§3.4）。
- B5 同一次取数的各板块使用了不同的汇率（§3.4）。按 §3.5，刷新时失败的板块沿用上次取数时的汇率，不算违反 B5。
- B6 首页上有任何修改、处理或审核操作，或者首页的操作改变了来源模块的数据（§3、§4）。

## 3. 通过线

**单例判定**：一条用例的所有断言都满足才算通过；一条验收写了多个场景时，全部场景都满足才算通过（同 04 册）。数值按第 1 节的判定口径比对，不设容差。

| 门槛 | 指标（分子 / 分母） | 通过线 | 依据与确认状态 |
| --- | --- | --- | --- |
| 验收门槛 | S0 中通过的 AC 条数 / 26 | 26 / 26 | 04 册要求全部满足；已确认 |
| D1～D4 维度门槛 | 各维度 S1 中通过的用例数 / 该维度已复核的用例数 | 100% | 规则确定，不存在合理的误差空间，而且金额会直接用于经营判断；建议，待业务确认 |
| D5 维度门槛 | 人工 rubric 判为通过的画面数 / 应检画面数（§3.5 的 9 种状态：正常、暂无资料、首次加载中、整页失败、单板块失败、刷新中、刷新完成、刷新失败、刷新时部分板块失败；× 中英文 × 1440、375 px） | 100% | 状态和文案都有明确规定；建议，待业务确认 |
| 随机一致性（S2） | 与 oracle 完全一致的数据组数 / 200 | 200 / 200；出现任何不一致都要查清是实现还是 oracle 的问题 | 建议，待研发和测试确认 |
| 阻断项 | B1～B6 的出现次数 | 0 | PRD 明文禁止；已确认 |
| 上线门槛 | 以上全部满足 | 同时满足 | 建议，待业务确认 |

- **排除规则**：用例本身的期望值错误（经 PRD 判定）时，修正用例后重跑，不算实现失败。PRD 目前没有待确认事项，所以没有因口径未定而排除的用例。
- **关于小样本**：S0 和 S1 全部通过，只能说明这些场景正确，不能说明所有组合都正确，S2 用随机组合补充覆盖。S3 抽 30 项全部一致时，按 rule of three，不一致率的 95% 置信上限约为 3/30 = 10%，不能说明不一致率为 0。需要更紧的上限时就要增加样本，例如抽 300 项对应约 1%。
- **上线后（L3）的门槛**：首页数字与 M3、M5 现行值按 01 册规则重算结果一致的抽样项数 / 抽样项数。对账基准已由 PRD 确定为 M3、M5 的现行值（E-Q6 中 PRD 能确定的部分）。按 01 册的精度和取舍规则，在同一汇率下重算的结果应与页面完全一致，因此建议目标为 100%、容差为 0。抽样量（每月 30 辆车、30 笔应收账款）和容差**待业务确认**。
- **失败兜底**：Eval 不通过时不上线。上线后发现某个指标出错时，优先让该板块按 §3.5 显示失败，不展示错误的数字，同时告知运营人员该指标暂不可用。

## 4. 标注方法

M17 的预期结果由 PRD 规则唯一确定。这里的“标注”指**编写并复核每条用例的期望值**，以及对画面做人工判定。不使用模型做判定，因此不需要校准模型 judge。

**阶段与角色**

| 阶段 | 做什么 | 角色 | 产物 |
| --- | --- | --- | --- |
| 启动 | 测试按 PRD 独立实现 oracle，不复用研发的计算代码；用 oracle 重算 S0 的期望值，并与 04 册比对 | 测试编写，PRD 复核口径 | oracle、S0 比对记录 |
| 启动 | 复核 S1 的期望值：测试先手算，再用 oracle 重算，两者一致才入库 | 测试编写，PRD 复核 | S1 v1（标“合成”） |
| 扩展 | 编写 S2 的生成规则和不变量，例如：外销数量 = 各月外销数量之和；余额 ≤ 发生额；逾期中的应收账款到期日早于今天 | 测试 | S2 生成规则 |
| 持续 | 生产对账抽样，首页值与 M3、M5 现行值的重算结果逐项比对 | 测试比对，运营协助核实 | S3 对账记录 |

**分歧仲裁**：oracle、手算和实现三者不一致时，先按 PRD 原文判定是哪一方错了。PRD 没有写到的情况，记为新的待确认项交 PRD 补充，测试和研发不自行决定口径。仲裁结果同时更新用例和 oracle。

**D5 人工 rubric**（每项二元判定：通过或不通过）

| 检查项 | 通过（正例） | 不通过（反例） |
| --- | --- | --- |
| R1 顶部区域 | 只有数据更新时间（到分钟，标明时区）和刷新按钮 | 出现“首页”标题、副标题或口径说明文字 |
| R2 失败表现 | 失败的板块显示失败提示和重试，没有任何数字 | 失败的板块显示 0 或 0.00 USD |
| R3 刷新失败 | 整体失败时保留旧数字，提示“数据更新失败，当前显示 {时间} 的数据”；部分板块失败时，失败板块提示“本板块更新失败，当前显示 {该板块上次成功取数的时间} 的数据” | 数据更新时间变成当前时间却没有提示；失败板块的提示时间写成本次刷新时间 |
| R4 缺失注明 | 注明中的 N 与 oracle 一致，并紧跟对应的数值；“含 N 辆合同价”在累计、当年度、本月下方可见，趋势各期在数值旁可以查看 | N 不对，或者注明离数值太远、看不出对应哪个数 |
| R5 趋势表达 | 值用柱状、环比用曲线；环比为“-”的期曲线断开；“截至今日”可见 | 曲线在“-”处连成 0% |
| R6 英文界面 | 界面文字全部为英文；企业名称、编号、金额、日期按原值展示 | 有漏译，或者把企业名称翻译了 |

- 人工判定由测试执行；每次 release 由设计或 PRD 随机抽 20% 的画面复审。复审结论与测试不一致时，按上面的分歧仲裁处理，并修订 rubric 的正反例。
- 可以统计人工判定的一致率（复审中结论相同的画面数 / 复审的画面数），用 Wilson 区间说明不确定性。目前没有执行数据，不填写数值。

## 5. 跑评频率

以下为建议节奏，按研发的实际流程调整。本文只做设计，不接入任何自动化。

| 层级 | 触发 | 范围 | 责任 | 产物 |
| --- | --- | --- | --- | --- |
| L1 确定性检查 | 每次提交涉及首页的计算、取数或展示 | S0 中 D1～D4 的计算断言、S1 中已复核的 code 用例，以及 B1、B4、B5 的单元检查 | 研发 | 用例通过与失败清单 |
| L2 发布评估 | 每次 release | S0 全量（含 E2E）、S1 全量、S2 200 组、D5 人工 rubric、B1～B6 | 测试执行，PRD 和设计抽查 | 各维度的通过情况、阻断项结论 |
| 依赖变更回归 | M2、M3、M5、M11 的规则或 ERP 字段发生变更 | S0 中受影响的章节，加上 S1 中对应的用例 | 测试 | 回归记录 |
| 每周回归 | 每周一次（建议） | 在测试环境用最新的 ERP 同步数据跑 oracle，与首页比对 | 测试 | 差异清单 |
| L3 线上对账 | 上线后每月一次（建议，抽样量待业务确认） | S3：抽样车辆和应收账款，逾期明细全量，与 M3、M5 现行值的重算结果比对 | 测试比对，运营协助核实 | 对账报告；不一致项转为缺陷 |

- M17 不使用模型，所以不设每月一次的新模型探索评估。每月的 L3 对账就是线上业务验证，用来确认首页数字与业务实际一致。离线评估通过不代表线上数字一定正确。
- **失败回流**：线上对账、运营反馈或缺陷中发现的问题，复现后加入 S1，标“真实”和发现日期，并补一条防止再犯的 L1 断言。
- **样本更新**：PRD 每次修改口径，同步更新 S0 期望值、S1 和 oracle。ERP 出现新的字段取值（例如新币种、新单据类型）时，补充分布外用例。
- **版本管理**：用例集与 PRD 提交号绑定（当前为 `317e877f`），每条用例记录来源、复核人和版本。S1、S2 只用于发现缺陷，S3 才反映线上真实情况，两者的统计结果分开报告。
- **变更记录**：v1.0 依据 `016a075e`，提出 E-Q1～E-Q6。v1.1 依据 `317e877f`：E-Q1～E-Q5 已由 PRD 定稿；E-Q6 的对账基准已确定为 M3、M5 现行值，抽样量和容差仍待业务确认；E-13、E-15 按定稿规则改写，补齐 E-17～E-24。
