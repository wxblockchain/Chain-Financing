**评估范围与前提**

**本版纳入的评审变更（WS-683，PRD `e5dbee4b`）**：企业、运营账号都没有停用、启用状态；运营端只有“全体运营”一种收件范围，没有“本人”；分类为业务办理进度、业务提醒、待处理事项、运营告警（仅运营端），没有“账户安全”；删去“运营移除业务角色”和“企业没有任何业务角色”的情况。相关 Case 打“评审变更回归”标签，它们来自真实的评审决定，不是生产事故。

**Eval 对 PRD 的理解（已从 PRD 推出，不另提问）**

- “打开他人的、另一端的消息与打开不存在的消息结果完全相同”同样适用于接口：详情、已读、全部已读接口对这三种消息的响应相同，且不能改变他人消息的已读状态（01 §3 归属与隔离）。
- 未读数始终等于本人“分类：全部 + 已读状态：未读”的结果条数，包括原业务已办完、已不可访问、分类为“其他”的消息（01 §5 未读数）。D3 以此为不变量。
- 未读数恰为 99 时显示“99”，100 起显示“99+”；全部已读确认中的条数是实际条数，不显示“99+”（01 §5、§7）。
- 运营账号在“开通”之后、首次改密之前产生的全体运营消息，对该账号为未读（AC-04 场景二、状态机 1）。开通前的为已读（AC-20）。
- 送达时效只适用于收件人可以查看的时候；不能查看期间生成的消息，在恢复后直接可见，不计入时效统计（01 §4.4）。

## 4. 标注方法

**L3 上线后核对（方案）**

- 用户或运营反馈“收不到、收重了、看到了别人的消息、点进去不对、未读数不准”时，按“账号、消息编号、现象、预期”登记，作为线上问题回流；涉及可见范围或权限的按 B1、B5 立即处理。
- 离线 Eval 只证明“按 PRD 口径做对了”，不能证明用户因此及时办理了业务。消息被打开、被前往都只是代理指标，业务是否办完以原业务模块的结果为准。上线后另看：待处理事项类消息从产生到首次打开的时长分布；从消息前往原业务的比例；M7a 确权申请在到期关闭前被债务人处理的比例中，经消息进入的占多少（数据归 M7a、M7b）；长期未读超过 99 条的账号占比（反映是否需要更细的分类或提醒，不计为 M10 缺陷）。具体指标和门槛由业务方在上线前确定，**待确认**。

**失败回流与版本管理**

- 每个线上问题和每次口径变更都转成至少一条 Case，并标注来源（线上问题编号或 PRD 提交号）。
- 规则集、随机不变量的生成规则、来源联调集、时效抽样记录分别管理版本，并记录对应的 PRD 提交号（当前为 `e5dbee4b`）和各来源 03 册的提交号。来源联调集反映真实接入，规则集和随机序列用于发现缺陷，两者的结果不混在一起报告。
- PRD 口径变更时（例如 Q-EV-M10-01～05 定稿，或来源增减消息），先改相关 Case 的预期值和联调集的行，再重新运行受影响的层级。
