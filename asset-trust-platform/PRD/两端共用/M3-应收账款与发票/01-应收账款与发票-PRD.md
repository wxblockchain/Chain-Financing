## 1. 模块是什么

本模块是运营端资产数据的主入口。平台把 ERP 中每一张已审核的内销发票作为一笔应收账款，在一处回答四个问题：这笔资产值多少、何时到期、债务人已经还了多少、背后的车辆卖得怎样和是否足额投保。运营人员先在这里判断一笔资产的状况，再通过单据编号进入合同信息、车辆履约、提单信息、保单信息、资金收付核实细节。本模块不重复展示这些模块的完整内容，只展示它们对本笔资产的结论（进度、比率），并承接风控预警（M8）提供的预警信息。债权人、债务人企业用户在各自业务入口中只读查看与本企业有关的应收账款详情，可见范围与调整前一致，不因资产全景扩大。本模块也是确权申请（M7a）、债务人确认（M7b）、运营审核与出库（M9）共同引用的应收账款资料来源。

基本原则：

- 一张已审核的内销发票就是一笔应收账款。内销发票的内销卖方对应的平台企业是债权人，内销买方对应的平台企业是债务人；应收账款金额、币种取自内销发票。
- 平台企业与 ERP 企业的对应由运营人员在 M2 关联；应收账款按内销发票上的 ERP 企业与关联结果对应到平台企业，不按名称比对。
- 应收账款起算日、到期日由平台按提单装船日期和内销发票账期计算；内销发票上 ERP 给出的账款起算日、到期日同时展示供对照，不用 ERP 值替代平台计算值。
- 回款是债务人为本内销发票向债权人支付的内销收款；外销收款（终端客户向债务人付款）只用于终端回款进度，不计入本笔应收账款的回款。
- 一个事实只在一个模块完整展示。本模块对其他模块的单据只展示摘要和结论，点击单据编号进入其所在模块的详情。
- 风控规则的判定、提示与处理全部由风控预警（M8）负责；本模块不自行判定任何风控条件，只承接 M8 提供的预警信息。
- 平台不生成、不签署、不修改任何单据。任何角色都不能新增、修改或删除应收账款、发票、车辆、合同和款项资料；运营人员只能对核心资料差异记录核实。

**一个完整的例子**（企业名称、编号、金额与日期为演示值）。运营人员已在 M2 为平台企业 Carloha Holding、Carloha Nigeria 分别关联了 ERP 中的同名企业。ERP 中有一张已审核的内销发票 PI-0012：内销卖方 Carloha Holding、内销买方 Carloha Nigeria，关联内销合同 SC-0008，内销发票日期 2026-09-05，金额 90,000.00 USD，账期 90 天，ERP 账款起算日 2026-09-10、账款到期日 2026-12-09，车辆 VIN-A、VIN-B、VIN-C 的内采单价各 30,000.00 USD。平台形成应收账款 AR-0012，按关联结果对应到债权人 Carloha Holding、债务人 Carloha Nigeria。VIN-A、VIN-B 在提单 BL-01 上于 2026-09-10 装船；在 VIN-C 装船前，起算日展示“未确定（尚有 1 辆车未装船）”，这笔应收账款不能申请确权。VIN-C 在提单 BL-02 上于 2026-09-20 装船，之后在中转港换装到提单 BL-03（装船日期 2026-10-05）；VIN-C 按初始提单 BL-02 计，平台确定应收账款起算日为三辆车中最晚的 2026-09-20，到期日为 2026-12-19。内销发票部分同时展示 ERP 账款起算日 2026-09-10、账款到期日 2026-12-09，供运营人员对照。债务人先后两次付款，ERP 在本发票下登记内销收款 25,000.00 USD 和 20,000.00 USD：已收款金额 45,000.00 USD，待收款金额 45,000.00 USD，已收款比率 50.00%，回款状态“部分收款”。VIN-A、VIN-B 已外销出库，终端销售进度 66.66%（已售 2 辆／共 3 辆）；两车外销收款合计 47,000.00 USD（VIN-A 32,000.00 USD、VIN-B 15,000.00 USD），终端回款进度 52.22%。保单按内采单价的 110% 投保，保险覆盖率 110.00%。2026-12-14（剩余 5 天）运营人员打开“应收账款”，看到 AR-0012 的到期日 2026-12-19（剩余 5 天）被突出显示；M8 对 AR-0012 有 1 条未处理预警，列表预警列显示“1 条”。进入详情后，概要中关联预警为“未处理 1 条、已处理 0 条”，运营人员点“未处理 1 条”进入 M8 查看该预警；返回后点 VIN-B 进入车辆履约（M5）查看该车的外销合同与收款，返回后点回款记录中的交易流水号进入资金收付（M14）核对付款凭证，再点内销合同号 SC-0008 进入合同信息（M4）。债权人企业用户在 M7a 打开同一笔应收账款，看到相同的金额、起算日、到期日、已收款和待收款，但看不到资产健康度、预警信息和车辆的上下游信息。

### 1.2 本期不做

- 二手车业务；外采发票（关联外采合同的发票）不形成应收账款，在合同信息（M4）的外采合同中展示。
- 在平台录入、编辑、删除或补传任何单据、车辆、合同和款项资料；企业端和运营端都没有这类操作。
- 合同、提单、保单、外采、外销、资金收付的完整信息与其计算规则：分别由合同信息（M4）、车辆履约（M5）、提单信息（M12）、保单信息（M13）、资金收付（M14）定义，本模块只展示摘要、结论和跳转。
- 平台企业与 ERP 企业的关联与取消关联操作：由 M2 定义，本模块只使用关联结果。
- 风控规则的判定、提示与处理：功能清单列在应收账款下的风控逻辑（账款日期不一致、合同日期存疑、价格倒挂、保险未足额覆盖、回款风险、车辆出库与收款等）由风控预警（M8）完善，本模块只承接 M8 提供的预警信息。
- 航程与到港等外部数据：三方数据源本期未接入，不展示。
- 汇率维护：由 M11 汇率管理定义。
- 确权申请、债务人确认、运营审核与出库的操作和状态定义：分别由 M7a、M7b、M9 定义；本模块展示其结果，并在债权人详情中提供发起申请入口（规则按 M7a）。
- 业务总览。
- 中文以外的语言（功能清单要求简体中文）。

## 2. 术语

| 术语 | 含义 |
| --- | --- |
| 应收账款 | 由一张已审核的内销发票形成的债权。一张内销发票对应一笔应收账款 |
| 应收账款编号 | 平台为每笔应收账款生成的编号（功能清单中称“应收账款资产编号”），与内销发票一一对应，全平台唯一，生成后不变 |
| 内销发票 | 内销卖方开给内销买方、关联内销合同的发票（Proforma Invoice）。关联外采合同的发票是外采发票，不属于本模块 |
| 内销合同 | 内销卖方与内销买方之间的新车内销合同。一张内销发票关联一份内销合同 |
| 内销卖方、内销买方 | 内销发票上的卖方、买方，即 ERP 中的企业 |
| 债权人、债务人 | 内销卖方、内销买方分别对应的平台企业，见[买卖双方与平台企业的对应](#party-match) |

| 账期 | 内销发票上的账款天数（整数天，如 90 天），功能清单中也称“合同账期（tenor）” |
| 应收账款起算日、应收账款到期日 | 平台计算的起算日与到期日，见[账期与到期状态（F-M3-04）](#F-M3-04)。内销发票上 ERP 给出的称“ERP 账款起算日”“ERP 账款到期日”，只供对照 |
| 初始提单 | 一辆车首次装船时的提单。车辆转运时会出现在多张提单上，其中装船日期最早的一张为初始提单 |
| 回款、回款记录 | 债务人为本内销发票向债权人支付的内销收款。每条回款记录只属于一张内销发票 |
| 外采 | 债权人向外采供应商采购车辆，单据为外采合同、外采发票 |
| 外销、终端 | 债务人把车辆卖给终端客户，单据为外销合同、外销出库、外销收款。“终端销售”“终端回款”分别指外销出库和外销收款 |
| 价格对比 | 一辆车的外采单价、内采单价、外销单价，统一以美元对照 |
| 外采单价 | 本车的外采价格，见[车辆清单（F-M3-13）](#F-M3-13) |
| 内采单价 | 本车在内销发票车辆明细中的单价，即债务人从债权人处采购本车的价格 |
| 外销单价 | 本车在外销合同中的车辆单价 |
| 物流节点 | 一辆车当前所处的物流节点，由车辆履约（M5）判定，本模块原样展示 |
| 美元折算值 | 功能清单标注“（美元）”的金额，由平台按[美元折算与比率](#usd-rule)得出 |
| 预警信息 | 运营端对本笔应收账款是否存在需关注事项的有／无标识，由 M8 关联预警和本模块核心资料状态得出，见[预警信息（F-M3-14）](#F-M3-14) |
| 关联风控预警 | M8 生成、关联到本笔应收账款的风控预警。预警的规则、内容和处理都以 M8 为准 |
| 核心资料 | 内销发票中决定应收账款身份、金额与期限的资料，以及已确定的应收账款起算日，见[差异的产生与展示](#core-diff)。已有值出现差异时进入核实 |
| 原资料 | 本笔应收账款首次形成（或该项首次取得）时的核心资料，始终是展示与后续业务的依据 |
| VIN | 车辆识别代号，用来从本应收账款的车辆进入车辆履约（M5） |

<a id="shared-rules"></a>
## 3. 共用规则

本节规则适用于本模块全部功能，其他章节直接引用，不重复展开。其中[采信范围](#adopt-scope)、[来源值、金额与时间](#display-values)、[美元折算与比率](#usd-rule)、[单据编号跳转](#doc-links)、[详情三层结构](#detail-groups)是六个运营端资产数据模块（应收账款、合同信息、车辆履约、提单信息、保单信息、资金收付）共用的规则，其他模块可直接引用本节。

<a id="adopt-scope"></a>
### 3.1 采信范围

- 平台只采信 ERP 中已审核的单据。未审核的内销发票不形成应收账款；未审核的提单、付款、合同、外采、外销单据不参与本模块的任何展示和计算。

<a id="display-values"></a>
### 3.2 来源值、金额与时间

- ERP 提供的值按原值展示，不翻译、不改写。
- ERP 没有提供某项值时，该项展示“未提供”；附件没有取得时展示“附件未取得”；关联单据在平台中不存在时，在对应位置展示“未取得”（如“内销合同未取得”）。
- 金额与币种代码同时展示，数值在前、币种代码在后，带千分位，例如“60,000.00 USD”。ERP 提供的金额按原值展示，不四舍五入、不截断。
- 不同币种的原币金额不直接相加；需要合计时按美元折算值合计。
- ERP 提供的日期（发票日期、合同日期、装船日期、出库日期、收付日期等）按原样展示，不做时区换算。
- 平台计算的日期（应收账款起算日、应收账款到期日）只有日期，不带时区；涉及“今天”的判断（到期状态、剩余天数、临近到期）统一按 UTC+1 的当前日期。
- 平台自己记录的时间（首次取得时间、核实时间）展示到分钟并标注时区：按用户在 M1、M2 选择的时区展示；两模块不提供时区设置时统一按 UTC 展示。

<a id="placeholder"></a>
#### 缺失值的展示（运营端）

- 运营端取不到或算不出的值，统一以占位符“-”展示，不展示文字。本册各表“缺失时”一栏及正文中写作“未提供”“无法计算”“无法折算”“附件未取得”“未取得”的，都是缺失原因，页面上均显示为“-”；读屏读出对应的原因文字。
- 原因需要让运营人员知道时，写在“-”下方，例如保险覆盖率下方注明“N 辆车在多张保单中”。
- 以下是业务状态，照常以文字展示，不改为“-”：未确定（含“尚有 N 辆车未装船”）、到期日未确定、未装船、未投保、未出库、未收款、暂无外销、暂无回款记录、无关联预警、无。
- 企业端按原文字展示，不使用占位符。

<a id="usd-rule"></a>
### 3.3 美元折算与比率

- 美元折算值按 M11 汇率管理中查看时的当前汇率（1 USD = R NGN）折算：原币为 USD 时等于原值；原币为 NGN 时等于原币金额 ÷ R；其他币种 M11 没有汇率，展示“无法折算”。
- 美元折算值保留两位小数，四舍五入；合计与比率用未取舍的值计算，展示时再取舍。
- 比率以百分数展示，保留两位小数、向下截取（例如 99.996% 展示为 99.99%），保证未达到 100% 时不会显示为 100.00%；超过 100% 时按实际值展示，不封顶。
- 比率的分子或分母无法取得（未提供、无法折算）时，比率展示“无法计算”。
- 分母为 0 时，比率展示“无法计算”。

## 4. 应收账款的形成与识别（F-M3-01）

适用范围：平台从 ERP 取得内销发票时的处理规则。结果对全部角色可见，没有用户操作。取得方式由研发决定，本 PRD 不限定。

流程参见：[应收账款形成与差异识别（图 M3-1）](./02-应收账款与发票-流程图与状态机.md#fig-m3-1)。
验收参见：[应收账款的形成与识别](./04-应收账款与发票-验收.md#acc-f-m3-01)。

<a id="receivable-identity"></a>
### 4.1 一张内销发票一笔应收账款

- 平台只对已审核的内销发票形成应收账款；外采发票不形成应收账款。
- 平台以“内销卖方 + 内销发票号”识别同一张内销发票；首次取得时形成一笔应收账款并生成应收账款编号。
- 内销发票缺少发票号或金额时不形成应收账款。
- 再次取得同一张内销发票、且核心资料与原资料一致时，不形成新的应收账款，也不产生差异记录。
- 再次取得同一张内销发票、但核心资料任一项已有值与原资料不一致时，不形成新的应收账款，按[核心资料差异核实（F-M3-07）](#F-M3-07)进入“差异待核实”。
- 应收账款币种取内销发票币种。

<a id="party-match"></a>
### 4.2 买卖双方与平台企业的对应

- 运营人员在 M2 新增或编辑平台企业时，为其关联 ERP 企业，规则见 M2 [关联 ERP 企业（F-EN-10）](../../运营端/M2-运营登录与企业管理/01-运营登录与企业管理-PRD.md#F-EN-10)：一个平台企业可关联多个 ERP 企业，一个 ERP 企业同一时刻只能关联一个平台企业。
- 平台按内销发票上内销卖方、内销买方的 ERP 企业与关联结果对应：内销卖方所关联的平台企业为债权人，内销买方所关联的平台企业为债务人。不按企业名称、登记号比对。
- 债权人、债务人展示平台企业名称。
- 双方都已对应时，本笔应收账款出现在对应企业的入口中（见[企业查看应收账款详情（F-M3-09）](#F-M3-09)）。
- 任一方的 ERP 企业没有关联任何平台企业时，本笔应收账款照常形成并对运营人员可见；该方展示 ERP 上的企业名称，详情中标“未对应平台企业”及具体是哪一方（列表不展示该标识）；对应不上的一方企业看不到本笔应收账款。之后运营人员在 M2 为某平台企业补充关联该 ERP 企业时，本笔应收账款立即自动对应并出现在其入口中。
- 运营人员在 M2 取消某平台企业与 ERP 企业的关联后，以该 ERP 企业为内销卖方或内销买方的应收账款立即不再对应该平台企业，该方改为展示 ERP 企业名称并标“未对应平台企业”；有处理中确权申请时能否取消关联按 M2。
- 同一平台企业同时拥有债权人、债务人角色，不改变它在某张内销发票中的身份：它只能以卖方身份查看本企业开出的发票形成的应收账款，以买方身份查看本企业收到的发票形成的应收账款。

<a id="data-update"></a>
### 4.3 资料更新

- 内销合同、提单、保单、回款记录、外采与外销单据、附件，以及内销发票中原来缺失、后来补齐的项，随 ERP 更新后直接成为当前展示内容，本模块的计算值随之更新。
- 各角色只看到当前资料，平台不提供资料更新的历史记录，也不展示变化前的内容。
- 核心资料已有值的变化不按资料更新处理，按[核心资料差异核实（F-M3-07）](#F-M3-07)处理。

<a id="start-date"></a>
### 7.1 应收账款起算日与到期日

- 应收账款起算日 = 本内销发票全部车辆装船日期中最晚的一个。车辆按 VIN 对应到提单（提单的完整信息见提单信息（M12））。
- 一辆车出现在多张提单上（如转运）时，取该车初始提单的装船日期。
- 车辆分多张提单陆续装船时，全部车辆都有装船日期后才确定起算日；之前起算日展示“未确定（尚有 N 辆车未装船）”，到期日、到期状态同为未确定，这期间本笔应收账款不能申请确权（按 M7a 申请资格，到期状态须为“未到期”）。车辆没有已审核的提单、或其初始提单没有装船日期，都按未装船计。
- 应收账款到期日 = 应收账款起算日 + 账期（整数天，按日历日计算）。起算日未确定、或内销发票没有账期时，到期日为“未确定”。
- 起算日确定之后，提单装船日期变化使计算结果不同时，按[核心资料差异核实（F-M3-07）](#F-M3-07)进入“差异待核实”，起算日、到期日和到期状态继续按原值展示和判断（待确认，见[待确认事项](#pending)）。

| 业务信息 | 含义 | 缺失时 | 运营 | 债权人 | 债务人 |
| --- | --- | --- | --- | --- | --- |
| 账期 | 内销发票上的账款天数，如“90 天” | 展示“未提供” | 可见 | 可见 | 可见 |
| 应收账款起算日 | 平台计算值 | “未确定（尚有 N 辆车未装船）” | 可见 | 可见 | 可见 |
| 应收账款到期日 | 平台计算值 | “未确定” | 可见 | 可见 | 可见 |
| ERP 账款起算日 | 内销发票上 ERP 给出的账款起算日，在[基础交易（F-M3-12）](#F-M3-12)中展示，只供对照，不改变应收账款起算日 | 展示“未提供” | 可见 | 不可见 | 不可见 |
| ERP 账款到期日 | 内销发票上 ERP 给出的账款到期日，在[基础交易（F-M3-12）](#F-M3-12)中展示，只供对照，不改变应收账款到期日和到期状态 | 展示“未提供” | 可见 | 不可见 | 不可见 |

<a id="due-status"></a>
### 7.2 到期状态

| 到期状态 | 条件 |
| --- | --- |
| 到期日未确定 | 应收账款到期日未确定（含尚有车辆未装船） |
| 未到期 | 当前日期（UTC+1）早于或等于到期日 |
| 已到期 | 当前日期（UTC+1）晚于到期日 |

- 到期时点为到期日当天结束（UTC+1 的 24:00）：到期日当天仍为“未到期”。
- 到期状态由“未到期”变为“已到期”时，处理中的确权申请由 M7a 关闭（状态“已关闭”，原因“应收账款已到期”）；本模块不直接撤销申请。

<a id="days-left"></a>
### 7.3 剩余天数与临近到期

- 未到期时展示“剩余 N 天”，N = 到期日 − 当前日期（UTC+1）；到期日当天为“剩余 0 天”。
- 已到期时展示“已到期 N 天”，N = 当前日期（UTC+1）− 到期日。
- 到期日未确定时不展示剩余天数。
- 剩余 0—7 天为“临近到期”，在列表和概要中突出显示。

## 9. 资产健康度（F-M3-11）

适用角色与前提：运营人员。四项指标在详情“进度与核对”层并列展示，列表不展示；企业端不可见。

验收参见：[资产健康度](./04-应收账款与发票-验收.md#acc-f-m3-11)。

| 指标 | 计算 | 展示 |
| --- | --- | --- |
| 已收款比率 | 见[已收、待收与比率](#repay-summary) | 百分数 |
| 终端销售进度 | 本发票已完成销售的车辆数 ÷ 本发票车辆总数 | 百分数，并注明“已售 X 辆／共 Y 辆” |
| 终端回款进度 | 本发票全部车辆外销收款金额（美元）合计 ÷ 应收账款金额（美元） | 百分数 |
| 保险覆盖率 | 应收账款保险金额（美元）÷ 应收账款金额（美元） | 百分数，并展示应收账款保险金额（美元） |

- 完成销售按车辆已外销出库判定：车辆在车辆履约（M5）中已有外销出库，即为已完成销售。
- 每辆车的外销收款金额取自[车辆清单（F-M3-13）](#F-M3-13)。
- 应收账款保险金额 = 本发票全部车辆的车辆保险金额（美元）合计。车辆保险金额按保单信息（M13）的[车辆保险金额](../../运营端/M13-保单信息/01-保单信息-PRD.md#F-M13-05)：保单的保险金额按保单内各车内采单价的比例分摊到每辆车，即本车内采单价（美元）× 该保单保险覆盖率。
- 车辆没有保单时，该车保险金额按 0 计入合计。
- 任一车辆有保单但车辆保险金额无法计算时，保险覆盖率展示“无法计算”。
- 任一车辆同时在多张保单中时，不汇总该车的车辆保险金额（不取最大值、也不相加），保险覆盖率展示“无法计算”，并注明“N 辆车在多张保单中”。
- 比率的精度与无法计算的处理按[美元折算与比率](#usd-rule)。

| 没有未处理的关联风控预警，核心资料状态为“一致” | “无” |

详情概要“关联预警”：

- 第一行为“未处理 N 条”，N 大于 0 时可进入 M8 查看；第二行为“已处理 M 条”。
- 核心资料状态为“差异待核实”时，第一行为“待核实”，未处理、已处理条数照常列在下方。
- 没有任何关联风控预警、且核心资料状态为“一致”时，展示“无”。

共同规则：

- 条数只统计 M8 的关联风控预警，核心资料差异不计入条数。
- 预警的类型、名称、比较口径、差异明细和处理结果以 M8 为准，本模块不复述、不改写，也没有处理预警的操作。
- 关联风控预警不改变本模块的任何金额、比率和状态，也不影响能否发起确权申请。
- M8 结果读取失败时，按[加载失败](#load-fail)仅该处提示失败并可重试，不展示为“无”。

## 13. 确权与审核进度（F-M3-10）

适用角色与前提：运营人员可见全部；企业用户可见本笔应收账款的确权与审核进度，债权人企业用户另有发起申请入口。

流程参见：[各角色进入应收账款的路径（图 M3-6）](./02-应收账款与发票-流程图与状态机.md#fig-m3-6)。
验收参见：[确权与审核进度](./04-应收账款与发票-验收.md#acc-f-m3-10)。

<a id="apply-progress"></a>
### 13.1 确权与审核进度

- 以进度条展示本笔应收账款最近一笔确权申请的进度，分为“发起申请”“债务人确认”“运营审核”“出库”四个环节；申请状态名称与环节对应关系由 M7a 定义，出库环节由 M9 定义，本模块按其原样展示。
- 申请状态与前三个环节的对应：

| 申请状态 | 发起申请 | 债务人确认 | 运营审核 |
| --- | --- | --- | --- |
| 待债务人确认 | 已完成 | 进行中 | 未开始 |
| 债务人已驳回 | 已完成 | 已驳回 | 未开始 |
| 待运营审核 | 已完成 | 已确认 | 进行中 |
| 运营审核通过 | 已完成 | 已确认 | 通过 |
| 已关闭（关闭前为待债务人确认） | 已完成 | 已关闭（应收账款已到期） | 未开始 |
| 已关闭（关闭前为待运营审核） | 已完成 | 已确认 | 已关闭（应收账款已到期） |

- 出库环节：申请状态不是“运营审核通过”时为“未开始”；为“运营审核通过”时按 M9 [出库进度对外提供（F-M9-08）](../../运营端/M9-运营审核与资产出库/01-运营审核与资产出库-PRD.md#F-M9-08)的角色口径展示：运营看到未出库／出库处理中／出库失败（附失败环节与原因）／已出库（附已出库时间）；债权人看到未出库／出库处理中／已出库（出库失败显示为未出库）；债务人不展示出库环节。
- 运营审核只有“通过”，没有不通过；未通过前一直处于“待运营审核”。
- 债务人驳回时，进度条停在“债务人确认”并展示驳回原因和驳回时间；已关闭时，进度条停在关闭时所处环节并标“已关闭（应收账款已到期）”。
- 没有申请时，进度条展示为“未申请”。
- 进度条旁展示该笔申请的申请编号，可进入对应申请详情（运营进入 M9，企业按 M7a、M7b）；申请当次提交的依据以申请详情为准，本模块详情始终展示当前资料。
- 债权人企业用户和运营人员看到本笔应收账款最近一笔申请；债务人企业用户看到发给本企业的最近一笔申请。

<a id="apply-entry"></a>
### 13.2 债权人发起申请入口

- 债权人企业用户查看本企业为债权人的应收账款详情时，提供“发起申请”入口。本笔可申请时可发起；不可申请时不能发起，并展示全部不可申请原因。
- 申请资格、确认内容与提交结果全部按 M7a 单笔发起确权申请（F-M7a-03），本模块不新增规则；提交成功后，进度条按新申请的状态更新。
- 运营人员、债务人企业用户的详情中没有该入口；同时拥有两种角色的企业，只在本企业作为债权人的应收账款详情中看到该入口。

## 14. 核心资料差异核实（F-M3-07）

适用角色与前提：运营人员。本笔应收账款的核心资料状态为“差异待核实”时可记录核实；状态为“一致”时没有核实入口。

流程参见：[核心资料状态（图 M3-3）](./02-应收账款与发票-流程图与状态机.md#fig-m3-3)。
验收参见：[核心资料差异核实](./04-应收账款与发票-验收.md#acc-f-m3-07)。

<a id="core-diff"></a>
### 14.1 差异的产生与展示

- 核心资料包括：内销发票的内销发票日期、内销卖方、内销买方、币种、金额、账期，内销发票车辆明细中的 VIN 与内采单价（含车辆增减），以及已确定的应收账款起算日。
- 平台再次取得同一张内销发票或新的提单资料，使上述任一项已有值与原资料不一致时，核心资料状态变为“差异待核实”。原来缺失、后来补齐的项属于资料更新，不算差异；应收账款起算日从“未确定”变为确定也不算差异。
- ERP 账款起算日、ERP 账款到期日不是核心资料，变化时直接更新。
- 详情和列表继续以原资料展示和计算，不用新取得的值覆盖。
- 运营端展示每一项差异：资料项、原资料值、新取得值、取得时间；车辆差异逐车展示增加、减少或内采单价变化的 VIN；起算日差异同时展示导致变化的提单号。
- 已处于“差异待核实”时又取得新的差异，新差异追加展示。

<a id="verify-record"></a>
### 14.2 记录核实

运营人员针对本笔应收账款当前全部未核实的差异记录一次核实：

| 业务信息 | 类型与取值 | 必填与默认 | 校验与失败结果 |
| --- | --- | --- | --- |
| 核实说明 | 文本，说明核实过程、依据及与 ERP 来源方的沟通结果 | 必填，无默认 | 去除首尾空格后为 1—500 字；为空或超长时不能提交并提示 |
| 核实依据文件 | 附件 | 选填 | PDF、JPG、PNG；最多 5 个；单个不超过 20 MB；不符合时该文件不能加入并提示原因 |

结果：

- 提交后核心资料状态变为“一致”，原资料继续有效，不自动更正、不另建应收账款；差异和本次核实保留在核实记录中。
- 每次核实记录核实人、核实时间、说明、依据文件和所针对的差异，记录不可编辑、不可删除，按时间从新到旧展示。
- 之后又取得新的差异时，状态再次变为“差异待核实”。

边界与异常：

- 两名运营人员同时核实同一笔应收账款时，先提交者生效；后提交者提示“该差异已被他人处理，请刷新后查看”，本次内容不保存。
- 提交时又取得了新的差异，提交仍按提交时可见的差异生效，新差异使状态回到“差异待核实”。
- 提交失败时保留已填写内容，提示失败并可重新提交。

<a id="enterprise-diff"></a>
### 14.3 企业可见差异

- 核心资料状态为“差异待核实”时，债权人、债务人企业用户在详情中看到说明“本笔应收账款的核心资料存在差异，平台正在核实，当前展示原资料”，不展示差异明细、核实说明和依据文件。
- 状态为“一致”时不展示该说明。

<a id="core-impact"></a>
### 14.4 对后续业务的影响

- 核心资料状态是本模块向 M7a、M7b、M9 提供的信息；状态为“差异待核实”时不能对本笔应收账款发起新的确权申请（按 M7a 申请资格）。
- 申请提交后，核心资料变为“差异待核实”或其他资料更新，不要求债务人重新确认或运营重新审核，申请照常推进（按 M7a 规则）；本模块不撤销、驳回或终止任何申请。

## 15. 企业查看应收账款详情（F-M3-09）

适用角色与前提：已完成 M1 首次入驻的企业用户。详情只读，企业端没有任何编辑、补传或核实操作。企业端可见范围不因资产全景调整而扩大。

验收参见：[企业查看应收账款详情](./04-应收账款与发票-验收.md#acc-f-m3-09)。

<a id="enterprise-entry"></a>
### 15.1 谁能看、从哪里进

| 角色 | 可查看的应收账款 | 入口 |
| --- | --- | --- |
| 债权人企业用户 | 本企业为债权人的全部应收账款，含已到期、已收清的记录 | M7a 应收账款列表及申请记录 |
| 债务人企业用户 | 本企业为债务人、且已有确权申请发给本企业的应收账款 | M7b 确权申请列表及申请详情 |

- 企业需同时满足“是该应收账款的对应一方”（按[买卖双方与平台企业的对应](#party-match)）和“拥有对应角色”。例如本企业关联了内销卖方的 ERP 企业，但运营未分配债权人角色时，看不到这笔应收账款。
- 同一企业同时拥有两种角色时，两个入口分别按本企业在该发票中的身份显示；同一笔应收账款不会因双角色而在两个入口同时出现。
- 角色被取消或账号被停用后，立即失去对应查看范围，再打开按[不可访问](#no-access)处理。
- 运营人员在 M2 取消平台企业与某 ERP 企业的关联后，该企业立即失去由这一关联对应的应收账款查看范围。
- 债务人企业用户没有“全部应付”的独立列表；查看范围随确权申请出现，驳回或审核结束后仍可从已处理申请中查看。

<a id="enterprise-scope"></a>
### 15.2 可见内容

企业详情按[详情的结构与顺序](#detail-groups)展示下表中可见的部分，取值与运营端相同：

| 部分 | 债权人企业用户 | 债务人企业用户 |
| --- | --- | --- |
| 概要 | 债权人 → 债务人、应收账款编号、应收账款金额及币种、应收账款起算日、应收账款到期日（不展示剩余天数）、到期状态、已收款金额（美元）、待收款金额（美元）、回款状态 | 与债权人相同 |
| 账期 | 可见 | 可见 |
| 资产健康度 | 不可见 | 不可见 |
| 内销发票 | 内销发票号、内销发票日期、内销发票金额及币种、账期、内销发票附件 | 与债权人相同 |
| 内销合同摘要 | 内销合同号（不可点击）、内销合同日期、内销合同金额及币种、内销合同付款条件、账期、内销合同附件 | 与债权人相同 |
| 车辆清单 | VIN（不可点击）、内采单价（原币及币种） | 与债权人相同 |
| 回款记录 | 交易流水号（不可点击）、收付日期、付款方 → 收款方、金额及币种、收款银行、收款账号、凭证附件 | 收付日期、付款方 → 收款方、金额及币种 |
| 确权与审核进度 | 可见，出库环节按[确权与审核进度](#apply-progress)的债权人口径 | 可见，不展示出库环节 |
| 发起申请入口 | 有，见[债权人发起申请入口](#apply-entry) | 无 |
| 核心资料差异 | 只见说明，见[企业可见差异](#enterprise-diff) | 只见说明 |

企业端不可见：一切美元折算值（已收款金额、待收款金额除外）、已收款比率、资产健康度、预警信息与关联预警、ERP 账款起算日与到期日、首次取得时间、核心资料差异明细与核实记录、M8 风控预警，以及车辆清单中除 VIN、内采单价以外的全部字段和单据跳转。

<a id="status-combo"></a>
## 16. 状态组合与对后续业务的影响

一笔应收账款同时有核心资料状态、到期状态、回款状态三个独立维度，以及由 M7a、M7b、M9 提供的确权与审核进度。下表写清各组合下运营和企业看到什么，以及能否发起新申请（按 M7a 申请资格，此处只列与本模块状态有关的条件）。

| 核心资料状态 | 到期状态 | 回款状态 | 运营看到 | 企业看到 | 能否发起新申请 |
| --- | --- | --- | --- | --- | --- |
| 一致 | 未到期 | 未收款 | 三个状态原样展示 | 三个状态原样展示 | 可以（其他条件由 M7a 定义） |
| 一致 | 未到期 | 部分收款 | 三个状态原样展示 | 三个状态原样展示 | 可以（其他条件由 M7a 定义） |
| 一致 | 未到期 | 已收清 | 三个状态原样展示 | 三个状态原样展示 | 不可以，已收清 |
| 一致 | 已到期 | 任一 | 三个状态原样展示，到期日旁为“已到期 N 天” | 三个状态原样展示 | 不可以，已到期 |
| 一致 | 到期日未确定（含尚有车辆未装船） | 任一 | 三个状态原样展示，起算日注明未确定原因 | 三个状态原样展示 | 不可以，无法判断是否未到期 |
| 差异待核实 | 任一 | 任一 | 预警信息为“有”（没有未处理关联预警时，列表预警列为“待核实”），原资料、差异明细及核实入口 | 原资料及差异说明 | 不可以，核心资料待核实 |

- 资产健康度、预警信息和关联预警只对运营展示，不影响能否发起新申请，也不改变任何状态。
- 任一方未对应平台企业时，对应不上的一方企业看不到本笔应收账款；能否申请同样取决于内销卖方能否对应到拥有债权人角色的平台企业。

## 17. 待确认事项与依赖

下表各项在确认前按“当前处理”执行；推荐口径确认后直接转为规则。

| 编号 | 事项（具体冲突点） | 推荐与当前处理 | 影响 |
| --- | --- | --- | --- |
| Q-M3-03 | 起算日确定后，提单装船日期变化是否应改变起算日 | 推荐：按核心资料差异处理，运营核实前继续按原起算日。理由：与“核心资料不静默覆盖”一致，避免到期日在申请处理中被改动 | [差异的产生与展示](#core-diff)、M7a、M9 |
| Q-M3-11 | 车辆清单默认显示哪些列 | 推荐按信息架构方案：VIN、物流节点、三项单价、外销收款金额默认显示，其余分组展开 | [车辆清单](#F-M3-13)、原型 |
| Q-M3-12 | 原“车辆归属判定”（外采合同买方、外销合同卖方与本应收账款主体比对）是否保留，与合同信息（M4）一并确认 | 当前车辆按 VIN 关联外采合同、外销合同，不做主体比对 | [车辆清单](#F-M3-13)、合同信息（M4） |

依赖：

- ERP：提供已审核的内销发票（含车辆明细与内采单价、账期、ERP 账款起算日与到期日、附件）、内销合同、内销收款及凭证。取得方式由研发决定。
- M2：运营人员为平台企业关联、取消关联 ERP 企业，并提供关联结果，见 M2 [关联 ERP 企业（F-EN-10）](../../运营端/M2-运营登录与企业管理/01-运营登录与企业管理-PRD.md#F-EN-10)。
- 合同信息（M4）：内销合同、外采合同（外采合同号、外采供应商、本车外采合同单价）、外采发票（本车外采发票单价与币种）、外销合同（外销合同号、外销客户、本车外销单价、外销收款）的详情入口与本车值。
- 车辆履约（M5）：每辆车的当前物流节点、是否外销出库与外销出库日期，以及车辆履约详情入口。
- 提单信息（M12）：每辆车所在提单（含初始提单）、装船日期、提单附件及详情入口。
- 保单信息（M13）：每辆车所在保单、车辆保险金额、车辆是否在多张保单中、保单附件及详情入口。
- 资金收付（M14）：回款记录的交易流水号、银行、账号、凭证，以及收付记录详情入口。
