# 应收账款与发票 · 功能与业务规则

2026-11-13｜运营端：运营人员；企业端：债权人企业用户、债务人企业用户（只读详情）｜需求评审稿

本模块共三册：本册写功能、业务规则与字段规则；[流程图与状态机](./02-应收账款与发票-流程图与状态机.md)画出主要流程与状态；[验收](./04-应收账款与发票-验收.md)供测试使用。本模块自身不发送任何消息，所以没有 03 消息通知册，并非缺失。

编号说明：功能编号（F-M3-*）标在章节标题上，供验收追溯；编号沿用原值，已删除的条目不再占号，缺号不代表遗漏。文中“M1”“M2”“M4”—“M9”均指资产可信平台的同级模块。

本册只定义信息需求与业务行为；页面布局与交互承载由 Hallmark 设计决定。以下设计约束由用户指定，保持不变：分类清晰、页面层级少，可有多个二级菜单；运营端左侧菜单名称为“应收账款”；列表以应收账款为单位展示；详情中应收账款信息与发票信息分开呈现，并按[详情的信息分类与顺序](#detail-groups)排列；详情顶部应收账款编号与发票号码之间不加竖线等分隔符。

## 1. 模块是什么

本模块把平台从 ERP 取得的每一张发票作为一笔应收账款，集中呈现这笔应收账款的全部核心事实：谁欠谁、欠多少、何时到期、对应哪些车辆和哪些合同、本笔应收账款已收回多少、还剩多少未收、确权与审核到了哪一步，以及核心资料是否出现过需要核实的差异。运营人员在这里查看全部应收账款，并对核心资料差异记录核实；债权人和债务人企业用户在各自业务入口中只读查看与本企业有关的应收账款详情。本模块是上游采购、车辆履约、下游销售三段追溯的起点，也是确权申请、债务人确认和运营审核共同引用的资料来源。

基本原则：

- 一张发票就是一笔应收账款。发票的卖方（开票方）是债权人，买方（购票方）是债务人；应收账款金额取自发票金额；账款起算日取自 ERP 发票信息，不用发票开立日期代替。
- 平台以发票为入口，按发票获取对应的合同，以及上游采购、车辆履约、下游销售等相关资料。ERP 提供的是关键字段；本 PRD 定义的其他字段默认 ERP 具备，未提供时按缺失规则展示。
- 债权人、债务人是平台企业，由运营人员在 M2 邀请并分配角色；平台通过比对发票上的买卖双方主体与平台企业主体，确定一笔应收账款属于哪两家企业。
- 平台不生成、不签署、不修改发票与合同。任何角色（含运营人员）都不能新增、修改或删除发票、车辆、合同和款项资料；运营人员只能对核心资料差异记录核实。
- 发票信息和发票对应的车辆范围默认固定；ERP 再次提供的内容与原资料不一致时，保留原资料并进入核实，不静默覆盖、不另建一笔应收账款。合同和款项资料随 ERP 更新。
- 款项数据以 ERP 传值为准，企业端与运营端展示同一组数值；本模块不做汇率折算。回款数据偏差过大时由 M8 风控预警提示，本模块只在运营端详情中展示预警字段。
- 运营人员可以查看全部应收账款；企业用户只能查看本企业作为买卖一方的应收账款，且只读。

**一个完整的例子**（企业名称为演示值）。ERP 提供一张发票：卖方 Carloha Holding、买方 Carloha Nigeria，发票号码 INV-0012，发票开立日期 2026-09-01，发票金额 60,000.00 USD，销售清单含 2 辆车（VIN-A 车型甲单价 30,000.00 USD；VIN-B 车型甲单价 30,000.00 USD），装船日期 2026-09-10，账款起算日 2026-09-10，天数 90，账款到期日 2026-12-09（时区 Africa/Lagos）。平台把买卖双方与平台企业主体比对，分别对应到运营已邀请、并分别分配了债权人和债务人角色的两家企业，形成一笔应收账款：债权人 Carloha Holding、债务人 Carloha Nigeria，应收账款金额 60,000.00 USD，账款起算日 2026-09-10，到期日 2026-12-09，到期状态“未到期”。平台按发票取得对应合同（合同号码、价格条款 CIF、付款条件“装船后 90 天”、未开票金额等）。债务人先后两次付款；ERP 在本发票下登记两笔收款：25,000.00 USD 和 10,000.00 USD（后一笔所属交易共 50,000.00 USD，其余 40,000.00 USD 登记在另一张发票下）；累计已收为两笔收款合计 35,000.00 USD，ERP 给出未收金额 25,000.00 USD，回款状态为“部分收款”，运营端回款预警为“无”。运营人员在应收账款列表中按 VIN-A 找到这笔应收账款，在详情中依次查看应收账款信息、确权与审核进度、发票信息、车辆明细、合同信息、回款信息，并从 VIN-A 进入上游采购、车辆履约和下游销售查看这辆车的经历。债权人企业用户在应收账款（债权人）入口打开同一笔应收账款，看到相同的核心事实，但看不到运营核实记录和风控预警；债权人发起确权申请后，债务人企业用户在确权申请（债务人）入口打开这笔应收账款进行核对。

### 1.2 本期不做

- 二手车业务。
- 融资标记及融资公司、融资金额、融资期限等字段。
- 在平台录入、编辑、删除或补传发票、车辆、合同、款项资料；企业端和运营端都没有这类操作。
- 另一套 ERP 财务应收单或应付单；同一份合同不为买卖双方各维护一份。
- 汇率折算与回款偏差判断：由 M8 风控预警使用 M11 汇率管理的汇率完成，本模块不折算任何金额。
- 汇率维护：由 M11 汇率管理定义。
- 发票红冲、作废、替代票：本期 ERP 不存在这类场景。
- 退款、冲销等特殊款项：本期 ERP 不提供这类数据。
- 平台根据天数或发票开立日期推算账款起算日、到期日：两者由 ERP 直接提供。
- 上游采购、车辆履约、下游销售资料的展示规则与状态判定：分别由 M4、M5、M6 定义，本模块只展示其状态并提供跳转。
- 确权申请、债务人确认、运营审核与出库的操作和状态定义：分别由 M7a、M7b、M9 定义；本模块展示其结果，并在债权人详情中提供发起申请入口（规则按 M7a）。
- 风控预警的比对与处理：由 M8 定义，本模块只展示关联预警的数量与入口。
- 中文、英文以外的语言。

## 2. 术语

| 术语 | 含义 |
| --- | --- |
| 应收账款 | 由一张发票形成的债权。一张发票对应一笔应收账款；应收账款金额、币种取自发票金额及币种，账款起算日取自 ERP 发票信息，不另行录入 |
| 应收账款编号 | 平台为每笔应收账款生成的编号，与发票一一对应，全平台唯一，生成后不变 |
| 发票 | 买卖双方之间、由卖方向买方开具的销售发票，由 ERP 提供 |
| 债权人 | 发票的卖方（开票方）所对应的平台企业 |
| 债务人 | 发票的买方（购票方）所对应的平台企业 |
| 平台企业 | 运营人员在 M2 邀请入驻的企业。每个平台企业只有一个企业用户，角色（债权人、债务人，可多选）由运营人员分配 |
| 债权人企业用户 | 拥有债权人角色、且是某笔应收账款债权人的平台企业的唯一用户 |
| 债务人企业用户 | 拥有债务人角色、且是某笔应收账款债务人的平台企业的唯一用户 |
| 核心资料 | 发票信息：发票号码、发票开立日期、卖方、买方、发票金额、币种、装船日期、账款起算日、天数、账款到期日及时区；以及发票对应的销售清单（VIN、车型、单价）。默认固定，已有值出现差异时进入核实 |
| 原资料 | 本笔应收账款首次形成时取得的核心资料，始终是展示与后续业务的依据 |
| 合同 | 买卖双方（债权人与债务人）就本笔应收账款所含车辆签订的合同，同一份合同只维护一份；一笔应收账款可以对应多份合同。上游采购（M4）、下游销售（M6）中的合同在各自的信息大类下展示，以所属大类区分，不另起名称 |
| 账款起算日、天数 | ERP 提供的账款起算日期，以及付款条件中约定的天数（如装船后 90 天） |
| 到期日时区 | ERP 随到期日一并提供的时区，用于判断是否到期；展示时写在到期日后面，不单独列为字段 |
| 收款登记 | ERP 中针对某一张发票登记的收款信息。客户 ERP 只有收款信息，没有债权人登记、债务人确认之分，本模块将其统一作为回款信息展示；回款明细即由本发票下的收款登记组成 |
| 累计已收、未收金额 | 累计已收为本发票下收款登记的收款金额合计；未收金额取自 ERP 的发票未收金额，按原值展示。企业端与运营端展示同一组数值 |
| 回款预警 | M8 风控预警针对本笔应收账款回款数据给出的预警（如某项值与按汇率折算的结果差距过大），本模块只展示有无及简要说明，不给核验结论 |
| 预警信息 | 运营端在列表和详情概要中展示的有／无标识，见[预警信息](#warning-flag) |
| VIN | 车辆识别代号，用来从应收账款的车辆进入上游采购、车辆履约、下游销售的同一辆车 |

<a id="shared-rules"></a>
## 3. 共用展示与异常规则

本节规则适用于本模块全部功能，其他章节直接引用，不重复展开。

<a id="display-values"></a>
### 3.1 来源值、金额与时间

- 发票、车辆、合同、款项的各项值按 ERP 原值展示，不翻译、不改写；切换中英文只改变平台自身的字段名称和状态名称。
- ERP 没有提供某项值时，该项展示“未提供”；某项附件没有取得时，展示“附件未取得”。合同等相关资料按发票获取，未取得时在对应位置展示“未取得”。
- 金额与币种代码同时展示，数值在前、币种代码在后，带千分位，例如“60,000.00 USD”。ERP 提供的金额按原值展示，不四舍五入、不截断。任何位置都不展示没有币种的金额。
- 各金额的币种由 ERP 提供。本模块不对任何金额做汇率折算，不同币种的金额不相加。
- ERP 提供的日期（发票开立日期、合同日期、装船日期、账款起算日、收款日期、到期日）按 ERP 日期原样展示，不做时区换算。
- 带时区的日期把时区写在日期后面，例如“2026-12-09（Africa/Lagos）”，时区不单独列为字段。
- 平台自己记录的时间（资料取得时间、核实时间）展示到分钟并标注时区：按用户在 M1、M2 选择的时区展示；两模块不提供时区设置时统一按 UTC 展示。

<a id="file-view"></a>
### 3.2 附件查看

- 每份附件展示附件名称和取得时间，可在线查看和下载。
- 同一份附件支持多个环节时只保存一份，在各环节引用，不要求重复提供。
- 附件打开或下载失败时，提示“文件暂时无法打开，请稍后重试”，不影响查看其他信息。

<a id="no-access"></a>
### 3.3 不可访问

- 企业用户打开不属于本企业、或本企业已失去对应角色的应收账款时，统一提示“该应收账款不存在或无权查看”，不透露该应收账款是否存在及其任何内容。
- 企业用户未完成 M1 规定的首次入驻步骤（改密、绑定钱包、完善并提交资料）时，不能进入任何应收账款入口，按 M1 引导完成入驻。

<a id="load-fail"></a>
### 3.4 加载失败

- 列表或详情加载失败时，提示加载失败并可重试；不展示不完整的金额或状态，避免把加载失败误显示为“未收款”“未取得”。
- 详情中某一部分（例如回款信息、确权与审核进度）加载失败时，仅该部分提示失败并可重试，其他部分正常展示。

<a id="F-M3-01"></a>
## 4. 应收账款的形成与识别（F-M3-01）

适用范围：平台从 ERP 取得发票时的处理规则。结果对全部角色可见，没有用户操作。本期默认 ERP 能提供本模块所需的全部资料，取得方式由研发决定，本 PRD 不限定。

流程参见：[应收账款形成与差异识别（图 M3-1）](./02-应收账款与发票-流程图与状态机.md#fig-m3-1)。
验收参见：[应收账款的形成与识别](./04-应收账款与发票-验收.md#acc-f-m3-01)。

<a id="receivable-identity"></a>
### 4.1 一张发票一笔应收账款

- 平台以“卖方 + 发票号”识别同一张发票；首次取得时形成一笔应收账款并生成应收账款编号。
- 再次取得同一张发票、且核心资料与原资料完全一致时，不形成新的应收账款，也不产生差异记录。
- 再次取得同一张发票、但核心资料任一项与原资料不一致时，不形成新的应收账款，按[核心资料差异核实（F-M3-07）](#F-M3-07)进入“差异待核实”。
- 本期只处理新车发票。

<a id="party-match"></a>
### 4.2 买卖双方与平台企业的对应

- 平台把发票上的卖方、买方主体信息，分别与平台企业登记的企业主体信息比对（比对项以 M1、M2 定义的企业主体字段为准，如企业名称、企业登记号），比对一致即对应：卖方对应的平台企业为债权人，买方对应的平台企业为债务人。
- 双方都能对应时，本笔应收账款出现在对应企业的入口中（见[企业查看应收账款详情（F-M3-09）](#F-M3-09)）。
- 任一方对应不上时，本笔应收账款照常形成并对运营人员可见，详情中标“未对应平台企业”及具体是哪一方（列表不展示该标识）；对应不上的一方企业看不到本笔应收账款。之后该企业在 M2 入驻或主体信息补齐、能够对应时，自动出现在其入口中。
- 同一平台企业同时拥有债权人、债务人角色，不改变它在某张发票中的身份：它只能以卖方身份查看本企业开出的发票形成的应收账款，以买方身份查看本企业收到的发票形成的应收账款。

<a id="data-update"></a>
### 4.3 资料更新

- 合同、附件、收款登记、未收金额等资料随 ERP 更新，以及发票信息中原来缺失的项由 ERP 补齐时，新内容直接成为当前展示内容。
- 各角色只看到当前资料，平台不提供资料补充或更新的历史记录，也不展示变化前的内容。
- 核心资料（发票信息和销售清单）已有值的变化不按资料更新处理，按[核心资料差异核实（F-M3-07）](#F-M3-07)处理。

## 5. 运营查看应收账款列表（F-M3-02）

适用角色与前提：运营人员，已登录运营端。可查看全部应收账款，包括未对应平台企业的应收账款。

验收参见：[运营查看应收账款列表](./04-应收账款与发票-验收.md#acc-f-m3-02)。

列表以应收账款为单位，每行一笔，只展示定位和判断所需的关键字段；累计已收、未收金额、确权与审核进度等在详情中查看：

| 业务信息 | 含义 | 来源与缺失时 |
| --- | --- | --- |
| 应收账款编号 | 本笔应收账款的编号 | 平台生成 |
| 发票号码 | 形成本笔应收账款的发票号码，与应收账款编号分列展示 | ERP 原值 |
| 债权人 | 债权人企业名称；未对应平台企业时展示发票卖方名称，列表不加“未对应平台企业”标识 | 平台对应结果 |
| 债务人 | 债务人企业名称；未对应平台企业时展示发票买方名称，列表不加“未对应平台企业”标识 | 平台对应结果 |
| 应收账款金额及币种 | 取自发票金额 | ERP 原值，按[来源值、金额与时间](#display-values)展示 |
| 应收账款到期日 | 见[账期与到期状态（F-M3-04）](#F-M3-04)，时区写在日期后面 | ERP 原值；未提供时展示“未提供” |
| 到期状态 | 未到期／已到期／到期日未确定，单独成列，不与到期日合并 | 平台判定 |
| 回款状态 | 未收款／部分收款／已收清 | 平台判定，见[回款状态](#repayment-status) |
| 预警信息 | 有／无，见[预警信息](#warning-flag) | 平台判定 |
| 操作 | “查看”，进入该应收账款详情 | 每行都有 |

查找与筛选：

- 按应收账款编号或发票号码查找，支持部分匹配。
- 按 VIN 查找，结果为车辆清单中包含该 VIN 的全部应收账款；同一 VIN 出现在多笔应收账款中时全部列出，不自动判断哪一笔有效。
- 按申请编号查找，结果为该申请对应的应收账款。
- 筛选：债权人、债务人、币种、到期状态、回款状态、预警信息、核心资料状态、确权与审核进度、账款起算日区间、到期日区间、是否未对应平台企业。多个条件同时生效。
- 默认按账款起算日从新到旧排列；账款起算日未提供的排在最后。
- 运营端左侧菜单名称为“应收账款”。

<a id="warning-flag"></a>
预警信息：

- 本笔应收账款存在未处理的 M8 风控预警（含回款预警），或核心资料状态为“差异待核实”时，预警信息为“有”；两者都没有时为“无”。
- 预警信息只对运营人员展示；核心资料状态本身不在列表和详情概要中单独展示，差异明细在详情中查看。

边界与异常：

- 平台尚未取得任何发票时，展示“暂无应收账款”；有应收账款但筛选无结果时，展示“没有符合条件的应收账款”并可清除筛选。
- 列表不提供新增、编辑、删除操作。
- 加载失败按[加载失败](#load-fail)处理。

- 企业端核心资料存在差异时，按[企业可见差异](#enterprise-diff)展示说明。

## 7. 账期与到期状态（F-M3-04）

适用角色与前提：运营人员；债权人、债务人企业用户可见。账期信息只读，在详情最上方的应收账款概要中展示。

流程参见：[到期状态（图 M3-4）](./02-应收账款与发票-流程图与状态机.md#fig-m3-4)。
验收参见：[账期与到期状态](./04-应收账款与发票-验收.md#acc-f-m3-04)。

| 业务信息 | 含义 | 缺失时 | 运营 | 债权人 | 债务人 |
| --- | --- | --- | --- | --- | --- |
| 账款起算日 | ERP 随发票提供的账款起算日，按原值展示 | 展示“未提供” | 可见 | 可见 | 可见 |
| 天数 | ERP 随发票提供的账期天数，按原值展示，如“90” | 展示“未提供” | 可见 | 可见 | 可见 |
| 应收账款到期日 | ERP 提供的账款到期日及时区，时区写在日期后面，如“2026-12-09（Africa/Lagos）” | 到期日未提供时展示“未提供”；只缺时区时展示日期并注明“时区未提供” | 可见 | 可见 | 可见 |

<a id="due-status"></a>
到期状态：

- 账款起算日、到期日与到期日时区都由 ERP 直接提供，平台不根据天数推算，也不用发票开立日期代替。
- 平台判断是否到期时，把 ERP 时区下的到期时点换算为 UTC+1，再与当前时间（UTC+1）比较；换算后的日期和时间只用于判断，不向任何角色展示。
- 到期时点为到期日当天结束（ERP 时区的 24:00）：到期日当天及之前为“未到期”，之后为“已到期”。
- ERP 未提供到期日或到期日时区时，到期状态为“到期日未确定”。
- 装船日期、账款起算日、天数、到期日及时区属于发票信息，默认固定：原来缺失的项由 ERP 补齐时，按补齐后的资料确定账款起算日和到期状态；已有值发生变化时按[核心资料差异核实（F-M3-07）](#F-M3-07)处理，账款起算日和到期状态仍按原资料判断。
- 到期状态由“未到期”变为“已到期”时，处理中的确权申请由 M7a 关闭（状态“已关闭”，原因“应收账款已到期”）；本模块不直接撤销申请。

- 累计已收、未收金额与应收账款金额之间的关系异常（如两者之和不等于应收账款金额）时，按原值展示；是否预警由 M8 判断，结果展示在运营端回款预警字段。

| 收款交易编号 | 这笔收款的交易编号 | 展示“未提供” | 可见 | 可见 | 不可见 |
| 收款日期 | 收到款项的日期 | 展示“未提供” | 可见 | 可见 | 可见 |
| 收款方 | 收款主体 | 展示“未提供” | 可见 | 可见 | 可见 |
| 付款方 | 付款主体 | 展示“未提供” | 可见 | 可见 | 可见 |
| 收款银行 | 收款银行 | 展示“未提供” | 可见 | 可见 | 不可见 |
| 收款账号 | 收款账号 | 展示“未提供” | 可见 | 可见 | 不可见 |
| 收款金额及币种 | 收款方实际收到、并登记在本发票下的金额 | 展示“未提供” | 可见 | 可见 | 可见 |
| 附件 | 这笔收款的凭证文件 | 展示“附件未取得” | 可见 | 可见 | 不可见 |

- 每条收款登记只属于一张发票；同一笔交易登记在多张发票下时，本笔应收账款只计本发票下登记的收款金额，登记在其他发票下的收款不出现在本笔回款明细中。
- 收款金额币种与应收账款币种不同时，各角色都按 ERP 原币种金额展示，不折算。
- 下游采购商向债务人的付款不属于本模块，不出现在本笔回款信息中。

## 9. 核心资料差异核实（F-M3-07）

适用角色与前提：运营人员。本笔应收账款的核心资料状态为“差异待核实”时可记录核实；状态为“一致”时没有核实入口。

流程参见：[核心资料状态（图 M3-3）](./02-应收账款与发票-流程图与状态机.md#fig-m3-3)。
验收参见：[核心资料差异核实](./04-应收账款与发票-验收.md#acc-f-m3-07)。

<a id="core-diff"></a>
### 9.1 差异的产生与展示

- 平台再次取得同一张发票，核心资料（发票开立日期、卖方、买方、发票金额、币种、装船日期、账款起算日、天数、账款到期日及时区，以及销售清单中的 VIN、车型、单价，含车辆增减）任一项已有值与原资料不一致时，核心资料状态变为“差异待核实”。原来缺失、后续补齐的项属于资料补充，不算差异。本期发票不存在红冲、作废和替代票，这类差异按 ERP 数据异常处理。
- 详情和列表继续以原资料展示，不用新取得的值覆盖。
- 运营端展示每一项差异：资料项、原资料值、新取得值、取得时间；车辆差异逐车展示增加、减少或变化的 VIN。
- 已处于“差异待核实”时又取得新的差异，新差异追加展示。

<a id="verify-record"></a>
### 9.2 记录核实

运营人员针对本笔应收账款当前全部未核实的差异记录一次核实：

| 业务信息 | 类型与取值 | 必填与默认 | 校验与失败结果 |
| --- | --- | --- | --- |
| 核实说明 | 文本，说明核实过程、依据及与 ERP 来源方的沟通结果 | 必填，无默认 | 去除首尾空格后为 1—500 字；为空或超长时不能提交并提示 |
| 核实依据文件 | 附件 | 选填 | PDF、JPG、PNG；最多 5 个；单个不超过 20 MB；不符合时该文件不能加入并提示原因 |

结果：

- 提交后核心资料状态变为“一致”，原资料继续有效，不自动更正、不另建应收账款；差异和本次核实保留在核实记录中。
- 每次核实记录核实人、核实时间、说明、依据文件和所针对的差异，记录不可编辑、不可删除，按时间从新到旧展示。
- 之后又取得新的差异时，状态再次变为“差异待核实”。

边界与异常：

- 两名运营人员同时核实同一笔应收账款时，先提交者生效；后提交者提示“该差异已被他人处理，请刷新后查看”，本次内容不保存。
- 提交时又取得了新的差异，提交仍按提交时可见的差异生效，新差异使状态回到“差异待核实”。
- 提交失败时保留已填写内容，提示失败并可重新提交。

<a id="enterprise-diff"></a>
### 9.3 企业可见差异

- 核心资料状态为“差异待核实”时，债权人、债务人企业用户在详情中看到说明“本笔应收账款的核心资料存在差异，平台正在核实，当前展示原资料”，不展示差异明细、核实说明和依据文件。
- 状态为“一致”时不展示该说明。

<a id="core-impact"></a>
### 9.4 对后续业务的影响

- 核心资料状态是本模块向 M7a、M7b、M9 提供的信息；状态为“差异待核实”时不能对本笔应收账款发起新的确权申请（按 M7a 申请资格）。
- 申请提交后，核心资料变为“差异待核实”或其他资料更新，不要求债务人重新确认或运营重新审核，申请照常推进（按 M7a 规则）；本模块不撤销、驳回或终止任何申请。

## 10. 企业查看应收账款详情（F-M3-09）

适用角色与前提：已完成 M1 首次入驻的企业用户。详情只读，企业端没有任何编辑、补传或核实操作。

验收参见：[企业查看应收账款详情](./04-应收账款与发票-验收.md#acc-f-m3-09)。

<a id="enterprise-entry"></a>
### 10.1 谁能看、从哪里进

| 角色 | 可查看的应收账款 | 入口 |
| --- | --- | --- |
| 债权人企业用户 | 本企业为债权人的全部应收账款，含已到期、已收清的记录 | M7a 应收账款列表及申请记录 |
| 债务人企业用户 | 本企业为债务人、且已有确权申请发给本企业的应收账款 | M7b 确权申请列表及申请详情 |

- 企业需同时满足“是该应收账款的对应一方”和“拥有对应角色”。例如本企业是发票卖方但运营未分配债权人角色时，看不到这笔应收账款。
- 同一企业同时拥有两种角色时，两个入口分别按本企业在该发票中的身份显示；同一笔应收账款不会因双角色而在两个入口同时出现（一张发票的卖方和买方不会是同一平台企业）。
- 角色被取消或账号被停用后，立即失去对应查看范围，再打开按[不可访问](#no-access)处理。
- 债务人企业用户没有“全部应付”的独立列表；查看范围随确权申请出现，驳回或审核结束后仍可从已处理申请中查看。

<a id="enterprise-scope"></a>
### 10.2 可见内容

企业详情按[详情的信息分类与顺序](#detail-groups)展示各表中对应角色列为“可见”的内容，包括：

- 应收账款概要（应收账款编号、发票号码、金额、债权人、债务人、账期、到期状态、回款状态）；核心资料存在差异时的说明见[企业可见差异](#enterprise-diff)。
- 确权与审核进度、发票信息与附件、车辆信息明细、合同信息。
- 债权人企业用户另有[债权人发起申请入口](#apply-entry)。
- 回款信息：回款统计（应收账款金额、累计已收、未收金额）和回款明细。跨币种金额按原币种如实展示，不折算。

企业端不可见：首次取得时间、核心资料差异明细与核实记录、预警信息、回款预警、风控预警，以及车辆信息明细中的履约进展、外采订单号、销售合同号及其状态和跳转。

- 运营与企业看到的 ERP 业务值和回款状态相同，差别只在可见范围。
- 债务人看不到回款明细中的收款交易编号、收款银行、收款账号和附件。

## 11. 确权审核进度与关联追溯入口（F-M3-10）

适用角色与前提：运营人员可见全部；企业用户可见本笔应收账款的确权与审核进度，债权人企业用户另有发起申请入口。

流程参见：[各角色进入应收账款的路径（图 M3-6）](./02-应收账款与发票-流程图与状态机.md#fig-m3-6)。
验收参见：[确权审核进度与关联追溯入口](./04-应收账款与发票-验收.md#acc-f-m3-10)。

<a id="apply-progress"></a>
### 11.1 确权与审核进度

- 以进度条展示本笔应收账款最近一笔确权申请的进度，放在应收账款概要下方。进度条分为“发起申请”“债务人确认”“运营审核”三个环节，出库环节在 M9 定义后接在其后；申请状态名称与环节对应关系由 M7a 定义，本模块按其原样展示。
- 申请状态与进度条的对应：

| 申请状态 | 发起申请 | 债务人确认 | 运营审核 |
| --- | --- | --- | --- |
| 待债务人确认 | 已完成 | 进行中 | 未开始 |
| 债务人已驳回 | 已完成 | 已驳回 | 未开始 |
| 待运营审核 | 已完成 | 已确认 | 进行中 |
| 运营审核通过 | 已完成 | 已确认 | 通过 |
| 已关闭（关闭前为待债务人确认） | 已完成 | 已关闭（应收账款已到期） | 未开始 |
| 已关闭（关闭前为待运营审核） | 已完成 | 已确认 | 已关闭（应收账款已到期） |

- 运营审核只有“通过”，没有不通过；未通过前一直处于“待运营审核”。
- 债务人驳回时，进度条停在“债务人确认”并展示驳回原因和驳回时间；已关闭时，进度条停在关闭时所处环节并标“已关闭（应收账款已到期）”。
- 没有申请时，进度条展示为“未申请”。
- 进度条旁展示该笔申请的申请编号，可进入对应申请详情；申请当次提交的依据以申请详情为准，本模块详情始终展示当前资料。
- 债权人企业用户和运营人员看到本笔应收账款最近一笔申请；债务人企业用户看到发给本企业的最近一笔申请。

<a id="apply-entry"></a>
### 11.2 债权人发起申请入口

- 债权人企业用户查看本企业为债权人的应收账款详情时，提供“发起申请”入口。本笔可申请时可发起；不可申请时不能发起，并展示全部不可申请原因（M7a 应收账款列表只标“可申请／不可申请”，原因在此处查看）。
- 申请资格、确认内容与提交结果全部按 M7a 单笔发起确权申请（F-M7a-03），本模块不新增规则；提交成功后，进度条按新申请的状态更新。
- 运营人员、债务人企业用户的详情中没有该入口；同时拥有两种角色的企业，只在本企业作为债权人的应收账款详情中看到该入口。

<a id="trace-entry"></a>

<a id="status-combo"></a>
## 12. 状态组合与对后续业务的影响

一笔应收账款同时有到期状态、回款状态、核心资料状态三个独立维度，运营端另有回款预警，以及由 M7a、M7b、M9 提供的确权与审核进度。到期状态、回款状态在列表和详情概要中展示，核心资料状态通过运营端预警信息体现，三者互不覆盖。下表写清各组合下运营和企业看到什么，以及能否发起新申请（按 M7a 申请资格，此处只列与本模块状态有关的条件）。

| 核心资料状态 | 到期状态 | 回款状态 | 运营看到 | 企业看到 | 能否发起新申请 |
| --- | --- | --- | --- | --- | --- |
| 一致 | 未到期 | 未收款 | 三个状态原样展示 | 三个状态原样展示 | 可以（其他条件由 M7a 定义） |
| 一致 | 未到期 | 部分收款 | 三个状态原样展示 | 三个状态原样展示 | 可以（其他条件由 M7a 定义） |
| 一致 | 未到期 | 已收清 | 三个状态原样展示 | 三个状态原样展示 | 不可以，未收金额为 0 |
| 一致 | 已到期 | 任一 | 三个状态原样展示 | 三个状态原样展示 | 不可以，已到期 |
| 一致 | 到期日未确定 | 任一 | 三个状态原样展示 | 三个状态原样展示 | 不可以，无法判断是否未到期 |
| 差异待核实 | 任一 | 任一 | 预警信息为“有”，原资料、差异明细及核实入口 | 原资料及差异说明 | 不可以，核心资料待核实 |

- 回款预警只对运营展示，不影响能否发起新申请；M9 运营审核时可通过 M8 查看。
- 任一方未对应平台企业时，对应不上的一方企业看不到本笔应收账款；能否申请同样取决于卖方能否对应到拥有债权人角色的平台企业。

<a id="pending"></a>
## 13. 待确认事项与依赖

本模块当前没有待确认事项。申请资格、申请状态名称与进度条环节由 M7a 定义，本模块按其原样引用；M7b、M9 在各自 PRD 中对齐。

依赖：

- ERP：以发票为入口提供发票、销售清单、合同、装船日期、账款起算日、天数、账款到期日及时区、币种、收款信息（收款登记）、发票未收金额等资料和附件。ERP 给出的是关键字段，本 PRD 定义的其他字段默认 ERP 具备，未提供时按缺失规则展示。取得方式由研发决定。客户 ERP 提供的各项资料都由平台对接，按下表由对应模块承接：

| ERP 功能 | 承接模块 |
| --- | --- |
| 内部销售：合同管理、发票管理、收款登记 | 本模块（M3） |
| 外部采购：外采订单、外采发票、外采付款、VIN 登记 | M4 上游采购 |
| 内部销售：提单登记、保单登记、费用登记；入库管理：清关登记 | M5 车辆履约 |
| 外部销售：整车销售／批售的合同、发票、收款 | M6 下游销售 |

- M2：提供平台企业、企业主体信息、企业唯一用户、运营分配的企业角色和运营人员账号；企业停用或角色变化后，本模块查看范围随之变化。
- M1：提供企业首次入驻完成状态、企业主体信息和用户时区设置。
- M4、M6：按本笔应收账款提供每辆车的归属结果、对应的外采订单号／销售合同号及其付款情况／收款情况，并提供采购交易详情、销售交易详情及按应收账款车辆追溯的入口和返回。
- M5：提供每辆车的履约进展和车辆履约详情的入口与返回。
- M7a：定义申请资格、申请状态、进度条环节对应、单笔发起确权申请（本模块债权人详情中的发起入口按其规则）以及到期时关闭处理中申请。
- M7b、M9：提供债务人处理、运营审核与出库的结果；M9 可通过 M8 查看回款预警。
- M8：提供与本笔应收账款关联的风控预警（是否有未处理预警、数量与入口），以及回款预警（有无、简要说明、入口）；回款偏差的比对口径、汇率折算与预警阈值在 M8 设计，所用汇率来自 M11 汇率管理。
