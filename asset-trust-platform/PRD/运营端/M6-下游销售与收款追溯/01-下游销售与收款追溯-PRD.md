# 下游销售与收款追溯 · 功能与业务规则

2026-11-12｜运营端：运营人员｜需求评审稿

本模块共三册：本册写功能、业务规则与字段规则；[流程图与状态机](./02-下游销售与收款追溯-流程图与状态机.md)画出主要流程与状态；[验收](./04-下游销售与收款追溯-验收.md)供测试使用。本模块自身不发送任何消息，所以没有 03 消息通知册，并非缺失。

编号说明：功能编号（F-M6-*）标在章节标题上，供验收追溯。文中“M1”—“M11”均指资产可信平台的同级模块；“应收账款”及其字段、状态以[应收账款与发票（M3）](../../两端共用/M3-应收账款与发票/01-应收账款与发票-PRD.md)为准。

本册只定义信息需求与业务行为；页面布局与交互承载由 Hallmark 设计决定。以下设计约束由用户指定，保持不变：分类清晰、页面层级少，可有多个二级菜单。

## 1. 模块是什么

本模块回答“应收账款里的这辆车，买方后来卖给了谁、依据哪份合同、开了哪些发票、从客户那里收到了多少钱”。平台以应收账款的发票为入口：按发票销售清单中的 VIN，取得 ERP 整车销售／批售中列有该 VIN 的合同，以及合同下的发票和发票下的收款。这些资料以合同为单位组成一笔销售交易。运营人员可以从应收账款（M3）中的某个 VIN 直接进入，看到这辆车对应的销售交易，以及这笔销售是否确实由本笔应收账款的买方卖出；也可以在下游销售列表中按 VIN、销售合同编号、发票号码、客户查找全部销售交易。本模块只供运营端使用，并为风控预警（M8）、运营审核与资产出库（M9）提供已有销售事实和原件的查看入口。

基本原则：

- 下游销售是本笔应收账款的买方（M3 中的债务人一方）把车辆卖给客户的交易，与形成应收账款的发票是两笔不同的交易。下游的合同、发票、收款单独展示，不并入应收账款，不改变应收账款的任何金额和状态。
- 客户向卖方的付款不是应收账款的回款：销售收款不计入 M3 的累计已收、未收金额和回款状态。
- 合同、发票、收款随同一笔销售交易一起展示，不按单据拆成互不相连的列表。同一份合同就是卖方与客户双方的合同，只展示一份，不为客户另列一份采购合同。
- VIN 相同不等于这笔销售就属于本笔应收账款的车辆：平台同时比对合同卖方是否就是本笔应收账款的买方，结果如实标出，不自动认定、不自动排除。
- 合同和发票常覆盖多辆车。发票金额按原值展示并标明所属合同的车辆数，不当作本笔应收账款车辆的销售金额；本笔应收账款车辆只看各自的销售价格。
- 下游销售资料以 ERP 传值为准。ERP 给出的是关键字段；本 PRD 定义的其他字段默认 ERP 具备，未提供时按缺失规则展示。各金额的币种由 ERP 提供，本模块不做汇率折算。任何角色都不能在平台新增、修改或删除下游资料。
- 客户只是交易对象，没有平台账号或确权职责。平台只展示 ERP 提供的客户名称和客户号，不另外采集客户的个人联系方式、证件、住址等信息。企业端（债权人、债务人）本期都看不到下游销售资料。

**一个完整的例子**（企业、客户名称和单据编号为演示值）。应收账款 AR-0012（发票号码 INV-0012，卖方 Carloha Holding、买方 Carloha Nigeria）的销售清单含 VIN-A、VIN-B 两辆车。平台按这两个 VIN 查找 ERP 整车销售／批售的合同，取得列有 VIN-A 的合同 SC-2045：销售合同编号 SC-2045，日期 2026-10-05，卖方 Carloha Nigeria，客户 Lagos Motors Ltd、客户号 C-0388，车辆为 VIN-A 销售价格 45,000,000.00 NGN、VIN-C 销售价格 45,000,000.00 NGN，未开票金额 0.00 NGN。合同下有发票 SI-3301：日期 2026-10-08，金额 90,000,000.00 NGN，未收金额 40,000,000.00 NGN；发票下有一笔收款：收款交易编号 RC-5501，收款日期 2026-10-20，付款方 Lagos Motors Ltd，收款方 Carloha Nigeria，收款金额 50,000,000.00 NGN。平台把这些资料组成销售交易 SC-2045，发票 SI-3301 的收款状态和销售交易的收款情况都是“部分收款”。ERP 中没有列有 VIN-B 的合同。运营人员在 AR-0012 的详情中点 VIN-A 进入本模块：看到 AR-0012 的 2 辆车里，VIN-A 的归属结果是“已对应”，对应销售交易 SC-2045，客户 Lagos Motors Ltd；VIN-B 的归属结果是“暂无下游销售”。运营人员打开 SC-2045，看到发票金额 90,000,000.00 NGN 标明“所属合同共 2 辆车，其中本笔应收账款 1 辆”，本笔应收账款车辆销售价格合计 45,000,000.00 NGN；查看合同原件和收款凭证后，从 VIN-A 进入车辆物流与履约追溯（M5）查看这辆车的提单和清关，再返回 AR-0012。AR-0012 的累计已收、未收金额和回款状态不因这笔销售收款发生任何变化。

### 1.2 本期不做

- 二手车业务。
- 在平台录入、编辑、删除或补传任何下游销售资料；运营端和企业端都没有这类操作。
- 客户（下游采购商）入驻、账号、确认或确权。
- 采集 ERP 客户名称、客户号以外的客户资料，例如个人联系方式、证件、住址和个人账户。
- 企业端查看下游销售资料，包括债权人和债务人。
- 把销售收款计入应收账款的回款，或用下游销售金额改变应收账款金额、回款或到期状态。
- 把发票金额或收款拆分到单辆车，以及计算单车毛利。
- 汇率折算：本模块不折算任何金额，不同币种的金额不相加。
- 人工认定车辆归属或记录核验结论：归属结果只按资料自动展示，随资料更新重新判定。
- 主体不一致、VIN 不一致的风控比对与处理：由 M8 定义，本模块只提供资料和预警入口。
- 车辆出库、交付、签收、借还、提前交车和退车退订等事件：客户 ERP 本期提供的整车销售／批售资料中没有这类信息，本模块不展示车辆交付状态。车辆的提单、保单、费用、清关资料在车辆物流与履约追溯（M5）查看。
- 退款、冲销等特殊款项：本期 ERP 不提供这类数据。
- 上游采购资料：由上游采购追溯（M4）定义。
- 中文、英文以外的语言。

## 2. 术语

| 术语 | 含义 |
| --- | --- |
| 下游销售 | 应收账款的买方把车辆卖给客户的交易，对应 ERP 外部销售中的整车销售／批售。归入“下游销售”信息大类，与应收账款（M3）、上游采购（M4）中的合同和发票以所属大类区分 |
| 客户 | 下游销售合同的买方，即下游采购商，按 ERP 原值展示名称和客户号；在平台中只是交易对象 |
| 卖方 | 下游销售合同的卖方，正常情况下就是本笔应收账款的买方 |
| 合同 | 下游销售中卖方与客户之间的销售合同，以销售合同编号标识，列明车辆 VIN 和每辆车的销售价格。客户视角的“采购合同”就是这同一份合同 |
| 发票 | 下游销售中卖方就某份合同向客户开出的发票。每张发票对应一份合同，一份合同可以有多张发票 |
| 收款 | ERP 中针对下游某一张发票登记的收款记录，收款金额为收款方实际收到的金额。分次收款各为一条 |
| 销售交易 | 一份合同，以及该合同下的发票和发票下的收款。下游销售列表以销售交易为单位 |
| 销售价格 | 合同中某辆车的销售价格及币种 |
| 未开票金额 | 合同中尚未开具发票的金额 |
| 未收金额 | 下游某张发票尚未收到的金额 |
| 归属结果 | 对“本笔应收账款的某辆车”判定的下游销售对应情况：已对应、多笔销售、卖方不一致、暂无下游销售 |
| 运营人员 | 运营端账号的使用者，即 M2 定义的运营管理员；本期运营端只有这一种角色，权限相同 |
| VIN | 车辆识别代号，用来从应收账款的车辆进入本模块 |

## 3. 共用展示与异常规则

本节规则适用于本模块全部功能，其他章节直接引用，不重复展开。展示口径与 M3 的[来源值、金额与时间](../../两端共用/M3-应收账款与发票/01-应收账款与发票-PRD.md#display-values)一致。

<a id="display-values"></a>
### 3.1 来源值、金额与时间

- 合同、发票、收款的各项值按 ERP 原值展示，不翻译、不改写；切换中英文只改变平台自身的字段名称、状态名称和提示。
- ERP 没有提供某项值时，该项展示“未提供”；某份附件没有取得时，展示“附件未取得”。
- 金额与币种代码同时展示，数值在前、币种代码在后，带千分位，例如“90,000,000.00 NGN”。ERP 提供的金额按原值展示，不四舍五入、不截断。任何位置都不展示没有币种的金额。
- 各金额的币种由 ERP 提供。本模块不对任何金额做汇率折算，不同币种的金额不相加；需要合计而币种不同时，按币种分别列出或展示“无法合计”，以各处规则为准。
- ERP 提供的日期（合同日期、发票日期、收款日期）按 ERP 日期原样展示，不做时区换算。
- 平台自己记录的时间（资料取得时间）展示到分钟并标注时区：按运营人员在 M2 账号设置中选择的时区展示；M2 不提供时区设置时统一按 UTC 展示。

<a id="file-view"></a>
### 3.2 附件查看

- 每份附件展示附件名称和取得时间，可在线查看和下载。
- 同一份文件支持多个环节时只保存一份，在各环节引用。
- 附件打开或下载失败时，提示“文件暂时无法打开，请稍后重试”，不影响查看其他信息。

<a id="no-access"></a>
### 3.3 不可访问

- 企业端没有任何下游销售入口。企业用户通过链接打开本模块任何内容时，统一提示“该内容不存在或无权查看”，不透露其是否存在及任何内容。
- 运营人员处于待首次改密、已停用或锁定中时不能使用本模块，判定以 M2 为准。

<a id="load-fail"></a>
### 3.4 加载失败

- 列表或详情加载失败时，提示加载失败并可重试；不展示不完整的金额或状态，避免把加载失败误显示为“未收款”“未取得”或“暂无下游销售”。
- 详情中某一部分（例如收款、关联应收账款）加载失败时，仅该部分提示失败并可重试，其他部分正常展示。

## 4. 下游销售资料的组织（F-M6-01）

适用范围：平台从 ERP 取得下游销售资料时的处理规则。结果对运营人员可见，没有用户操作。客户 ERP 外部销售中整车销售／批售的合同、发票、收款都由本模块对接；取得方式由研发决定，本 PRD 不限定。

流程参见：[下游销售资料的取得与组织（图 M6-1）](./02-下游销售与收款追溯-流程图与状态机.md#fig-m6-1)。
验收参见：[下游销售资料的组织](./04-下游销售与收款追溯-验收.md#acc-f-m6-01)。

<a id="erp-mapping"></a>
### 4.1 ERP 资料与本模块的对应

| ERP 功能 | ERP 字段 | 在本模块中的位置 |
| --- | --- | --- |
| 整车销售／批售：合同 | 销售合同编号、客户、客户号、VIN、销售价格（币种、金额） | [合同](#field-contract)；VIN 与销售价格在[合同车辆与销售价格](#field-vehicles)中逐车展示 |
| 整车销售／批售：发票 | 关联销售合同信息 | 发票归入该合同所在的销售交易，合同信息在[合同](#field-contract)中展示，[发票](#field-invoice)中只展示对应销售合同编号 |
| 整车销售／批售：发票 | 发票号码、日期、金额 | [发票](#field-invoice) |
| 整车销售／批售：收款 | 关联发票信息 | 收款归入该发票，发票信息在[发票](#field-invoice)中展示，[收款记录](#field-receipt)中只展示对应发票号码 |
| 整车销售／批售：收款 | 收款交易编号、收款日期、收款方、付款方、收款银行、收款账号、收款金额（收款方收到） | [收款记录](#field-receipt) |

本 PRD 另外定义、默认 ERP 具备的字段：合同日期、卖方、车型、价格条款、交货地点、付款条件、未开票金额、发票未收金额、各金额的币种，以及合同、发票、收款的附件。ERP 未提供时按[来源值、金额与时间](#display-values)展示“未提供”或“附件未取得”。

<a id="trade-identity"></a>
### 4.2 取得资料与组成销售交易

- 平台以应收账款的发票为入口：对发票销售清单中的每个 VIN，取得车辆中列有该 VIN 的全部合同，以及每份合同下的全部发票和每张发票下的全部收款。
- 平台以销售合同编号识别同一份合同；首次取得时形成一笔销售交易。
- 发票按其关联的销售合同归入对应销售交易；收款按其关联的发票归入该发票。
- 同一 VIN 列在多份合同中时，每份合同都形成销售交易，由[车辆归属判定（F-M6-02）](#F-M6-02)如实标出。
- 平台以“销售合同编号 + 发票号码”识别同一张发票，以“发票 + 收款交易编号”识别同一笔收款；同一份合同、同一张发票、同一笔收款再次取得且内容一致时，不重复展示，也不产生变化记录。
- 合同已取得但还没有发票、发票已取得但还没有收款，都是资料尚在补充，照常展示已取得部分。

<a id="trade-update"></a>
### 4.3 资料更新

- 下游销售资料随 ERP 持续补充。ERP 再次提供同一份资料但内容不同（含合同车辆增减、销售价格变化、发票金额或未收金额变化、未开票金额变化、附件更换）时，新内容成为当前展示内容，之前的版本保留在[资料补充记录](#supplement-log)中，不覆盖删除。
- ERP 不再提供某份资料时，该资料从当前展示中移除，移除记录保留在资料补充记录中。
- 资料更新后，[车辆归属判定（F-M6-02）](#F-M6-02)、[收款状态与收款情况](#collect-status)都按最新资料重新判定。
- 下游资料的更新不改变应收账款（M3）的销售清单、金额、回款和任何状态。

<a id="F-M6-02"></a>
## 5. 车辆归属判定（F-M6-02）

适用范围：平台对“应收账款中的每一辆车”判定其下游销售对应情况。结果对运营人员可见，没有用户操作。

流程参见：[车辆归属判定（图 M6-2）](./02-下游销售与收款追溯-流程图与状态机.md#fig-m6-2)。
验收参见：[车辆归属判定](./04-下游销售与收款追溯-验收.md#acc-f-m6-02)。

<a id="attribution"></a>
### 5.1 判定规则

对应收账款 R 销售清单中的某个 VIN：

1. 找出车辆中列有该 VIN 的全部销售交易。
2. 逐笔比对合同卖方与 R 的买方主体。比对方式与 M3 中[买卖双方与平台企业的对应](../../两端共用/M3-应收账款与发票/01-应收账款与发票-PRD.md#party-match)相同：R 的买方已对应平台企业时，与该平台企业登记的企业主体信息比对；未对应时，与 R 发票上的买方主体信息比对。合同卖方未提供时视为比对不一致。本期按主体本身比对，不把关联公司视为同一主体。
3. 按下表得出归属结果：

| 归属结果 | 判定条件 | 运营看到 |
| --- | --- | --- |
| 已对应 | 恰有 1 笔列有该 VIN 的销售交易，其合同卖方与 R 的买方比对一致 | 对应的销售交易；卖方不一致的其他销售交易另列为“其他列有该 VIN 的销售交易”，逐笔说明原因 |
| 多笔销售 | 有 2 笔及以上列有该 VIN 的销售交易，其合同卖方与 R 的买方比对一致 | 全部列出，按合同日期从新到旧；平台不判断哪一笔是本车的实际销售 |
| 卖方不一致 | 有列有该 VIN 的销售交易，但合同卖方都与 R 的买方比对不一致 | 全部列出，逐笔标“卖方与应收账款买方不一致”或“卖方未提供”；这些销售交易不视为本笔应收账款车辆的下游销售 |
| 暂无下游销售 | 没有任何销售交易列有该 VIN | 展示“平台尚未取得该车的下游销售资料”；这可能是车辆尚未售出，不表示业务有错误 |

- 归属结果是事实标注，不是审核结论，也不是风控预警；运营人员不需要也不能在本模块认定或更改归属结果。
- 同一 VIN 出现在多笔应收账款中时，对每笔应收账款分别判定，互不影响。
- 资料更新后自动重新判定，例如取得新合同后“暂无下游销售”可变为“已对应”。
- 是否构成主体不一致、VIN 不一致的风控预警，由 M8 判定。

## 6. 运营查看下游销售列表（F-M6-03）

适用角色与前提：可正常使用的运营人员。可查看平台已取得的全部销售交易。

验收参见：[运营查看下游销售列表](./04-下游销售与收款追溯-验收.md#acc-f-m6-03)。

列表以销售交易为单位，每行一笔：

| 业务信息 | 含义 | 来源与缺失时 |
| --- | --- | --- |
| 销售合同编号 | 合同编号 | ERP 原值 |
| 合同日期 | 合同日期 | ERP 原值；未提供时展示“未提供” |
| 卖方 | 合同卖方 | ERP 原值；未提供时展示“未提供” |
| 客户、客户号 | 合同的客户名称与客户号 | ERP 原值；未提供时展示“未提供” |
| 车辆数 | 合同列明的车辆数 | 平台计数 |
| 销售价格合计 | 合同各车销售价格之和，见[合同车辆与销售价格](#field-vehicles) | 平台合计；有价格未提供或币种不同时展示“无法合计” |
| 已开票金额 | 本合同下全部发票金额之和，币种不同时按币种分别列出 | 没有发票时展示 0；某张发票金额未提供时展示“未提供” |
| 累计已收 | 本合同下全部收款的收款金额合计，币种不同时按币种分别列出 | 没有收款时展示 0 |
| 收款情况 | 未收款／部分收款／已收清 | 平台判定，见[收款状态与收款情况](#collect-status) |
| 资料进度 | 六项资料全部取得时为“齐全”，否则为已取得项数与总数，如“4/6” | 平台判定，见[资料进度](#material-progress) |
| 关联应收账款 | 合同中的车辆出现在哪些应收账款中，展示应收账款编号；超过一笔时展示笔数 | 平台判定；没有时展示“未关联应收账款” |

查找与筛选：

- 按 VIN 查找，结果为车辆中列有该 VIN 的全部销售交易。
- 按销售合同编号、发票号码、收款交易编号查找，支持部分匹配。
- 按客户名称或客户号查找，支持部分匹配。
- 按应收账款编号或应收账款的发票号码查找，结果为车辆中列有该应收账款任一 VIN 的全部销售交易。
- 筛选：卖方、客户、币种、收款情况、资料进度是否齐全、合同日期区间。多个条件同时生效。
- 默认按合同日期从新到旧排列；日期未提供的排在最后。

边界与异常：

- 平台尚未取得任何下游销售资料时，展示“暂无下游销售资料”；有资料但查找或筛选无结果时，展示“没有符合条件的销售交易”并可清除条件。
- 列表不提供新增、编辑、删除操作。
- 加载失败按[加载失败](#load-fail)处理。

## 7. 按应收账款车辆追溯（F-M6-04）

适用角色与前提：可正常使用的运营人员。从应收账款（M3）详情的车辆信息明细中点某个 VIN 进入（见 M3 [关联追溯与风控入口](../../两端共用/M3-应收账款与发票/01-应收账款与发票-PRD.md#trace-entry)），带入该应收账款作为追溯对象和返回目标；也可在本模块按 VIN 查找后进入。

流程参见：[各入口与返回路径（图 M6-4）](./02-下游销售与收款追溯-流程图与状态机.md#fig-m6-4)。
验收参见：[按应收账款车辆追溯](./04-下游销售与收款追溯-验收.md#acc-f-m6-04)。

<a id="trace-receivable"></a>
### 7.1 从应收账款进入

展示本笔应收账款的下游销售总览，并定位到所点的 VIN：

| 业务信息 | 含义 | 来源与缺失时 |
| --- | --- | --- |
| 应收账款编号、发票号码、买方 | 追溯对象，取自 M3 | M3 原值 |
| 车辆数量 | 本笔应收账款销售清单的车辆数 | M3 原值 |
| 归属结果汇总 | 已对应、多笔销售、卖方不一致、暂无下游销售各几辆 | 平台判定 |
| 每辆车：VIN、车型 | 取自 M3 销售清单 | M3 原值 |
| 每辆车：归属结果 | 见[车辆归属判定（F-M6-02）](#attribution) | 平台判定 |
| 每辆车：对应的销售交易 | 合同卖方与本笔应收账款买方比对一致的销售交易（已对应时 1 笔，多笔销售时全部列出）：销售合同编号、合同日期、客户、客户号、该车销售价格及币种、发票张数、累计已收、收款情况 | ERP 原值与平台判定；缺失项展示“未提供”；没有时按归属结果展示 |
| 每辆车：其他列有该 VIN 的销售交易 | 合同卖方与本笔应收账款买方不一致的销售交易及原因 | 没有时不展示 |

- 每笔销售交易都可进入[销售交易详情（F-M6-05）](#F-M6-05)，并带上本笔应收账款作为对照对象和返回目标。
- 每辆车都可进入车辆物流与履约追溯（M5）查看同一 VIN，并带上本笔应收账款作为返回目标。
- 可返回进入前的应收账款详情。

<a id="trace-vin"></a>
### 7.2 按 VIN 查找进入

- 没有带入应收账款时，展示该 VIN 出现在哪些应收账款中（应收账款编号、发票号码、买方），以及对每笔应收账款的归属结果；选择某笔应收账款后按[从应收账款进入](#trace-receivable)展示。
- 该 VIN 不在任何应收账款的销售清单中、但列在某笔销售交易的合同中时，列出这些销售交易，标“未关联应收账款”，不判定归属结果。
- 该 VIN 既不在任何应收账款中、也不在任何销售交易中时，展示“未找到该 VIN 的下游销售资料”。

边界与异常：

- 从 M3 带入的 VIN 已不在该应收账款当前展示的销售清单中时，按该应收账款当前销售清单展示总览，不定位到该 VIN，并说明“该车已不在本笔应收账款的销售清单中”。
- 加载失败按[加载失败](#load-fail)处理。

## 8. 销售交易详情（F-M6-05）

适用角色与前提：可正常使用的运营人员，从下游销售列表、按应收账款车辆追溯、M8 或 M9 进入。详情只读，任何角色都没有编辑、补传入口。

验收参见：[销售交易详情](./04-下游销售与收款追溯-验收.md#acc-f-m6-05)。

<a id="detail-groups"></a>
### 8.1 详情包含的信息

详情包含以下信息类别，展示顺序与承载方式由 Hallmark 决定：

1. [合同](#field-contract)。
2. [合同车辆与销售价格](#field-vehicles)。
3. [发票](#field-invoice)及其下的[销售收款（F-M6-06）](#F-M6-06)。
4. [关联应收账款](#field-receivables)。
5. 处理信息：[资料进度](#material-progress)、[资料补充记录](#supplement-log)、[关联风控预警](#risk-entry)。

从按应收账款车辆追溯进入时，详情带上该应收账款作为对照对象：车辆明细中标出属于该应收账款的车辆，并展示[对照应收账款时的车辆金额](#price-rule)。

<a id="field-contract"></a>
### 8.2 合同

| 业务信息 | 含义 | 缺失时 |
| --- | --- | --- |
| 销售合同编号 | 合同编号 | 不会缺失（以此识别同一份合同） |
| 合同日期 | 合同日期 | 展示“未提供” |
| 卖方 | 合同卖方 | 展示“未提供” |
| 客户 | 合同买方的名称 | 展示“未提供” |
| 客户号 | ERP 中的客户编号 | 展示“未提供” |
| 价格条款 | 按 ERP 原值展示 | 展示“未提供” |
| 交货地点 | 按 ERP 原值展示 | 展示“未提供” |
| 付款条件 | 按 ERP 原值展示 | 展示“未提供” |
| 未开票金额及币种 | 合同中尚未开具发票的金额 | 展示“未提供” |
| 合同附件 | 已签合同文件，可多份 | 展示“附件未取得” |

- 合同只展示一份，即卖方与客户双方的同一份合同。
- 平台不对合同的法律或财务有效性下结论；价格条款等的专业解释不在本平台给出。

<a id="field-vehicles"></a>
### 8.3 合同车辆与销售价格

合同列明的每辆车一行，按 ERP 顺序展示。

| 业务信息 | 含义 | 缺失时 |
| --- | --- | --- |
| VIN | 合同列明的车辆 | 不会缺失（合同车辆以 VIN 为准） |
| 车型 | 车型 | 展示“未提供” |
| 销售价格及币种 | 该车在本合同中的销售价格 | 展示“未提供” |
| 所属应收账款 | 该 VIN 出现在哪些应收账款的销售清单中（应收账款编号）及对每笔的归属结果 | 没有时展示“未关联应收账款” |
| 车辆数 | 合同列明的车辆数 | 平台计数 |
| 销售价格合计 | 各车销售价格之和，币种全部相同时才计算 | 有价格未提供或币种不同时展示“无法合计” |

<a id="price-rule"></a>
对照应收账款时的车辆金额：

| 业务信息 | 含义 | 缺失时 |
| --- | --- | --- |
| 本笔应收账款车辆数 | 该应收账款的车辆中，列在本合同中的车辆数，同时展示合同车辆数，如“2 辆中的 1 辆” | 平台计数 |
| 本笔应收账款车辆销售价格合计 | 上述车辆的销售价格之和，币种全部相同时才计算 | 有价格未提供或币种不同时展示“无法合计” |

- 发票金额、收款金额都按原值展示，不按比例分摊到单辆车，不当作本笔应收账款车辆的销售金额。
- 车辆的提单、保单、清关等在 M5 展示；本模块的合同车辆只说明这辆车卖给了谁、以什么价格。

<a id="field-invoice"></a>
### 8.4 发票

一笔销售交易可以有多张发票，逐张展示，按发票日期从新到旧排列；一张都未取得时展示“发票未取得”。

| 业务信息 | 含义 | 缺失时 |
| --- | --- | --- |
| 发票号码 | 发票号码 | 不会缺失（以此识别同一张发票） |
| 发票日期 | 发票开具日期 | 展示“未提供” |
| 对应销售合同编号 | 开票时关联的合同 | 不会缺失（发票按此归入销售交易） |
| 发票金额及币种 | 发票金额，同时标明所属合同的车辆数 | 展示“未提供” |
| 未收金额及币种 | 该发票尚未收到的金额 | 展示“未提供” |
| 累计已收 | 该发票下收款的收款金额合计，币种不同时按币种分别列出 | 没有收款时展示 0 |
| 收款状态 | 未收款／部分收款／已收清，见[收款状态与收款情况](#collect-status) | 不会缺失 |
| 发票附件 | 发票原件 | 展示“附件未取得” |

- 发票的卖方、客户与所属合同相同，不重复展示。
- 下游发票只说明销售事实，不是应收账款的发票，不进入应收账款的发票信息和回款统计。

<a id="field-receivables"></a>
### 8.5 关联应收账款

列出合同车辆出现在其销售清单里的全部应收账款：应收账款编号、发票号码、买方、涉及本销售交易的 VIN 及车辆数、各 VIN 的归属结果。每笔应收账款都可进入 M3 应收账款详情。

<a id="risk-entry"></a>
### 8.6 关联风控预警

- 销售交易有关联风控预警（例如 M8 的主体不一致、VIN 不一致）时，展示未处理和已处理预警的数量，可进入 M8 查看；没有时展示“无关联预警”。
- 预警的比对口径、生成与处理由 M8 定义，本模块不重复比对。

<a id="F-M6-06"></a>
## 9. 销售收款（F-M6-06）

适用角色与前提：可正常使用的运营人员，在销售交易详情中查看；收款资料只读，由 ERP 持续补充。本期 ERP 不提供退款、冲销等特殊款项。

流程参见：[发票收款状态（图 M6-3）](./02-下游销售与收款追溯-流程图与状态机.md#fig-m6-3)。
验收参见：[销售收款](./04-下游销售与收款追溯-验收.md#acc-f-m6-06)。

<a id="collect-status"></a>
### 9.1 收款状态与收款情况

每张发票的收款状态按 ERP 提供的未收金额和该发票下的收款判定，口径与 M3 回款状态一致：

| 收款状态 | 判定条件 |
| --- | --- |
| 未收款 | 未收金额不为 0（或未提供），且该发票下没有收款 |
| 部分收款 | 未收金额大于 0（或未提供），且该发票下已有收款 |
| 已收清 | 未收金额为 0 |

每笔销售交易的收款情况按合同下的全部发票和未开票金额判定，自上而下取第一条满足的结果：

| 收款情况 | 判定条件 |
| --- | --- |
| 已收清 | 合同下至少有一张发票，全部发票的收款状态为“已收清”，且未开票金额为 0 |
| 未收款 | 合同下没有任何收款 |
| 部分收款 | 其他情况，例如已有收款但仍有发票未收清，或未开票金额不为 0 或未提供 |

- 收款状态和收款情况只描述卖方向客户的收款，与应收账款的回款状态无关，也不影响应收账款能否申请确权。
- 累计已收、未收金额与发票金额之间的关系异常（例如两者之和不等于发票金额）时，按原值展示，不由本模块更正；是否预警由 M8 判断。

<a id="field-receipt"></a>
### 9.2 收款记录

每张发票下逐笔展示收款，按收款日期从新到旧排列；没有收款时展示“暂无收款记录”。

| 业务信息 | 含义 | 缺失时 |
| --- | --- | --- |
| 对应发票号码 | 登记收款时关联的发票 | 不会缺失（收款按此归入发票） |
| 收款交易编号 | 收款交易编号 | 不会缺失（以此识别同一笔收款） |
| 收款日期 | 收款日期 | 展示“未提供” |
| 收款方 | 收款主体 | 展示“未提供” |
| 付款方 | 付款主体 | 展示“未提供” |
| 收款银行 | 收款方的收款银行 | 展示“未提供” |
| 收款账号 | 收款方的收款账号 | 展示“未提供” |
| 收款金额及币种 | 收款方实际收到的金额 | 展示“未提供” |
| 同一交易编号登记的其他发票 | 同一收款交易编号还登记在哪些下游发票下（以发票号码标识）及各自收款金额 | 没有时不展示 |
| 收款凭证 | 到账凭证、银行流水等附件 | 展示“附件未取得” |

<a id="receipt-owner"></a>
款项归属：

- 每条收款只属于一张发票；同一笔交易登记在多张发票下时，每张只计本发票下登记的收款金额。
- 分次收款各为一条收款记录。
- 付款方、收款方按 ERP 原值展示；付款方不是客户、收款方不是卖方时，本模块如实展示，是否预警由 M8 判断。
- 收款按发票展示，不拆分到单辆车，不计入任何应收账款的回款。
- 收款币种与发票币种不同时按 ERP 原币种展示，不折算。

<a id="F-M6-07"></a>
## 10. 资料进度与持续补充（F-M6-07）

适用角色与前提：可正常使用的运营人员。

验收参见：[资料进度与持续补充](./04-下游销售与收款追溯-验收.md#acc-f-m6-07)。

<a id="material-progress"></a>
### 10.1 资料进度

每笔销售交易按以下资料项逐项展示“已取得”或“未取得”，已取得的同时展示最近取得时间：

| 资料项 | 判定为已取得的条件 |
| --- | --- |
| 合同 | 销售交易已形成即为已取得 |
| 合同附件 | 已取得至少一份合同文件 |
| 发票 | 已取得至少一张发票 |
| 发票附件 | 已取得至少一份发票原件 |
| 收款 | 已有至少一笔收款 |
| 收款凭证 | 已取得至少一份收款凭证 |

- “未取得”只表示平台还没有这项资料，不表示业务有错误；收款未取得与“未收款”不冲突。
- 六项全部已取得时，资料进度为“齐全”。
- 资料进度不作为确权申请、运营审核或出库的条件；是否在审核中使用由 M9 定义。

<a id="supplement-log"></a>
### 10.2 资料补充记录

- 每次取得新资料、资料更新或资料被移除，记录资料项、变化内容（变化前后的值或文件）和取得时间，按时间从新到旧展示。
- 补充记录不可编辑、不可删除。

验收参见：[可见范围与跨模块入口](./04-下游销售与收款追溯-验收.md#acc-f-m6-08)。

<a id="visibility"></a>
### 11.1 谁能看

| 角色 | 能否查看下游销售 | 说明 |
| --- | --- | --- |
| 运营人员 | 可以查看全部内容 | 只读，没有编辑、补传或认定操作 |
| 债权人企业用户 | 不可以 | 企业端没有下游销售入口；应收账款详情中也没有下游销售入口，与 M3 [企业可见内容](../../两端共用/M3-应收账款与发票/01-应收账款与发票-PRD.md#enterprise-scope)一致；客户、销售价格和收款属于买方的销售商业信息，不向卖方展示 |
| 债务人企业用户 | 不可以 | 企业端没有下游销售入口；这些资料来自本企业 ERP，确权核对以应收账款为准，不需要在平台另看 |
| 客户 | 不适用 | 只是交易对象，没有平台账号 |

企业用户通过链接打开本模块内容时按[不可访问](#no-access)处理。

<a id="entries"></a>
### 11.2 进入与返回

| 从哪里进入 | 进入什么 | 返回到哪里 |
| --- | --- | --- |
| 应收账款（M3）详情中某个 VIN | [从应收账款进入](#trace-receivable)，定位到该 VIN | 该应收账款详情 |
| 下游销售列表 | [销售交易详情（F-M6-05）](#F-M6-05) | 下游销售列表，保留原查找与筛选条件 |
| 风控预警（M8）详情中的下游销售资料 | 对应销售交易详情 | 该预警详情 |
| 运营审核与资产出库（M9）中的下游销售资料 | 对应应收账款的[从应收账款进入](#trace-receivable)或某笔销售交易详情 | M9 中进入前的位置 |
| 本模块中某个 VIN | 车辆物流与履约追溯（M5）中同一 VIN | 本模块进入前的位置 |

- 本模块始终展示当前资料；M9 审核当次使用的依据以 M9 为准。
- 从其他模块带入的应收账款、销售交易或 VIN 已不存在时，展示“该内容不存在或已更新”，并可返回来源位置。

<a id="pending"></a>
## 12. 待确认事项与依赖

本模块当前没有待确认事项。

依赖：

- ERP：提供外部销售中整车销售／批售的合同、发票、收款，字段见[ERP 资料与本模块的对应](#erp-mapping)；合同日期、卖方、车型、价格条款、交货地点、付款条件、未开票金额、发票未收金额、各金额币种及各类附件等本 PRD 定义的其他字段默认 ERP 具备，未提供时按缺失规则展示。取得方式由研发决定。
- 应收账款与发票（M3）：提供应收账款编号、发票号码、买方及其平台企业对应结果、销售清单（VIN、车型），以及从 VIN 进入本模块的入口和返回目标。
- M1、M2：提供企业主体信息（用于卖方比对）、运营人员账号及状态、运营端账号设置中的界面语言与时区。
- 车辆物流与履约追溯（M5）：按 VIN 提供车辆履约查看入口并可返回本模块。
- 风控预警（M8）：使用本模块的下游资料进行主体、VIN 比对，向本模块提供关联预警数量与入口，并判断收款金额关系异常、付款方或收款方不一致是否预警。
- 运营审核与资产出库（M9）：从审核中进入本模块查看下游销售事实和原件，是否以本模块资料作为审核依据由 M9 定义。
