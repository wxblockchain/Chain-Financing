# 合约管理 · 功能与业务规则

2026-10-30｜管理端：运营管理人员｜需求评审稿

本模块共三册：本册写功能、业务规则、字段规则与交互逻辑；[流程图与状态机](./v1.0-合约管理-流程图与状态机.md)画出主要流程与状态；[验收](./v1.0-合约管理-验收.md)供测试使用。本模块的合约查看、配置、名称编辑和启用停用都不发送消息或邮件，所以没有 03 消息通知册，并非缺失。

依据标注：规则后的【确认】表示用户已明确，【建议·已采纳】表示诊断建议已由用户采纳，两者同样有效；未标注的是为落实上述规则所写的产品细化，涉及口径未定的已列入[待确认事项](#pending)。本册只定义信息需求与业务行为，页面布局、组件形态与交互承载由 Hallmark 设计决定。

## 1. 模块是什么

平台用来铸造代币的链上合约，由开发人员部署并配置到平台；运营管理人员查看全部已配置合约，可以编辑合约在平台上的名称，并选择启用或停用合约。运营在发行二审通过时，要从这些合约中选一份用来铸造；哪些合约可以被选，按本册的[发行二审可选的合约（F-CT-02）](#F-CT-02)判断。合约的部署和初始配置由开发人员负责。

基本原则：

- 新合约由开发人员部署并配置；配置后运营可以编辑名称、启用和停用【确认】。合约标准、对应资产类型、所在网络和合约地址对运营只读。
- 当前只支持 Ethereum 网络；当前只有 ERC-3525 标准的合约，对应的资产类型是应收账款【确认】（BR-17）。
- 只有运营管理人员能看到合约管理；监管机构和企业都看不到【确认】（简报 4.4）。
- 运营二审通过时必须选择一份合约【确认】（BR-14），只能从与该笔资产类型对应、状态为可用的合约中选择【建议·已采纳】（A-ISSUE）。

**一个完整的例子。** 开发人员在 Ethereum 上部署并配置一份 ERC-3525 合约，名称为“合约 K”，资产类型为应收账款，初始状态停用。运营甲打开合约管理，核对完整地址，把名称改为“应收账款合约 K”，保存后启用，列表显示新名称和状态“可用”。企业 A 的发行申请一审通过后，甲在二审中选择这份合约并通过。之后甲回到合约管理停用它，列表保留该合约并显示“停用”，新的二审不能再选择它。若一笔使用该合约的申请已铸造失败，运营仍可沿原合约手动重试，无需先启用；已铸造代币仍可按原条件申请销毁。

### 1.1 需求清单

本模块即简报的合约管理（A-CONTRACT）。

| 功能 | 谁 | 想做什么 | 为了什么 |
| --- | --- | --- | --- |
| [合约列表（F-CT-01）](#F-CT-01) | 运营管理人员 | 查看平台已配置的全部合约及其状态 | 核对铸造用的是哪份合约、部署在哪里、能否使用 |
| [编辑合约名称（F-CT-03）](#F-CT-03) | 运营管理人员 | 修改已配置合约在平台上的名称 | 便于识别和选择合约 |
| [启用与停用合约（F-CT-04）](#F-CT-04) | 运营管理人员 | 调整已配置合约的使用状态 | 控制该合约能否被新的发行二审选择 |
| [发行二审可选的合约（F-CT-02）](#F-CT-02) | 运营管理人员（在发行二审中） | 知道二审通过时能选哪些合约 | 只用对应资产类型、仍可使用的合约铸造 |

### 1.2 本期不做

- 在平台上新增、删除合约，或由运营修改合约标准、对应资产类型、所在网络、合约地址。
- Ethereum 以外的网络、ERC-3525 以外的合约标准、应收账款以外的资产类型【确认】（BR-17）。
- 合约的部署、升级与链上参数展示。
- 按合约统计铸造数量、代币数量等业务数据：代币的查看归代币台账（M4b）。
- 合约列表的搜索与筛选：合约数量少，列表一次展示全部合约。
- 合约配置变化时向运营发送消息。
- 在二审中选择合约的界面与提交流程：归代币发行 · 审核与铸造（M3b），本册只规定可选范围。

## 2. 术语

| 术语 | 含义 |
| --- | --- |
| 合约 | 部署在 Ethereum 上、平台用来铸造和销毁代币的链上程序。一份合约对应一个合约地址；地址不同即为另一份合约 |
| 合约标准 | 合约遵循的代币标准。当前只有 ERC-3525（半同质化代币标准） |
| 对应资产类型 | 这份合约用来为哪类可信资产铸造代币。当前只有应收账款 |
| 合约状态 | 合约在平台中的使用状态：可用或停用；“启用”操作使状态变为“可用”，见[合约状态](#status) |
| 可选的合约 | 运营在发行二审通过时可以选择的合约，见[发行二审可选的合约（F-CT-02）](#F-CT-02) |

## 3. 共同规则

<a id="access"></a>
### 3.1 谁能使用

- 只有账号正常、已登录的运营管理人员能使用合约管理；每个运营账号看到的内容相同，见[菜单权限矩阵（F-LG-10）](./v1.0-管理端登录与权限-PRD.md#F-LG-10)。
- 监管机构看不到合约管理，直接访问按[无权访问的处理（F-LG-12）](./v1.0-管理端登录与权限-PRD.md#F-LG-12)拒绝【确认】。
- 企业在面客端看不到合约管理；面客端展示代币所属合约时如何展示，由我的代币与销毁申请（M4a）定义。

<a id="readonly"></a>
### 3.2 合约从哪里来

- 合约由开发人员部署并完成初始配置【确认】；初始名称和状态随配置提供。
- 配置后，运营可按[编辑合约名称（F-CT-03）](#F-CT-03)和[启用与停用合约（F-CT-04）](#F-CT-04)维护；平台没有新增或删除合约的入口。
- 运营修改合约标准、对应资产类型、所在网络或合约地址，或绕过界面新增、删除合约时，操作被拒绝，合约不变。
- 开发人员新增合约或运营维护成功后，其他运营重新打开或刷新合约管理即可看到最新结果；不发送任何消息。
- 合约一经配置就一直保留在列表中；不再使用时停用，不从平台移除，保证已用它铸造的代币仍能找到所属合约。
- 同一份合约的合约地址不会变化；需要换地址时，由开发人员配置为另一份合约。

<a id="fields"></a>
### 3.3 合约的信息

依据：展示字段【建议·已采纳】（A-CONTRACT）。

以下信息初始由开发人员配置；运营可编辑名称、调整状态，其余信息只读。

| 业务信息 | 含义 | 取值 | 展示规则 |
| --- | --- | --- | --- |
| 合约名称 | 这份合约在平台上的名称，供运营识别；其他模块展示代币所属合约时也用它 | 开发人员配置初始文本，之后运营可编辑 | 展示当前已保存的名称原文，不随界面语言翻译；编辑规则见[编辑合约名称（F-CT-03）](#F-CT-03) |
| 合约标准 | 合约遵循的代币标准 | 当前只有 ERC-3525【确认】 | 中英文界面都写作 ERC-3525 |
| 对应资产类型 | 这份合约用来为哪类可信资产铸造代币 | 当前只有应收账款【确认】 | 随界面语言展示，名称与[可信资产](./v1.0-可信资产-PRD.md)中的资产类型一致 |
| 所在网络 | 合约部署在哪条区块链网络 | 当前只有 Ethereum【确认】 | 中英文界面都写作 Ethereum，不译为“以太坊”，也不写作 ETH，与[钱包地址与网络名称的展示](./v1.0-企业登录与企业账户-PRD.md#address-display)一致 |
| 合约地址 | 合约在 Ethereum 上的地址 | 开发人员配置的地址 | 缩写展示，保留大小写；运营可以核对完整地址，复制得到的是完整地址；缩写位数由设计确定，与[钱包地址与网络名称的展示](./v1.0-企业登录与企业账户-PRD.md#address-display)一致 |
| 合约状态 | 合约在平台中的使用状态 | 可用、停用 | 随界面语言展示，含义见[合约状态](#status)；运营操作见[启用与停用合约（F-CT-04）](#F-CT-04) |

- 界面语言切换后，对应资产类型和合约状态随之变化；合约名称、合约标准、所在网络和合约地址不变，见[界面语言与时区（F-LG-09）](./v1.0-管理端登录与权限-PRD.md#F-LG-09)。

<a id="status"></a>
### 3.4 合约状态

| 合约状态 | 含义 | 发行二审能否选择 | 已用它铸造的代币 |
| --- | --- | --- | --- |
| 可用 | 已启用，可作为新的发行二审选择 | 能，资产类型对应时，见[发行二审可选的合约（F-CT-02）](#F-CT-02) | 所属合约不变 |
| 停用 | 已停用，不能作为新的发行二审选择 | 不能 | 所属合约及展示不变，原业务继续办理，见[停用与既有业务](#inflight) |

- 合约初始状态由开发人员配置时设定；运营可通过启用和停用在两种状态间来回调整【确认】；不限制调整次数。
- 状态调整不改变合约的其他信息，不发送任何消息。
- 平台状态控制新业务选择，既有业务按[停用与既有业务](#inflight)继续【确认】。

流程参见：[合约状态机](./v1.0-合约管理-流程图与状态机.md#state-1)。

<a id="inflight"></a>
### 3.5 停用与既有业务

- 合约停用仅使其不能再被新业务选择，不代表链上无法执行；之前已确定合约的业务保持继续【确认】。
- 本期首次选择合约仍在运营发行二审进行，按[发行二审可选的合约（F-CT-02）](#F-CT-02)校验；二审通过已确定合约后，平台停用不撤销原选择、不要求改选。
- 已在铸造中的申请继续承接结果；铸造失败后运营仍可沿二审原合约手动重试，无需先将平台状态恢复可用，见[铸造失败手动重试（A-ISSUE-07）](./v1.0-代币发行-审核与铸造-PRD.md#A-ISSUE-07)。
- 已铸造代币仍可查看；满足到期、结清及无融资质押等原条件时，可继续提交、审核和执行销毁，失败由运营沿原合约手动重试，成功后原机构继续解除监管。
- 铸造、销毁与重试继续使用各笔业务原合约、原数量及原地址；平台停用不改变任何既有归属或业务状态，也不自动发起重试。
- 实际链上执行异常按对应业务失败及重试规则处理；平台启用、停用不会改变链上异常是否已恢复。链上异常所需恢复由开发人员处理，恢复后仍由运营手动重试。

<a id="F-CT-01"></a>
## 4. 合约列表（F-CT-01）

适用角色与前提：账号正常、已登录的运营管理人员。

依据：查看平台已配置的合约及展示字段（A-CONTRACT）；运营可编辑名称、启用和停用【确认】。

- 列表展示开发人员已配置的全部合约，包括停用的合约。每份合约可以看到[合约的信息](#fields)中的全部六项：合约名称、合约标准、对应资产类型、所在网络、合约地址、合约状态。
- 可用的合约排在停用的合约之前；同一状态内按开发人员配置的先后从新到旧排列，每次打开顺序一致。
- 每份已配置合约提供[编辑合约名称（F-CT-03）](#F-CT-03)与[启用与停用合约（F-CT-04）](#F-CT-04)的操作；权限边界见[合约从哪里来](#readonly)。
- 平台还没有配置任何合约时，说明平台尚未配置合约、合约由开发人员配置；不提供任何操作入口，不展示示例合约。此时发行二审没有可选的合约，见[发行二审可选的合约（F-CT-02）](#F-CT-02)。
- 读取失败时说明暂时无法读取、可以重试，不显示为“尚未配置合约”。两种情况须能区分。

流程参见：[合约从配置到被选用（图 1）](./v1.0-合约管理-流程图与状态机.md#fig-1)。

<a id="F-CT-03"></a>
## 5. 编辑合约名称（F-CT-03）

适用角色与前提：账号正常、已登录的运营管理人员；合约已由开发人员配置，可用、停用两种状态下均可编辑【确认】。

- 运营选择一份合约，编辑时带出当前已保存的名称；可核对合约地址，确认修改对象。
- 保存成功后返回合约列表，展示新名称；其他运营刷新后看到同一名称。
- 平台中引用该合约的名称展示取当前已保存的名称，包括发行二审、已有申请及代币所属合约的展示；名称变化不改变合约地址、既有申请选定的合约或代币所属关系。
- 编辑名称不修改链上合约，也不改变合约状态、可选资格和列表中按配置时间确定的先后顺序。

| 业务字段 | 含义与类型 | 必填条件与默认值 | 可编辑范围 | 校验与失败结果 |
| --- | --- | --- | --- | --- |
| 合约名称 | 合约在平台上的识别名称，文本 | 保存时必填；初始带出当前已保存值 | 运营可编辑可用或停用合约的名称 | 空值或纯空白不能保存，说明须填写名称，原名称不变；长度及重名边界见[合约名称校验边界（Q-CT-02）](#Q-CT-02) |

名称与状态维护共用以下规则，状态维护引用本处：

<a id="maintenance-results"></a>
### 5.1 维护中的取消、失败与冲突

- 取消或放弃未提交的操作，返回合约列表，原有信息和状态不变。
- 保存未成功时说明本次未完成，原有信息和状态不变，运营可重试；不能把未保存内容显示为已生效。
- 提交期间不重复办理同一次维护；重复提交不得造成额外变化。
- 另一位运营已修改同一项信息时，本次提交不覆盖其结果，展示最新值，运营重新核对后可再次操作；名称和状态分别维护，编辑名称不覆盖状态变化，调整状态不覆盖名称变化。
- 提交时已无权操作，按[无权访问的处理（F-LG-12）](./v1.0-管理端登录与权限-PRD.md#F-LG-12)拒绝，数据不变。
- 名称编辑与启用停用均不发送消息或邮件。

<a id="F-CT-04"></a>
## 6. 启用与停用合约（F-CT-04）

适用角色与前提：账号正常、已登录的运营管理人员；合约已由开发人员配置【确认】。

| 当前状态 | 运营可执行的操作 | 成功后的状态与结果 |
| --- | --- | --- |
| 可用 | 停用 | 状态变为停用，保留在列表中并按停用合约排序；新的发行二审不能再选；二审已选但尚未提交时按[提交时核对合约（F-CT-02）](#F-CT-02)处理 |
| 停用 | 启用 | 状态变为可用，按可用合约排序；资产类型匹配的发行二审重新可选；既有业务不以启用作为继续办理的前提 |

- 发起操作时展示目标合约的当前名称、可核对的完整地址、当前状态和将变为的状态，并说明对二审选择的影响，由运营确认后提交。
- 启用或停用成功后回到合约列表，显示新状态；其他运营刷新后看到最新状态。
- 已处于目标状态时保持该状态，说明当前状态，不再执行一次状态转换。
- 启用或停用只改变平台使用状态，合约名称、标准、对应资产类型、网络、地址和配置时间不变。
- 启用不自动通过发行二审或自动重试铸造；停用对已铸造失败、铸造中及已铸造代币的影响按[合约状态](#status)处理。
- 链上部署等异常造成的合约不可用仍需开发人员处理，平台启用不代表链上异常已经恢复。
- 取消、失败、重复提交、冲突及权限变化按[维护中的取消、失败与冲突](#maintenance-results)处理。

流程参见：[维护合约名称与状态（图 3）](./v1.0-合约管理-流程图与状态机.md#fig-3)、[合约状态机](./v1.0-合约管理-流程图与状态机.md#state-1)。

<a id="F-CT-02"></a>
## 7. 发行二审可选的合约（F-CT-02）

适用角色与前提：账号正常、已登录的运营管理人员，正在办理一笔待运营审核的发行申请。

依据：二审通过时必须选择发行 / 铸造合约【确认】（BR-14）；按资产类型匹配可用合约【建议·已采纳】（A-ISSUE）；当前只有 ERC-3525 合约，对应应收账款【确认】（BR-17）。

本节只规定哪些合约可以被选择；选择的界面、展示与提交流程归代币发行 · 审核与铸造（M3b）。

- 可选范围是同时满足以下两项的全部合约：
  - 合约状态为可用；
  - 对应资产类型与这笔发行申请所关联资产的资产类型相同。
- 停用的合约、对应资产类型不同的合约，不出现在可选范围中。

| 合约状态 | 对应资产类型与申请资产相同 | 能否被选择 |
| --- | --- | --- |
| 可用 | 是 | 能 |
| 可用 | 否 | 不能 |
| 停用 | 是 | 不能 |
| 停用 | 否 | 不能 |

- 可选的合约有多份时，由运营自行选择一份；平台不预先选定。
- 运营提交二审通过时，平台再确认一次所选合约仍为可用；已被停用时，本次二审通过不成立，申请保持待运营审核，要求重新选择合约。
- 没有任何可选的合约时，运营不能完成二审通过；已有匹配但停用的合约可在合约管理中启用，没有匹配合约时需由开发人员配置；驳回不受影响，仍可办理。
- 选择合约只在二审通过时进行；二审通过后不能改选，铸造失败重试沿用原合约，不受平台停用阻断，见[停用与既有业务](#inflight)。

流程参见：[发行二审选择合约（图 2）](./v1.0-合约管理-流程图与状态机.md#fig-2)。
