# 消息通知 · 功能与业务规则

2026-10-29｜面客端：企业用户；管理端：监管机构、运营管理人员｜需求评审稿

本模块共三册：本册写功能、业务规则、字段规则与交互逻辑；[流程图与状态机](./v1.0-消息通知-流程图与状态机.md)画出主要流程与状态；[验收](./v1.0-消息通知-验收.md)供测试使用。本模块自己不发送任何消息，每类消息由发送它的业务模块在自己的消息通知册中维护【确认】，所以本模块没有 03 消息通知册，并非缺失。各来源模块完成迁入之前，此前集中登记的消息暂存于[各来源消息过渡登记](./v1.0-消息通知-消息通知.md)，它不属于本模块的规则。

依据标注：规则后的【确认】表示用户已明确，【建议·已采纳】表示诊断建议已由用户采纳，【沿用参考件】表示用户确认按借贷平台消息通知的做法实现，三者同样有效；未标注的是为落实上述规则所写的产品细化。功能编号沿用原值，新增功能接续编号，所以章节中的编号不按顺序排列。本册只定义信息需求与业务行为，页面布局、组件形态与交互承载由 Hallmark 设计决定。

## 1. 模块是什么

消息通知是代币发行平台的站内信箱，面客端和管理端各有一个。业务进行中发生需要某人知道的事情时，由对应的业务模块（来源模块）发出一条站内消息；本模块负责让企业用户、监管机构和运营管理人员：

1. 在本端任何业务页面看到未读数，并打开最近消息预览；
2. 打开消息列表，按分类和已读状态筛选；
3. 打开一条消息读完整内容，读完自动变为已读；需要时一次标记全部已读；
4. 从消息前往原业务查看或办理，再回到消息。

基本原则：

- **本模块只承接，不发消息。** 发什么、何时发、发给谁、写什么、去向哪一笔业务，都由来源模块在自己的消息通知册中维护【确认】。本册只定义消息的接收、展示、阅读与前往规则，以及来源接入时须提供的信息；来源增减或修改消息时，本册不随之修改。
- **站内消息为主。** 邮件只用于监管机构邀请，由发送它的模块定义，不进入消息中心【确认】（BR-24）。
- **读消息不等于办业务。** 已读不代表已审核、已解除质押或已处理；办理始终在原业务中完成。
- **消息记录的是当时的事实。** 原业务之后的变化不改写旧消息中的业务事实。
- **平台支持中文和英文【确认】。** 每条消息都有中英文两套内容，按用户当前的界面语言展示。

**一个完整的例子。** 某来源模块按自己的通知规则，向全体运营发出一条“有新的事项等待审核”的消息 → 运营管理人员甲在任一业务页面看到未读数加 1，打开最近消息预览看到这一条 → 甲点开它，详情展示成功后对甲变为已读，甲的未读数减 1，同事乙的未读数不变 → 甲前往消息所说的那一笔业务办理 → 乙稍后在列表中筛选“未读”，打开同一条消息并前往时，看到这笔业务已由甲办完，只能查看当前结果 → 乙切换界面语言为英文，这条消息的标题和正文随之显示英文，业务编号和时间不变 → 乙对剩余未读执行全部已读。

### 1.1 需求清单

简报的三个功能标识在本模块的落点：企业消息通知（C-MSG）在面客端，监管机构消息通知（R-MSG）与运营消息通知（A-MSG）在管理端。三者共用下表功能，差别只在收件范围和可承接的分类。

| 功能 | 谁 | 想做什么 | 为了什么 |
| --- | --- | --- | --- |
| [谁能看到哪些消息（MSG-01）](#MSG-01) | 企业用户、监管机构、运营管理人员 | 只看到发给自己的消息 | 不错收、不泄露他人业务 |
| [来源接入要求（MSG-06）](#MSG-06) | 各来源模块 | 按统一要求登记每类消息 | 所有来源的消息在两端表现一致 |
| [消息入口与未读数（MSG-02）](#MSG-02) | 企业用户、监管机构、运营管理人员 | 在任何业务页面知道有几条未读 | 不漏掉需要处理的事项 |
| [最近消息预览（MSG-07）](#MSG-07) | 企业用户、监管机构、运营管理人员 | 不离开当前页面就看到最近的消息 | 快速判断是否要处理 |
| [消息列表（MSG-03）](#MSG-03) | 企业用户、监管机构、运营管理人员 | 浏览自己的全部消息 | 回看历史进展 |
| [按分类与已读状态筛选（MSG-08）](#MSG-08) | 企业用户、监管机构、运营管理人员 | 只看某一类或只看未读 | 在消息较多时找到要处理的 |
| [消息详情与已读（MSG-04）](#MSG-04) | 企业用户、监管机构、运营管理人员 | 读完整内容，读后标为已读 | 区分看过和没看过的消息 |
| [全部已读（MSG-09）](#MSG-09) | 企业用户、监管机构、运营管理人员 | 一次清空当前范围内的未读 | 全体运营消息较多时不必逐条打开 |
| [前往原业务（MSG-05）](#MSG-05) | 企业用户、监管机构、运营管理人员 | 从消息直接到那一笔业务 | 少找一步，直接查看或办理 |

### 1.2 本期不做

- 本模块不发送、编辑或撤回消息，不维护消息模板，不提供公告或按人群群发。
- 邮件、短信、浏览器推送不进入消息中心；本模块不发送任何站外消息。
- 不提供删除、归档或清空，消息长期保留。
- 不提供逐条“标为已读”和“标为未读”：打开详情即已读，另有全部已读。
- 不提供通知开关或偏好设置；用户不能退订任何消息。
- 面客端与管理端的消息互不汇总，未读数不合计。
- 不提供查看他人阅读情况的功能。
- 正文只支持纯文本，不支持富文本或可执行内容。
- 中文、英文以外的语言。

## 2. 术语

| 术语 | 含义 |
| --- | --- |
| 来源模块 | 发出消息的业务模块，例如代币发行、销毁审核、监管机构管理；它对消息内容、收件范围和去向负责 |
| 消息通知册 | 来源模块 PRD 中的 03 册，逐条写明本模块发出的每类消息 |
| 收件范围 | 一条消息发给谁。本平台有三种：某个企业、某个监管机构、全体运营 |
| 全体运营 | 一种收件范围：所有运营管理人员账号都能看到同一条消息，但每个人各自记录是否已读 |
| 原业务 | 消息所说的那一笔具体业务，例如某笔发行申请、某笔销毁申请；由来源模块定义如何识别 |
| 原动作 | 消息提示可以去做的办理动作，例如“审核这笔申请”；原业务往下推进后可能已不适用 |
| 未读数 | 本人能看到、尚未读过的消息条数 |
| 最近消息预览 | 从消息入口打开、展示最近 10 条的简要列表 |
| 同一事实 | 同一收件范围、同一笔原业务、同一个业务事件，以及来源规定的必要次数或节点；同一事实只有一条消息 |

<a id="MSG-01"></a>
## 3. 谁能看到哪些消息（MSG-01）

依据：企业侧和管理侧都需要消息通知【确认】；监管机构只能看到本机构的数据【确认】（BR-15）。

| 访问者 | 消息入口与未读数 | 能看到哪些消息 |
| --- | --- | --- |
| 未登录 | 不展示 | 不能看。直接打开消息链接时先去对应端登录，登录后按当前身份回到原消息 |
| 面客端游客 | 不展示 | 不能看。按[游客引导与功能限制（C-GUEST-01）](./v1.0-企业登录与企业账户-PRD.md#C-GUEST-01)，消息通知对游客不可用 |
| 面客端企业用户（已认证或未认证） | 展示 | 发给本企业的消息。未认证只限制办理业务，不限制查看消息 |
| 管理端监管机构，尚未完成首次登录强制改密 | 不展示 | 不能看。完成改密后再按当前身份回到原目标 |
| 管理端监管机构 | 展示 | 发给本机构的消息 |
| 管理端运营管理人员 | 展示 | 发给全体运营的消息 |

**三种收件范围。**

- 本企业：只有该企业可见。每个企业只有一个登录地址（见[企业登录与企业账户](./v1.0-企业登录与企业账户-PRD.md)），所以本企业的消息就是该企业用户本人的消息。
- 本机构：只有该监管机构可见；其他监管机构和运营都看不到，也不计入他们的未读数。
- 全体运营：所有运营管理人员看到的范围相同；每个人各自记录已读，甲读了不影响乙的已读状态和未读数。运营账号开通前已经存在的全体运营消息，新账号可以查看，对新账号直接为已读，不计入其未读数。
- 只有这三种收件范围。来源没有写明收件范围的不发送，不改发给全体运营或其他机构，也不猜测收件人。

**归属与隔离。**

- 企业的消息归属于企业，不归属于某个登录地址。上游登录地址变更后，按上游提供的稳定企业标识接续，历史消息、未读数和已读状态不变【确认】。
- 监管机构被停用后，本机构在途业务的消息照常生成、归属该机构，仍可查看并前往处理【确认】；停用对登录与新业务的限制由管理端账号与监管机构管理模块（M5）定义。
- 查看、计数和阅读一律按当前登录的身份和端判断；改写链接中的消息编号、身份或端标识，也取不到他人或其他端的消息。打开他人的消息、其他端的消息与打开不存在的消息，结果完全相同，不透露该消息是否存在。
- 面客端与管理端的消息互不进入对方。同一个业务事件需要企业和运营都知道时，由来源分别登记两端，两端各有一条，各自已读。
- 收到消息不代表获得原业务的查看或办理权限；前往原业务时按当前权限重新判断，见[前往原业务（MSG-05）](#MSG-05)。

流程参见：[一条消息从来源发出到收件人看到（图 1）](./v1.0-消息通知-流程图与状态机.md#fig-1)。

<a id="MSG-06"></a><a id="common"></a>
## 4. 来源接入要求（MSG-06）

本节定义各来源接入消息通知时要提供哪些信息、不满足时如何处理，以及所有消息共同遵守的承接规则。每条消息具体发什么、何时发、发给谁、写什么、去向哪一笔业务，由来源模块在自己的消息通知册中维护。

<a id="intake-fields"></a>
### 4.1 接入字段

每类消息由来源模块在自己的消息通知册中逐项写明下列信息。

**识别与归属**

| 字段 | 是否必填 | 要求 | 不满足时 |
| --- | --- | --- | --- |
| 消息名称与事件编号 | 必填 | 来源模块内唯一，登记后不改作他用 | 补齐后再发 |
| 发送来源 | 必填 | 唯一负责发送该类消息的模块；其他模块不发同义消息 | 补齐后再发 |
| 端 | 必填 | 面客端或管理端二选一；同一事件两端都要通知时分别登记 | 补齐后再发 |
| 分类 | 必填 | 从[消息分类](#categories)中选一个本端适用的分类；来源不能自造分类 | 补齐后再发；已收到的消息分类无法识别时显示“其他 / Other”，消息照常展示 |
| 收件范围 | 必填 | 本企业、本机构、全体运营三选一，并写明如何确定是哪个企业或哪个机构 | 无法确定时不发送，见[谁能看到哪些消息（MSG-01）](#MSG-01) |

**触发与同一事实**

| 字段 | 是否必填 | 要求 | 不满足时 |
| --- | --- | --- | --- |
| 触发与不触发 | 必填 | 在哪个功能的哪个环节、什么结果真正生效后发送；哪些情况不发送 | 补齐后再发 |
| 同一事实的区分依据 | 必填 | 收件范围 + 原业务 + 事件，以及必要的次数或节点；按[同一件事只收一条](#same-fact)处理 | 补齐后再发 |
| 合并规则 | 来源规定多个结果合并为一条时必填 | 写明合并条件和合并后保留的事实 | 未登记时不合并，每个结果各自一条 |
| <a id="occurred-at"></a>发生时间 | 必填 | 业务事实发生的时间；到点触发的事件取应到时点 | 补齐后再发，不用送达或阅读时间代替 |

**内容与去向**

| 字段 | 是否必填 | 要求 | 不满足时 |
| --- | --- | --- | --- |
| 标题与正文 | 必填 | 中文、英文各一套完整的纯文本标题和正文【确认】；写明必须出现的业务值；遵守[内容要求](#content-rules) | 缺少可读的标题和正文时不生成消息 |
| 原业务识别信息 | 去向为原业务时必填 | 原业务的名称与编号等识别信息由来源模块定义【确认】；本模块只按来源提供的内容展示 | 缺少时列表、预览与详情都不显示该项，不用其他业务的信息补位 |
| 打开后去哪 | 必填 | 原业务、本端固定页面、不跳转三选一；不接受站外、另一端或其他平台的地址 | 补齐后再发；已收到但去向缺失或异常的按[内容与去向异常](#intake-fallback)处理 |
| 查看与办理条件 | 去向为原业务时必填 | 查看与办理原业务各需要什么身份或权限，按原业务所属模块的规则 | 补齐后再发；前往时仍按当前权限重新判断 |

- 来源缺少必填信息时补齐后再发；不发空白消息，不用 0、虚假编号或其他业务的信息补位。
- 邮件不进入消息中心。来源模块需要发邮件时，在自己的消息通知册中单独写明；本平台只有监管机构邀请发邮件【确认】（BR-24）。

<a id="categories"></a>
### 4.2 消息分类

两端使用同一套分类【沿用参考件】。每条消息由来源按下表归入其中一类。

| 分类 | English | 归入什么消息 | 适用端 |
| --- | --- | --- | --- |
| 业务办理进度 | Business progress | 某项业务有了办理结果或进入下一步，例如审核有了结论、链上处理成功、对方已处理 | 面客端、管理端 |
| 业务提醒 | Business reminders | 业务状态本身没有变化，但需要用户注意，通常由时间或条件触发 | 面客端、管理端 |
| 认证与合规 | Verification & compliance | 认证、资格或合规状态发生变化，例如认证失效 | 面客端、管理端 |
| 账户安全 | Account security | 账户本身的安全相关变化，例如密码变更、账户停用或恢复 | 面客端、管理端 |
| 审核任务 | Review tasks | 有新的事项等待本端人员审核或处理 | 管理端 |
| 运营告警 | Operations alerts | 平台自动处理的结果需要运营人员知悉，尤其是失败待重试 | 管理端，仅全体运营 |

- “其他 / Other”只是分类无法识别时的兜底，不是可选的分类。
- 分类只影响查看和筛选，不改变收件范围。

<a id="same-fact"></a>
### 4.3 同一件事只收一条

- 同一事实只有一条消息。重复送达、重试、刷新、重新登录都不新增消息，也不改变这条消息的顺序、发生时间和已读状态；已读的仍是已读。
- 同一笔原业务上发生新的真实事实（新的一次提交、新的一次审核结果、新的一次失败），各自是一条新消息。
- 来源对同一事实补充信息时，在原消息上补齐；补齐不倒退事实，也不让消息重新变为未读。
- 只有来源登记了合并规则时才合并。本模块不按同一天、同一企业或同一笔业务自行合并。

<a id="delivery-time"></a>
### 4.4 送达时效

依据：参考借贷平台实现【确认】。

- 业务事件发生后 60 秒内，消息出现在收件人的列表与预览中，未读数同步更新。60 秒从业务事件发生时起算。
- 由时间到点触发的事件，从应到的时点起算，最晚 6 分钟内可见：来源判定最多用 5 分钟，消息展示最多再用 60 秒。来源模块须把判定延迟控制在 5 分钟以内。

<a id="content-rules"></a>
### 4.5 内容与语言

- 每条消息的标题和正文都有中文、英文两套，按本人当前的界面语言展示【确认】。切换界面语言后，历史消息的标题和正文随之切换；金额、数量、时间、业务编号和驳回意见等事实不变。
- 来源提供的驳回意见、备注等由用户填写的原文，按原文展示，不翻译。
- 分类名称、空状态、全部已读确认等本模块自身的文字，同样提供中英文两套。
- 数量、金额、时间等业务值取事件发生时的值，之后原业务变化不改写；未知的值不显示，不显示为 0。
- 站内消息不出现密码、验证码、钱包签名内容、完整钱包地址、证件号码、私人联系方式、协议文件原件或下载地址。

<a id="intake-fallback"></a>
### 4.6 已收到消息的内容与去向异常

以下规则适用于已进入本人可见范围的消息，不替代来源接入时补齐必填信息的要求。

| 情况 | 阅读与计数 | 前往入口 |
| --- | --- | --- |
| 去向缺失，或来源设为不跳转 | 正常可读、计数和已读 | 没有入口，也不提示错误 |
| 只缺少原业务识别信息 | 正常可读、计数和已读；列表、预览与详情中缺项都不显示 | 其他定位完整时仍可前往 |
| 分类无法识别 | 归入“其他 / Other”，正常可读、计数和已读 | 按登记的去向与权限处理 |
| 当前界面语言的内容缺失 | 显示另一种语言，正常计数和已读 | 按登记的去向与权限处理 |
| 中英文内容都无法展示 | 用分类、发生时间和通用标题“通知 / Notification”展示这一条，不暴露内部标识，不影响其他消息 | 按登记的去向与权限处理 |
| 去向指向本端以外的地址 | 正文保留，正常计数和已读 | 不提供入口 |

流程参见：[一条消息从来源发出到收件人看到（图 1）](./v1.0-消息通知-流程图与状态机.md#fig-1)。

## 5. 消息入口、最近预览与未读数（MSG-02、MSG-07）

适用角色与前提：按[谁能看到哪些消息（MSG-01）](#MSG-01)能看消息的企业用户、监管机构和运营管理人员。

**入口。** 在本端每个业务页面都能看到消息入口及本人未读数；从入口打开最近消息预览，也能直接进入完整的消息列表（不带筛选）。各业务页面使用同一批消息和同一份已读状态。

**最近消息预览【沿用参考件】。**

- 展示最近 10 条，已读和未读都包括；每条可看到标题、原业务识别信息（来源提供时）、摘要、分类、时间和是否已读。
- 只打开预览不会让消息变为已读；点某一条进入它的详情。
- “查看全部”进入完整消息列表。
- 预览里不提供全部已读，避免误以为只处理这 10 条。
- 没有消息时说明还没有消息；读取失败时可以重试，不显示为没有消息。
- 打开预览不影响当前业务页面上尚未保存的内容。

**未读数。**

- 等于本人能看到、尚未读过的消息条数，全部分类合计；与列表中的未读状态一致。
- 原业务已办完、已不可访问，都不影响计数：只要消息未读，就计入。
- 为 0 时不显示数字；超过 99 时显示“99+”【沿用参考件】。
- 读取失败时保留上一次的数字，不清零。
- 新消息到达时，未读数和预览一起更新，不打断用户当前的操作。在一个页面或浏览器标签里读了消息，同一身份的其他页面和标签最晚 60 秒内随之更新。

流程参见：[入口、列表、详情、已读与返回（图 4）](./v1.0-消息通知-流程图与状态机.md#fig-4)。

## 6. 消息列表与筛选（MSG-03、MSG-08）

适用角色与前提：按[谁能看到哪些消息（MSG-01）](#MSG-01)能看消息的企业用户、监管机构和运营管理人员。

**列表。** 列表可以直接打开和刷新，范围是本人能看到的全部消息，不受预览 10 条的限制。每条可看到标题、原业务识别信息（来源提供时）、摘要、分类、时间和是否已读，点击进入详情。

**筛选【确认】。**

- 分类：“全部”加上本人实际有消息的分类；无法识别分类的消息归入“其他”。
- 已读状态：全部、未读、已读，默认“全部”。
- 两个条件同时生效。刷新页面后筛选保持不变；修改筛选后从第一条重新开始。链接中的筛选条件无效时，按默认条件展示，不显示为没有消息。

**排序。** 按消息产生时间从新到旧，同一时间的顺序固定；每条展示的时间是[发生时间](#occurred-at)。重复送达不改变顺序，读过也不重排。在“未读”筛选下读过的消息，仍留在当前结果中，重新筛选或刷新后才按新条件移除。

**加载【沿用参考件】。** 每次加载 20 条，“加载更多”把结果追加到已加载内容之后；没有更多时明确提示。加载进行中不能重复触发。已加载和后续加载的结果不重复、不遗漏。

**新消息。** 符合当前筛选的新消息自动插入列表顶部，不改变用户当前的阅读位置；不符合的不插入，切换到对应筛选时才能看到。

**空列表。** 以下两种情况须能区分：从未收到过消息，说明还没有任何消息；筛选后没有结果，说明当前筛选下没有消息，并可一键清除筛选。

**加载失败。** 第一批加载失败时可以重试，不显示为空列表；“加载更多”失败时，保留已加载的内容和所在位置，可以重试；某一条内容异常只影响这一条。

<a id="MSG-04"></a><a id="MSG-09"></a>
## 7. 消息详情、已读与全部已读（MSG-04、MSG-09）

适用角色与前提：按[谁能看到哪些消息（MSG-01）](#MSG-01)能看消息的企业用户、监管机构和运营管理人员，且这条消息属于本人。

**详情。**

- 详情可以直接打开和刷新，刷新后仍是同一条消息。
- 展示完整标题、分类、发生时间、完整正文、原业务识别信息（来源提供时），以及前往原业务的入口（有去向时）。正文是纯文本，其中的标签或脚本按文字显示，不会被执行。
- 从列表或预览进入的，返回后回到原来的列表，筛选条件、已加载的批次和所在位置都保持不变；刚读过的消息在列表中原地变为已读。直接从链接打开、没有列表可回的，返回到不带筛选的消息列表。
- 从消息前往原业务后，可以回到这条消息。

**自动已读。**

- 详情内容展示成功后，这条消息对本人自动变为已读，未读数同步减少。
- 详情加载失败时不算已读，说明失败，可重试或返回列表。
- 已读保存失败时，消息仍为未读，正文照常可读，可以重试；重试只处理已读，不会重新发送消息，也不会办理业务。
- 已读的消息再次打开，不再改变未读数。只打开预览、在列表中看到或复制编号，都不改变已读状态。
- 已读只属于“本人与这条消息”：读一条全体运营消息，不改变其他运营管理人员的已读状态，也不改变原业务的进度。

**全部已读【确认】。**

- 作用范围：当前筛选条件下本人全部未读的消息，包括还没有加载出来的部分；不扩大到其他筛选条件下的消息。
- 当前范围内没有未读消息时，这个操作不可用，并说明原因。
- 执行前须确认。确认时写明当前筛选条件，以及将被标为已读的未读条数（包括尚未加载的部分）。
- 取消时，所有消息保持不变。
- 执行期间不能重复提交。成功后，范围内的消息全部变为已读，未读数同步更新；因其他页面已读导致实际条数不同时，按实际处理结果反馈。失败时全部保持原状，可以重试，不会只成功一部分。
- 确认之后新到的消息不在本次范围内，仍为未读。
- 执行中登录失效时，不提示成功；重新登录后按实际的已读结果展示。
- 全部已读只改变本人的阅读状态，不影响其他运营管理人员，也不代表相关业务已经完成。

流程参见：[入口、列表、详情、已读与返回（图 4）](./v1.0-消息通知-流程图与状态机.md#fig-4)、[全部已读（图 6）](./v1.0-消息通知-流程图与状态机.md#fig-6)、[本人阅读状态（状态机 1）](./v1.0-消息通知-流程图与状态机.md#state-1)。

## 8. 前往原业务（MSG-05）

适用角色与前提：本人打开了一条去向为原业务或本端固定页面的消息。

- 前往原业务时，定位到消息所说的那一笔，不换成最新一笔或其他业务。
- 本模块不办理业务；查看和办理都在原业务中完成，由用户主动操作。
- 能否查看、能否办理，按来源登记的查看与办理条件，以及原业务所属模块的当前权限和当前状态判断。例如监管机构只能前往本机构的业务【确认】（BR-15）。
- 进入详情时检查原业务能否查看；检查失败时仍允许前往，由原业务页面重新判断权限，不放宽任何权限。列表与预览中不逐条检查。
- 前往固定页面时，直接打开该页面，页面仍按本人当前权限判断。
- 前往后可以回到这条消息。原业务页面有尚未保存的内容时，按原业务自己的离开提示处理。

**原业务当前情况与用户结果。** 已读和未读的处理相同。

| 原业务当前情况 | 用户能做什么 | 消息本身 |
| --- | --- | --- |
| 本人有权查看，消息提示的原动作仍可办理 | 前往原业务查看或办理 | 正文不变 |
| 本人有权查看，原动作已办完或已不适用（例如另一位运营已处理） | 前往查看这一笔的当前结果；不再提供旧动作，不能重开或再次办理 | 正文保留当时的事实 |
| 原业务不存在，或本人当前无权查看 | 不能前往；统一说明相关内容暂不可访问，不区分是不存在还是无权 | 正文照常可读，未读时仍计入未读数 |
| 来源设为不跳转，或去向缺失 | 没有前往入口，也不提示错误 | 正文照常可读 |

流程参见：[入口、列表、详情、已读与返回（图 4）](./v1.0-消息通知-流程图与状态机.md#fig-4)。

## 9. 登录状态与安全

- 退出、登录失效或切换身份后，消息入口、未读数、预览、列表和详情一并清除，回到对应端的登录状态；必须真正清除，之后迟到的数据也不显示。面客端按[退出与切换钱包（C-AUTH-03）](./v1.0-企业登录与企业账户-PRD.md#C-AUTH-03)；管理端按管理端账号与监管机构管理模块（M5）的登录规则。
- 任何一处读取消息时发现登录已失效，都按失效统一处理，不当作普通的读取失败。
- 自动更新消息不算用户活跃，不延长登录有效期。
- 从链接直接打开消息时未登录：先登录（监管机构首次登录还须先改密），之后按当前身份回到原消息；登录前不展示正文，也不透露这条消息是否存在。登录后发现消息不属于当前身份时，按不存在处理。
- 切换到另一个企业或另一个管理端账号后，前一个身份的正文、未读数和迟到的操作结果都不会出现。

## 11. 待确认事项与依赖

依赖：
