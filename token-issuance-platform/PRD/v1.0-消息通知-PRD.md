# 消息通知 · 功能与业务规则

2026-10-29｜面客端：企业用户；管理端：监管机构、运营管理人员｜需求评审稿

本模块共四册：本册写功能、业务规则、字段规则与交互逻辑；[流程图与状态机](./v1.0-消息通知-流程图与状态机.md)画出主要流程与状态；[消息通知](./v1.0-消息通知-消息通知.md)逐条定义本平台发送的每一类消息；[验收](./v1.0-消息通知-验收.md)供测试使用。

依据标注：规则后的【确认】表示用户原文已明确，【建议·已采纳】表示诊断建议已由用户采纳，两者同样有效；未标注的是为落实上述规则所写的产品细化，涉及口径未定的已列入[待确认事项](#pending)。本册只定义信息需求与业务行为，页面布局、组件形态与交互承载由 Hallmark 设计决定。

## 1. 模块是什么

消息通知让企业、监管机构和运营管理人员及时知道与自己相关的业务进展。代币发行、销毁和解除质押过程中，每到一个需要对方知道或处理的节点，本平台就向对应的人发一条站内消息；监管机构被邀请开户时，另发一封邀请邮件。本模块定义两部分内容：一是三类角色在各自端上怎样接收、查看和阅读站内消息（本册）；二是平台发哪些消息、何时发、发给谁、写什么、打开后去哪（[消息通知册](./v1.0-消息通知-消息通知.md)）。

基本原则：

- 站内消息为主；只有监管机构邀请走邮件【确认】（BR-24）。
- 消息只告知，不办业务。读消息不等于已审核、已解除质押；办理始终在原业务中完成。
- 消息记录的是发生当时的事实。原业务之后的变化不改写旧消息，打开时按原业务的当前状态处理。
- 每个人只看到发给自己的消息：企业只看到本企业的，监管机构只看到本机构的，运营管理人员看到发给全体运营的。

**一个完整的例子。** 企业 A 选择资产 R-001 和监管机构 B 提交发行申请 → 监管机构 B 的管理端出现一条“新的待审申请”，未读数加 1 → B 打开消息，消息变为已读，B 前往这笔申请完成一审并上传监管协议 → 企业 A 收到“监管审核通过”；全体运营收到“待二审的申请” → 运营人员甲打开消息前往二审，选择合约后通过 → 企业 A 收到“运营审核通过” → 铸造成功后企业 A 收到“铸造成功”。运营人员乙稍后打开同一条“待二审的申请”，这条消息对乙才变为已读；乙前往这笔申请时看到它已铸造成功，不再出现审核操作。

### 1.1 需求清单

简报的三个功能标识在本模块的落点：企业消息通知（C-MSG）在面客端，监管机构消息通知（R-MSG）与运营消息通知（A-MSG）在管理端。三者共用下表前五项功能，各自接收的消息不同，见[消息通知册](./v1.0-消息通知-消息通知.md)。

| 功能 | 谁 | 想做什么 | 为了什么 |
| --- | --- | --- | --- |
| [谁收到、谁能看到（MSG-01）](#MSG-01) | 企业、监管机构、运营管理人员 | 只看到发给自己的消息 | 不错收、不泄露他人业务 |
| [消息入口与未读数（MSG-02）](#MSG-02) | 企业、监管机构、运营管理人员 | 在任何业务页面知道有几条未读 | 不漏掉需要处理的事项 |
| [消息列表（MSG-03）](#MSG-03) | 企业、监管机构、运营管理人员 | 浏览自己的全部消息 | 回看历史进展 |
| [消息详情与已读（MSG-04）](#MSG-04) | 企业、监管机构、运营管理人员 | 读完整内容，读后标为已读 | 区分看过和没看过的消息 |
| [前往原业务（MSG-05）](#MSG-05) | 企业、监管机构、运营管理人员 | 从消息直接到那一笔申请或记录 | 少找一步，直接查看或办理 |
| [各类站内消息与邀请邮件](./v1.0-消息通知-消息通知.md) | 系统按业务节点发送 | 把审核、铸造、销毁、解除质押的进展告知相关方 | 推动流程往下走 |

### 1.2 本期不做

- 短信、浏览器推送等其他渠道；监管机构邀请以外的邮件。
- 消息通知开关或偏好设置；用户不能退订任何消息。
- 发送、编辑或撤回消息，公告或按人群群发。
- 删除、归档、清空消息。
- 全部已读、按分类或已读状态筛选、最近消息预览：简报未列，见[消息中心辅助功能（Q-M7-05）](#Q-M7-05)。
- 简报事件清单与[认证失效通知（NT-C09）](./v1.0-消息通知-消息通知.md#NT-C09)以外的消息，例如监管机构信息编辑、停用 / 启用、重置密码，企业数币账户变更，登录与退出，都不发消息。
- 在面客端查看管理端消息，或在管理端查看面客端消息。

## 2. 术语

| 术语 | 含义 |
| --- | --- |
| 站内消息 | 在本平台面客端或管理端内查看的消息，不经过邮件或短信 |
| 收件人 | 一条消息发给谁。本平台有四种：某个企业、某个企业用户本人、某个监管机构、全体运营 |
| 全体运营 | 一种收件人：所有运营管理人员账号都能看到同一条消息，但每个人各自记录是否已读 |
| 原业务 | 消息所说的那一笔具体业务，例如某笔发行申请、某笔销毁申请、某笔资产的解除质押 |
| 原动作 | 消息提示可以去做的办理动作，例如“一审”“重试铸造”；原业务往下推进后可能已不适用 |
| 未读数 | 本人能看到、尚未读过的消息条数 |
| 同一事实 | 同一收件人、同一笔原业务、同一个业务节点（失败类再加“第几次”）；同一事实只有一条消息 |

<a id="MSG-01"></a>
## 3. 谁收到、谁能看到（MSG-01）

依据：企业侧和管理侧都需要消息通知【确认】；各角色接收的事件【建议·已采纳】（简报 4.5）；监管机构只能看到本机构的数据【确认】（BR-15）。

| 访问者 | 消息入口与未读数 | 能看到哪些消息 |
| --- | --- | --- |
| 未登录 | 不展示 | 不能看。直接打开消息链接时先去对应端登录，登录后按当前身份回到原消息 |
| 面客端游客（地址未匹配到上游） | 不展示 | 不能看。按[游客引导与功能限制（C-GUEST-01）](./v1.0-企业登录与企业账户-PRD.md#C-GUEST-01)，消息通知对游客不可用 |
| 面客端企业态 | 展示 | 发给本企业的消息，以及发给本人的消息 |
| 管理端监管机构，尚未完成首次登录强制改密 | 不展示 | 不能看。完成改密后再按当前身份回到原目标 |
| 管理端监管机构 | 展示 | 发给本机构的消息 |
| 管理端运营管理人员 | 展示 | 发给全体运营的消息 |

**收件人的确定。**

- 发给企业的消息：收件人是该笔发行申请或代币所属的企业。
- 发给企业用户本人的消息：只有[认证失效通知（NT-C09）](./v1.0-消息通知-消息通知.md#NT-C09)，收件人是认证失效的那个企业用户本人。
- 发给监管机构的消息：收件人是该笔发行申请所选的监管机构；销毁后的解除质押消息发给该笔资产铸造时的监管机构。
- 发给全体运营的消息：所有运营管理人员账号看到的范围相同；每个人各自记录已读，甲读了不影响乙的已读状态和未读数。
- 运营账号开通前已经存在的全体运营消息，新账号可以查看，对新账号直接为已读，不计入其未读数。
- 每类消息的收件人只按[消息通知册](./v1.0-消息通知-消息通知.md)写明的执行；无法确定收件人时不发送，不改发给全体运营或其他机构。

**隔离。**

- 企业只看到本企业的消息，看不到其他企业的；监管机构只看到本机构的，看不到其他机构和运营的；运营看不到发给企业或监管机构的消息。
- 面客端与管理端的消息互不进入对方，也不合计未读数。同一个业务节点需要企业和运营都知道时，两端各有一条，各自已读。
- 查看、计数和阅读一律按当前登录的身份判断；改写链接中的消息编号或身份信息，也取不到他人的消息。打开他人的消息与打开不存在的消息，结果相同，不透露该消息是否存在。
- 收到消息不代表获得原业务的查看或办理权限；前往原业务时按当前权限重新判断，见[前往原业务（MSG-05）](#MSG-05)。

<a id="MSG-02"></a>
## 4. 消息入口与未读数（MSG-02）

适用角色与前提：按[谁收到、谁能看到（MSG-01）](#MSG-01)能看消息的企业、监管机构和运营管理人员。

- 面客端企业态、管理端监管机构与运营管理人员，在本端每个业务页面都能看到消息入口及本人未读数，并能由此进入消息列表。
- 未读数等于本人能看到、尚未读过的消息条数；与列表中的未读状态一致。
- 未读数为 0 时不显示数字。
- 新消息到达或本人读了消息后，未读数随之更新，不打断用户当前的操作，不影响当前页面尚未保存的内容。
- 未读数读取失败时保留上一次的数字，不清零、不显示为 0。
- 原业务已办完、已不可访问，都不影响计数：只要消息未读，就计入。

流程参见：[打开消息与前往原业务（图 4）](./v1.0-消息通知-流程图与状态机.md#fig-4)。

<a id="MSG-03"></a>
## 5. 消息列表（MSG-03）

适用角色与前提：同[消息入口与未读数（MSG-02）](#MSG-02)。

- 列表展示本人能看到的全部消息，已读和未读都包括。
- 排序按消息产生时间从新到旧；重复送达、读过都不改变顺序。
- 消息数量较多时分批加载，每批条数由设计确定；已加载与后续加载的结果不重复、不遗漏。
- 新消息到达时出现在列表顶部，不改变用户当前的阅读位置。
- 列表可以直接打开和刷新；刷新后仍是本人的消息。

每条消息在列表中展示：

| 业务信息 | 含义 | 缺失时 |
| --- | --- | --- |
| 标题 | 这条消息告知的业务节点，例如“监管审核通过”，按[消息通知册](./v1.0-消息通知-消息通知.md)各事件的必须内容 | 不会缺失；来源无法提供可读标题时不生成消息 |
| 摘要 | 正文的简要部分 | 不显示该项 |
| 业务对象 | 原业务的识别信息：上游资产编号；销毁类消息另带该笔销毁申请的提交时间 | 不显示该项，不用其他业务的信息补位 |
| 时间 | 业务节点发生的时间，不是送达或阅读时间 | 不会缺失 |
| 是否已读 | 本人对这条消息是否已读 | 不会缺失 |

**空列表与失败。**

- 从未收到过消息时，说明还没有消息。
- 第一批加载失败时说明失败并可重试，不显示为没有消息；后续批次加载失败时，保留已加载内容和所在位置，可以重试。
- 某一条内容异常只影响这一条，其他消息照常展示。

<a id="MSG-04"></a>
## 6. 消息详情与已读（MSG-04）

适用角色与前提：同[消息入口与未读数（MSG-02）](#MSG-02)，且这条消息属于本人。

**详情。**

- 展示完整标题、时间、完整正文、业务对象，以及前往原业务的入口（该类消息设有去向时）。
- 详情可以直接打开和刷新，刷新后仍是同一条消息。
- 正文只是文字；正文中出现的标签或脚本按文字显示，不会被执行。
- 从列表进入的，返回后回到原列表的原位置，刚读过的消息在原位置变为已读。直接从链接打开、没有列表可回的，返回到消息列表。

**自动已读。**

- 详情内容展示成功后，这条消息对本人自动变为已读，未读数同步减少。
- 详情加载失败时不算已读，说明失败，可重试或返回列表。
- 已读保存失败时，消息仍为未读，正文照常可读，可以重试；重试只处理已读，不会重新发送消息，也不会办理业务。
- 已读的消息再次打开，不再改变未读数。只在列表中看到、未打开详情，不改变已读状态。
- 已读只属于“本人与这条消息”：读一条全体运营消息，不改变其他运营管理人员的已读状态，也不改变原业务的进度。

状态参见：[本人阅读状态（状态机 1）](./v1.0-消息通知-流程图与状态机.md#state-1)。

<a id="MSG-05"></a>
## 7. 前往原业务（MSG-05）

适用角色与前提：本人打开了一条设有去向的消息。每类消息去向哪一笔原业务，见[消息通知册](./v1.0-消息通知-消息通知.md)各事件的“打开后去哪”。

- 前往时定位到消息所说的那一笔（那笔发行申请、那笔销毁申请、那笔资产的解除质押），不换成最新一笔或其他业务。
- 本模块不办理业务；查看和办理都在原业务中完成，由用户主动操作。
- 是否能查看、能否办理，按原业务所属模块的当前权限和当前状态判断。例如监管机构只能前往本机构的申请【确认】（BR-15）。
- 前往后可以回到这条消息。

**原业务当前情况与用户结果。** 已读和未读的处理相同，下表不再区分。

| 原业务当前情况 | 用户能做什么 | 消息本身 |
| --- | --- | --- |
| 本人有权查看，消息提示的原动作仍可办理（例如这笔申请仍是“待运营审核”） | 前往原业务查看或办理 | 正文不变 |
| 本人有权查看，原动作已办完或已不适用（例如另一位运营已重试成功，或申请已被驳回终止） | 前往查看这一笔的当前结果；不再提供旧动作，不能重开或再次办理 | 正文保留当时的事实 |
| 原业务不存在，或本人当前无权查看 | 不能前往；统一说明相关内容暂不可访问，不区分是不存在还是无权 | 正文照常可读，仍计入未读（如未读） |
| 该类消息设为不跳转（例如邀请邮件不在站内） | 没有前往入口，也不提示错误 | 正文照常可读 |

流程参见：[打开消息与前往原业务（图 4）](./v1.0-消息通知-流程图与状态机.md#fig-4)。

<a id="common"></a>
## 8. 消息的共同规则

本节规则适用于[消息通知册](./v1.0-消息通知-消息通知.md)中的每一类消息。

<a id="channel"></a>
**渠道。**

- 企业、监管机构、运营管理人员的业务消息都只发站内消息【确认】（BR-24）。
- 只有监管机构邀请发邮件，不另发站内消息；邀请时监管机构尚未登录过管理端【确认】（BR-04、BR-24）。

<a id="when-sent"></a>
**何时发。**

- 业务节点真正生效后才发，例如审核结果已保存、链上铸造或销毁结果已确认。操作取消、校验不通过、提交失败都不发。
- 消息出现在列表与未读数中的时效待确认，见[送达时效（Q-M7-04）](#Q-M7-04)。

<a id="same-fact"></a>
**同一事实只收一条。**

- 同一事实只有一条消息。重复送达、刷新、重新登录都不新增消息，也不改变这条消息的顺序、时间和已读状态；已读的仍是已读。
- 同一笔原业务上发生新的真实事实，各自一条新消息。例如：同一笔申请铸造失败、重试后再次失败，是两条“铸造失败待重试”；销毁申请被驳回后企业再次发起，新的销毁申请是一条新的“新的销毁申请”。
- 不按同一企业、同一天、同一资产把不同的事实合并为一条。

<a id="content-rules"></a>
**内容。**

- 每条消息有可读的标题和正文；必须出现的业务值见消息通知册各事件。
- 数量、金额、时间、驳回意见取事件发生时的值，之后原业务变化不改写。
- 代币数量与币种按“代币数量 = 应收账款美元金额、币种 USD”展示【确认】（BR-19）。
- 未知的值不显示，不显示为 0，不用其他业务的信息补位。
- 站内消息不出现密码、钱包签名内容、协议文件原件或下载地址。监管机构邀请邮件中的初始密码见[邀请邮件是否包含初始密码（Q-M7-02）](#Q-M7-02)。
- 具体措辞由设计确定，须表达消息通知册写明的业务信息。

<a id="session"></a>
## 9. 登录状态与安全

- 退出、登录失效或切换身份后，消息入口、未读数、列表和详情一并清除，回到对应端的登录状态；之后迟到的数据也不显示。面客端的退出、切换钱包与登录到期按[退出与切换钱包（C-AUTH-03）](./v1.0-企业登录与企业账户-PRD.md#C-AUTH-03)；管理端按管理端账号与监管机构管理模块（M5）的登录规则。
- 切换到另一个企业或另一个管理端账号后，前一个身份的消息、未读数和操作结果都不会出现。
- 读取消息时发现登录已失效，按登录失效处理，不当作普通的读取失败。
- 从链接直接打开消息时未登录：先登录（监管机构首次登录还须先改密），之后按当前身份回到原消息；登录前不展示正文，也不透露该消息是否存在。登录后发现消息不属于当前身份时，按不存在处理。
- 企业的消息归属于企业，不归属于某个登录地址；上游登录地址变更后的接续见[企业登录地址变更后的消息接续（Q-M7-07）](#Q-M7-07)。
- 监管机构被停用后不能登录，也就看不到消息；停用期间的消息见[监管机构停用期间的消息（Q-M7-06）](#Q-M7-06)。

## 10. 与相邻模块的分工

| 相邻模块 | 与本模块的关系 |
| --- | --- |
| M1 企业登录与企业账户 | 提供企业态、游客态与登录状态；游客不能使用消息通知；企业数币账户变更不发消息；在调取时点确认认证失效时触发[认证失效通知（NT-C09）](./v1.0-消息通知-消息通知.md#NT-C09) |
| M3a 代币发行·企业申请 | 企业提交发行申请时触发监管机构的“新的待审申请”；企业从消息前往自己的发行申请查看进度与结果 |
| M3b 代币发行·审核与铸造 | 监管一审、运营二审、铸造成功与失败触发相应消息；监管与运营从消息前往申请详情办理；发行申请的识别信息以 M3b 维护的衔接字段清单为准 |
| M4a 我的代币与销毁申请 | 企业提交销毁申请时触发运营的“新的销毁申请”；企业从消息前往自己的销毁申请查看进度与结果 |
| M4b 销毁审核、解除质押与代币台账 | 销毁驳回、销毁成功与失败、解除质押触发相应消息；运营与监管从消息前往办理；销毁申请与解除质押记录的识别信息以 M4b 维护的衔接字段清单为准 |
| M5 管理端账号、权限与监管机构管理 | 邀请监管机构时触发邀请邮件；提供管理端登录、首次登录强制改密、角色与菜单权限（消息通知对运营与监管都可见【确认】，简报 4.4） |

各业务模块只需写明“在哪个环节触发哪一类消息”，并链接到[消息通知册](./v1.0-消息通知-消息通知.md)的对应事件；消息的收件人、内容与去向以消息通知册为准，不在各模块重复定义。

## 11. 待确认事项与依赖

| 编号 | 事项（写清具体冲突点） | 当前处理与影响 |
| --- | --- | --- |
| <a id="Q-M7-01"></a>Q-M7-01 | 消息事件由谁维护：参考件（借贷平台运营端消息通知）的做法是消息中心只承接，每类消息由发送它的业务模块在自己的“消息通知”册中维护；本平台简报第 11 节把全部事件（4.5 节）划给 M7 | 按简报执行：全部事件集中在本模块[消息通知册](./v1.0-消息通知-消息通知.md)，M3a、M3b、M4a、M4b、M5 不另建消息通知册，只链接到对应事件。若改为参考件的做法，需把各事件迁到对应模块，本模块只保留消息的接收、查看与阅读规则，以及[消息的共同规则](#common) |
| <a id="Q-M7-02"></a>Q-M7-02 | 邀请邮件是否包含初始密码：简报写“邀请邮件（含初始账号）”，初始账号由运营分配“邮箱、密码”；未写明密码是否随邮件发送 | 按简报理解为邮件包含登录邮箱和初始密码，首次登录强制改密降低风险。若改为初始密码由运营线下告知，只需从邮件中去掉密码；影响[监管机构邀请邮件（NT-R03）](./v1.0-消息通知-消息通知.md#NT-R03) |
| <a id="Q-M7-03"></a>Q-M7-03 | 邀请邮件发送失败与重置密码的告知：简报未说明邮件发送失败时运营看到什么、能否重新发送；运营重置监管机构密码后，新密码如何告知监管机构，简报事件清单中没有对应消息 | 本模块不新增事件。邮件发送失败不撤销已添加的监管机构，是否提示与重新发送由 M5 确定；重置密码的告知方式由 M5 确定，如需发邮件，须先由用户确认新增事件 |
| <a id="Q-M7-04"></a>Q-M7-04 | 送达时效：简报未给出业务节点发生后，消息多久出现在列表和未读数中 | 暂不设定数值；相关验收只核对“会出现”，时效待验 |
| <a id="Q-M7-05"></a>Q-M7-05 | 消息中心辅助功能：参考件提供全部已读、按分类与已读状态筛选、最近消息预览，简报未列 | 本期不做。专业建议：至少增加“全部已读”和“只看未读”，因为全体运营消息会发给每位运营管理人员，未读数容易累积；确认后补入本册与验收 |
| <a id="Q-M7-06"></a>Q-M7-06 | 监管机构停用期间的消息：已选择该机构的申请在停用期间推进（例如销毁成功需解除质押），消息怎么处理；停用的机构能否再被企业选择，简报未说明 | 消息照常生成并归属该机构，停用期间看不到，启用后可见；停用后的业务办理归属与可选范围由 M3a、M4b、M5 确定 |
| <a id="Q-M7-07"></a>Q-M7-07 | 企业登录地址变更后的消息接续：需要上游稳定不变的企业标识，与 M1 的[识别同一企业的上游标识（Q-M1-07）](./v1.0-企业登录与企业账户-PRD.md#Q-M1-07)相同 | 消息归属企业而非登录地址；标识确定前无法保证地址变更后历史消息的接续 |
| <a id="Q-M7-08"></a>Q-M7-08 | 原业务的识别信息：M3b、M4b 尚未定义发行申请、销毁申请的编号 | 暂以上游资产编号识别发行申请与代币（同一资产只能发起一次发行，BR-08、BR-12），销毁申请另加提交时间；M3b、M4b 定义编号后补入消息内容 |

依赖：

- M1、M5：面客端与管理端的登录、退出、登录失效、首次登录强制改密及菜单权限。
- M3a、M3b、M4a、M4b、M5：在各自环节生效后触发消息，并提供消息通知册写明的业务值；原业务的查看与办理权限、当前状态由这些模块判断。
- 邮件服务（D8）：发送监管机构邀请邮件。
