## 1. 模块是什么

代币发行·审核与铸造是管理端处理企业发行申请的地方。企业在代币发行·企业申请（M3a）以一笔可信资产签名提交申请后，所选的监管机构在这里做一审：与企业线下签署监管协议后，通过时上传协议，或填写意见驳回。一审通过后，平台运营做二审：通过时选择铸造合约，平台随即在 Ethereum 上铸造代币；也可以填写意见驳回。铸造失败时，由运营手动重试。监管机构和运营共用同一个申请详情，按角色区分能看到的数据和能做的操作。

基本原则：

- 审核顺序固定：监管一审 → 运营二审 → 铸造（BR-03）【确认】。任一级驳回，申请直接终止，不能修改，这笔资产也不能再次发起（BR-12）【确认】。
- 监管机构只看选择了本机构的申请（BR-15）【确认】；运营可查看全平台全部状态的申请，只能对待运营审核、铸造失败的申请操作【确认】，见[数据范围（F-LG-11）](../M5-管理端登录与权限/01-管理端登录与权限-PRD.md#F-LG-11)。
- 监管协议在线下签署；监管机构一审通过时必须上传，PDF 或图片，最多 10 份，每份不超过 10MB（BR-10、BR-11）【确认】。
- 运营二审通过时必须选择铸造合约，可选范围按资产类型筛选（BR-14）【确认】【建议·已采纳】；所选合约还须能无损承载本申请的完整资产价值小数精度与唯一到期时点。通过分“选择合约”“发起铸造”两步完成；确认后由平台用开发人员配置的签名私钥直接签名并发起链上铸造，运营不使用钱包；平台须取得铸造结果，铸造失败可以再次发起【确认】。代币数量按申请记录的完整资产价值 1:1 确定（BR-19），单位为二审所选合约的代币符号，不以 USD 为单位【确认】；运营在发起铸造时填写代币单位价值，默认按“1 COU = 1 USD”带入，代币数量不因单位价值改变；到期时点和接收地址取申请记录。
- 代币单位价值统一按币本位展示为“1 COU = X USD”；铸造初始资产估值等于完整代币数量乘以代币单位价值，由平台计算并只读展示，不另行填写，也不改写应收账款原值。
- 铸造交易写入链上的内容以本册[上链字段](#onchain-fields)为唯一口径：接收地址、完整代币数量、初始代币单位价值、唯一到期时点、资产编号和企业业务签名值【确认】；M3a、M4b 引用。
- 申请状态只引用简报第 5 节，本模块不另行定义；资产的发行状态以[发行状态](../../两端共用/M2-可信资产/01-可信资产-PRD.md#issue-status)为准。两端衔接的信息以本册[两端衔接字段清单](#handoff)为唯一口径，M3a 引用。

**一个完整的例子。** 企业 A 以一笔完整资产价值 50,000.00 USD、到期日 2027-03-31（带来源时区）的应收账款签名提交了发行申请，选择监管机构 C，系统把 A 提交时的登录地址记录为接收地址。C 收到“新的待审申请”，在发行审核中看到这笔申请处于“待监管审核”，查看申请信息和关联资产。A 与 C 线下签署监管协议后，C 上传两份协议文件（一份 PDF、一份扫描图片），填写审核意见后一审通过；申请变为“待运营审核”，A 收到“监管审核通过”，全体运营收到“待二审的申请”。运营甲打开这笔申请，核对资产、企业、监管意见和协议，第 1 步从可用合约中选择资产类型为应收账款的 ERC-3525 合约，第 2 步确认完整代币数量仍为 50,000.00 COU，填写“1 COU = 0.8 USD”，平台只读算出铸造初始资产估值 40,000.00 USD；甲再核对接收地址、唯一到期时点、资产编号和 A 的业务签名值后确认。二审通过，申请变为“铸造中”，A 收到“运营审核通过”；平台签名并提交铸造交易，甲在进度中看到等待链上结果。首次铸造失败，申请变为“铸造失败”，全体运营收到“铸造失败待重试”，A 不收消息，在 M3a 中仍看到“发行处理中”；运营乙查看失败说明后重试，申请回到“铸造中”。铸造成功后，申请变为“铸造成功”，资产发行状态变为“已发行”，这笔资产自铸造成功起由 C 监管；A 收到“铸造成功”，在 M3a 的申请详情中看到铸造结果；运营和 C 在申请详情中点击铸造结果的代币编号，分别进入全平台代币台账和本机构代币台账中这枚代币的代币详情。

### 1.2 本期不做

- 企业提交、撤回或修改发行申请：企业提交属于 M3a；提交后任何角色都不能撤回或修改（BR-12）【确认】。
- 驳回后重新打开申请，或把申请退回上一环节修改：驳回即终止【确认】。
- 在平台上签署监管协议：协议线下签署，平台只接收监管机构上传的文件（BR-10、D7）【确认】。
- 一审通过后替换、删除或补传协议文件。
- 审核人修改代币数量、到期时点、接收地址、资产编号或企业业务签名值：代币数量按完整资产价值 1:1（BR-19）【确认】，保留完整小数精度，单位为所选合约的代币符号；到期时点取申请记录中上游提供的唯一业务值（BR-13）【确认】；接收地址取企业提交时的选择，资产编号与签名值取申请记录。
- 合约的部署与初始配置由开发人员负责；运营在[合约管理（M6）](../M6-合约管理/01-合约管理-PRD.md)查看、编辑名称、启用和停用【确认】；本模块只选择合约，不维护合约信息。
- 代币铸造之后的融资、销毁和解除监管：属于我的代币与销毁申请（M4a）、销毁审核、解除监管与代币台账（M4b）。
- 运营用个人钱包签名铸造交易，或在平台上配置、查看铸造签名私钥：私钥由开发人员配置，平台直接调用【确认】。
- 运营内部分派、认领审核任务：全体运营看到同一批申请，谁先提交谁的结果生效，见[操作的共同要求](#concurrency)。

## 2. 术语

| 术语 | 含义 |
| --- | --- |
| 发行申请 | 企业以一笔可信资产申请铸造代币的记录，由 M3a 提交产生，有唯一的申请编号；一笔申请只对应一笔资产，企业提交前已用钱包对申请的业务信息签名 |
| 资产价值 | 应收账款完整金额与币种，不做折算、取整或扣减，按[可信资产的术语](../../两端共用/M2-可信资产/01-可信资产-PRD.md#2-术语)；申请记录保留完整值，普通列表的主显示可以直接截断至两位小数但须标明已截断并可核对完整值，审核详情、二审确认和上链使用完整值 |
| 一审 | 企业所选监管机构对发行申请的审核，通过时必须上传监管协议 |
| 二审 | 平台运营对一审已通过的发行申请的审核，通过时必须选择铸造合约 |
| 本机构的申请 | 对某个监管机构而言，企业提交时选择了该机构的发行申请 |
| 监管协议 | 企业与所选监管机构线下签署、由监管机构在一审通过时上传的协议文件 |
| 监管意见 | 监管机构一审通过时填写的审核意见，选填 |
| 驳回意见 | 监管机构或运营驳回时填写的理由，必填 |
| 铸造合约 | 运营二审时选择、用于铸造这笔代币的合约；合约由开发人员配置，在合约管理（M6）中查看 |
| 可用合约 | 资产类型为应收账款、网络为 Ethereum、状态为启用的合约【确认】，见[可选合约范围](#available-contracts) |
| 代币符号 | 合约对应的代币符号，作为代币数量的单位【确认】，按[合约的代币符号](../M6-合约管理/01-合约管理-PRD.md#symbol)；合约在二审时才选定，二审前不展示代币数量 |
| 代币单位价值 | 1 个 COU 对应的 USD 价值，统一按币本位展示为“1 COU = X USD”；铸造时由运营填写初始值，铸造后由 M4b 按单笔代币维护当前值；不改变发行数量或应收账款原值 |
| 铸造初始资产估值 | 铸造时完整代币数量乘以初始代币单位价值所得的 USD 金额；平台自动计算并只读展示，不由运营另行填写 |
| 铸造 | 二审通过后，平台用所选合约在 Ethereum 上为企业铸造代币，结果为成功或失败 |
| 平台签名 | 平台用开发人员预先配置的签名私钥，对铸造交易签名并提交 Ethereum【确认】；运营无需使用钱包，也看不到私钥 |
| 铸造交易哈希 | 铸造交易提交到 Ethereum 后得到的交易标识，用于核对链上结果 |
| 业务签名 | 企业提交申请前用登录地址对申请业务信息所做的签名，由 M3a 保存；签名值随铸造写入链上；与平台签名不是同一件事 |
| 发行申请文件 | 企业在 M3a 填写申请信息时选填、随申请提交的补充文件；不是监管协议，不属于当前已确认的业务签名和上链字段 |
| 上链字段 | 铸造交易写入链上的业务字段，见[上链字段](#onchain-fields) |
| 监管 | 监管机构对这笔资产的监管，从代币铸造成功开始，到监管机构解除监管为止（BR-21）【确认】；融资由下游借贷平台提供，监管与融资分开表述，不将监管表述为质押【确认】 |
| 处理中的发行申请 | 申请状态为待监管审核、待运营审核、铸造中或铸造失败的申请，与 M3a 的口径一致 |
| 终止的发行申请 | 申请状态为监管驳回或运营驳回的申请 |
| 发行处理中 | 企业在 M3a 中对真实状态“铸造中”“铸造失败”的统一展示名称，不是业务状态；本模块的监管机构和运营始终看到真实状态 |

<a id="access"></a>
## 3. 谁能使用

依据：发行审核菜单对运营与监管的可见性与操作【确认】（简报 4.4）；监管机构只能看到本机构的申请（BR-15）【确认】。

| 身份 | 能看到发行审核吗 | 能看到哪些申请 | 能做什么 |
| --- | --- | --- | --- |
| 运营管理人员（账号正常、已登录） | 看得到 | 全平台全部状态的发行申请【确认】 | 待运营审核时二审通过（选择合约）或二审驳回；铸造失败时按[重试条件](#A-ISSUE-07)重试；其他状态只能查看【确认】 |
| 监管机构（账号正常、已登录，含机构已停用） | 看得到 | 只有本机构的申请，任何状态 | 本机构待监管审核申请的一审通过（上传协议）、一审驳回；其他状态只能查看 |
| 待首登改密、锁定的管理端账号；未登录 | 看不到 | 无 | 按[账号状态](../M5-管理端登录与权限/01-管理端登录与权限-PRD.md#account-status)和[无权访问的处理（F-LG-12）](../M5-管理端登录与权限/01-管理端登录与权限-PRD.md#F-LG-12)处理 |

- 机构被停用后，仍可查看本机构的全部申请，并继续审核已选择它的待审申请【确认】，见[停用与启用（F-RG-05）](../M5-机构管理/01-机构管理-PRD.md#F-RG-05)。
- 访问范围以外的申请或不存在的申请（包括通过直接链接、改写编号访问），结果完全相同：不返回任何内容，统一说明“无权查看或申请不存在”，不透露申请是否存在，见[无权访问的处理（F-LG-12）](../M5-管理端登录与权限/01-管理端登录与权限-PRD.md#F-LG-12)。协议文件下载同样适用。
- 发起本角色没有的操作（例如监管机构尝试二审，运营尝试一审），被拒绝，申请不变，说明无权操作。
- 拒绝由平台判定，不能只靠隐藏入口；绕过界面提交审核同样被拒绝。

### 3.1 入口

- 管理端“发行审核”菜单，运营与监管机构都可见，见[菜单权限矩阵（F-LG-10）](../M5-管理端登录与权限/01-管理端登录与权限-PRD.md#F-LG-10)。进入后是本人范围内的[发行申请列表（R-ISSUE-01、A-ISSUE-01）](#R-ISSUE-01)。
- 从可信资产的资产详情中关联的发行申请进入该申请的[申请详情（R-ISSUE-02、A-ISSUE-02）](#R-ISSUE-02)：运营见[全平台资产列表与资产详情](../../两端共用/M2-可信资产/01-可信资产-PRD.md#F-AS-05-assets)，监管机构见[监管机构查看关联资产（F-AS-06）](../../两端共用/M2-可信资产/01-可信资产-PRD.md#F-AS-06)。
- 从消息进入：运营打开[待二审的申请（NT-A01）](./03-代币发行-审核与铸造-消息通知.md#NT-A01)、[铸造失败待重试（NT-A03）](./03-代币发行-审核与铸造-消息通知.md#NT-A03)或[铸造超时待处理（NT-A05）](./03-代币发行-审核与铸造-消息通知.md#NT-A05)后进入该笔申请的申请详情，按当前身份、权限和申请当前状态重新判断，见[前往原业务（MSG-05）](../../两端共用/M7-消息通知/01-消息通知-PRD.md#MSG-05)。企业提交申请时 M3a 本身不发送消息。

<a id="concurrency"></a>
### 3.2 操作的共同要求

本节适用于一审通过、一审驳回、二审通过、二审驳回和铸造重试五个操作。

- 每个操作执行前须确认；取消或离开不保存未提交的内容，包括已上传但未提交的协议文件、已填写的意见和已选的合约，申请保持原状态。
- 提交时以申请的最新状态判断：申请已不在该操作适用的状态（例如另一位运营已完成二审、已重试），本次操作不执行，说明这笔申请的状态已变化并展示最新状态和结果；不重复执行，不覆盖他人的结果。
- 提交进行中给出处理中反馈，同一次操作不能重复提交；重复点击、刷新或网络重发都只生效一次。
- 保存失败时申请保持原状态，可以重试，不出现只改了一部分的情况（例如状态已变但协议未保存）。
- 提交过程中登录结束（主动退出、登录到期或无操作登出）时，按[登录有效期、无操作登出与退出（F-LG-06）](../M5-管理端登录与权限/01-管理端登录与权限-PRD.md#F-LG-06)处理；未确认生效的操作视为未提交，迟到的结果不显示。
- 每个操作须可追溯：操作的账号、所属角色（监管机构另记机构）、时间、操作前后的申请状态，以及意见、协议文件、所选合约等提交内容。

## 4. 查看发行申请

<a id="R-ISSUE-01"></a><a id="A-ISSUE-01"></a>
### 4.1 发行申请列表（R-ISSUE-01、A-ISSUE-01）

适用角色与前提：账号正常、已登录的监管机构或运营管理人员。

- 监管机构列出本机构的全部发行申请；运营列出全平台的全部发行申请。两者都包括处理中、终止和铸造成功的申请。
- 每笔申请展示：申请编号、企业名称、资产编号、资产价值（含币种）、监管机构名称、提交时间、申请状态。
- 可以按申请状态筛选；可以按申请编号、资产编号或企业名称查找。
- 待本人处理的申请须能直接识别：监管机构为“待监管审核”，运营为“待运营审核”和“铸造失败”。
- 可以进入每笔申请的[申请详情（R-ISSUE-02、A-ISSUE-02）](#R-ISSUE-02)。
- 申请状态变化后，列表展示最新状态。
- 还没有任何申请时，说明暂无发行申请；筛选或查找没有结果时，说明没有符合条件的申请，与“暂无申请”区分。
- 读取失败时说明暂时无法获取，可以重试；不说成“没有申请”。
- 监管机构看到的条数、筛选和查找结果只包含本机构的申请，见[数据范围（F-LG-11）](../M5-管理端登录与权限/01-管理端登录与权限-PRD.md#F-LG-11)。

<a id="R-ISSUE-02"></a><a id="A-ISSUE-02"></a>
### 4.2 申请详情（R-ISSUE-02、A-ISSUE-02）

适用角色与前提：账号正常、已登录的监管机构（申请属于本机构）或运营管理人员。

依据：监管和运营共用同一个申请详情，按角色区分操作和数据范围【确认】（简报第 11 节）。

<a id="detail-identity"></a>
**申请的识别信息。** 审核人进入详情时须能同时确认是哪家企业、哪一笔申请、现在到了哪一步，因此企业名称、申请编号和申请状态三项都须展示，不能只展示其中一项：

- 企业名称是审核对象：监管机构据此对应与之线下签署监管协议的企业，运营据此核对企业。从审核判断看，它是首先需要确认的信息。
- 申请编号是这笔申请的唯一标识：同一企业可以有多笔申请，只看企业名称无法区分；消息、列表查找和沟通都以申请编号定位。
- 申请状态展示真实状态，决定本人当前能否办理，见[申请状态与各角色看到的内容、能做的操作](#status)。
- 三项在详情中的位置与呈现方式由设计决定。

申请详情由以下几部分组成，各项含义与可见范围以[两端衔接字段清单](#handoff)为准：

- 申请信息：见[申请信息](#handoff-application)，包括企业提交时冻结的发行申请文件。另展示企业名称，运营可以进入该企业在可信资产中的企业详情，见[运营查看企业与资产（F-AS-05）](../../两端共用/M2-可信资产/01-可信资产-PRD.md#F-AS-05)；监管机构看不到企业详情。
- 关联资产：资产编号、债务人名称、资产价值（应收账款金额与币种）、到期日，以及资产最新的确权状态、回款状态和发行状态，与可信资产的三个状态一致【确认】（[资产状态定义](../../两端共用/M2-可信资产/01-可信资产-PRD.md#status-fields)；回款状态按[回款状态归并](../../两端共用/M2-可信资产/01-可信资产-PRD.md#repayment-status)取值）；结清、逾期的经过不在申请详情展示，到资产详情中查看【确认】；可以进入该资产在可信资产中的资产详情。运营另看到[上游变更提示](../../两端共用/M2-可信资产/01-可信资产-PRD.md#upstream-change)（上游已撤销确权、上游已删除）；监管机构看不到这类提示。
- 审核进度：按顺序展示提交、监管一审、运营二审、铸造四个环节；每个环节展示是否已完成、结果和完成时间，尚未到达的环节展示为未开始。各环节展示的内容见[审核结果与意见](#handoff-review)。
- 业务签名：只有运营可见，监管机构看不到【确认】，见[业务签名记录](#handoff-signature)；申请处于任何状态都可以查看。
- 监管协议：见[查看与下载监管协议（R-ISSUE-03、A-ISSUE-03）](#R-ISSUE-03)。
- 铸造结果：见[铸造结果（A-ISSUE-06）](#A-ISSUE-06)。
- 当前可做的操作：按下方组合表。

<a id="status"></a>
**申请状态与各角色看到的内容、能做的操作。** 申请状态引用简报第 5 节：待监管审核 → 监管驳回（终止）/ 待运营审核 → 运营驳回（终止）/ 铸造中 → 铸造成功 / 铸造失败（→ 运营重试 → 铸造中）【建议·已采纳】。

| 申请状态 | 监管机构（本机构）能做什么 | 运营能做什么 | 监管协议 | 铸造结果 | 资产发行状态 |
| --- | --- | --- | --- | --- | --- |
| 待监管审核 | 一审通过（上传协议）或一审驳回 | 只能查看 | 无 | 无 | 发行申请中 |
| 监管驳回 | 只能查看，申请已终止 | 只能查看，申请已终止 | 无 | 无 | 已驳回 |
| 待运营审核 | 只能查看 | 二审通过（选择合约）或二审驳回 | 监管机构与运营都可查看、下载 | 无 | 发行申请中 |
| 运营驳回 | 只能查看，申请已终止 | 只能查看，申请已终止 | 监管机构与运营都可查看、下载 | 无 | 已驳回 |
| 铸造中 | 只能查看 | 只能查看；不能重试、不能驳回 | 监管机构与运营都可查看、下载 | 正在铸造 | 发行申请中 |
| 铸造失败 | 只能查看；看到铸造失败，看不到失败说明 | 可沿二审原合约手动重试，平台停用不阻断；实际链上异常按[铸造失败手动重试（A-ISSUE-07）](#A-ISSUE-07)处理；看到每次失败的时间与失败说明 | 监管机构与运营都可查看、下载 | 失败记录（仅运营可见失败说明） | 发行申请中 |
| 铸造成功 | 只能查看 | 只能查看 | 监管机构与运营都可查看、下载 | 展示铸造结果 | 已发行 |

- 监管驳回、运营驳回、铸造成功是终态，申请不再变化；铸造成功后代币的后续状态在代币台账（M4b）中查看。
- 资产发行状态一列由可信资产模块定义，此处只说明对应关系。
- 企业在 M3a 中把铸造中、铸造失败统一看作“发行处理中”，看不到失败与重试；本模块按上表展示真实状态，见[关联发行申请的铸造阶段展示](../../两端共用/M2-可信资产/01-可信资产-PRD.md#minting-display)。
- 操作入口只在上表允许的状态、对上表允许的角色出现；绕过界面发起同样被拒绝，见[谁能使用](#access)。

其他规则：

- 申请信息是提交时的记录，不随资产或账户之后的变化而改变；关联资产的状态展示最新值。
- 发行申请文件在申请提交成功时冻结，本机构监管与运营从“待监管审核”起即可逐份查看、下载；任何角色都不能替换、删除或补传。其他监管机构及无权访问者不能通过文件地址读取。读取失败时说明本次未能打开，可以重试，不影响申请其他信息。
- <a id="review-asset-change"></a>申请提交后，资产在上游被撤销确权、删除，或回款状态变为已逾期、已结清时，都不自动拦截审核、铸造或重试，也不自动终止申请；详情向审核人展示资产最新的确权状态和回款状态，运营另见上游变更提示，由审核人判断是否驳回【确认】。能否驳回仍按[申请状态与角色](#status)判断，铸造中、铸造失败时不增加驳回操作。
- 确权状态沿用可信资产的[确权状态](../../两端共用/M2-可信资产/01-可信资产-PRD.md#confirm-status)；回款状态与可信资产列表、详情使用同一[回款状态归并](../../两端共用/M2-可信资产/01-可信资产-PRD.md#repayment-status)结果，依据见[结清与逾期依据](../../两端共用/M2-可信资产/01-可信资产-PRD.md#overdue)。
- 先逾期后结清的资产，申请详情的回款状态为“已结清”；曾逾期的经过在资产详情的回款进度中查看。回款状态无法确定时，按可信资产规则说明暂时无法确认，不归入未到期、已逾期或已结清。
- 上游已删除的资产按可信资产规则保留最近一次信息，不编造新的状态。
- 上游平台暂时不可用时，申请详情照常可查看，关联资产展示本平台最近一次保存的信息，见[上游平台暂时不可用](../../两端共用/M2-可信资产/01-可信资产-PRD.md#common-errors)；审核操作不依赖上游，照常可用。
- 读取失败时说明暂时无法获取，可以重试。
- 字段名称、状态取值和说明文字按本人当前界面语言展示中文或英文；金额、数量、代币符号、编号、机构名称、企业名称、文件名称、意见原文不随语言变化。普通列表的金额主显示可以直接截断至两位小数，但须标明已截断并可核对完整值；审核详情、二审确认和铸造结果显示完整值。所有时间按本人时区展示并标明时区，见[界面语言与时区（F-LG-09）](../M5-管理端登录与权限/01-管理端登录与权限-PRD.md#F-LG-09)；时区只改变展示，不改变申请记录、签名和上链中的唯一到期时点。

流程参见：[发行申请状态（图 3）](./02-代币发行-审核与铸造-流程图与状态机.md#fig-3)、[查看申请与数据范围（图 4）](./02-代币发行-审核与铸造-流程图与状态机.md#fig-4)。

<a id="R-ISSUE-03"></a><a id="A-ISSUE-03"></a>
### 4.3 查看与下载监管协议（R-ISSUE-03、A-ISSUE-03）

适用角色与前提：申请的一审已通过（申请状态为待运营审核、运营驳回、铸造中、铸造失败或铸造成功）；监管机构限本机构的申请。

依据：运营二审时查看监管协议，企业和运营都可以查看 / 下载监管协议（BR-18）【确认】；协议在一审通过时上传（BR-10）【确认】。

- 展示一审通过时上传的全部协议文件，每份可以单独查看和下载；每份展示文件名称、上传时间和上传的监管机构。
- 文件名称按上传时的原文展示。
- 一审通过前（待监管审核）和监管驳回的申请没有协议，也不能通过直接访问取得；一审过程中已上传但未提交的文件，任何人都看不到。
- 一审通过后，任何角色都不能替换、删除或补传协议文件。
- 查看或下载失败时说明本次未能打开，可以重试；不影响查看申请的其他信息。

## 5. 监管一审

依据：监管一审只看本机构申请；通过时必须上传监管协议，通过后转运营二审；驳回需填写意见，驳回即终止（R-ISSUE、BR-03、BR-10、BR-11、BR-12、BR-15）【确认】。

流程参见：[监管一审（图 1）](./02-代币发行-审核与铸造-流程图与状态机.md#fig-1)。

<a id="R-ISSUE-04"></a>
### 5.1 监管一审：上传协议并通过（R-ISSUE-04）

适用角色与前提：账号正常、已登录的监管机构；申请属于本机构，状态为“待监管审核”。机构已停用的照常可以办理【确认】。

- 通过前须上传监管协议，至少 1 份、最多 10 份。
- 可以选填监管意见；监管意见对运营可见，对企业不可见，见[审核结果与意见](#handoff-review)。
- 提交前可以移除已上传的文件、继续添加，直到总数达到 10 份。
- 确认时须说明：通过后申请转入运营二审；协议文件提交后不能替换或删除；企业和运营都可以查看、下载这些文件。

协议文件与监管意见：

| 业务信息 | 含义/类型 | 必填条件/默认值 | 可编辑范围 | 校验与失败结果 |
| --- | --- | --- | --- | --- |
| 监管协议文件 | 企业与本机构线下签署的协议；文件，可多份 | 通过时必填，至少 1 份；无默认值 | 提交前可添加、移除；提交后不能修改 | 格式须为 PDF、JPG、JPEG、PNG【确认】，其他格式不添加并说明支持的格式；单份超过 10MB 的不添加并说明上限；总数已达 10 份时不能再添加并说明上限；空文件不添加；单份上传失败时说明该文件未上传成功，可重试或移除，不影响其他文件 |
| 监管意见 | 一审通过时的审核意见；文本 | 选填；无默认值 | 提交前可修改；提交后不能修改 | 最多 500 个字符【确认】，超过时说明上限、不能提交；只含空格视为未填写 |

- 只有上传成功的文件计入份数；有文件仍在上传或上传失败未移除时，不能提交通过，并说明原因。
- 一次提交中同名文件可以并存，各自作为一份。

提交时再次核对：申请仍为“待监管审核”且仍属于本机构，按[操作的共同要求](#concurrency)处理。

通过成功后：

- 申请状态变为“待运营审核”；记录一审结果“通过”、通过时间、操作账号、监管意见和全部协议文件。
- 资产发行状态保持“发行申请中”。
- 协议文件即时对运营（本模块）和企业（M3a）开放查看与下载。
- 向企业发送[监管审核通过（NT-C01）](./03-代币发行-审核与铸造-消息通知.md#NT-C01)，向全体运营发送[待二审的申请（NT-A01）](./03-代币发行-审核与铸造-消息通知.md#NT-A01)。
- 监管机构看到一审已通过，申请转为只能查看。

| 情况 | 用户看到的结果与可继续操作 |
| --- | --- |
| 没有上传成功的文件就提交 | 不能提交，说明通过时须上传监管协议 |
| 文件格式、大小、份数或空文件不符合要求 | 该文件不添加，说明具体原因；已添加的其他文件保留 |
| 申请状态已变化（例如已在另一个登录中处理） | 不执行，说明状态已变化，展示最新状态 |
| 保存失败 | 说明一审未提交成功，申请仍为待监管审核，已上传的文件和已填写的意见保留，可以重试 |

<a id="R-ISSUE-05"></a>
### 5.2 监管一审：驳回（R-ISSUE-05）

适用角色与前提：同[监管一审：上传协议并通过（R-ISSUE-04）](#R-ISSUE-04)。

| 业务信息 | 含义/类型 | 必填条件/默认值 | 可编辑范围 | 校验与失败结果 |
| --- | --- | --- | --- | --- |
| 驳回意见 | 驳回的理由，企业与运营都可见；文本 | 必填；无默认值 | 提交前可修改；提交后任何角色都不能修改 | 为空或只含空格时不能提交，说明须填写驳回意见；最多 500 个字符【确认】，超过时说明上限、不能提交 |

- 驳回不需要上传协议文件；驳回时不保存任何协议文件。
- 确认时须说明：驳回后申请终止，不能撤销，企业不能修改申请，这笔资产不能再次发起发行申请。

驳回成功后：

- 申请状态变为“监管驳回”，终态；记录驳回时间、操作账号和驳回意见。
- 资产发行状态变为“已驳回”，见[发行状态](../../两端共用/M2-可信资产/01-可信资产-PRD.md#issue-status)。
- 向企业发送[监管审核驳回（NT-C02）](./03-代币发行-审核与铸造-消息通知.md#NT-C02)；不给运营发消息。

驳回意见为空、申请状态已变化或保存失败时，申请保持“待监管审核”，按上表和[操作的共同要求](#concurrency)提示，已填写的意见保留。

## 6. 运营二审

依据：二审查看申请、资产、监管意见与协议；通过时选择铸造合约后铸造，分选择合约、发起铸造两步完成并展示进度，铸造由平台签名与链上交互【确认】；驳回需填写意见，驳回即终止（A-ISSUE、BR-03、BR-12、BR-14、BR-18）【确认】；合约按资产类型筛选【建议·已采纳】。

流程参见：[运营二审与铸造（图 2）](./02-代币发行-审核与铸造-流程图与状态机.md#fig-2)。

<a id="A-ISSUE-04"></a>
### 6.1 运营二审：选择铸造合约并通过（A-ISSUE-04）

适用角色与前提：账号正常、已登录的运营管理人员；申请状态为“待运营审核”。任何一位运营都可以办理。

通过分两步完成：第 1 步选择合约，第 2 步发起铸造【确认】。

- 过程中须展示进度，标明共两步、当前在哪一步；确认后在同一次操作中继续展示[铸造进度](#minting-progress)【确认】。
- 第 2 步可以返回第 1 步改选，已选合约保留；取消或离开不保存，申请保持“待运营审核”。
- 同一信息只在一步中完整展示：合约的详细信息只在第 1 步展示，第 2 步只引用合约名称。

<a id="choose-contract"></a>
**第 1 步：选择合约**

- 从可用合约中选择一个能无损承载本申请完整代币数量与唯一到期时点的铸造合约；不预选，一笔申请只能选一个。选定后才能进入第 2 步。
- 每个可选合约展示：合约名称、标准（ERC-3525）、代币符号、对应资产类型（应收账款）、所在网络（Ethereum）和合约地址；可以核对完整合约地址。合约信息以合约管理（M6）为准，名称展示取[当前已保存名称（F-CT-03）](../M6-合约管理/01-合约管理-PRD.md#F-CT-03)；改名不改变二审所选合约及其地址。
- <a id="available-contracts"></a>只列出资产类型为应收账款、网络为 Ethereum、状态为启用的合约【确认】，见[发行二审可选的合约（F-CT-02）](../M6-合约管理/01-合约管理-PRD.md#F-CT-02)。三个条件须同时满足；不满足任一条件的合约不出现在可选范围中。

| 业务信息 | 含义/类型 | 必填条件/默认值 | 可编辑范围 | 校验与失败结果 |
| --- | --- | --- | --- | --- |
| 铸造合约 | 用于铸造这笔代币的合约；单选，从可用合约中选 | 通过时必填；不预选 | 提交前可改选；提交后不能更换，重试也沿用，见[铸造失败手动重试（A-ISSUE-07）](#A-ISSUE-07) | 未选择时不能进入第 2 步；提交时所选合约已不可用的，不能提交，说明该合约当前不可用，要求返回第 1 步重新选择 |

<a id="start-minting"></a>
**第 2 步：填写单位价值并发起铸造**

本步填写初始代币单位价值，并展示本次铸造写入链上的其他内容（[上链字段](#onchain-fields)）：

| 业务信息 | 含义 | 必填条件与编辑规则 |
| --- | --- | --- |
| 接收地址 | 申请记录的接收地址，即铸造到账地址；可核对完整地址 | 只读 |
| 代币数量 | 完整值等于申请记录的完整资产价值，保留相同小数精度，单位为所选合约的代币符号，不以 USD 为单位 | 只读；单位价值改变时数量不变 |
| 代币单位价值 | 1 个 COU 对应的 USD 价值，按“1 COU = X USD”展示 | 必填；默认 1 USD；提交前可修改；必须大于 0；小数精度和最大值按 Q-M3B-01 待确认 |
| 铸造初始资产估值 | 完整代币数量 × 代币单位价值，单位 USD；输入单位价值后即时更新 | 只读；不提供单独输入，不改写应收账款原值 |
| 到期日 | 申请记录的唯一到期时点；按运营本人时区展示并标明时区，不改变上链业务值 | 只读 |
| 资产编号 | 申请记录的资产编号 | 只读 |
| 企业业务签名值 | 企业提交申请时的签名值，与[业务签名记录](#handoff-signature)一致；缩写展示，可核对完整值 | 只读 |

另展示交易所用合约：第 1 步所选合约的名称。合约是交易对象，不是写入链上的字段；标准、代币符号、网络和合约地址已在第 1 步展示，不再重复。

确认时须说明：确认后二审即通过、不能撤销，平台随即签名并在 Ethereum 上发起铸造，结果在铸造进度和申请详情中展示。

提交时再次核对：申请仍为“待运营审核”；所选合约仍为可用合约，并且能无损承载本申请的完整代币数量、初始代币单位价值与唯一到期时点；代币单位价值有效且大于 0。

通过成功后：

- 记录二审结果“通过”、通过时间、操作账号、所选合约、初始代币单位价值和自动计算的铸造初始资产估值；申请状态变为“铸造中”。
- 平台随即用所选合约提交铸造交易，把申请记录的完整代币数量铸造到申请记录的接收地址，并按[上链字段](#onchain-fields)写入初始代币单位价值、唯一到期时点、资产编号和企业业务签名值：由平台签名并提交铸造交易，取得链上结果，见[铸造结果（A-ISSUE-06）](#A-ISSUE-06)。
- 资产发行状态保持“发行申请中”。
- 向企业发送[运营审核通过（NT-C03）](./03-代币发行-审核与铸造-消息通知.md#NT-C03)；不给监管机构发消息。

<a id="minting-progress"></a>
**铸造进度**

确认后依次展示以下阶段，并标明每个阶段是否完成、当前在哪个阶段：

1. 二审通过：记录二审结果，申请变为“铸造中”。
2. 平台签名并提交：平台用开发人员配置的签名私钥对铸造交易签名，提交到 Ethereum；运营无需操作钱包。
3. 等待链上结果：交易已提交，展示铸造交易哈希（可核对和复制完整值），等待 Ethereum 返回结果。
4. 铸造结果：成功或失败。

- 铸造不依赖进度的查看：运营在任一阶段关闭进度或离开，铸造照常进行；申请详情展示“铸造中”及所处阶段，取得结果后按[铸造结果（A-ISSUE-06）](#A-ISSUE-06)记录。
- 查看进度期间取得结果的，直接展示结果：成功时展示代币数量（含代币符号）和铸造交易哈希；失败时展示失败说明（取得时），并可以按[铸造失败手动重试（A-ISSUE-07）](#A-ISSUE-07)再次发起。
- 平台未能签名或提交（例如签名私钥不可用、交易被拒绝）也是铸造失败，没有铸造交易哈希，按[铸造结果（A-ISSUE-06）](#A-ISSUE-06)处理，可以再次发起。
- 等待链上结果满 10 分钟仍没有结果时，进度中说明已超时、申请仍为铸造中、需线下联系开发人员处理，见[铸造超时提醒](#mint-timeout)。
- 铸造重试使用同一套进度，第一个阶段为“记录重试，申请回到铸造中”。

| 情况 | 用户看到的结果与可继续操作 |
| --- | --- |
| 没有任何可用合约 | 说明暂无可用的铸造合约，已有匹配但停用的合约时可在合约管理启用，没有匹配合约时需由开发人员配置；不能通过，仍可驳回 |
| 可用合约都不能无损承载本申请的完整代币数量或唯一到期时点 | 说明当前没有可准确铸造这笔申请的合约，不能通过；运营仍可驳回，不得改用截断金额或本地日期铸造 |
| 合约读取失败 | 说明暂时无法获取合约，可以重试；不说成“没有可用合约” |
| 未选择合约就提交 | 不能提交，说明须选择铸造合约 |
| 代币单位价值为空、为 0、为负数或不符合已确认精度 | 不能提交，说明须按“1 COU = X USD”填写有效单位价值；申请仍为待运营审核 |
| 所选合约在提交时已不可用 | 不能提交，说明该合约当前不可用，要求重新选择；申请仍为待运营审核 |
| 申请状态已变化（例如另一位运营已完成二审） | 不执行，说明状态已变化，展示最新状态和结果 |
| 保存失败 | 说明二审未提交成功，申请仍为待运营审核，可以重试；不发起铸造 |

<a id="A-ISSUE-05"></a>
### 6.2 运营二审：驳回（A-ISSUE-05）

适用角色与前提：同[运营二审：选择铸造合约并通过（A-ISSUE-04）](#A-ISSUE-04)。

| 业务信息 | 含义/类型 | 必填条件/默认值 | 可编辑范围 | 校验与失败结果 |
| --- | --- | --- | --- | --- |
| 驳回意见 | 驳回的理由，企业与监管机构都可见；文本 | 必填；无默认值 | 提交前可修改；提交后任何角色都不能修改 | 为空或只含空格时不能提交，说明须填写驳回意见；最多 500 个字符【确认】，超过时说明上限、不能提交 |

- 驳回不需要选择合约。
- 确认时须说明：驳回后申请终止，不能撤销，企业不能修改申请，这笔资产不能再次发起发行申请；已上传的监管协议保留。

驳回成功后：

- 申请状态变为“运营驳回”，终态；记录驳回时间、操作账号和驳回意见。
- 资产发行状态变为“已驳回”。
- 监管协议照常保留，企业、监管机构和运营仍可查看、下载。
- 向企业发送[运营审核驳回（NT-C04）](./03-代币发行-审核与铸造-消息通知.md#NT-C04)；不给监管机构发消息。

驳回意见为空、申请状态已变化或保存失败时，申请保持“待运营审核”，按上表和[操作的共同要求](#concurrency)提示，已填写的意见保留。

## 7. 铸造

依据：二审通过后铸造；铸造失败由运营手动重试（BR-14）【确认】；铸造成功后资产进入监管（BR-21）【确认】；需要“铸造中”状态承接链上结果返回前的时间差【建议·已采纳】；同一笔资产不可重复铸造（BR-08）【建议·已采纳】。

流程参见：[运营二审与铸造（图 2）](./02-代币发行-审核与铸造-流程图与状态机.md#fig-2)。

<a id="onchain-fields"></a>
**上链字段（唯一口径）【确认】。** 二审通过后，平台用开发人员配置的签名私钥签名并提交铸造交易，交易写入以下六项；首次铸造与每次重试写入的字段与取值相同：

| 上链字段 | 取值 |
| --- | --- |
| 接收地址 | 申请记录的接收地址，即铸造到账地址 |
| 代币数量 | 等于申请记录的完整资产价值，保留相同小数精度，单位为所用合约的代币符号 cou |
| 初始代币单位价值 | 运营在二审时确认的完整值，业务方向为“1 COU = X USD”；不使用倒数汇率或页面截断值 |
| 到期日 | 申请记录的唯一到期时点，不使用查看者时区换算后的本地日期 |
| 资产编号 | 申请记录的资产编号，供链下关联这笔资产 |
| 企业业务签名值 | 企业提交发行申请时的签名值，见[业务签名记录](#handoff-signature) |

- 合约、网络、交易时间和链上代币标识由链本身产生，不另行写入。
- 签名地址可由签名值推出，不另外上链。
- 企业签名内容为资产编号、完整资产价值（数值即完整代币数量）、唯一到期时点、接收地址四项，这四项均在上链字段中；初始代币单位价值由运营在企业签名之后确定并上链，不属于企业签名内容。金额不使用两位截断展示值，到期不使用查看者本地日期。任何人只凭链上相应字段即可验证签名，见 M3a [提交时的业务签名](../../面客端/M3a-代币发行-企业申请/01-代币发行-企业申请-PRD.md#signing)。
- 不上链：企业名称、债务人与交易对手信息、合同发票等材料；监管机构名称与监管协议；审核意见、驳回意见、解除监管记录、操作人员账号；发行申请编号、销毁申请编号（平台按交易哈希对应申请）；签名时间、签名地址；“1 COU =”等展示文字；铸造初始资产估值（可由链上数量和单位价值计算）。
- 被驳回的申请，平台不提交任何链上交易，其签名不上链；已提交但执行失败的铸造交易，其中的字段会随失败交易留在链上，这是链的特性，不代表代币已铸造。
- 销毁交易由企业钱包签署并直接提交，不沿用铸造的平台签名模式；链上约束与记录见 M4b [企业钱包直接提交销毁交易](../M4b-销毁审核与解除质押/01-销毁审核与解除质押-PRD.md#platform-signing)。
- 依赖（待开发验证）：ERC-3525 合约能否无损承载上游完整资产价值、初始代币单位价值的小数精度与唯一到期时点，如何携带资产编号、单位价值与签名值（代币属性、事件或元数据），以及对交易成本的影响，由开发人员确认；本册只规定上链哪些字段与业务值，不规定写入方式。验证完成前不能以页面截断值或查看者本地日期替代。合约是否校验签名不作要求，链上记录即可，是否由合约校验由研发评估。

<a id="A-ISSUE-06"></a>
### 7.1 铸造结果（A-ISSUE-06）

适用角色与前提：运营管理人员；监管机构限本机构的申请。申请已进入铸造（状态为铸造中、铸造失败或铸造成功）。

- 铸造使用二审所选合约；完整代币数量等于申请记录的完整资产价值（1:1，保留相同小数精度），单位为所用合约的代币符号，不以 USD 为单位【确认】；初始代币单位价值取二审确认值，按“1 COU = X USD”展示；到期时点等于申请记录的唯一到期时点，接收地址等于申请记录的接收地址；交易同时写入初始代币单位价值、资产编号和企业业务签名值，按[上链字段](#onchain-fields)。应收账款的完整金额与到期时点由上游提交后不再变更【确认】，所以铸造结果中的数量、到期时点和接收地址与申请记录一致，单位价值不改写这些申请事实。
- 一笔申请最多铸造成功一次；铸造中不能再次发起铸造。
- 铸造中：申请详情说明代币正在铸造，运营和监管机构都看到所处阶段（平台签名并提交、等待链上结果）和已提交的铸造交易哈希，超时提醒只有运营看到，见[铸造过程记录](#mint-process)；不提供重试或驳回。长时间没有结果时按[铸造超时提醒](#mint-timeout)处理。二审已确定原合约后，平台停用不终止铸造或改变原选择，继续承接实际结果【确认】，见[停用与既有业务](../M6-合约管理/01-合约管理-PRD.md#inflight)。

<a id="mint-timeout"></a>
铸造超时提醒【确认】：

- 一次铸造自申请进入“铸造中”起满 10 分钟仍未取得链上结果（成功或失败），即为铸造超时。首次铸造和每次重试分别计时。
- 超时后申请状态不变，仍为“铸造中”：不自动转为铸造失败，也不开放重试或驳回。
- 向全体运营发送[铸造超时待处理（NT-A05）](./03-代币发行-审核与铸造-消息通知.md#NT-A05)，每次铸造最多一条。运营在申请详情中看到这次铸造已超时、开始铸造的时间和已提交的铸造交易哈希（未能提交的没有），并说明需线下联系开发人员处理。
- 运营线下联系开发人员处理；线下处理的过程不在平台记录。
- 平台继续取得结果；之后取得成功或失败结果时，按下方铸造成功或铸造失败处理，超时提醒随之不再展示。
- 监管机构仍看到“铸造中”及所处阶段与已提交的铸造交易哈希，看不到超时提醒；企业仍看到“发行处理中”。两者都不收超时消息。

铸造成功时：

- 申请状态变为“铸造成功”，终态；记录[铸造结果](#handoff-mint)。
- 资产发行状态变为“已发行”。
- 这笔资产自铸造成功起由所选监管机构监管，开始时间为铸造时间（BR-21）【确认】；监管与融资分开表述，解除监管属于 M4b。
- 代币进入代币台账（M4b）与企业的我的代币（M4a），产生平台内唯一的代币编号，记入[铸造结果](#handoff-mint)。申请详情中点击代币编号按角色进入这枚代币的代币详情：运营进入[全平台代币台账（A-TOKEN-01）](../M4b-销毁审核与解除质押/01-销毁审核与解除质押-PRD.md#A-TOKEN-01)，监管机构进入[本机构代币台账（R-TOKEN-01）](../M4b-销毁审核与解除质押/01-销毁审核与解除质押-PRD.md#R-TOKEN-01)；企业在 M3a 进入我的代币的[代币详情（C-TOKEN-02）](../../面客端/M4a-我的代币与销毁申请/01-我的代币与销毁申请-PRD.md#C-TOKEN-02)。
- 向企业发送[铸造成功（NT-C05）](./03-代币发行-审核与铸造-消息通知.md#NT-C05)；不给运营和监管机构发消息。

铸造失败时：

- 申请状态变为“铸造失败”；记录这一次失败的时间、失败说明（取得时记录，取不到时不展示，不编造原因）和铸造交易哈希（已提交上链的才有）。失败包括平台未能签名或提交交易，以及交易提交后链上执行失败。
- 资产发行状态保持“发行申请中”；接收地址继续使用申请提交时记录的登录地址。
- 运营在申请详情中看到每一次失败的时间和失败说明，以及每一次重试的时间和操作账号；监管机构只看到“铸造失败”，看不到失败说明；企业按 M3a 看到“发行处理中”、无需操作，看不到失败、失败说明和重试。
- 向全体运营发送[铸造失败待重试（NT-A03）](./03-代币发行-审核与铸造-消息通知.md#NT-A03)，每次失败一条；不给企业和监管机构发消息。

<a id="A-ISSUE-07"></a>
### 7.2 铸造失败手动重试（A-ISSUE-07）

适用角色与前提：账号正常、已登录的运营管理人员；申请状态为“铸造失败”。任何一位运营都可以办理。

- 重试一律沿用二审所选合约，不能改选【确认】；完整代币数量、初始代币单位价值、唯一到期时点、接收地址、资产编号和企业业务签名值沿用原二审记录，不能更改，企业不再签名；新的铸造交易写入的[上链字段](#onchain-fields)与首次相同。
- 提交重试时核对申请仍为铸造失败、仍对应二审原合约且没有已成功或正在执行的铸造；不重新按首次[可选合约范围](#available-contracts)筛选。平台停用不阻断原业务或手动重试，无需先启用【确认】，见[停用与既有业务](../M6-合约管理/01-合约管理-PRD.md#inflight)。
- 重试只有确认一步：展示代币数量（单位为原合约的代币符号）、接收地址和原合约名称，均不能更改。
- 确认后申请状态回到“铸造中”，记录重试时间和操作账号；平台签名并提交新的铸造交易，进度按[铸造进度](#minting-progress)展示，之后按[铸造结果（A-ISSUE-06）](#A-ISSUE-06)处理。
- 重试不是新的审核通过，不再发送[运营审核通过（NT-C03）](./03-代币发行-审核与铸造-消息通知.md#NT-C03)。
- 本期不限制重试次数。

| 情况 | 用户看到的结果与可继续操作 |
| --- | --- |
| 二审原合约仅在平台停用 | 既有业务继续，运营可沿原合约手动重试，无需先启用；不能改选合约 |
| 原合约存在实际链上执行异常 | 说明实际异常，申请保持铸造失败，不能改选；由开发人员处理后运营沿原合约手动重试。平台启用不代表链上异常已经恢复，恢复本身不发起铸造 |
| 申请状态已变化（例如另一位运营已重试） | 不执行，说明状态已变化，展示最新状态 |
| 重试未能记录（保存失败） | 说明本次未能重新发起铸造，申请保持铸造失败，不产生新的失败记录，可以再次重试 |
| 重试已记录，但平台未能签名或提交交易 | 申请回到铸造失败，按[铸造结果（A-ISSUE-06）](#A-ISSUE-06)记录这一次失败，可以再次重试 |

## 8. 两端衔接字段清单

依据：两端衔接的信息（申请字段、驳回意见、铸造结果、监管协议）在 M3a、M3b 中使用同一份字段清单，由 M3b 维护、M3a 引用【确认】（简报第 11 节）。

- 本节是这些信息的唯一口径：名称、含义、产生环节与各角色可见范围以本节为准。M3a 的申请详情、申请列表、监管协议和铸造结果引用本节；本模块各功能也引用本节。
- 需要改动时先改本节，再同步 M3a。
- 企业一列指企业在 M3a 中看到的内容，具体展示规则见 M3a；监管机构一列限本机构的申请。
- 所有时间按查看者所选时区展示并标明时区；面客端按[偏好设置（C-PROFILE-02）](../../面客端/M1-企业登录与企业账户/01-企业登录与企业账户-PRD.md#C-PROFILE-02)，管理端按[界面语言与时区（F-LG-09）](../M5-管理端登录与权限/01-管理端登录与权限-PRD.md#F-LG-09)。时区只改变展示，不改变申请记录、签名与上链中的唯一到期时点。

**业务签名记录。** 企业提交前用登录地址对这笔申请业务信息所做的签名，由 M3a 随申请保存，任何角色都不能修改；申请处于任何状态都可以查看。企业在 M3a 中查看，管理端只有运营可以查看，监管机构看不到，直接访问也取不到【确认】；签名规则见[提交时的业务签名](../../面客端/M3a-代币发行-企业申请/01-代币发行-企业申请-PRD.md#signing)。

| --- | --- | --- | --- | --- |
| 签名地址 | 签名所用的登录地址，即签名时企业的登录地址；缩写展示，可核对和复制完整地址；之后上游登录地址变更不改变它 | 可见 | 不可见【确认】 | 可见 |
| 签名时间 | 完成签名的时点，记录签署时点，不属于签名内容，不上链 | 可见 | 不可见【确认】 | 可见 |

- 所签内容就是这笔申请提交时的资产编号、完整资产价值、唯一到期时点和接收地址；这四项均在[上链字段](#onchain-fields)中，运营后置确定的初始代币单位价值不属于企业签名内容；不另行展示签名原文。之后机构改名、账户改备注名或查看者切换时区，不改变签名记录。

- 签名记录读取失败时，说明暂时无法获取，可以重试；不影响查看申请的其他信息。

| 关联资产信息与资产状态 | 上游平台，按[可信资产](../../两端共用/M2-可信资产/01-可信资产-PRD.md)定义 | 不能；发行状态由本模块的驳回、铸造成功结果推动 | 运营看全平台；监管机构看关联资产 |
| 企业信息、企业当前登录地址 | 上游平台、企业登录与企业账户（M1），按可信资产模块供运营查看 | 不能 | 只有运营 |
| 审核结果与意见 | 本模块 | 提交后不能 | 按[审核结果与意见](#handoff-review) |
| 监管协议文件 | 监管机构在一审通过时上传 | 提交后不能 | 按[监管协议](#handoff-agreement) |
| 可用合约 | 合约管理（M6），开发人员初始配置，运营可在该模块改名与启用停用 | 本模块不能维护 | 只有运营在二审时选择 |
| 铸造结果与铸造过程记录 | 本模块，平台签名提交铸造交易后取得的 Ethereum 链上结果（D5） | 不能 | 按[铸造结果](#handoff-mint) |

## 11. 待确认事项、跨模块同步与依赖

本模块沿用 M3a 的两项待确认：

| 编号 | 事项 | 当前处理与影响 |
| --- | --- | --- |
| Q-M3A-01 | 发行申请文件的支持格式 | 建议沿用监管协议的 PDF、JPG、JPEG、PNG，并按实际内容识别；用户裁定前不把格式写成已确认验收。管理端须预留格式提示与错误说明的承载。 |
| Q-M3A-02 | 是否把申请文件内容摘要加入企业业务签名和上链字段 | 建议本期不扩展，沿用当前四字段企业签名；初始代币单位价值由运营二审确定并单独上链，不加入企业签名。管理端只展示冻结的申请文件，不新增文件摘要链上核对。若用户要求链上不可抵赖证明，M3a、M3b 与合约能力须同步重审。 |
| Q-M3B-01 | 代币单位价值允许的小数位数和最大值 | 已确认按“1 COU = X USD”展示、必须大于 0；小数位数与最大值尚未确认。研发须先核验链上可无损承载范围，产品确认前，涉及超出已确认范围的输入与链上验收待验、不判通过。 |

除以上两项外，当前没有跨模块待同步差异。

依赖：

- 代币发行·企业申请（M3a）：提交申请并记录申请信息。
- 可信资产（M2）与上游平台（D2、D3）：资产信息、资产状态、上游变更提示。
- 管理端登录与权限、监管机构管理（M5）：登录、菜单权限、数据范围、语言与时区、停用后的在途业务。
- 文件存储与访问控制：承接 M3a 随申请提交的文件，按企业、所选监管机构和运营的范围授权读取；提交后保持不可修改，内容识别、安全检测与越权拦截能力由研发验证（待验证）。
- [合约管理（M6）](../M6-合约管理/01-合约管理-PRD.md)：可用合约及其信息，含作为代币数量单位的[代币符号](../M6-合约管理/01-合约管理-PRD.md#symbol) cou【确认】；合约能否无损承载本次完整代币数量与唯一到期时点、能否在链上提供代币符号由开发人员验证（待验证）；合约状态为启用或停用。
- Ethereum ERC-3525 合约（D5）：铸造的执行与成功、失败结果；铸造交易携带[上链字段](#onchain-fields)，合约能否无损承载完整数量、代币单位价值的小数精度与唯一到期时点、如何携带资产编号、单位价值与签名值及对交易成本的影响由开发人员确认（待开发验证）；铸造的实现、结果获取与验证由研发、测试负责。
- 平台签名私钥：由开发人员配置，平台签名铸造交易时直接调用【确认】；不可用时铸造失败，由开发人员处理后运营再次发起。
- 线下协议签署（D7）：企业与监管机构线下签署监管协议，平台只接收上传的文件。
- 消息通知（M7）：承接本模块发出的消息。
