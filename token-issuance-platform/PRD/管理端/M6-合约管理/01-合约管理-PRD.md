# 合约管理 · 功能与业务规则

2026-11-09｜管理端：运营管理人员｜需求评审稿

本模块共三册：本册写功能、业务规则、字段规则与交互逻辑；[流程图与状态机](./02-合约管理-流程图与状态机.md)画出主要流程与状态；[验收](./04-合约管理-验收.md)供测试使用。本模块的合约查看、名称编辑、启用停用和单位价值链上更新都不由本模块发送消息或邮件，所以没有 03 消息通知册，并非缺失。

依据标注：规则后的【确认】表示用户已明确，【建议·已采纳】表示诊断建议已由用户采纳，两者同样有效；未标注的是为落实上述规则所写的产品细化。本册只定义信息需求与业务行为，页面布局、组件形态与交互承载由 Hallmark 设计决定。

## 1. 模块是什么

平台用来铸造代币的链上合约，由开发人员部署并配置到平台；运营管理人员在本模块查看全部已配置合约、编辑平台名称，并选择启用或停用。M6 同时向代币发行模块提供[供新发行使用的合约资格（F-CT-02）](#F-CT-02)，并规定本平台合约必须执行的整枚转让、销毁发起地址限制和单位价值链上更新能力；发行申请、销毁申请、审核、融资、单位价值调整的办理及重试过程由对应模块定义。

基本原则：

- 新合约由开发人员部署并配置；配置后运营可以编辑名称、启用和停用【确认】。合约标准、代币符号、对应资产类型、所在网络和合约地址对运营只读。
- 当前只支持 Ethereum 网络；当前只有 ERC-3525 标准的合约，对应的资产类型是应收账款【确认】（BR-17）。
- 只有运营管理人员能看到合约管理；机构和企业都看不到【确认】（简报 4.4）。
- 运营发起铸造时必须选择一份合约【确认】（BR-14），只能从与该笔资产类型对应、所在网络为 Ethereum、状态为启用的合约中选择【确认】（A-ISSUE）。
- 本平台合约铸造的每枚代币不允许拆分或部分转让；发生链上转移时，只能把该枚代币的当前全部持有数量一次性转给一个接收地址，由合约在链上强制校验【确认】。
- 每枚代币只能由铸造时的第一个持有地址，即铸造到账地址，作为链上交易发送地址发起销毁；当前登录地址、后续受让地址、平台地址或其他地址均不能替代，由合约在销毁时强制校验【确认】。

**一个完整的例子。** 开发人员在 Ethereum 上部署并配置一份 ERC-3525 合约，名称为“合约 K”，资产类型为应收账款，初始状态停用。运营甲打开合约管理，核对完整地址，把名称改为“应收账款合约 K”，保存后启用，列表显示新名称和状态“启用”，该合约进入供新发行使用的合约范围。甲之后停用它，列表仍保留这份合约，但它退出供新发行使用的范围；已经绑定这份合约的业务及代币归属不被改写。合约执行代币转移时拒绝部分转让，执行销毁时拒绝非铸造到账地址发送的交易。

<a id="out-of-scope"></a>
### 1.2 本期不做

- 在平台上新增、删除合约，或由运营修改合约标准、代币符号、对应资产类型、所在网络、合约地址。
- <a id="Q-CT-03"></a>七项合约信息之外的详情能力：本期不增加链上参数或其他合约信息；铸造数量、代币清单等业务数据仍归代币台账。七项信息具体由列表、抽屉或独立页承载，由 Hallmark 设计决定【确认】。
- <a id="no-explorer"></a><a id="Q-CT-04"></a>从合约地址跳转区块链浏览器：本期不提供；运营可以核对并复制完整地址，自行前往外部渠道查询【确认】。
- <a id="Q-CT-06"></a>要求外部钱包或区块链浏览器显示 COU 图标：本期不做，不要求为此增加合约侧信息；M6 平台内的图标与符号降级仍按[合约的信息](#fields)执行【确认】。
- Ethereum 以外的网络、ERC-3525 以外的合约标准、应收账款以外的资产类型【确认】（BR-17）。
- 合约的部署、升级与链上参数展示。
- 在合约管理中提供代币转让、融资质押或解除质押入口；相关业务即使由其他模块或系统发起，也须遵守[完整转让限制（F-CT-05）](#F-CT-05)。
- 按合约统计铸造数量、代币数量等业务数据：代币的查看归代币台账（M4b）。
- 合约列表的搜索与筛选。
- 合约配置变化时向运营发送消息。
- 运营发起铸造时选择、提交合约，以及铸造和失败重试的办理过程：归代币发行 · 审核与铸造（M3b），本册只提供合约资格和平台状态影响。
- 在合约管理中提供单位价值调整入口或调整记录：归销毁执行、解除资产托管与代币台账（M4b），本册只规定合约须提供的[单位价值链上更新（F-CT-07）](#F-CT-07)。
- 销毁申请、平台入口资格核对、钱包连接与结果承接过程：归我的代币与销毁申请（M4a）、销毁执行、解除资产托管与代币台账（M4b），本册只规定合约必须执行的链上销毁校验。

## 2. 术语

| 术语 | 含义 |
| --- | --- |
| 合约 | 部署在 Ethereum 上、平台用来铸造和销毁代币的链上程序。一份合约对应一个合约地址；地址不同即为另一份合约 |
| 合约标准 | 合约遵循的代币标准。当前只有 ERC-3525（半同质化代币标准） |
| 对应资产类型 | 这份合约用来为哪类可信资产铸造代币。当前只有应收账款 |
| 合约状态 | 合约在平台中的使用状态：启用或停用；运营执行“启用”或“停用”操作后，状态随之变为同名状态，见[合约状态](#status) |
| 供新发行使用的合约 | 同时满足状态启用、资产类型匹配、所在网络为 Ethereum 的合约，见[供新发行使用的合约资格（F-CT-02）](#F-CT-02) |
| 完整转让 | 把一枚代币在转让发起时的当前全部持有数量，一次性转给一个接收地址；转让后原地址不再持有该枚代币，不产生拆分出的新持有份额 |
| 部分转让 | 只转出一枚代币当前持有数量的一部分，或一次转给多个接收地址，导致原地址仍有余额或形成多个持有份额；本平台合约不允许 |
| 铸造到账地址 | 一枚代币铸造时的第一个接收地址、也是第一个持有地址；随铸造记录确定，之后的登录地址和持有地址变化都不改写 |
| 销毁发起地址 | 销毁链上交易的发送地址；必须等于该代币的铸造到账地址，其他地址不能替代 |
| 单位价值 | 每个代币对应的 USD 价值；铸造时由 M3b 写入铸造初始单位价值，之后按[单位价值链上更新（F-CT-07）](#F-CT-07)更新 |

## 3. 共同规则

<a id="access"></a>
### 3.1 谁能使用

- 只有账号正常、已登录的运营管理人员能使用合约管理；每个运营账号看到的内容相同，见[菜单权限矩阵（F-LG-10）](../M5-管理端登录与权限/01-管理端登录与权限-PRD.md#F-LG-10)。
- 机构看不到合约管理，直接访问按[无权访问的处理（F-LG-12）](../M5-管理端登录与权限/01-管理端登录与权限-PRD.md#F-LG-12)拒绝【确认】。
- 企业在面客端看不到合约管理；面客端展示代币所属合约时如何展示，由我的代币与销毁申请（M4a）定义。

<a id="readonly"></a>
### 3.2 合约从哪里来

- 合约由开发人员部署并完成初始配置【确认】；初始名称和状态随配置提供，初始名称同样须符合[合约名称](#name-rules)的长度与不重名规则。
- 配置后，运营可按[编辑合约名称（F-CT-03）](#F-CT-03)和[启用与停用合约（F-CT-04）](#F-CT-04)维护；平台没有新增或删除合约的入口。
- 运营修改合约标准、代币符号、对应资产类型、所在网络或合约地址，或绕过界面新增、删除合约时，操作被拒绝，合约不变。
- 开发人员新增合约或运营维护成功后，其他运营重新打开或刷新合约管理即可看到最新结果；不发送任何消息。
- 合约一经配置就一直保留在列表中；不再使用时停用，不从平台移除，保证已用它铸造的代币仍能找到所属合约。
- 同一份合约的合约地址不会变化；需要换地址时，由开发人员配置为另一份合约。

<a id="fields"></a>
### 3.3 合约的信息

依据：展示字段【建议·已采纳】（A-CONTRACT）。

以下信息初始由开发人员配置；运营可编辑名称、调整状态，其余信息只读。

| 业务信息 | 含义 | 取值 | 展示规则 |
| --- | --- | --- | --- |
| 合约名称 | 这份合约在平台上的名称，供运营识别；其他模块展示代币所属合约时也用它 | 开发人员配置初始文本，之后运营可编辑 | 展示当前已保存的名称原文，不随界面语言翻译；编辑规则见[编辑合约名称（F-CT-03）](#F-CT-03) |
| 合约标准 | 合约遵循的代币标准 | 当前只有 ERC-3525【确认】 | 中英文界面都写作 ERC-3525 |
| <a id="symbol"></a>代币符号 | 合约登记的代币简称，用来识别这份合约铸造的代币；随合约部署确定 | 开发人员部署时设定，为 COU【确认】；平台不能修改；部署后需要更换时，由开发人员部署新合约并配置为另一份合约【确认】 | 合约列表展示设计提供的 COU 图标和原文符号；图标暂时不可用时只展示符号，不影响查看和维护；符号保留大小写，中英文界面相同，不要求不同合约的符号互不相同 |
| 对应资产类型 | 这份合约用来为哪类可信资产铸造代币 | 当前只有应收账款【确认】 | 随界面语言展示，名称与[可信资产](../../两端共用/M2-可信资产/01-可信资产-PRD.md)中的资产类型一致 |
| 所在网络 | 合约部署在哪条区块链网络 | 当前只有 Ethereum【确认】 | 中英文界面都写作 Ethereum，不译为“以太坊”，也不写作 ETH，与[钱包地址与网络名称的展示](../../面客端/M1-企业登录与企业账户/01-企业登录与企业账户-PRD.md#address-display)一致 |
| 合约地址 | 合约在 Ethereum 上的地址 | 开发人员配置的地址 | 缩写展示，保留大小写；运营可以核对完整地址，复制得到的是完整地址；缩写位数由设计确定，与[钱包地址与网络名称的展示](../../面客端/M1-企业登录与企业账户/01-企业登录与企业账户-PRD.md#address-display)一致 |
| 合约状态 | 合约在平台中的使用状态 | 启用、停用【确认】 | 随界面语言展示，含义见[合约状态](#status)；运营操作见[启用与停用合约（F-CT-04）](#F-CT-04) |

- COU 图标是合约列表中代币符号的展示资源，不作为第八项合约信息，也不提供运营编辑入口。图标资源不可用时只展示 COU，不影响查看和维护；外部钱包或区块链浏览器显示图标不在本期范围。
- 界面语言切换后，对应资产类型和合约状态随之变化；合约名称、合约标准、代币符号、所在网络和合约地址不变，见[界面语言与时区（F-LG-09）](../M5-管理端登录与权限/01-管理端登录与权限-PRD.md#F-LG-09)。

<a id="status"></a>
### 3.4 合约状态

| 合约状态 | 含义 | 是否进入供新发行使用的范围 | 既有合约归属 |
| --- | --- | --- | --- |
| 启用 | 可进入供新发行使用的合约范围 | 能，资产类型对应且所在网络为 Ethereum 时，见[供新发行使用的合约资格（F-CT-02）](#F-CT-02) | 所属合约不变 |
| 停用 | 退出供新发行使用的范围 | 不能 | 已确定的合约选择与代币所属合约不变，见[停用与既有归属](#inflight) |

- 合约状态只有“启用”和“停用”两个取值【确认】；运营可执行的操作与当前状态相反：启用的合约可停用，停用的合约可启用，见[启用与停用合约（F-CT-04）](#F-CT-04)。
- 合约初始状态由开发人员配置时设定；运营可通过启用和停用在两种状态间来回调整【确认】；不限制调整次数。
- 状态调整不改变合约的其他信息，不发送任何消息。
- 平台状态控制是否进入供新发行使用的范围，既有合约归属按[停用与既有归属](#inflight)保持【确认】。

流程参见：[合约状态机](./02-合约管理-流程图与状态机.md#state-1)。

<a id="inflight"></a>
### 3.5 停用与既有归属

- 合约停用只使其退出[供新发行使用的合约资格（F-CT-02）](#F-CT-02)，不删除合约，也不改写此前已经确定的合约选择、代币所属合约或链上事实【确认】。
- 合约平台状态不代表链上合约的实际执行能力；启用、停用不会把链上异常标记为已恢复，也不自动发起任何发行、销毁或重试。
- 已绑定合约的发行、销毁及失败重试如何继续，由 M3b、M4a、M4b 按各自状态和资格规则定义；M6 只保证平台状态变化不撤销或改写既有合约归属。
- 合约被平台停用后，所属代币仍可按[单位价值链上更新（F-CT-07）](#F-CT-07)更新单位价值【确认】。

<a id="F-CT-05"></a>
### 3.6 完整转让限制（F-CT-05）

适用对象：由本平台合约铸造、尚未销毁的每枚代币。该规则是链上合约的业务限制，不是合约管理页面的操作。

- 每次转让只能指定一个接收地址，转让数量必须等于该枚代币在转让发起时的当前全部持有数量【确认】。转让成功后，全部数量归接收地址，原地址不再保留该枚代币的任何数量。
- 只转出部分数量、转让后原地址仍保留余额、一次拆给多个接收地址，均属于部分转让；合约拒绝执行，代币的持有地址与持有数量不变【确认】。
- 任何平台或调用方都不能绕过该限制；直接调用合约发起部分转让时同样被拒绝【确认】。调用方有前置校验时可以提前阻止提交，但不能替代合约校验。
- 转给普通地址或合约地址都适用同一整枚转让限制；融资质押、解除质押、批量办理及释放条件由下游借贷业务定义，不在本册展开。
- 合约授权不改变持有地址或持有数量，不属于转让；铸造、销毁和[单位价值链上更新（F-CT-07）](#F-CT-07)也不按本节的转让处理，分别沿用原业务规则。
- 合约启用或停用只影响供新发行使用的资格，不改变该链上限制；既有代币和未来新铸造代币遵守同一规则。

流程参见：[完整转让的合约校验（图 4）](./02-合约管理-流程图与状态机.md#fig-4)。

<a id="F-CT-06"></a>
### 3.7 销毁发起地址限制（F-CT-06）

适用对象：由本平台合约铸造、尚未销毁的每枚代币。企业申请、平台入口校验、钱包提交及链上结果承接按 M4a、M4b 办理；本节只定义合约必须执行的销毁底线。

- 每枚代币的铸造到账地址在铸造时确定，是该代币唯一的销毁发起地址【确认】。代币完整转让、质押或解除质押都不转移也不改写销毁发起权。
- 铸造到账地址的钱包对销毁交易签名一次并直接广播；连接钱包、切换地址和平台资格校验均不签名，平台不进行业务预签名、交易签名或代发，也不等待运营审核。企业钱包承担 gas。
- 合约执行销毁前，必须同时核对：交易发送地址等于该代币铸造到账地址；代币完整位于该地址；质押地址为空；销毁数量为该代币完整数量；代币尚未销毁。发送地址为当前登录地址、后续受让地址、平台地址或其他地址，或任一链上条件不一致时，合约拒绝销毁，代币持有与数量不变【确认】。
- 到期、结清和下游融资结果由平台入口校验，不作为合约强制字段。绕过平台入口直接调用合约时仍受上述链上硬约束，但可能绕过链下业务准入；链上结果如何监测和承接由 M4b 定义。
- 代币转让给其他地址后，受让地址即使持有整枚代币也不能发起销毁，铸造到账地址也不能销毁当前不在该地址的代币。代币完整转回铸造到账地址后，仍只能由铸造到账地址签名发起；其他销毁资格由 M4a、M4b 判断。
- 企业无法控制铸造到账地址时不能发起销毁；本期不提供由当前登录地址、受让地址、运营或机构代签及强制销毁的替代路径。
- 合约启用或停用不改变本限制；销毁失败后的后续办理由 M4a、M4b 定义，但每笔新交易都须由铸造到账地址重新签名，合约重新执行完整校验。
- 产品要求一次钱包交易签名完成销毁。若现有合约必须先执行独立授权交易再执行销毁交易，或必须由平台地址提交，则与本期业务决策冲突；研发须在交付前验证并调整合约能力，未验证前相关链上验收标记待验，不能以两次签名作为默认产品流程。

流程参见：[销毁发起地址的合约校验（图 5）](./02-合约管理-流程图与状态机.md#fig-5)。

### 3.8 单位价值链上更新（F-CT-07）

适用对象：由本平台合约铸造的每枚代币。本节定义合约须提供的单位价值更新能力及其约束；更新的业务入口、新值校验、提交前核对、调整记录和结果展示由[调整代币单位价值（A-TOKEN-02）](../M4b-销毁审核与解除质押/01-销毁审核与解除质押-PRD.md#A-TOKEN-02)定义，M6 不提供运营操作入口。

- 更新由运营管理人员发起，平台向该代币所属合约提交链上更新【确认】。
- 以下情形都可以更新【确认】：
  - 代币在质押合约中；
  - 代币有提交锁、尚未形成销毁申请；
  - 代币处于违约期间；
  - 代币所属合约已被平台停用。
- 以下情形不可更新【确认】：
  - 代币有销毁中的申请；
  - 代币已销毁。
- 更新只改变该代币的单位价值，不改变所属合约、持有地址、持有数量、质押状态、铸造到账地址和铸造初始单位价值，也不属于转让。
- 合约平台状态只影响供新发行使用的资格，不影响本能力；更新始终提交到代币所属的原合约，不改选其他合约。
- 链上更新失败时，该代币的单位价值保持原有效值；结果承接和失败后的办理由 M4b 定义。

## 4. 合约列表（F-CT-01）

适用角色与前提：账号正常、已登录的运营管理人员。

依据：查看平台已配置的合约及展示字段（A-CONTRACT）；运营可编辑名称、启用和停用【确认】。

- 列表展示开发人员已配置的全部合约，包括停用的合约。每份合约可以看到[合约的信息](#fields)中的全部七项：合约名称、合约标准、代币符号、对应资产类型、所在网络、合约地址、合约状态。
- M6 必须让运营完整查看七项合约信息；具体在列表直接展示，还是由列表进入抽屉或独立页查看，由 Hallmark 设计决定。M6 不增加七项之外的详情能力；按合约查看已铸造代币等统计属于[本期不做](#out-of-scope)。
- 合约地址可核对和复制完整地址；本期不提供跳转区块链浏览器的入口。
- 启用的合约排在停用的合约之前；同一状态内按开发人员配置的先后从新到旧排列，每次打开顺序一致。
- 分页、返回位置、空状态与读取失败按可信资产（M2）的[业务列表通用规则](../../两端共用/M2-可信资产/01-可信资产-PRD.md#list-common)。
- 每份已配置合约提供[编辑合约名称（F-CT-03）](#F-CT-03)与[启用与停用合约（F-CT-04）](#F-CT-04)的操作；权限边界见[合约从哪里来](#readonly)。
- 平台还没有配置任何合约时，说明平台尚未配置合约、合约由开发人员配置；不提供任何操作入口，不展示示例合约。此时供新发行使用的合约范围为空，见[供新发行使用的合约资格（F-CT-02）](#F-CT-02)。
- 读取失败时说明暂时无法读取、可以重试，不显示为“尚未配置合约”。两种情况须能区分。

## 5. 编辑合约名称（F-CT-03）

适用角色与前提：账号正常、已登录的运营管理人员；合约已由开发人员配置，启用、停用两种状态下均可编辑【确认】。

- 运营选择一份合约，编辑时带出当前已保存的名称；可核对合约地址，确认修改对象。
- 保存成功后返回合约列表，展示新名称；其他运营刷新后看到同一名称。
- M6 向其他模块提供当前已保存的合约名称；名称变化不改变合约地址或既有合约归属。其他模块在何处展示名称由对应模块定义。
- 编辑名称不修改链上合约，也不改变合约状态、可选资格和列表中按配置时间确定的先后顺序。
- 只调整本合约名称的大小写或首尾空白，不算与其他合约重名，可以保存；保存时仍按[合约名称](#name-rules)处理首尾空白与字符形式。
- 两位运营同时把不同合约改为相同名称时，先保存成功的生效；后提交的按重名不能保存，原名称不变。

| 业务字段 | 含义与类型 | 必填条件与默认值 | 可编辑范围 | 校验与失败结果 |
| --- | --- | --- | --- | --- |
| <a id="name-rules"></a>合约名称 | 合约在平台上的识别名称，单行文本 | 保存时必填；初始带出当前已保存值 | 运营可编辑启用或停用合约的名称 | 保存前去除首尾空白；去除后为空、含不允许的字符、超过 60 个用户感知字符或与其他合约重名时不能保存，说明对应原因，原名称不变；详细规则见下方 |

- 名称保存前去除首尾所有 Unicode 空白字符；名称内部只允许保留普通空格，普通空格作为名称内容计入长度，不自动合并。
- 名称中不允许换行、制表符、控制字符或零宽字符；存在任一此类字符时不能保存。【建议·已采纳】
- 名称最多 60 个用户感知字符【确认】；组合字符或完整 emoji 按用户看到的一个字符计为一个，不能按字节、编码单元或组成码点分别累计。【建议·已采纳】
- 名称不能与其他合约的名称相同【确认】，比较范围包括停用的合约；比较时先去除首尾空白，把 Unicode 规范等价的字符形式视为相同，再忽略大小写。仅改变同一份合约自身名称的大小写或首尾空白不受重名限制。【建议·已采纳】

名称与状态维护共用以下规则，状态维护引用本处：

<a id="maintenance-results"></a>
### 5.1 维护中的取消、失败与冲突

- 取消或放弃未提交的操作，返回合约列表，原有信息和状态不变。
- 平台已明确返回维护失败时，说明本次未完成，原有信息和状态不变，运营可重试；不能把未保存内容显示为已生效。
- 提交后未取得明确成功或失败结果时，说明结果待核对；在核对完成前，不把拟修改值显示为已生效，也不推定原值未变化。【建议·已采纳】
- 结果待核对时，平台重新读取该合约对应维护项的最新已保存值：最新值等于本次目标值时确认成功；最新值不等于本次目标值时展示最新值，运营重新核对后再操作。【建议·已采纳】
- 暂时无法读取最新值时保持结果待核对，同一合约的同一维护项暂不允许重复提交；其他合约以及同一合约的另一维护项仍可办理。读取恢复后按最新已保存值解除待核对状态。【建议·已采纳】
- 提交期间不重复办理同一次维护；重复提交不得造成额外变化。
- 另一位运营已修改同一项信息时，本次提交不覆盖其结果，展示最新值，运营重新核对后可再次操作；名称和状态分别维护，编辑名称不覆盖状态变化，调整状态不覆盖名称变化。
- 提交时已无权操作，按[无权访问的处理（F-LG-12）](../M5-管理端登录与权限/01-管理端登录与权限-PRD.md#F-LG-12)拒绝，数据不变。
- 名称编辑与启用停用均不发送消息或邮件。

## 6. 启用与停用合约（F-CT-04）

适用角色与前提：账号正常、已登录的运营管理人员；合约已由开发人员配置【确认】。

| 当前状态 | 运营可执行的操作 | 成功后的状态与结果 |
| --- | --- | --- |
| 启用 | 停用 | 状态变为停用，保留在列表中并按停用合约排序；退出供新发行使用的合约范围 |
| 停用 | 启用 | 状态变为启用，按启用合约排序；资产类型对应且所在网络为 Ethereum 时，进入供新发行使用的合约范围 |

- 发起操作时展示目标合约的当前名称、可核对的完整地址、当前状态和将变为的状态，并说明对供新发行使用资格的影响，由运营确认后提交。
- 启用或停用成功后回到合约列表，显示新状态；其他运营刷新后看到最新状态。
- 已处于目标状态时保持该状态，说明当前状态，不再执行一次状态转换。
- 启用或停用只改变平台使用状态，合约名称、标准、代币符号、对应资产类型、网络、地址和配置时间不变。
- 启用或停用不自动发起发行、销毁或重试；既有合约归属按[停用与既有归属](#inflight)处理。
- 链上部署等异常造成的合约无法执行仍需开发人员处理，平台启用不代表链上异常已经恢复。
- 取消、失败、重复提交、冲突及权限变化按[维护中的取消、失败与冲突](#maintenance-results)处理。

流程参见：[维护合约名称与状态（图 3）](./02-合约管理-流程图与状态机.md#fig-3)、[合约状态机](./02-合约管理-流程图与状态机.md#state-1)。

## 7. 供新发行使用的合约资格（F-CT-02）

本节只定义 M6 向代币发行 · 审核与铸造（M3b）提供的合约资格；选择界面、默认值、提交核对、无合约时的办理结果及铸造重试全部由 M3b 定义。

- 可选范围是同时满足以下三项的全部合约：
  - 合约状态为启用；
  - 对应资产类型与这笔发行申请所关联资产的资产类型相同；
  - 所在网络为 Ethereum（本期只有这一种取值）。
- 停用、对应资产类型不同或所在网络不是 Ethereum 的合约，不进入供新发行使用的合约范围。

| 合约状态 | 对应资产类型与申请资产相同 | 所在网络为 Ethereum | 是否进入供新发行使用的范围 |
| --- | --- | --- | --- |
| 启用 | 是 | 是 | 能 |
| 启用 | 是 | 否 | 不能 |
| 启用 | 否 | 是或否 | 不能 |
| 停用 | 是或否 | 是或否 | 不能 |

- 运营成功启用或停用合约后，该合约按最新状态进入或退出此范围；平台未配置合约或没有合格合约时，M6 提供的范围为空。
- 已经被业务选定的合约不因后续退出此范围而改写，见[停用与既有归属](#inflight)。

<a id="dependencies"></a>
## 9. 依赖

- 开发人员：部署合约并完成初始配置，提供合约名称、合约标准、代币符号、对应资产类型、所在网络、合约地址和初始状态【确认】；合约须执行[完整转让限制（F-CT-05）](#F-CT-05)与[销毁发起地址限制（F-CT-06）](#F-CT-06)【确认】，并验证企业钱包一次交易签名即可直接提交销毁。链上部署等异常由开发人员处理。
- 单位价值链上更新：合约须提供[单位价值链上更新（F-CT-07）](#F-CT-07)，代币位于质押合约中时平台也能在链上更新其单位价值【确认】；违约期间和所属合约被平台停用后同样由平台提交更新。
- 设计资源：合约列表使用 COU 图标；图标资源暂时不可用时只展示代币符号，不阻断查看、改名或启停。
- Ethereum 链（D5）：合约的铸造与销毁在链上执行。标准、代币符号、网络、地址须与链上部署一致；平台名称与使用状态按本册维护，由研发实现，测试验证。
