**评估范围。** 本模块是企业以一笔可信资产申请铸造代币的地方：选资产、选监管机构、选接收账户、确认、用登录地址签名后提交，再跟踪审核与铸造结果。规则确定，不含模型生成内容，所以本 Eval 回答的问题是：**本模块交付后的产品表现，是否达到 PRD 的成功标准**，不评模型能力。具体包括五点：

- 只有本企业能看到、能操作本企业的申请、签名记录与监管协议；
- 只有满足全部条件的提交才产生申请，且一笔资产、一次提交只产生一笔申请；
- 业务签名是否只由登录地址对确认过的四项上链字段签出，记录不可改，并与铸造上链的值一致；
- 企业看到的申请状态、审核进度、驳回意见、协议、铸造结果和 NT-R01 是否按规则出现；
- 用户在每一步和每种异常下能否看懂并走得下去。

与 04 册的分工：04 册是逐条验收标准，测试用例与执行步骤由测试小队编写。本 Eval 在 04 册之上做三件事：

1. 按风险把验收归入维度，并划出阻断项；
2. 规定 case 的组织方式与通过线；
3. 规定标注、跑评节奏、失败回流与版本管理。

本 Eval 不替代测试用例。

**不在范围内：**

- M3b 的监管一审、运营二审、合约选择、铸造执行与重试：只核对它们推动后企业侧看到的结果，以及签名值是否随铸造上链；
- M2 发起条件本身的判定（回款状态归并、到期兜底等）：本 Eval 只核对提交路径是否按 M2 的结果放行或拦截，判定本身见 [M2 Eval](../../两端共用/M2-可信资产/可信资产-Eval.md)；
- M1 的身份判定、认证调取时点、数币账户的登记与引用：本模块直接使用 M1 的结果，见 [M1 Eval](../M1-企业登录与企业账户/企业登录与企业账户-Eval.md)；本 Eval 只核对提交前的认证复核与接收账户选用；
- M7 的消息展示、已读与前往：只核对 NT-R01 的触发、收件范围与内容；
- 视觉与布局，由 Hallmark 设计负责。

**判定方式用语：**

- **code-based**：自动化断言，包括接口响应、页面状态、数据库记录、链上数据读取、响应体敏感字段扫描、文案字符串比对；
- **human**：人工按二元 rubric 判定；涉及真实钱包的操作由测试人员执行，结果仍按断言判定；
- **LLM-as-judge**：本模块不用于任何阻断判定，只在第 4 节写明的条件下，作为文案批量初筛的辅助。

### D1 访问范围与数据隔离

| 项 | 内容 |
| --- | --- |
| 定义 | 每类身份只看到、只能做 PRD 允许的事；企业只能查看本企业的申请、签名记录和监管协议。拒绝由平台判定，不靠隐藏入口；拒绝说明不透露申请是否存在 |
| 需求来源 | 01 册第 3 节谁能使用、3.1 入口（消息前往按当前身份重新判断）、C-ISSUE-07（协议只对本企业、一审通过后开放）；02 册图 3。对应验收 AC-M3A-01、02、03、27、32，以及 AC-M3A-30 中“直接访问取不到协议”的部分 |
| 通过条件 | 按身份分：<br>• 未登录、游客：看不到代币发行，直接访问列表、详情、协议、提交接口都被拒绝，响应不含申请数据；<br>• 未认证企业用户：看得到入口，只看到认证引导，接口不返回申请数据，不能发起或提交；<br>• 已认证企业用户：只看到本企业全部申请；上游登录地址变更后用新地址登录，原有申请、进度、协议、签名记录都在。<br>另外：访问其他企业的申请、协议文件与访问不存在的申请，说明完全相同（无权查看或申请不存在）；从消息前往时按当前身份重新判断 |
| 失败条件 | 任一情况即失败：<br>• 被拒绝的请求返回了任何申请字段，包括条数、申请编号、资产编号、金额、签名值；<br>• 只隐藏了入口，直接 URL 或接口能拿到数据；<br>• “无权”与“不存在”的说明、状态码或响应结构可区分；<br>• 构造企业参数拿到他企业的申请；<br>• 换登录地址后申请丢失或被拆分；<br>• 失去认证后从消息前往仍看到申请数据 |
| 失败后果 | 他企业的资产、申请与签名信息泄露；属于合规与安全事故 |
| 判定方式 | code-based：按“身份 × 资源 × 访问方式（入口 / 直接 URL / 接口）”做矩阵断言，对响应体做字段扫描；“无权”与“不存在”的响应逐字节比对（时间戳等非业务字段除外）。阻断项由安全角色复核 |

### D2 提交把关与申请唯一性

| 项 | 内容 |
| --- | --- |
| 定义 | 可选范围只含可发起的资产、启用的监管机构和本企业已登记的账户，三项都单选；提交时按最新信息再核对认证、资产发起条件、机构仍启用、账户仍存在，任一项不满足或无法确认就不产生申请；一笔资产最多一笔申请，一次提交最多一笔申请；提交后不能撤回、修改、重新提交，被驳回的资产不能再次发起 |
| 需求来源 | 01 册第 1 节基本原则（BR-08、BR-12）、第 4 节三步规则、C-ISSUE-01～03 可选范围、4.4 提交时的再次核对、提交成功后、提交不成功的情况；02 册图 1。对应验收 AC-M3A-04、06、07、09（可选范围部分）、10 场景一、13、14、15、16、17，AC-M3A-08 场景一，AC-M3A-22 中“不能再次发起”的部分 |
| 通过条件 | 以下全部满足：<br>① 可选资产只含本企业满足 M2 发起条件的资产；从可信资产发起时已选中，从代币发行发起时不预选；带入的资产已不满足条件时不选中并说明原因；<br>② 监管机构只列启用的机构，接收账户列本企业全部已登记账户，两项都不预选、都单选，都选定才能进入确认；<br>③ 提交时重新调取认证结论，旧结果不放行；上游调取失败、超时或不可用时不放行；<br>④ 提交时重新判断资产发起条件，机构仍启用、账户仍存在；任一项不满足不产生申请，资产保持可发行，未受影响的选择保留；<br>⑤ 重复点击、刷新、网络重发、并发会话只产生一笔申请；<br>⑥ 离开、取消或登录结束不保存任何内容；<br>⑦ 没有撤回、修改、重新提交的操作，绕过界面同样被拒绝；被驳回资产再次发起被拒绝 |
| 失败条件 | 任一情况即失败：<br>• 未认证、认证调取失败或不满足发起条件时提交成功，包括绕过界面直接调用提交接口；<br>• 同一笔资产产生第二笔申请；同一次提交产生多笔申请；<br>• 用已停用的机构或已删除的账户提交成功；<br>• 不可发起的资产、停用的机构出现在可选范围中；<br>• 提交失败后资产不再是可发行，或已选内容被清空；<br>• 已提交的申请被撤回、修改，或被驳回资产再次提交成功 |
| 失败后果 | 不合格资产或失去资格的企业发行代币、一笔资产重复融资，或代币铸造到已不受企业维护的地址；属于不可逆的资产与合规风险 |
| 判定方式 | code-based：上游 mock 与 M5 / M1 数据注入，在“进入确认后、提交前”改变认证、资产、机构、账户状态的时序断言；并发提交与请求重放脚本；接口直连断言；数据库计数断言 |

### D3 业务签名与申请记录完整性

| 项 | 内容 |
| --- | --- |
| 定义 | 每笔申请由登录地址在 Ethereum 上签名一次，签名内容恰为资产编号、资产价值、到期日、接收地址四项，取值与确认环节一致；平台核对签名有效、来自登录地址、内容与本次提交一致才提交；申请记录与签名记录提交后不可改；铸造成功时签名值与四项字段随铸造上链，被驳回的申请不上链；代币数量按资产价值 1:1，单位为合约代币符号 |
| 需求来源 | 01 册第 1 节基本原则、4.4 确认环节展示与说明、提交时的业务签名、提交成功后（申请记录、登录地址顺延）、5.3 业务签名记录、铸造结果、第 6 节数据来源与归属；M3b [上链字段](../../../PRD/管理端/M3b-代币发行-审核与铸造/01-代币发行-审核与铸造-PRD.md#onchain-fields)。对应验收 AC-M3A-12、29、37、38、40，AC-M3A-11 的只读部分，AC-M3A-17 中“改备注名不改接收地址”的部分，AC-M3A-23 中“接收地址、数量、到期日与申请一致”的部分 |
| 通过条件 | 以下全部满足：<br>① 签名内容只有四项，不含监管机构名称、币种、签名时间或其他申请的信息；四项取值与确认环节展示一致；<br>② 只接受登录地址的签名；钱包为其他地址或非 Ethereum 网络时不能提交；取消签名不提交；<br>③ 签名无效、签名地址不是登录地址、内容与本次提交不一致时，平台拒绝；<br>④ 提交不成功后再次提交须重新签名；<br>⑤ 签名记录（签名地址、签名时间、签名值）任何状态可查看、不可修改；登录地址变更后签名地址不变；<br>⑥ 申请记录的资产、资产价值、到期日、接收地址提交后不变；改备注名或登录地址顺延都不改变接收地址；<br>⑦ 铸造成功：链上签名值等于签名记录，链上四项与签名内容一致，可由链上数据验证出签名地址；被驳回的申请没有任何链上交易；<br>⑧ 代币数量等于资产价值（两位小数），单位为合约代币符号，不以 USD 为单位；申请阶段不展示预计发行数量 |
| 失败条件 | 任一情况即失败：<br>• 未签名、非登录地址签名、无效签名或内容被篡改的签名使提交成功；<br>• 签名内容多出或缺少字段，或取值与确认环节不同；<br>• 签名记录、申请记录可被修改，或随备注名、登录地址变化；<br>• 链上签名值或字段与记录不一致；被驳回申请的签名上链；<br>• 代币数量与资产价值不等，或单位写成 USD；申请阶段出现预计发行数量 |
| 失败后果 | 企业未认可的业务信息被铸造上链、代币铸造到错误地址或数量错误；链上签名无法证明企业意思表示；属于不可逆的资产与合规风险 |
| 判定方式 | code-based 为主：签名构造与篡改脚本（错地址、错内容、无效格式、旧签名）、记录写接口拒绝断言、数据库字段比对；链上读取比对放在“真实联调”切片（测试链）。真实钱包的签名交互由测试人员执行，钱包中显示的签名内容由测试人员截图留证 |

| 失败条件 | 任一情况即失败：<br>• 列表遗漏申请，或“查看”进入别的申请；<br>• 企业端出现“铸造失败”、重试节点、失败原因、运营账号或一审监管意见；<br>• 驳回意见被截断、翻译或张冠李戴；<br>• 一审通过前可见协议，或一审通过后不可见；<br>• 铸造结果在成功前出现，或接收地址、数量、到期日与申请记录不一致；<br>• 资产变化使申请被自动终止或状态改变；<br>• NT-R01 发给其他机构、运营或企业，重复发送，提交失败时发送，或含钱包地址 |
| 失败后果 | 企业误判申请进度或结果（如把发行处理中误认为失败而重复咨询），监管机构漏审或收到不存在的待审任务；地址等信息越过收件范围；影响业务进程与信息安全 |
| 判定方式 | code-based：M3b 测试桩推动全部状态与失败子情形，断言列表、详情、进度节点与响应字段；消息表按“收件人 × 申请编号”计数与内容比对。驳回意见长文本可读性与状态说明由 human 按第 4 节 rubric 判定 |

### D5 异常可理解性与信息呈现

| 项 | 内容 |

## 3. 通过线

本模块是确定性规则，同一输入的结果固定，所以规则类维度的通过线贴近 100%，并不是照搬 99% 一类的经验值。另外两点：缺陷修复成本低，而一旦失败可能让不合格资产发行代币、代币铸造到错误地址、企业未认可的信息上链，且不可逆。

下表数值除已标注“PRD 确定”或“业务方确认”的以外，都是**建议、待业务与测试确认**。

**单例判定。** 一条 case 只有在两个条件同时满足时才算通过：

- “预期行为”全部满足；
- “禁止行为”一项都没有出现。

一条验收写了多个场景时，拆成的每条原子 case 都通过，才算该验收通过。这与 04 册的读法一致。

**指标口径：**

- 维度通过率 = 本轮该维度判定为通过的 case 数 ÷ 本轮该维度有效执行的 case 数。
- **排除规则**：因环境故障而无法判定的 case 标为“无效”，比如上游 mock 宕机、M3b 测试桩不可用、测试链拥堵导致读不到交易、测试钱包不可用（不是 case 有意模拟的不可用）。无效 case 不计入分母，必须重跑。一轮中无效 case 超过 5%（建议值）时，整轮作废。
- **不能排除的情况**：产品行为错误不得标为无效，比如上游不可用时放行了提交。
- **切片**：每个维度分两个切片单独统计，不合并。“模拟环境”切片用上游 mock、时间 mock、M3b 测试桩与签名构造脚本；“真实联调”切片接上游平台测试环境、真实钱包与测试链上的真实铸造。

**随机性控制：**

- 依赖真实时序的 case，如并发提交、请求重放、提交前状态变化、真实钱包签名、测试链读取，每轮重复执行 3 次。P0 case 须 3 次全部通过，任何一次失败都按失败处理，直到查明原因。
- 认证调取时点与登录到期类 case 一律用时间 mock 固定“当前时点”，不依赖执行时的真实时间。
- 不稳定的 case，只有在证明是环境问题后才能标为无效。

**统计与不确定性：**

- 规则类 case 不计算置信区间，逐条看是否失败。
- 小样本零失败不等于低风险。例如某个切片 50 条 0 失败，按 Wilson 方法计算的 95% 区间上界约为 7%，这是公式算出的说明值，不是评测结果。所以阻断项靠“每条 case 0 失败 + 绕过界面的变体 + 时序矩阵”来覆盖，不靠通过率。
- D5 人工评分与 L3 线上比例指标，用 Wilson 区间报告。
- 版本比较用同一版本的 case 集做逐条配对，只看有没有回归，不报告“提升”。
- 本文没有任何执行数据，不填写任何分数或区间。

**失败兜底**（PRD 已确定，Eval 核对兜底是否存在）：

- 提交前再次核对认证、资产条件、机构、账户，任一项不满足或无法确认都不产生申请；
- 签名核对不通过不提交，再次提交须重新签名；
- 重复提交只产生一笔申请；
- 提交前离开、取消或登录结束不保存，资产保持可发行；
- 各类读取失败可以重试，不说成“没有”；
- 上游暂时不可用不影响查看已提交的申请；
- 协议打开失败可以重试，不影响其他信息；
- 消息发送失败不撤销申请。

每条兜底至少对应 1 条 case。发布后如果出现阻断项，按第 5 节回流：先止血，再补 case。止血手段（例如暂停“代币发行”的新申请入口，保留查看）**待业务确认**。

## 4. 标注方法

本模块大部分 case 由自动化断言判定。人工标注主要用在四处：

- 定义预期结果，把 PRD 转成可断言的期望，尤其是 5.1 状态映射表、签名内容四项的取值与提交时序矩阵的期望；
- 真实钱包签名交互，由测试人员执行并对钱包中显示的签名内容截图留证；
- D5 呈现类判定，以及驳回意见长文本、确认环节后果说明的完整性；
- 阻断项复核。

**角色：**

| 角色 | 职责 |
| --- | --- |
| 产品（PRD 负责人） | rubric 与预期结果的最终解释人；PRD 有歧义时负责仲裁，必要时回到 PRD 流程修订。本 Eval 不改 PRD |
| 测试负责人 | 把验收拆成 case，标注 P0 / P1 / P2，维护 AC↔case 映射与时序矩阵，执行判定 |
| 安全复核 | 复核 B1、B5、B6、B8 相关的 case 与结果，以及签名构造与重放脚本的覆盖面 |
| 业务复核（运营代表） | 复核 B2～B4、B7 相关 case 的期望值，确认提交把关与驳回终止的判定符合审核实际 |
| 研发（链与钱包） | 定义签名格式并提供签名构造工具；提供上游 mock、时间 mock、M3b 测试桩、测试链读取脚本；标注“无效”case 的环境原因 |
| 中英文审校 | D5 文案判定，包括确认环节说明、各类失败说明、状态值、NT-R01 |

**分阶段：**

- **启动**：产品与测试负责人对 64 条启动 case 逐条共同标注预期行为与禁止行为；5.1 状态映射表的七行期望与签名四项的取值由产品逐项签认。D5 的 8 条 case 由产品与审校各自独立按 rubric 判定，分歧交产品负责人仲裁，仲裁理由写入 case 备注。
- **扩展**：新增 case 由测试负责人起草。产品抽查新增 case 的 20%（建议值），阻断项相关的 case 全部复核。
- **持续**：每次 release 后，D5 人工判定结果抽 10%（建议值）由第二人复判；复判不一致时，修 rubric 或补正反锚点。

**D5 二元 rubric**（每条判是或否，全部为“是”才通过）：

| 条目 | 级别 | 判定问题 | 正例锚点 | 反例锚点 |
| --- | --- | --- | --- | --- |
| R1 可区分 | P1 | 读取失败、确实没有可发起资产、没有启用机构、没有任何申请，用户能否分辨？ | 账户读取失败显示“暂时无法获取数币账户，可以重试” | 账户读取失败显示“您还没有数币账户” |
| R2 不泄露 | P0 | 拒绝说明是否不透露申请或协议是否存在，且不出现他企业的任何信息？ | 访问他企业申请与不存在的编号，都显示“无权查看或申请不存在” | 显示“该申请属于其他企业”；显示“申请已被驳回，无权查看” |
| R3 有出路 | P1 | 每种失败是否给出了可以继续的操作（重试、重新选择、切换地址或网络、重新签名、前往可信资产、进入已有申请）？ | 机构已停用：说明该机构当前不可选择，并回到选择机构 | 只显示“提交失败” |
| R4 后果说清 | P1 | 确认环节是否在提交前说明了五项：数量以铸造结果为准且按 1:1、不能撤回或修改、任一级驳回即终止且资产不能再发起、代币进入所选地址、需线下签署协议且提交前须签名？ | 五项同屏可见，看到后才可提交 | 只写“请确认信息”；“驳回即终止”藏在折叠内容里且可直接提交 |
| R5 双语与原文 | P1 | 字段名、状态值、说明随语言切换；驳回意见、编号、金额保持原文？ | 英文界面状态为 Pending regulator review，驳回意见仍为中文原文 | 英文界面状态仍为“待监管审核”；驳回意见被机器翻译 |
| R6 长值呈现 | P1 | 地址与签名值缩写展示、保留大小写，可核对并复制完整值？ | 签名值缩写展示，复制得到完整签名 | 签名值完整铺开无法阅读；复制得到缩写 |

R4 中五项说明的排布与交互形态由设计确定，本 rubric 只判是否在提交前全部可见；R6 中缩写位数由设计确定，本 rubric 只判是否缩写、能否取得完整值。

**人机对齐（LLM-as-judge）。** 启动阶段不使用 LLM-as-judge。之后如果 D5 画面数量（中英文 × 三步与确认 × 十余种失败说明 × 七种状态）超出人工承受范围，可以引入 LLM 只做 R1、R3、R5 的批量初筛，条件如下：

- 先用人工已判定的 case 建立校准集，校准集与日常评测集隔离，不用于调提示词以外的任何用途；
- 在校准集上，LLM 与人工判定的一致率达到约定门槛（**建议 95% 以上，待确认**），才能启用；
- 启用后，LLM 判为不通过的 case 一律转人工；LLM 判为通过的 case，人工抽 10% 复核；
- LLM 不参与任何阻断项的判定，也不参与 R2、R4。

目前没有任何样本，所以**不声称 judge 已可靠**。

关于 L3 指标：

- 比例指标按 Wilson 区间报告；
- 告警阈值与观察周期**待业务确认**；

- L3 用真实流量统计，与第 2 节加重后的风险覆盖集分开解读。

**失败回流。** 来源有五类：线上工单、L3 异常与一致性告警、运营或监管机构在审核中发现的申请信息问题、安全告警、外部变化探索中发现的问题。处理流程：

1. 测试在约定时限内（**建议 3 个工作日，待确认**）脱敏并复现，确认属于 M3a 行为问题，而不是 M1、M2、M3b 或上游的问题；属于其他模块的，转交对应模块的 Eval 负责人；
2. 写成 case，放入“历史失败”类别，标注“真实”及来源编号，与合成 case 区分；
3. 涉及 B 类的问题，同时补一条绕过界面的变体；涉及提交时序的，同时补进时序矩阵；
4. 确认是 PRD 规则缺口而不是实现缺陷时，交 PRD 负责人处理；本 Eval 不改 PRD。
