PRD 更新后，本 Eval 按第 5 节的“版本管理”同步。

**评估范围。** 本模块是规则确定的钱包登录与账户功能，不含模型生成内容。所以本 Eval 回答的问题是：**本模块交付后的产品表现，是否达到 PRD 的成功标准**，不评模型能力。具体包括四点：

- 身份判定对不对；
- 越权和泄露是否被挡住；
- 账户数据是否可信；
- 用户在异常时能否看懂并走得下去。

与 04 册的分工：04 册是逐条验收标准，测试用例与执行步骤由测试小队编写。本 Eval 在 04 册之上做三件事：

1. 按风险把验收归入维度，并划出阻断项；
2. 规定 case 的组织方式与通过线；
3. 规定标注、跑评节奏、失败回流与版本管理。

本 Eval 不替代测试用例。

**不在范围内：**

- M3a / M4a 的业务签名环节、M7 的消息展示：只核对本模块交给它们的结果；
- 视觉与布局，由 Hallmark 设计负责；
- 资产可信平台自身的正确性。

**判定方式用语：**

- **code-based**：自动化断言，包括接口响应、页面状态、数据库/日志扫描、文案字符串比对；
- **human**：人工按二元 rubric 判定；
- **LLM-as-judge**：本模块不用于任何阻断判定，只在第 4 节写明的条件下，作为文案批量初筛的辅助。

### D1 登录与身份判定正确性

| 项 | 内容 |
| --- | --- |
| 定义 | 只有经过“连接钱包 → 登录签名 → 验签”这一路径才能登录；登录后按地址调取上游，判定为企业用户（已认证 / 未认证）、游客或登录不成立，判定结果与 01 册调取结果表逐行一致 |
| 需求来源 | 01 册 C-AUTH-01、登录签名规则、C-AUTH-02；识别同一个用户与企业；02 册图 1、登录状态机。对应验收 AC-M1-01～09、31、32 |
| 通过条件 | 以下全部满足：<br>① 签名一次有效、5 分钟有效期、签名地址与连接地址一致、仅 Ethereum，这些由平台校验，绕过界面也成立；<br>② 地址的大小写、带或不带 0x 前缀，都匹配到同一账户；<br>③ 以下六类调取结果，各自得到 PRD 规定的身份：调取到唯一账户、调取不到、账户锁定或禁用、调取失败、一个地址对应多个账户、建立企业用户失败；<br>④ 同一上游账户换地址登录后，按稳定标识复用，是同一个企业用户 |
| 失败条件 | 任一情况即失败：<br>• 重放签名或过期签名建立了登录；<br>• 他人地址的签名建立了登录；<br>• 调取失败、超时被判为游客；<br>• 一个地址对应多个账户时，取了其中一个账户；<br>• 客户端伪造的上游数据被采信；<br>• 按企业名称、邮箱等做了近似匹配；<br>• 换地址后产生了新用户、拆分了历史 |
| 失败后果 | 冒用登录、错误放行业务，或正常企业被拒之门外；属于资产与合规风险 |
| 判定方式 | code-based 为主：接口与 E2E 断言、上游 mock 注入、签名重放脚本。真实钱包交互（包括硬件钱包延迟确认）由测试人员执行，结果仍按断言判定 |

### D2 权限边界与数据隔离

| 项 | 内容 |
| --- | --- |
| 定义 | 每类身份只看到、只能做 PRD 允许的事。拒绝由平台判定，不靠隐藏入口；不残留、不泄露其他地址或其他企业的数据 |
| 需求来源 | 01 册 C-AUTH-04、C-GUEST-01、C-PROFILE-01 展示规则（只读、只本人可见、不残留）、6.1“谁能使用”、第 7 节数据来源与归属。对应验收 AC-M1-10、14、15、17、33，以及 AC-M1-19 中“绕过界面编辑或删除被拒绝”的部分 |
| 通过条件 | 按身份分：<br>• 未登录、游客：直接访问 8 类功能都被拒绝，且响应中不含业务数据。8 类功能为用户信息、企业信息、企业账户、可信资产、代币发行、我的代币、销毁申请、消息通知；<br>• 未认证企业用户：可用用户信息、企业信息和消息；业务功能被拦下并给出认证引导；<br>• 已认证企业用户：只看到本企业数据。<br>另外，资料修改请求一律被拒绝；退出后换地址登录，不残留上一个地址的任何资料 |
| 失败条件 | 任一情况即失败：<br>• 任一被拒绝的请求返回了业务字段，包括列表条数、地址或名称；<br>• 只隐藏了入口，直接访问能拿到数据；<br>• 看到其他企业的数币账户或资料；<br>• 绕过界面改资料成功；<br>• 游客从上游返回后未重新登录就变成企业用户 |
| 失败后果 | 数据泄露、越权操作；属于合规与安全事故 |
| 判定方式 | code-based：按“身份 × 功能 × 访问方式（入口 / 直接 URL / 接口）”做矩阵断言，对响应体做敏感字段扫描。阻断项由安全角色复核 |

### D3 会话生命周期与上游同步

| 项 | 内容 |
| --- | --- |
| 定义 | 以下几件事按 PRD 发生，时点正确，且只发生一次：<br>• 登录有效期；<br>• 退出；<br>• 登录后钱包切换地址；<br>• 原目标返回；<br>• 调取时点；<br>• 上游变化，包括认证变化、锁定禁用、资料变化、登录地址变更；<br>• 认证失效通知 |
| 需求来源 | 01 册 C-AUTH-03、C-AUTH-05、C-AUTH-06；03 册 NT-C09；02 册图 2、图 5、登录状态机。对应验收 AC-M1-11、12、30、35～39、41 |
| 通过条件 | 以下全部满足：<br>① 企业用户 7 天、游客 4 小时，按绝对时长到期，不因操作延长；<br>② 登录后钱包切换地址：不提示、不结束登录，身份仍按登录地址；<br>③ 原目标 30 分钟内有效、只能成功使用一次，登录后重新判权；<br>④ 超过 60 秒后的下一次请求、以及关键业务动作提交前，都重新调取；<br>⑤ 认证失效后不结束登录、停止业务，NT-C09 每次失效只发一条；<br>⑥ 发现登录地址变更或锁定禁用后，结束登录；<br>⑦ 上游不可用时身份不变，但关键动作不放行 |
| 失败条件 | 任一情况即失败：<br>• 有效期被延长或提前结束；<br>• 关键动作用旧调取结果放行；<br>• 地址变更后旧登录还能查看受保护内容；<br>• NT-C09 重复发送、漏发，或在调取失败时误发；<br>• 原目标被跨会话使用，或使用两次；<br>• 登录后切换钱包地址就结束了登录 |
| 失败后果 | 已失去资格的企业继续办理业务（合规风险），或正常用户被频繁打断 |
| 判定方式 | code-based：用时间 mock 推进 60 秒、5 分钟、30 分钟、4 小时、7 天；断言上游调取次数与时点、消息表计数。另设“真实联调”切片（见第 3 节），04 册已说明模拟环境不能替代真实联调 |

### D4 数币账户完整性

| 项 | 内容 |
| --- | --- |
| 定义 | 数币账户列表中的每个地址都经签名证明归本企业控制，且不重复；登录地址按规则自动列入和顺延；被引用的账户删不掉；发行申请只能选用有效账户 |
| 需求来源 | 01 册 6.1 共同规则、C-ACCOUNT-01～05；02 册图 3、图 4、数币账户状态机。对应验收 AC-M1-19～29、44、45 |
| 通过条件 | 以下全部满足：<br>① 只有地址归属签名通过才产生账户，签名地址必须等于要登记的地址；<br>② 格式校验、去重（不区分大小写，含登录地址）、备注名 1～100 字符，三者都在签名前拦截；<br>③ 引用的判定与 PRD 一致：有代币铸造到（含已销毁）、处理中的申请选用；被驳回申请不算引用；<br>④ 确认删除时再判一次引用；<br>⑤ 登录地址变更后，原地址顺延为普通账户、新地址复用或新增，每个地址只列一条，创建时间与引用关系保留；<br>⑥ 发行申请不预选账户，只能选已登记账户，提交时复核账户仍存在 |
| 失败条件 | 任一情况即失败：<br>• 未签名、签名失败、或用别的地址签名，却产生了账户；<br>• 同一地址出现两条；<br>• 被引用的账户被删除；<br>• 登录地址变更后丢失账户，或重复新增；<br>• 已提交申请或已铸造代币的地址被改动；<br>• 已删除的账户仍能被选用、仍能提交；<br>• 保存失败后留下半条账户 |
| 失败后果 | 代币铸造到不受企业控制的地址，或引用关系断裂；属于不可逆的资产损失 |
| 判定方式 | code-based：断言状态机迁移、数据库记录，并构造并发场景（删除确认与提交申请并发）。地址归属签名的真实钱包交互由测试人员执行 |

### D5 异常可理解性与信息呈现

| 项 | 内容 |
| --- | --- |
| 定义 | 用户在每种状态和异常下都能看懂当前情况，并有下一步出路；不泄露内部原因或上游登记情况；地址、网络名、语言与时区按共用规则呈现 |
| 需求来源 | 01 册钱包地址与网络名称的展示、各功能的异常表、C-PROFILE-01 三种企业状态的说明、C-PROFILE-02、前往资产可信平台确认；03 册 NT-C09 标题与正文。对应验收 AC-M1-13、16、18、34、40、42、43 |
| 通过条件 | 满足第 4 节 rubric R1～R6 全部条目，并且：<br>• NT-C09 的中英文标题、正文与 03 册逐字一致；<br>• Ethereum 在中英文界面都不翻译；<br>• 页面上的地址一律缩写并保留大小写，复制得到完整地址 |
| 失败条件 | 任一情况即失败：<br>• 读取失败显示成空资料或“没有账户”；<br>• 三种企业状态用同一句说明；<br>• 提示中暴露“该地址未在上游登记”或内部判定原因；<br>• 只靠钱包自身提示说明签名用途；<br>• 切换语言后已填写内容丢失；<br>• 时区改变了事件先后顺序 |
| 失败后果 | 用户误判自身状态（如把读取失败当作没有资格），咨询量上升；泄露地址登记情况 |
| 判定方式 | 分三种：<br>• code-based：文案字符串比对、地址格式正则、时区换算断言；<br>• human：说明是否可区分、是否有出路，由产品与中英文审校按 rubric 判定；<br>• LLM-as-judge：启动阶段不用 |

## 2. Case 数量与覆盖

**规模。** 以下数量都是计划数，不是已完成的用例。

| 阶段 | 规模 | 依据 |
| --- | --- | --- |
| 启动集 | 52 条原子 case：D1 11、D2 11、D3 10、D4 12、D5 8 | 04 册共 45 条验收，其中不少一条含多个场景。启动集先把 B1～B8 与每个功能的主路径拆成原子 case，保证每条验收至少被 1 条 case 覆盖 |

| 历史失败 | 0（预留） | 0 | 本模块尚未上线，**没有真实失败案例**。槽位预留给线上回流，见第 5 节 |

## 3. 通过线

本模块是确定性规则，同一输入的结果固定，所以规则类维度的通过线贴近 100%，并不是照搬 99% 一类的经验值。另外两点：缺陷修复成本低，而一旦失败可能造成资产损失、越权，且不可逆。

下表数值除已标注“PRD 确定”的以外，都是**建议、待业务与测试确认**。

**单例判定。** 一条 case 只有在两个条件同时满足时才算通过：

- “预期行为”全部满足；
- “禁止行为”一项都没有出现。

一条验收写了多个场景时，拆成的每条原子 case 都通过，才算该验收通过。这与 04 册的读法一致。

**指标口径：**

- 维度通过率 = 本轮该维度判定为通过的 case 数 ÷ 本轮该维度有效执行的 case 数。
- **排除规则**：因环境故障而无法判定的 case 标为“无效”，比如上游 mock 宕机、测试钱包不可用。无效 case 不计入分母，必须重跑。一轮中无效 case 超过 5%（建议值）时，整轮作废。
- **不能排除的情况**：产品行为错误不得标为无效，比如超时后判成游客。
- **切片**：每个维度分两个切片单独统计，不合并。“模拟环境”切片用上游 mock 与时间 mock；“真实联调”切片接资产可信平台测试环境与真实钱包。

**发布门槛：**

| 层级 | 门槛 | 依据 |
| --- | --- | --- |
| 关键阻断项 B1～B8 | 每一轮、每条相关 case 都是 0 失败。任何一次失败都阻断发布，不能用其他维度的高分抵消 | 失败不可逆，或构成安全事故 |
| D1、D2、D4 | P0 case 100% 通过；P1 case 通过率不低于 95%，未通过的 P1 须有缺陷单，并经产品与测试负责人书面放行；P2 不设发布门槛，记入缺陷清单，在后续版本修复 | P0 按业务方口径不允许带入发布；P1、P2 的门槛为建议，待确认 |
| D3（模拟环境） | P0 case 100% 通过 | 时点与次数类规则是确定的 |
| D3（真实联调） | 首次上线前，真实联调切片的 P0 case 100% 通过；上游接口或钱包 SDK 变更后重跑 | 04 册已说明，模拟环境不能据此判定真实联调通过 |
| D5 | R2（不泄露）属于 P0，任何一次不通过都阻断发布；NT-C09 文案逐字比对类 case 100% 通过；其余人工 rubric 类 case（P1）通过率不低于 95%；P2 不设门槛 | 呈现问题的成本相对低，但泄露上游登记情况属于信息泄露 |
| 整体 | 以上各项同时满足；与上一版本逐条对比时，P0 case 从“通过”变为“失败”的数量为 0；P1 由通过变为失败的，逐条说明原因 | 防止修一处、坏一处 |

**P0 / P1 / P2 的划分：**

| 级别 | 口径 | 本模块中的典型情况 | 来源 |
| --- | --- | --- | --- |
| P0 | 影响业务进程，或危及平台安全 | B1～B8 全部阻断项；企业无法登录或身份判错（含调取失败误判为游客、地址写法不同匹配不到）；认证失效、地址变更后仍放行业务；越权访问、跨企业数据残留；未签名地址入账、被引用账户被删、登录地址顺延出错；D5 中 R2（泄露上游登记情况或内部原因） | 口径为业务方 11-05 确认；典型情况由本 Eval 按口径归类 |

- 一条 case 涉及多个级别时，按其中最高的级别计。
- 判不准时就高不就低，由产品负责人仲裁。
- 每条 case 的最终级别由测试负责人在启动集评审时标注，产品负责人确认。

**随机性控制：**

- 依赖真实钱包或网络时序的 E2E case，如签名延迟、钱包切换地址，每轮重复执行 3 次。P0 case 须 3 次全部通过，任何一次失败都按失败处理，直到查明原因。
- 不稳定的 case，只有在证明是环境问题后才能标为无效。

**统计与不确定性：**

- 规则类 case 不计算置信区间，逐条看是否失败。
- 小样本零失败不等于低风险。例如某个切片 50 条 0 失败，按 Wilson 方法计算的 95% 区间上界约为 7%，这是公式算出的说明值，不是评测结果。所以阻断项靠“每条 case 0 失败 + 绕过界面的变体”来覆盖，不靠通过率。
- D5 人工评分与 L3 线上比例指标，用 Wilson 区间报告。
- 版本比较用同一版本的 case 集做逐条配对，只看有没有回归，不报告“提升”。
- 本文没有任何执行数据，不填写任何分数或区间。

**失败兜底**（PRD 已确定，Eval 核对兜底是否存在）：

- 调取失败时，登录不成立，可以重试；
- 建立企业用户失败时，给出错误码、重试与退出；
- 保存失败时，保持上一次成功保存的状态；
- 确认删除时再判一次引用；
- 提交时复核所选账户仍存在。

每条兜底至少对应 1 条 case。发布后如果出现阻断项，按第 5 节回流：先下线或止血，再补 case。止血手段（例如暂停新增数币账户）**待业务确认**。

本模块大部分 case 由自动化断言判定。人工标注主要用在三处：

- 定义预期结果，把 PRD 转成可断言的期望；
- D5 呈现类判定；
- 阻断项复核。

| R6 签名告知 | P1 | 发起签名前，平台自己说明了签名用途，没有只靠钱包提示？ | 确认签名步骤写明“不涉及转账或资金授权” | 直接唤起钱包，页面没有说明 |

R5 中“缩写位数”由设计确定，本 rubric 只判是否缩写、是否保留大小写，不判位数。

**人机对齐（LLM-as-judge）。** 启动阶段不使用 LLM-as-judge。之后如果 D5 画面数量（中英文 × 宽度 × 状态）超出人工承受范围，可以引入 LLM 只做 R2、R4 的批量初筛，条件如下：

- 先用人工已判定的 case 建立校准集，校准集与日常评测集隔离，不用于调提示词以外的任何用途；
- 在校准集上，LLM 与人工判定的一致率达到约定门槛（**建议 95% 以上，待确认**），才能启用；
- 启用后，LLM 判为不通过的 case 一律转人工；LLM 判为通过的 case，人工抽 10% 复核；
- LLM 不参与任何阻断项的判定。

目前没有任何样本，所以**不声称 judge 已可靠**。

## 5. 跑评频率

**分层节奏。** 以下都是建议节奏，只描述触发条件、责任与产物，不接入任何自动化。

| 层级与节奏 | 触发条件 | 范围 | 责任 | 产物 |
| --- | --- | --- | --- | --- |
| L1 确定性检查，每次 commit | M1 相关代码，或上游 / 钱包对接代码有改动 | 可在上游 mock 下快速判定的 code-based case：签名重放 / 过期 / 地址不一致、权限矩阵中的接口直连、地址格式与去重、备注名长度、引用判定、NT-C09 文案比对、日志敏感字段扫描（B8） | 研发 | 通过 / 失败清单；B 类失败直接阻止合入（建议） |
| L2 人工与全量评估，每次 release | 发版候选 | 启动集或稳态集全量：两个切片（模拟环境 + 真实联调）；时间 mock 类 case（60 秒、5 分钟、30 分钟、4 小时、7 天）；真实钱包 E2E 跑 3 次；D5 人工 rubric 判定 | 测试负责人执行，产品与安全复核 | 按维度、按切片的通过率表，阻断项清单，与上一版本的逐条回归对比，放行签字 |
| 每周回归 | 每周固定一次（建议）；同时有 M3a / M4a 联动改动时，加跑相关 case | D3、D4 中跨模块的 case（关键动作提交前调取、引用判定、申请选用账户），以及标为“需求变更回归”的 case | 测试 | 周回归记录 |
| 外部变化探索，每月或按事件触发 | 本模块不调用模型，所以“每月 frontier eval”换成以下几类：钱包 SDK 升级或新增钱包；资产可信平台接口、时延或限流变化；浏览器或硬件钱包的新版本 | 兼容性与 OOD case：新钱包的签名格式、硬件钱包延迟、新的上游字段或登记标识 | 研发与测试 | 兼容性报告；新增的 OOD case |

**L3 线上业务验证**（上线后，**只观察，不作为发布门槛**）。目的是区分“离线 case 全部通过”与“真实用户确实能用”。

| 指标 | 口径（分子 ÷ 分母） | 用途 |
| --- | --- | --- |
| 登录漏斗各步转化率 | 下一步人数 ÷ 上一步人数；步骤为连接、确认签名、验签通过、调取完成、身份判定 | 定位在哪一步流失 |
| 调取失败率 | 调取失败、超时次数 ÷ 调取次数 | 上游可用性，同时反证 B3 |
| 游客占比 | 判为游客的登录次数 ÷ 登录成功次数 | 发现地址写法匹配问题，或上游登记问题 |
| 认证引导前往率 | 确认前往资产可信平台的次数 ÷ 认证引导展示次数 | 引导是否有效 |
| 新增数币账户签名通过率 | 签名通过次数 ÷ 进入签名次数；按失败原因分层 | 发现“签名地址不一致”这类易错点 |
| 安全告警数 | 来源无法确认、一个地址对应多个账户、缺少稳定标识的告警次数 | 异常应接近 0，出现即调查 |

关于 L3 指标：

- 比例指标按 Wilson 区间报告；
- 告警阈值与观察周期**待业务确认**；
- L3 的任何数值都不得反过来改写离线 case 的判定结果；
- L3 用真实流量统计，与第 2 节加重后的风险覆盖集分开解读。

**失败回流。** 来源有四类：线上工单、L3 异常、安全告警、外部变化探索中发现的问题。处理流程：

1. 测试在约定时限内（**建议 3 个工作日，待确认**）脱敏并复现，确认属于 M1 行为问题；
2. 写成 case，放入“历史失败”类别，标注“真实”及来源编号，与合成 case 区分；
3. 涉及 B 类的问题，同时补一条绕过界面的变体；
4. 确认是 PRD 规则缺口而不是实现缺陷时，交 PRD 负责人处理；本 Eval 不改 PRD。

**样本更新与版本管理：**

- **版本号**：Eval case 集按 `Eval-M1-vX.Y` 管理，每个版本记录所依据的 PRD 提交（当前为 `e0fc67d`）。
- **PRD 有新提交时**：对比 01～04 册的变化，更新受影响的 case 与 AC↔case 映射；被规则变更作废的 case 归档，不删除，并标注作废原因与提交号。
- **规则改过的 case**：打上“需求变更回归”标签，至少保留到下一个 release 之后。
- **两个集合分开管理**：风险覆盖集按 PRD 与风险扩充；统计集只用于 L3，跟随真实流量漂移更新，不混入人为构造的对抗样本。

- 真实联调环境与资产可信平台测试账号的可用性，以及上游的时延与限流约定。01 册 D1 依赖写明“在对接时核实”；
- 关键业务动作的清单，由 M3a / M4a 认定；
