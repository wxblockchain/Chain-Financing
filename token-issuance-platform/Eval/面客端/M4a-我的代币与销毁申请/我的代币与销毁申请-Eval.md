**评估范围。** 本模块是企业查看本企业已铸造代币、在满足条件时申请销毁、并跟踪审核、销毁与解除监管进度的地方。规则确定，不含模型生成内容，所以本 Eval 回答的问题是：**本模块交付后的产品表现，是否达到 PRD 的成功标准**，不评模型能力。具体包括五点：

- 只有本企业能看到本企业的代币、销毁申请、签名记录与监管协议，企业看不到管理端内部信息；
- 只有同时满足到期、结清、双重无融资质押、持有地址条件且没有处理中申请的代币才能产生销毁申请，一枚代币同一时刻最多一笔处理中的申请，数量恒为完整铸造数量；风险暂停时拒绝新申请、保留查询与既有事实；
- 业务签名是否由登录地址签署代币、完整数量、持有地址与本次申请授权标识四项；授权仅用于当前企业与当前提交，成功后占用，失效后不可复用，记录与链上签名值及授权标识一致；
- 企业看到的代币信息、持有信息、销毁进度、驳回意见、销毁结果、解除监管进度和 NT-A02 是否按规则出现，没有把未知或进行中的结果显示成已完成；
- 用户在每种限制、异常和读取失败下能否看懂并走得下去。

与 04 册的分工：04 册是逐条验收标准，测试用例与执行步骤由测试小队编写。本 Eval 在 04 册之上做三件事：

1. 按风险把验收归入维度，并划出阻断项；
2. 规定 case 的组织方式与通过线；
3. 规定标注、跑评节奏、失败回流与版本管理。

本 Eval 不替代测试用例。

**不在范围内：**

- M4b 的运营审核、驳回、执行销毁、手动重试、平台签名私钥与解除监管办理：只核对它们推动后企业侧看到的结果，以及企业签名值与授权标识是否随销毁交易上链；暂停新增不替代既有业务的当前条件判断；
- M3a / M3b 的发行与铸造：本模块只承接铸造成功的结果，见 [M3a Eval](../M3a-代币发行-企业申请/代币发行-企业申请-Eval.md)；
- M2 的到期、结清与回款状态归并本身：本 Eval 只核对资格判断是否按 M2 与上游给出的事实放行或拦截，见 [M2 Eval](../../两端共用/M2-可信资产/可信资产-Eval.md)；
- M1 的身份判定与认证调取时点：本模块直接使用 M1 的结果，见 [M1 Eval](../M1-企业登录与企业账户/企业登录与企业账户-Eval.md)；本 Eval 只核对提交前的身份与认证复核；
- 下游借贷平台的融资结果与链上质押转移本身的正确性：本 Eval 只核对两项结果的组合是否按 6.2 判定；
- M7 的消息展示、已读与前往：只核对 NT-A02 的触发、收件范围与内容；
- 视觉与布局，由 Hallmark 设计负责。

**判定方式用语：**

- **code-based**：自动化断言，包括接口响应、页面状态、数据库记录、链上数据读取、响应体敏感字段扫描、文案字符串比对；
- **human**：人工按二元 rubric 判定；涉及真实钱包的操作由测试人员执行，结果仍按断言判定；
- **LLM-as-judge**：本模块不用于任何阻断判定，只在第 4 节写明的条件下，作为文案批量初筛的辅助。

### D2 销毁资格判定与提交把关

| 项 | 内容 |
| --- | --- |
| 定义 | 只有同时满足 6.1 全部六项条件的代币才能产生销毁申请：已到期、上游明确已结清、下游与链上均确认无融资质押、没有处理中申请且未销毁、身份有效、链上持有地址为铸造到账地址且质押地址为空；任一项不满足或无法确认都不产生申请。列表“申请销毁”按最近一次成功取得的信息提供，不构成资格承诺；缺失或无法确认不提供，点击后重新取数、提交前再次完整判断，不规定缓存时长；风险暂停关闭新入口与提交，保留查询和在途事实，恢复后重新校验、取得新授权并签名；一枚代币最多一笔处理中的申请，一次提交最多一笔申请；申请销毁数量恒为完整铸造数量，企业不能改代币、数量或地址；驳回后再次申请是新申请，须重新满足全部条件 |

| 通过条件 | 以下全部满足：<br>① 平台未暂停新申请，且最近一次成功取得的信息显示未销毁、无处理中申请、已到期、上游明确已结清、持有地址为铸造到账地址且质押地址为空时才提供列表“申请销毁”，含最近一次被驳回的代币；其余情况不显示，也不显示禁用按钮；<br>② 恰好到达到期时点即为已到期；不同查看时区资格结论相同；提前结清仍须等到期；不按余额为零、已有回款或逾期状态推断结清；<br>③ 融资双重校验与 6.2 九种组合逐行一致：只有两项均无质押才通过；一有一无按有质押处理并提示联系平台；任一未知不放行，不声称确定无质押；<br>④ 违约代币（留在质押合约地址）与持有地址不是铸造到账地址的代币不能申请销毁，绕过界面同样被拒绝；<br>⑤ 签名后提交前重新确认身份、认证与全部资格，旧结果不放行；上游、下游或链上无法确认时不放行；<br>⑥ 重复点击、刷新、网络重发、并发会话只产生一笔申请；已有处理中申请时定位原申请；结果未确认时不新增申请；<br>⑦ 申请销毁数量等于完整铸造数量，绕过界面传入其他数量、其他代币或其他地址被拒绝；<br>⑧ 待审、销毁中、销毁失败（等待运营重试）都占用原申请，企业不能新申请；已销毁的代币无论监管是否解除都不能再申请；<br>⑨ 原合约被平台停用不阻断满足原条件的提交；<br>⑩ 风险暂停后任何新提交均被拒绝，未成功提交的授权失效；既有申请不回滚、不自动驳回或改阶段，查询保留；恢复后重新取得当前资格、新授权并重新签名 |
| 失败条件 | 任一情况即失败：<br>• 任一条件不满足或无法确认时提交成功，包括绕过界面直接调用提交接口；<br>• 只凭单一来源或缓存的“未融资”放行；两项结果不一致时放行；<br>• 违约代币或持有地址异常的代币产生申请；<br>• 同一代币同时存在两笔处理中申请；同一次提交产生多笔申请；已销毁代币产生新申请；<br>• 申请数量不是完整铸造数量，或企业改动了代币、数量、地址；<br>• 销毁失败期间企业能新申请或自行重试；<br>• 监管中、历史逾期或合约在平台停用被当作阻断理由；<br>• 风险暂停仍产生新申请，或暂停擅改既有申请状态、阻止原有查询；恢复后以旧授权放行 |

**为什么不照搬 60/30/10。** 本模块的主要风险集中在资格把关（B3～B5）、签名及单次授权（B6、B7、B10）、风险暂停（B11）、状态虚报（B8）和越权（B1、B2），这些都在异常与对抗路径上；正常路径步骤固定，所以异常与对抗的占比调高。

## 3. 通过线

本模块是确定性规则，同一输入的结果固定，所以规则类维度的通过线贴近 100%，并不是照搬 99% 一类的经验值。另外两点：缺陷修复成本低，而一旦失败可能让有融资质押、未结清或不在原地址的代币被销毁，或企业未认可的销毁上链，且不可逆。

**已确认的仅是 P0 定义“影响业务进程，或危及平台安全”。** 本节全部发布门槛（含 P0 100%、B 类零失败、P1 95%、P2 处置和整体放行规则）均为**建议、待测试 / 安全 / 发布负责人确认**，不由该定义推导为已获确认。PRD 已规定的单例业务行为（例如消息 60 秒内可见）仍作为预期行为。

**单例判定。** 一条 case 只有在两个条件同时满足时才算通过：

- “预期行为”全部满足；
- “禁止行为”一项都没有出现。

一条验收写了多个场景时，拆成的每条原子 case 都通过，才算该验收通过。这与 04 册的读法一致。

**指标口径：**

- 维度通过率 = 本轮该维度判定为通过的 case 数 ÷ 本轮该维度有效执行的 case 数。
- **排除规则**：因环境故障而无法判定的 case 标为“无效”，比如上游或下游 mock 宕机、M4b 测试桩不可用、测试链拥堵导致读不到交易、测试钱包不可用（不是 case 有意模拟的不可用）。无效 case 不计入分母，必须重跑。一轮中无效 case 超过 5%（建议值）时，整轮作废。
- **待判定与未执行**：必要执行证据、已选安全参数或联调条件未就绪时单列数量与原因，不标通过、不冒充环境无效；不计入有效执行分母，同时报告必需 case 的执行覆盖率（有效判定数 ÷ 本轮必需 case 总数）。建议必需 case 全部完成判定后才可评价发布门槛，待确认。
- **不能排除的情况**：产品行为错误不得标为无效，比如链上查询失败时放行了提交。
- **切片**：每个维度分两个切片单独统计，不合并。“模拟环境”切片用上游 mock、下游 mock、链上读取 mock、时间 mock、M4b 测试桩与签名构造脚本；“真实联调”切片接上游平台测试环境、下游借贷平台测试环境、真实钱包与测试链上的真实质押与销毁。

| D4 | P0 case 100% 通过；持有信息、监管协议、阶段说明类 P1 case 通过率不低于 95%；NT-A02 文案逐字比对类 case 100% 通过；P2 不设门槛 | 状态虚报与收件范围错误影响业务进程；展示偏差有兜底 |
| D5 | R2（不泄露）属于 P0，任何一次不通过都阻断发布；文案逐字比对类 case 100% 通过；其余人工 rubric 类 case（P1）通过率不低于 95%；P2 不设门槛 | 呈现问题成本相对低，但拒绝说明透露对象是否存在属于信息泄露 |
| 整体 | 以上各项同时满足；与上一版本逐条对比时，P0 case 从“通过”变为“失败”的数量为 0；P1 由通过变为失败的，逐条说明原因 | 防止修一处、坏一处 |

**P0 / P1 / P2 的划分：**

| 级别 | 口径 | 本模块中的典型情况 | 来源 |
| --- | --- | --- | --- |
| P0 | 影响业务进程，或危及平台安全 | B1～B11 全部阻断项；错误授权被提交采信、暂停后接受新申请、暂停擅改既有事实；他企业数据残留；没有申请却有待审任务；未完成签名即产生申请；企业能修改监管协议；违约代币驳回后仍可申请或监管被误显示为已解除；满足全部条件的代币无法申请或无法提交；列表遗漏铸造成功的代币或已销毁代币消失；发行信息、数量、铸造到账地址与铸造结果不一致；持有信息查询失败时显示未融资或用铸造到账地址补行；企业侧出现内部失败信息、重试记录；签名内容或取值与确认环节不一致；D5 中 R2（拒绝说明透露对象是否存在） | 口径为业务方 11-05 确认；典型情况由本 Eval 按口径归类 |
| P1 | 规则执行有偏差，用户会误解或多走一步，但有兜底或绕行，不阻断业务、不涉及安全 | 不满足条件时仍显示禁用的“申请销毁”；限制原因只说出一项；监管协议查看失败没有重试；编号跳转进入了正确对象但返回路径丢失；读取失败显示为空；确认环节缺少后果说明；机构或合约名称未取当前值；数量单位写成 USD；D5 中仅涉及理解与呈现偏差的 R1、R3～R6（遇 P0 后果升级） | 建议，待确认 |
| P2 | 呈现与体验细节，不影响用户判断和操作 | 处理中反馈缺失但只产生一笔申请；非关键说明措辞不统一；中英文措辞小差异（不含状态值、限制说明与 NT-A02）；长值缩写位置欠佳但可查看完整值；暂无图标时的占位样式欠佳 | 建议，待确认 |

- 一条 case 涉及多个级别时，按其中最高的级别计。仅文字或交互缺陷可拆为 P1；若含越权、未签名提交、协议修改、错误销毁或监管结论、错误待审任务、错误对象跳转，仍按 P0，不因呈现类归属降级。P1 / P2 的定义及场景归类均为建议、待确认。
- 判不准时就高不就低，由产品负责人仲裁业务歧义，分级与发布处置由测试、安全、发布负责人决定。
- 每条 case 的最终级别由测试负责人标注，安全与发布负责人按机制确认；产品仅解释业务预期。

**随机性控制（以下重复次数为建议、待测试负责人确认）：**

- 依赖真实时序的 case，如并发提交、请求重放、提交前条件变化、真实钱包签名、测试链读取、下游结果变化，每轮重复执行 3 次。P0 case 须 3 次全部通过，任何一次失败都按失败处理，直到查明原因。
- 到期判断与登录到期类 case 一律用时间 mock 固定“当前时点”，不依赖执行时的真实时间。
- 不稳定的 case，只有在证明是环境问题后才能标为无效。

**统计与不确定性：**

- 规则类 case 不计算置信区间，逐条看是否失败。
- 小样本零失败不证明实际业务风险足够低，风险覆盖集也不满足真实流量随机抽样假设。因此阻断项靠“每条 case 0 失败 + 绕过界面的变体 + 资格矩阵 + 时序矩阵”来覆盖，不靠通过率。
- D5 人工二元判定与 L3 线上比例指标，计划报告样本量、分子 / 分母及 Wilson 95% 区间（置信水平建议、待确认）；稀少切片单列、不作总体外推。
- 版本比较在相同 PRD 预期与同一 case 集上逐条配对；此次三项签名变四项等规则已改的 case 先归档旧期望，再按新规则评审，不能直接把旧版与新版结果算回归。没有执行数据时不报告“提升”。
- 本文没有任何执行数据，不填写任何分数或区间。

**失败兜底**（PRD 已确定，Eval 核对兜底是否存在）：

- 任一资格条件不满足或无法确认，不产生申请，说明原因并可重新获取；
- 签名后提交前重新判断身份与全部资格；
- 签名核对不通过、取消 / 拒签、离开重进、身份 / 地址 / 内容 / 资格变化、暂停或明确提交失败时，原授权失效；重新提交须新授权、新签名；
- 重复提交只定位已有申请，授权不能二次用于新提交；结果未确认先取原实际结果，不新增授权或申请；
- 销毁执行结果未确认时保持销毁中，失败由运营手动重试，企业不能重复申请；
- 各类读取失败可以重试，不说成“没有”，未知值不补为零、未融资、已结清或已解除监管；
- 上游或下游暂不可用时仍可查看本平台已取得的代币、申请与结果；
- 消息未及时显示不改变已成功的申请。

每条兜底至少对应 1 条 case。发布后如果出现阻断项，按第 5 节回流：先止血，再补 case。止血的企业可见行为已由 01 册 6.4 确定：暂停新增、保留查询和既有事实，恢复后重新校验、新授权、新签名。触发阈值、权限、审批与操作流程待安全、研发、运营确认。

## 4. 标注方法

本模块大部分 case 由自动化断言判定。人工标注主要用在四处：

- 定义预期结果，把 PRD 转成可断言的期望，尤其是 6.2 九种组合、6.3 多条件组合、5.3 七种持有情况、9.2 阶段表与签名四项的取值及授权生命周期；
- 真实钱包签名交互，由测试人员执行并对钱包中显示的签名内容截图留证；
- D5 呈现类判定，以及限制原因、确认环节后果说明的完整性；
- 阻断项复核。

**角色：**

| 角色 | 职责 |
| --- | --- |
| 产品（PRD 负责人） | rubric 与预期结果的最终解释人；PRD 有歧义时负责仲裁，必要时回到 PRD 流程修订。本 Eval 不改 PRD |
| 测试负责人 | 把验收拆成 case，标注 P0 / P1 / P2，维护 AC↔case 映射、资格矩阵与时序矩阵，执行判定 |
| 安全复核 | 复核 B1、B2、B6、B7、B9～B11 相关的 case 与结果，以及签名构造、授权绑定 / 失效 / 占用、风险暂停时序与重放脚本的覆盖面 |
| 业务复核（运营代表） | 复核 B3～B5、B8 相关 case 的期望值，确认资格判断、防重与阶段展示符合审核与销毁实际 |
| 研发（链与钱包） | 定义签名格式并提供签名构造工具；提供上游与下游 mock、链上读取 mock、时间 mock、M4b 测试桩、测试链读取脚本；标注“无效”case 的环境原因 |
| 中英文审校 | D5 文案判定，包括限制说明、确认环节说明、各类失败说明、状态值、NT-A02 |

**分阶段（抽查比例为建议、待测试负责人确认）：**

- **启动**：产品与测试负责人对计划的 90 条启动 case 逐条标注预期行为与禁止行为；6.2 九种组合、5.3 七种持有情况、9.2 七个阶段的期望与签名四项的取值及授权生命周期由产品核对业务预期；测试、安全负责人核对授权生命周期证据。D5 的 8 条 case 由产品与审校各自独立按 rubric 判定，分歧交产品负责人仲裁，仲裁理由写入 case 备注。
- **扩展**：新增 case 由测试负责人起草。测试安排第二位标注人抽查新增 case 的 20%（建议值），阻断项相关的 case 全部复核。
- **持续**：每次 release 后，D5 人工判定结果抽 10%（建议值）由第二人复判；复判不一致时，修 rubric 或补正反锚点。

**D5 二元 rubric**（每条判是或否，全部为“是”才通过）：

| 条目 | 级别 | 判定问题 | 正例锚点 | 反例锚点 |
| --- | --- | --- | --- | --- |
| R1 可区分 | P1 | 读取失败、确实没有代币或申请、条件不满足、条件无法确认，用户能否分辨？ | 持有信息查询失败显示“暂时无法获取持有信息，可以重试”；到期依据取不到显示“暂时无法确认到期情况” | 持有信息查询失败显示“未融资”；到期依据取不到显示“未到期” |
| R2 不泄露 | P0 | 拒绝说明是否不透露代币或申请是否存在，且不出现他企业的任何信息与管理端内部记录？ | 访问他企业代币与不存在的编号，都显示“相关内容暂不可访问” | 显示“该代币属于其他企业”；显示“运营 ops01 已驳回” |
| R3 有出路 | P1 | 每种限制或失败是否给出了可以继续的操作（重新获取、联系平台、切换地址或网络、重新签名、查看已有申请、前往我的代币或代币发行）？ | 融资结果不一致：说明按有质押处理，请联系平台 | 只显示“不能申请销毁” |
| R4 后果说清 | P1 | 确认环节是否在提交前说明了四项：由平台运营审核后执行销毁、销毁成功后仍需原监管机构解除监管且二者不同时完成、提交后不能撤回或修改、须用登录地址签名？ | 四项在提交前可获知，看到后才可提交 | 只写“请确认信息”；未告知“仍需解除监管”即允许提交 |
| R5 双语与原文 | P1 | 字段名、状态值、说明随语言切换；驳回意见、编号、数量、代币符号、Ethereum 保持原文？ | 英文界面阶段为英文，驳回意见仍为中文原文，数量为 50,000.00 cou | 英文界面阶段仍为“待解除监管”；驳回意见被机器翻译；cou 被翻译 |
| R6 长值呈现 | P1 | 地址、签名值与授权标识缩写展示、保留大小写，可核对并复制完整值？ | 签名值与授权标识缩写展示，复制得到对应完整原值 | 签名值或授权标识无法核对；复制得到缩写 |

R4 中四项说明的排布与交互形态由设计确定，本 rubric 只判是否在提交前全部可见；R6 中缩写位数由设计确定，本 rubric 只判是否缩写、能否取得完整值。

**人机对齐（LLM-as-judge）。** 启动阶段不使用 LLM-as-judge。之后如果 D5 画面数量（中英文 × 列表与详情 × 七种持有情况 × 七个阶段 × 十余种限制说明）超出人工承受范围，可以引入 LLM 只做 R1、R3、R5 的批量初筛，条件如下：

- 先用人工已判定的 case 建立校准集，用于调提示词的校准集与独立保留的验收集分开，后者不用于调参，以验收集验证 judge 对齐；
- 在校准集上，LLM 与人工判定的一致率达到约定门槛（**建议 95% 以上，待确认**），才能启用；
- 启用后，LLM 判为不通过的 case 一律转人工；LLM 判为通过的 case，人工抽 10% 复核；
- LLM 不参与任何阻断项的判定，也不参与 R2、R4；95% 门槛及 10% 复核比例均由测试 / 评估负责人确认，不要求产品定参数。

本轮未提供人工校准与 judge 对齐的执行样本，所以**不声称 judge 已可靠**。

关于 L3 指标：

- L3 用真实流量统计，与第 2 节加重后的风险覆盖集分开解读。

**失败回流。** 来源有五类：线上工单、L3 异常与一致性告警、运营在销毁审核中发现的申请或资格问题、安全告警、外部变化探索中发现的问题。处理流程：

1. 测试在约定时限内（**建议 3 个工作日，待确认**）脱敏并复现，确认属于 M4a 行为问题，而不是 M1、M2、M4b、下游或链上查询的问题；属于其他模块的，转交对应模块的 Eval 负责人；
2. 写成 case，放入“历史失败”类别，标注“真实”及来源编号，与合成 case 区分；
3. 涉及 B 类的问题，同时补一条绕过界面的变体；涉及资格或时序的，同时补进资格矩阵或时序矩阵；
4. 确认是 PRD 规则缺口而不是实现缺陷时，交 PRD 负责人处理；本 Eval 不改 PRD。
