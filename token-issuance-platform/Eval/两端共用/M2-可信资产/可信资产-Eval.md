C2 只针对 EV-D2-08 的金额与上游结清状态不一致场景，不解释为“所有未结清资产都不能发起”。正常未结清、有未回款余额且满足其余条件的汽车贸易资产仍可发起。拦截不等于按金额自行认定已结清；原始结清依据继续保留，回款归并展示仍按现有 4.3 判断。本文不把该冲突擅自改为新的回款状态。C1 只明确查询匹配，不推导资产编号存储或唯一性规则。PRD 与 04 册尚未纳入的补充，由 PRD 负责人在其流程中同步；本次只更新 Eval。

本模块自身不发送消息，所以没有 03 册（01 册开头已写明）；本 Eval 也不设消息类检查。PRD 更新后，本 Eval 按第 5 节的“版本管理”同步。

**评估范围。** 本模块展示上游资产可信平台已确权的应收账款，并决定资产能否发起发行申请。规则确定，不含模型生成内容，所以本 Eval 回答的问题是：**本模块交付后的产品表现，是否达到 PRD 的成功标准**，不评模型能力。具体包括五点：

- 每个角色是否只看到自己范围内的资产与企业；
- 确权、回款、发行三个状态是否判得对，尤其是到期兜底与“暂时无法确认”；
- “申请发行”入口与提交是否只对满足全部条件的资产开放，一笔资产是否只有一笔申请；
- 展示的资产信息是否与上游一致、分级是否正确、是否只读；
- 用户能否查找到资产，并看懂当前状态和不能发起的原因。

与 04 册的分工：04 册是逐条验收标准，测试用例与执行步骤由测试小队编写。本 Eval 在 04 册之上做三件事：

1. 按风险把验收归入维度，并划出阻断项；
2. 规定 case 的组织方式与通过线；
3. 规定标注、跑评节奏、失败回流与版本管理。

本 Eval 不替代测试用例。

**不在范围内：**

- M3a 申请流程本身（选监管机构、选数币账户、签名提交）、M3b 审核与铸造、M4a / M4b 代币状态：只核对它们推动的发行状态，以及从本模块进入它们的入口；
- M1 的身份判定（已认证 / 未认证 / 游客）：本模块直接使用 M1 的判定结果，判定本身见 [M1 Eval](../../面客端/M1-企业登录与企业账户/企业登录与企业账户-Eval.md)；
- 上游平台自身数据的正确性，以及与上游的同步时效（01 册第 10 节写明“本册不设时效要求”）；
- 视觉与布局，由 Hallmark 设计负责。

**判定方式用语：**

- **code-based**：自动化断言，包括接口响应、页面状态、数据库记录、响应体敏感字段扫描、文案字符串比对；
- **human**：人工按二元 rubric 判定；
- **LLM-as-judge**：本模块不用于任何阻断判定，只在第 4 节写明的条件下，作为文案批量初筛的辅助。

### D1 访问范围与数据隔离

| 项 | 内容 |
| --- | --- |
| 定义 | 每个角色只能看到 PRD 允许的资产与企业信息。拒绝由平台判定，不靠隐藏入口；拒绝时的说明不透露资产是否存在 |
| 需求来源 | 01 册 5.1 无权查看、3.1 资产来源（只看本企业作为债权人的资产）、3.3 / 3.4（只供运营）、8.4（变更提示只在运营端）、第 9 节（监管机构只看关联资产）、5.6（筛选在原可见范围内进行）；02 册图 6。对应验收 AC-AS-02、18、19、34，以及 AC-AS-31、33、37、40 中与可见范围有关的部分 |
| 通过条件 | 按角色分：<br>• 游客：看不到可信资产入口，直接访问不返回任何资产信息；<br>• 未认证企业用户：看得到入口，只看到认证引导，列表与详情接口都不返回资产数据；<br>• 已认证企业用户：只看到本企业作为债权人的资产，包括已驳回、已发行的资产；<br>• 监管机构：只看到选择了本机构的申请所使用的资产，无论申请处于什么状态，包括被本机构驳回、被运营驳回；看不到企业列表、企业详情、企业用户信息、数币账户和上游变更提示；<br>• 运营：可看全平台企业、资产、数币账户和变更提示。<br>另外：访问范围外的资产与访问不存在的资产，说明完全相同，都是“无权查看或资产不存在”；筛选（包括币种选项）只在原可见范围内取值 |
| 失败条件 | 任一情况即失败：<br>• 被拒绝的请求返回了任何资产或企业字段，包括列表条数、资产编号、名称、金额；<br>• 只隐藏了入口，直接 URL 或接口能拿到数据；<br>• “无权查看”与“不存在”的说明、状态码或响应结构可区分；<br>• 通过构造筛选参数拿到范围外的资产，或币种选项暴露了范围外资产使用的币种；<br>• 企业端、监管端出现企业用户信息、数币账户或“上游已撤销确权 / 上游已删除”提示 |
| 失败后果 | 他企业应收账款、债务人与交易数据泄露；属于合规与安全事故 |
| 判定方式 | code-based：按“角色 × 资源 × 访问方式（入口 / 直接 URL / 接口）”做矩阵断言，对响应体做字段扫描；“无权”与“不存在”的响应逐字节比对（时间戳等非业务字段除外）。阻断项由安全角色复核 |

### D2 资产状态判定正确性

| 项 | 内容 |
| --- | --- |
| 定义 | 确权、回款、发行三个状态按 PRD 取值并按规则变化：回款状态按归并表判定，到期兜底按上游带时区的到期时点触发；发行状态只由 M3a / M3b 的业务结果推动、只向前、不回退；关联申请的铸造阶段在企业端与管理端分别按规则展示 |
| 需求来源 | 01 册 F-AS-02：4.1 状态字段一览、4.2 确权状态、4.3 结清与逾期依据与回款状态归并、4.4 发行状态与关联申请的铸造阶段展示、5.3 上游暂时不可用、5.5 时区不改变判断；02 册图 2、图 4。对应验收 AC-AS-10、11、12、14、15、16、17、20、36 |
| 通过条件 | 以下全部满足：<br>① 回款状态严格按 4.3 归并表从上到下判定，已结清优先；列表与详情使用同一结果；<br>② 到达到期时点、仍未取得上游最新状态时，自动变为已逾期；到期时点本身已属于到期；上游暂时不可用时仍执行；之后以上游新状态为准；<br>③ 结清依据取不到、依据缺失或与到期兜底冲突时，判为“暂时无法确认”，单独展示、单独可筛选，不归入三个正常取值，也不按回款金额或余额自行认定结清；<br>④ 先逾期后结清：当前为已结清，回款进度说明曾逾期，只出现在“已结清”筛选结果中；<br>⑤ 是否到期只看上游时点，切换查看者时区不改变任何状态；<br>⑥ 发行状态只按 可发行 → 发行申请中 → 已驳回 / 已发行 变化；上游撤销确权、删除，结清逾期变化，代币的监管、融资、销毁状态，都不改变发行状态；<br>⑦ 关联申请真实状态为铸造中、铸造失败时，企业端显示“发行处理中”，运营与监管机构显示真实状态；审核阶段与驳回不被归并；<br>⑧ C2 场景中，保留上游未结清的原始依据和实际回款记录，不能仅凭回款状态仍为未到期就放行发起；按 D3 执行拦截 |
| 失败条件 | 任一情况即失败：<br>• 已过到期时点仍显示“未到期”，包括上游不可用期间；<br>• 未知状态显示为“未到期”，或按回款金额自行判为已结清；<br>• 到期兜底后覆盖了上游新回传的事实；<br>• 先逾期后结清的资产出现在“已逾期”筛选结果中，或并列展示两个当前回款状态；<br>• 切换时区改变了回款状态或能否发起；<br>• 发行状态回退，或终态（已驳回、已发行）再变化；<br>• 发行状态被上游变更或代币状态推动；<br>• 企业端出现“铸造失败”，或管理端把真实状态显示成“发行处理中” |
| 失败后果 | 已逾期或已结清的资产被当作可发行资产发行代币，形成没有足额底层资产的代币；或正常资产被拦下；属于业务与资产风险 |
| 判定方式 | code-based 为主：回款状态归并做决策表全量断言（结清 × 逾期 × 到期 × 上游可用性组合）；时间 mock 推进到期时点前后；时区切换断言；状态机迁移断言。另设“真实联调”切片，接上游平台测试环境（见第 3 节） |

### D3 发起条件与申请唯一性

| 项 | 内容 |
| --- | --- |
| 定义 | 只有同时满足 7.1 全部六个条件且未命中 C2 的已接收资产，才提供“申请发行”入口、才能提交成功；提交时按最新信息重新判断，包含 C2；一笔资产任何时候最多只有一笔发行申请；不满足时在详情中列出全部当前原因 |
| 需求来源 | 01 册 F-AS-04：7.1 发起条件、7.2 发起与结果、7.3 重复发起与条件变化；5.2 上游信息缺失；3.2 补充信息不影响发起；8.4（撤销确权后不能发起）；02 册图 5。对应验收 AC-AS-05、06、25、26、27、28、29、41，以及 AC-AS-15 场景三、AC-AS-17、AC-AS-33 场景三、AC-AS-37 中“按可发行或未到期筛选不等于都能发起”的部分 |
| 通过条件 | 以下全部满足：<br>① 六个条件（可发行；已确权并展示“债权人已确权”；回款状态未到期；USD；L1 完整含销售发票；各依据均已取得）全部满足且未命中 C2 时，列表与详情都提供入口；<br>② 任一条件不满足或命中 C2 时，两处都不提供入口，详情列出全部不满足的原因，回款原因使用当前归并结果；C2 的说明须表达金额与上游未结清依据不一致、不能发起，不得误报上游已结清，具体中英文措辞待产品审校；<br>③ L2 缺失、补充信息整组没有、债务人下游客户交易的回款情况，都不影响发起；<br>④ 进入申请流程后未提交就离开，资产保持可发行；提交成功后变为发行申请中；<br>⑤ 提交时重新判断六个条件及 C2；条件已变化、命中 C2 或已有申请时拒绝提交并说明原因；<br>⑥ 绕过界面直接调用发起或提交接口，平台同样按六个条件及 C2 判定 |
| 失败条件 | 任一情况即失败：<br>• 不满足条件的资产提供了入口，或提交成功；<br>• 同一笔资产产生第二笔发行申请（包括并发提交）；<br>• 满足条件的资产没有入口；<br>• 债务人下游客户交易的未回款被计入本笔，或列为不能发起的原因；<br>• 多个原因只列了一个；把历史逾期列为当前阻断原因；<br>• 未提交离开后资产不再是可发行 |
| 失败后果 | 以不合格资产发行代币，或一笔资产重复融资；属于不可逆的资产与合规风险 |
| 判定方式 | code-based：条件逐项单独不满足与两两组合的断言；并发提交脚本；接口直连断言；提交前修改上游状态的时序断言。原因说明的可理解性由 human 按第 4 节 R3 判定 |

### D4 资产信息完整性与只读一致性

| 项 | 内容 |

| 定义 | 展示的资产、回款、企业与数币账户信息与上游最新信息一致；字段分级与展示 / 只入库处理正确；材料随所属环节展示且可查看下载；任何角色都不能新增、修改、删除；上游撤销确权、删除只在运营端提示 |

## 3. 通过线

本模块是确定性规则，同一输入的结果固定，所以规则类维度的通过线贴近 100%，并不是照搬 99% 一类的经验值。另外两点：缺陷修复成本低，而一旦失败可能让不合格资产发行代币、一笔资产重复融资或数据越权，且不可逆。

下表数值除已标注“PRD 确定”或“业务方确认”的以外，都是**建议、待业务与测试确认**。

**单例判定。** 一条 case 只有在两个条件同时满足时才算通过：

- “预期行为”全部满足；
- “禁止行为”一项都没有出现。

一条验收写了多个场景时，拆成的每条原子 case 都通过，才算该验收通过。这与 04 册的读法一致。

**指标口径：**

- 维度通过率 = 本轮该维度判定为通过的 case 数 ÷ 本轮该维度有效执行的 case 数。
- **排除规则**：因环境故障而无法判定的 case 标为“无效”，比如上游 mock 宕机、上游测试环境不可用（不是 case 有意模拟的不可用）、M3a / M3b 测试桩不可用。无效 case 不计入分母，必须重跑。一轮中无效 case 超过 5%（建议值）时，整轮作废。
- **不能排除的情况**：产品行为错误不得标为无效，比如上游不可用期间未执行到期兜底。
- **切片**：每个维度分两个切片单独统计，不合并。“模拟环境”切片用上游 mock 与时间 mock；“真实联调”切片接上游平台测试环境与真实的 M3a / M3b 流程。

| 关键阻断项 B1～B9 | 每一轮、每条相关 case 都是 0 失败。任何一次失败都阻断发布，不能用其他维度的高分抵消 | 失败会影响业务进程、接收范围，或构成资产与安全风险；B9 为按已确认 P0 口径的归类，发布数值门槛仍待确认 |
| D1、D3 | P0 case 100% 通过；P1 case 通过率不低于 95%，未通过的 P1 须有缺陷单，并经产品与测试负责人书面放行；P2 不设发布门槛，记入缺陷清单，在后续版本修复 | P0 按业务方口径不允许带入发布；P1、P2 的门槛为建议，待确认 |
| D2（模拟环境） | 回款状态决策表及 C2 的原始依据保留 / 发起拦截 case 100% 通过；其余 P0 case 100% 通过；P1 同 D1 | 归并规则是确定的决策表，任何一行出错都会让一类资产判错 |
| D2（真实联调） | 首次上线前，真实联调切片的 P0 case 100% 通过；上游接口、字段或时区格式变更后重跑 | 模拟环境不能代表上游真实的时区与状态回传方式 |
| D4 | P0 case（含 C3 的接收拒绝）100% 通过；只入库字段、字段齐全性类 P1 case 通过率不低于 95%；P2 不设门槛 | 事实值错误影响审核与 1:1 代币数量；展示细节成本较低 |
| D5 | R2（不泄露）属于 P0，任何一次不通过都阻断发布；筛选匹配规则（含 C1 的四类列表大小写变体）、文案逐字比对类 case 100% 通过；其余人工 rubric 类 case（P1）通过率不低于 95%；P2 不设门槛 | 呈现问题成本相对低，但泄露资产是否存在属于信息泄露 |
| 整体 | 以上各项同时满足；与上一版本逐条对比时，P0 case 从“通过”变为“失败”的数量为 0；P1 由通过变为失败的，逐条说明原因 | 防止修一处、坏一处 |

**P0 / P1 / P2 的划分：**

| 级别 | 口径 | 本模块中的典型情况 | 来源 |
| --- | --- | --- | --- |
| P0 | 影响业务进程，或危及平台安全 | B1～B9 全部阻断项（含 C2 冲突放行、C3 非汽车贸易资产被接收）；满足条件的资产没有入口或无法提交；回款状态判错（任何会改变能否发起的错误，含时区改变判断、先逾期后结清判为已逾期）；发行状态推动错误；L1 事实值（金额、币种、到期日、确权状态）与上游不一致；债务人下游交易被计入本笔；L1 缺失未拦下；D5 中 R2（拒绝说明透露资产是否存在） | 口径为业务方 11-05 确认；典型情况由本 Eval 按口径归类 |
| P1 | 规则执行有偏差，用户会误解或多走一步，但有兜底或绕行，不阻断业务、不涉及安全 | 企业端出现“铸造失败”或管理端显示“发行处理中”；只入库字段被展示；不能发起时原因列不全；筛选匹配规则偏差（部分编号匹配、大小写敏感）；读取失败、无匹配、无资产说明混用；详情返回丢失条件或页码；材料无法打开时没有重试；L2 缺失与整组没有的说明混用；中英文状态值不切换；D5 中 R1、R3～R6 | 建议，待确认 |
| P2 | 呈现与体验细节，不影响用户判断和操作 | 超长名称缩略位置欠佳但可查看完整名称；非关键说明措辞不统一；中英文措辞小差异（不含状态值与原因说明）；分页末页数据变化时的过渡体验 | 建议，待确认 |

- 一条 case 涉及多个级别时，按其中最高的级别计。
- 判不准时就高不就低，由产品负责人仲裁。
- 每条 case 的最终级别由测试负责人在启动集评审时标注，产品负责人确认。

**随机性控制：**

- 依赖真实时序的 case，如并发提交、上游不可用跨过到期时点、提交前上游状态变化，每轮重复执行 3 次。P0 case 须 3 次全部通过，任何一次失败都按失败处理，直到查明原因。
- 到期兜底类 case 一律用时间 mock 固定“当前时点”，不依赖执行时的真实时间。
- 不稳定的 case，只有在证明是环境问题后才能标为无效。

**统计与不确定性：**

- 规则类 case 不计算置信区间，逐条看是否失败。
- 小样本零失败不等于低风险。例如某个切片 50 条 0 失败，按 Wilson 方法计算的 95% 区间上界约为 7%，这是公式算出的说明值，不是评测结果。所以阻断项靠“每条 case 0 失败 + 绕过界面的变体 + 决策表全量组合”来覆盖，不靠通过率。
- D5 人工评分与 L3 线上比例指标，用 Wilson 区间报告。
- 版本比较用同一版本的 case 集做逐条配对，只看有没有回归，不报告“提升”。
- 本文没有任何执行数据，不填写任何分数或区间。

**失败兜底**（PRD 已确定，Eval 核对兜底是否存在）：

- 上游暂时不可用时，展示最近一次保存的信息，并继续执行到期兜底；
- 状态取不到或依据冲突时，判为暂时无法确认，不能发起；
- 提交时按最新信息重新判断，不满足时不能提交；
- 材料无法打开时，可以重试，不影响其他信息；
- 筛选读取失败时，保留条件，可以重试；
- 上游删除资产时，保留最近一次保存的信息。

C2、C3 的补充拒绝：C2 不产生申请，仍保留实际回款与上游结清事实；C3 不形成平台业务资产，不能仅以隐藏资产或禁止申请代替拒收。

每条兜底至少对应 1 条 case。发布后如果出现阻断项，按第 5 节回流：先止血，再补 case。止血手段（例如暂停全部“申请发行”入口）**待业务确认**。

## 4. 标注方法

本模块大部分 case 由自动化断言判定。人工标注主要用在三处：

- 定义预期结果，把 PRD 转成可断言的期望，尤其是回款状态决策表每个组合的期望值；
- D5 呈现类判定，以及 D3 不能发起原因的完整性；
- 阻断项复核。

**角色：**

| 角色 | 职责 |
| --- | --- |
| 产品（PRD 负责人） | rubric 与预期结果的最终解释人；PRD 有歧义时负责仲裁，必要时回到 PRD 流程修订。本 Eval 不改 PRD |
| 测试负责人 | 把验收拆成 case，标注 P0 / P1 / P2，维护 AC↔case 映射与决策表，执行判定 |
| 安全复核 | 复核 B1、B2、B8 相关的 case 与结果 |
| 业务复核（运营代表） | 复核 B9（行业拒收）、B4～B7 相关 case 的期望值，确认不合格资产与状态推动的判定符合审核实际 |
| 中英文审校 | D5 文案判定，包括状态值、不能发起的原因、空状态与异常说明 |
| 研发 | 提供上游 mock、时间 mock、并发提交脚本与 M3a / M3b 测试桩，标注“无效”case 的环境原因 |

**分阶段：**

- **启动**：产品与测试负责人对 60 条启动 case 逐条共同标注预期行为与禁止行为；回款状态决策表的期望值由产品逐行签认。D5 的 10 条 case 与 D3 的原因说明类 case，由产品与审校各自独立按 rubric 判定，分歧交产品负责人仲裁，仲裁理由写入 case 备注。
- **扩展**：新增 case 由测试负责人起草。产品抽查新增 case 的 20%（建议值），阻断项相关的 case 全部复核。
- **持续**：每次 release 后，D5 人工判定结果抽 10%（建议值）由第二人复判；复判不一致时，修 rubric 或补正反锚点。

**D5 二元 rubric**（每条判是或否，全部为“是”才通过）：

| 条目 | 级别 | 判定问题 | 正例锚点 | 反例锚点 |
| --- | --- | --- | --- | --- |
| R1 可区分 | P1 | 读取失败、无匹配、可见范围内无资产、上游未提供、暂无该项信息、暂时无法确认，用户能否分辨？ | 筛选读取失败显示“本次未能取得筛选结果，可重试”；补充信息整组没有显示“暂无该项信息” | 读取失败显示“无符合条件的资产”；L1 缺失显示为空白 |
| R2 不泄露 | P0 | 拒绝说明是否不透露资产是否存在，且企业端、监管端没有出现只供运营的信息？ | 访问他企业资产与不存在的编号，都显示“无权查看或资产不存在” | 显示“该资产属于其他企业”；企业端看到“上游已撤销确权” |
| R3 原因完整 | P1 | 不能发起时，是否列出了全部当前原因，且使用当前回款结果与 C2 补充规则？ | 非 USD 且缺 L1：同时列出两个原因；C2 场景说明金额与上游未结清依据不一致、不可发起（语义锚点，具体文案待审校） | 只列一个原因；先逾期后结清同时列“已逾期”“已结清”；C2 只展示未到期而没有拦截原因，或误称上游已结清 |
| R4 双语一致 | P1 | 中英文的字段名、状态值、原因说明含义一致，上游原文不翻译？ | 英文界面状态为 Overdue，企业名称按上游中英文分别展示 | 英文界面状态仍为“已逾期”；标的物名称被翻译 |
| R5 名称与地址呈现 | P1 | 名称缩略保留开头与结尾并可查看完整名称；地址缩写保留大小写，复制得到完整地址？ | 超长债务人名称首尾保留，悬停或展开可看全名 | 只保留开头；复制得到缩写地址 |
| R6 回款经过如实 | P1 | 当前回款状态只有一个，曾逾期、信息不一致等事实在回款进度中说明？ | 先逾期后结清：状态为已结清，回款进度写明曾逾期 | 同时展示“已结清”“已逾期”两个当前状态 |

R5 中缩略的具体位数与交互形态由设计确定，本 rubric 只判是否保留首尾、能否看全名、是否保留大小写。

英文界面中债权人名称取中文注册名还是英文名称，原型阶段已提出待 PRD 定口径（WS-508 设计评论）。本 Eval 按 01 册 5.5 现行口径判定 R4；PRD 口径变化后，按第 5 节版本管理更新锚点。

**人机对齐（LLM-as-judge）。** 启动阶段不使用 LLM-as-judge。之后如果 D5 画面数量（中英文 × 四类列表 × 状态与异常）超出人工承受范围，可以引入 LLM 只做 R1、R4 的批量初筛，条件如下：

- 先用人工已判定的 case 建立校准集，校准集与日常评测集隔离，不用于调提示词以外的任何用途；
- 在校准集上，LLM 与人工判定的一致率达到约定门槛（**建议 95% 以上，待确认**），才能启用；
- 启用后，LLM 判为不通过的 case 一律转人工；LLM 判为通过的 case，人工抽 10% 复核；
- LLM 不参与任何阻断项的判定，也不参与 R2。

目前没有任何样本，所以**不声称 judge 已可靠**。

## 5. 跑评频率

| 层级与节奏 | 触发条件 | 范围 | 责任 | 产物 |

| --- | --- | --- |

| 材料打开失败率 | 材料查看或下载失败次数 ÷ 材料查看或下载次数 | 材料存储与上游文件可用性 |

关于 L3 指标：

- 比例指标按 Wilson 区间报告；
- 告警阈值与观察周期**待业务确认**；
- L3 的任何数值都不得反过来改写离线 case 的判定结果；
- L3 用真实流量统计，与第 2 节加重后的风险覆盖集分开解读。

**失败回流。** 来源有五类：线上工单、L3 异常、运营在审核中发现的资产信息或状态问题、安全告警、外部变化探索中发现的问题。处理流程：

1. 测试在约定时限内（**建议 3 个工作日，待确认**）脱敏并复现，确认属于 M2 行为问题，而不是上游数据本身错误；
2. 写成 case，放入“历史失败”类别，标注“真实”及来源编号，与合成 case 区分；
3. 涉及 B 类的问题，同时补一条绕过界面的变体；涉及回款状态的，同时补进决策表；
4. 确认是 PRD 规则缺口而不是实现缺陷时，交 PRD 负责人处理；本 Eval 不改 PRD。
