**本轮边界来源。** 业务方 11-06 评论 `84e664de-5d27-4737-91d3-cd90bbbff3af` 要求只处理本 issue 的 M2；PRD 在 `9c13023` 落地，影响核验评论为 `652728ff-f64a-4ce1-b928-2451f9487da0`。本 Eval 按 C6 同步，旧 EV-D1-06、EV-D2-06 的预期归档到 `d1a8680`，不能用于本版判定。

**产品规则状态。** 最新 PRD 第 10 节无待确认产品事项；本次覆盖的业务预期均按上述规则确定。评估规模、发布门槛、人工抽样比例、联调环境与执行排期仍是第 3～5 节的建议或执行依赖，不冒称业务方已经批准，也不据此把产品规则改回待确认。金额预警的具体视觉承载由设计负责；数据获取机制与响应协议由研发负责。
本模块自身不发送消息，所以没有 03 册（01 册开头已写明）；本 Eval 不另设消息维度，但对 AC-AS-44 保留“不触发消息”的负向检查。PRD 更新后，本 Eval 按第 5 节的“版本管理”同步。

**评估范围。** 本模块展示上游资产可信平台已确权的应收账款，并决定资产能否发起发行申请。规则确定，不含模型生成内容，所以本 Eval 回答的问题是：**本模块交付后的产品表现，是否达到 PRD 的成功标准**，不评模型能力。具体包括五点：

- 每个角色是否只看到自己范围内的资产与企业；
- 确权、回款、发行三个状态是否判得对，尤其是到期兜底与“暂时无法确认”；
- “申请发行”入口与提交是否只对满足全部条件的资产开放，一笔资产是否只有一笔申请；
- 展示的资产信息是否与上游一致、分级是否正确、是否只读；
- 用户能否查找到资产，并看懂当前状态和不能发起的原因。

与 04 册的分工：04 册是逐条验收标准，测试用例与执行步骤由测试小队编写。本 Eval 在 04 册之上做三件事：

1. 按风险把验收归入维度，并划出阻断项；
2. 规定 case 的组织方式与通过线；
3. 规定标注、跑评节奏、失败回流与版本管理。

本 Eval 不替代测试用例。

**不在范围内：**

- 发行模块内部的机构选择或分配、申请处理、驳回主体、发行执行及其他模块的代币业务：本 Eval 只检查 M2 带入固定资产、返回原来源、完整值承接、当前申请结果与机构关联的只读展示，以及资产发行状态对返回结果的消费；不设计、修改或执行这些外部流程。
- M1 的身份判定（已认证 / 未认证 / 游客）：本模块直接使用 M1 的判定结果，判定本身见 [M1 Eval](../../面客端/M1-企业登录与企业账户/企业登录与企业账户-Eval.md)；
- 上游平台自身数据的正确性，以及与上游的同步时效（01 册第 10 节写明“本册不设时效要求”）；
- 铸造数量换算、代币符号、合约精度与接口实现方式不属于 M2；视觉与布局由 Hallmark 设计负责。

**判定方式用语：**

- **code-based**：自动化断言，包括接口响应、页面状态、数据库记录、响应体敏感字段扫描、文案字符串比对；
- **human**：人工按二元 rubric 判定；
- **LLM-as-judge**：本模块不用于任何阻断判定，只在第 4 节写明的条件下，作为文案批量初筛的辅助。

### D1 访问范围与数据隔离

| 项 | 内容 |
| --- | --- |
| 定义 | 每个角色只能看到 PRD 允许的资产与企业信息。拒绝由平台判定，不靠隐藏入口；拒绝时的说明不透露资产是否存在 |
| 需求来源 | 01 册 5.1 无权查看、3.1 资产来源（只看本企业作为债权人的资产）、3.3 / 3.4（只供运营）、8.4（上游变更提示与金额预警只在运营端）、第 9 节（监管机构只看关联资产）、5.6（筛选在原可见范围内进行）；02 册图 6。对应验收 AC-AS-02、18、19、34，以及 AC-AS-31、33、37、40、44 中与可见范围有关的部分 |
| 通过条件 | 按角色分：<br>• 游客：看不到可信资产入口，直接访问不返回任何资产信息；<br>• 未认证企业用户：看得到入口，只看到认证引导，列表与详情接口都不返回资产数据；<br>• 已认证企业用户：只看到本企业作为债权人的资产，包括已驳回、已发行的资产；<br>• 监管机构：只看到发行模块当前机构关联结果包含本机构的资产，关联如何建立不由 M2 定义；申请当前结果为处理中、已驳回或已发行时均使用当前关联结果判定，监管在 M2 无审核、驳回或其他处理操作；看不到企业列表、企业详情、企业用户信息、数币账户、上游变更提示和金额关系预警；<br>• 运营：可看全平台企业、资产、唯一当前登录地址、变更提示与金额关系预警。<br>另外：访问范围外的资产与访问不存在的资产，说明完全相同，都是“无权查看或资产不存在”；筛选（包括币种选项）只在原可见范围内取值 |
| 失败条件 | 任一情况即失败：<br>• 被拒绝的请求返回了任何资产或企业字段，包括列表条数、资产编号、名称、金额；<br>• 只隐藏了入口，直接 URL 或接口能拿到数据；<br>• “无权查看”与“不存在”的说明、状态码或响应结构可区分；<br>• 通过构造筛选参数拿到范围外的资产，或币种选项暴露了范围外资产使用的币种；<br>• 企业端、监管端出现企业用户信息、数币账户、“上游已撤销确权 / 上游已删除”提示或金额预警标记 / 说明 |
| 失败后果 | 他企业应收账款、债务人与交易数据泄露；属于合规与安全事故 |
| 判定方式 | code-based：按“角色 × 资源 × 访问方式（入口 / 直接 URL / 接口）”做矩阵断言，对响应体做字段扫描；“无权”与“不存在”的说明及业务响应字段比对（请求 ID / 时间戳等非业务字段除外）。阻断项由安全角色复核 |

### D2 资产状态判定正确性

| 项 | 内容 |
| --- | --- |
| 定义 | 确权、回款、发行三个状态按 PRD 取值并按规则变化：回款状态按归并表判定，到期兜底按上游带时区的到期时点触发；发行状态只消费发行模块返回的结果、只向前、不回退；关联申请编号、当前状态与有值的已关联机构只读展示，不解释内部流程或推断驳回主体 |
| 需求来源 | 01 册 F-AS-02：4.1 状态字段一览、4.2 确权状态、4.3 结清与逾期依据与回款状态归并、4.4 发行状态与关联申请当前结果展示、5.3 上游暂时不可用、5.5 时区不改变判断；02 册图 2、图 4。对应验收 AC-AS-10、11、12、14、15、16、17、20、36、44 |
| 通过条件 | 以下全部满足：<br>① 回款状态严格按 4.3 归并表从上到下判定，已结清优先；列表与详情使用同一结果；<br>② 到达到期时点、仍未取得上游最新状态时，自动变为已逾期；到期时点本身已属于到期；上游暂时不可用时仍执行；之后以上游新状态为准；<br>③ 结清依据取不到、依据缺失或与到期兜底冲突时，判为“暂时无法确认”，单独展示、单独可筛选，不归入三个正常取值，也不按回款金额或余额自行认定结清；<br>④ 先逾期后结清：当前为已结清，回款进度说明曾逾期，只出现在“已结清”筛选结果中；<br>⑤ 是否到期只看上游时点，切换查看者时区不改变任何状态；<br>⑥ 发行状态只按 可发行 → 发行申请中 → 已驳回 / 已发行 变化；上游撤销确权、删除，结清逾期变化，代币的监管、融资、销毁状态，都不改变发行状态；<br>⑦ 发行模块返回申请已提交 / 处理中时，资产为发行申请中；返回已驳回时为已驳回，返回已发行及代币编号时为已发行；合法访问者看到其权限内的申请编号与当前结果，不做内部阶段映射或推断主体；运营只读显示有值的已关联监管机构，无值不补造；监管可见范围仅消费当前关联结果；<br>⑧ 金额关系异常按 C2 保留上游原值，不因此改判已结清、暂时无法确认或改变发行状态；上游状态依据本身缺失、时点冲突仍按 4.3 归并并限制发起，两类情况分开判定 |
| 失败条件 | 任一情况即失败：<br>• 已过到期时点仍显示“未到期”，包括上游不可用期间；<br>• 未知状态显示为“未到期”，或按回款金额自行判为已结清；<br>• 到期兜底后覆盖了上游新回传的事实；<br>• 先逾期后结清的资产出现在“已逾期”筛选结果中，或并列展示两个当前回款状态；<br>• 切换时区改变了回款状态或能否发起；<br>• 发行状态回退，或终态（已驳回、已发行）再变化；<br>• 发行状态被上游变更或代币状态推动；<br>• M2 自行映射内部阶段、推断驳回主体，或展示的申请编号 / 当前结果 / 有值机构与发行模块返回结果不符 |
| 失败后果 | 已逾期或已结清的资产被当作可发行资产发行代币，形成没有足额底层资产的代币；或正常资产被拦下；属于业务与资产风险 |

### D3 发起条件与申请唯一性

| 项 | 内容 |
| --- | --- |
| 定义 | 只有同时满足 7.1 全部六个条件的已接收资产，才提供“申请发行”入口、才能提交成功；提交时按最新信息重新判断六个条件，金额关系不参与校验；一笔资产任何时候最多只有一笔发行申请；不满足时在详情中列出全部当前原因 |
| 需求来源 | 01 册 F-AS-04：7.1 发起条件、7.2 发起与结果、7.3 重复发起与条件变化；5.2 上游信息缺失；3.2 补充信息不影响发起；8.4（撤销确权后不能发起）；02 册图 5。对应验收 AC-AS-05、06、25、26、27、28、29、41、44，以及 AC-AS-15 场景三、AC-AS-17、AC-AS-33 场景三、AC-AS-37 中“按可发行或未到期筛选不等于都能发起”的部分 |

## 3. 通过线

本模块是确定性规则，同一输入的结果固定，所以规则类维度的通过线贴近 100%，并不是照搬 99% 一类的经验值。另外两点：缺陷修复成本低，而一旦失败可能让不合格资产发行代币、一笔资产重复融资或数据越权，且不可逆。

下表数值除已标注“PRD 确定”或“业务方确认”的以外，都是**建议、待业务与测试确认**。

**单例判定。** 一条 case 只有在两个条件同时满足时才算通过：

- “预期行为”全部满足；
- “禁止行为”一项都没有出现。

一条验收写了多个场景时，拆成的每条原子 case 都通过，才算该验收通过。这与 04 册的读法一致。

**指标口径：**

- 维度通过率 = 本轮该维度判定为通过的 case 数 ÷ 本轮该维度有效执行的 case 数。
- **排除规则**：因环境故障而无法判定的 case 标为“无效”，比如上游 mock 宕机、上游测试环境不可用（不是 case 有意模拟的不可用）、发行结果接口或机构关联结果的测试替身不可用。无效 case 不计入分母，必须重跑。一轮中无效 case 超过 5%（建议值）时，整轮作废。
- **不能排除的情况**：产品行为错误不得标为无效，比如上游不可用期间未执行到期兜底。
- **切片**：每个维度分两个切片单独统计，不合并。“模拟环境”切片用上游 mock 与时间 mock；“真实联调”切片接上游平台测试环境与发行模块实际提供的结果边界；只验证 M2 对结果的消费，不执行外部机构分配、申请处理或发行执行流程。

**发布门槛：**

- 一条 case 涉及多个级别时，按其中最高的级别计。
- 判不准时就高不就低，由产品负责人仲裁。
- 每条 case 的最终级别由测试负责人在启动集评审时标注，产品负责人确认。

**随机性控制：**

- 依赖真实时序的 case，如并发提交、上游不可用跨过到期时点、提交前上游状态变化，每轮重复执行 3 次。P0 case 须 3 次全部通过，任何一次失败都按失败处理，直到查明原因。
- 到期兜底类 case 一律用时间 mock 固定“当前时点”，不依赖执行时的真实时间。
- 不稳定的 case，只有在证明是环境问题后才能标为无效。

**统计与不确定性：**

- 规则类 case 不计算置信区间，逐条看是否失败。
- 小样本零失败不等于低风险。例如某个切片 50 条 0 失败，按 Wilson 方法计算的 95% 区间上界约为 7%，这是公式算出的说明值，不是评测结果。所以阻断项靠“每条 case 0 失败 + 绕过界面的变体 + 决策表全量组合”来覆盖，不靠通过率。
- D5 人工评分与 L3 线上比例指标，用 Wilson 区间报告。
- 版本比较只对规则未变化且输入相同的 case 作逐条配对；规则变化的 case 单列新旧预期，不把改判当作实现回归或提升。
- 本文没有任何执行数据，不填写任何分数或区间。

**失败兜底**（PRD 已确定，Eval 核对兜底是否存在）：

- 上游暂时不可用时，展示最近一次保存的信息，并继续执行到期兜底；
- 必要状态依据缺失或到期判断冲突时，判为暂时无法确认、不能发起；单纯金额关系异常不适用此兜底；
- 提交时按最新信息重新判断，不满足时不能提交；
- 材料无法打开时，可以重试，不影响其他信息；
- 筛选读取失败时，保留条件，可以重试；
- 上游删除资产时，保留最近一次保存的信息。

C2 的非阻断兜底：不校验金额关系、不改写源值，仅运营列表预警 / 详情说明；其他六条件仍严格校验。C3 逐笔拒收非汽车贸易资产、不影响同批合格项，不能以隐藏或禁止申请代替拒收。

每条兜底至少对应 1 条 case。发布后如果出现阻断项，按第 5 节回流：先止血，再补 case。止血手段（例如暂停全部“申请发行”入口）**待业务确认**。

## 4. 标注方法

本模块大部分 case 由自动化断言判定。人工标注主要用在三处：

- 定义预期结果，把 PRD 转成可断言的期望，尤其是回款状态决策表每个组合的期望值；
- D5 呈现类判定，以及 D3 不能发起原因的完整性；
- 阻断项复核。

**角色：**

| 角色 | 职责 |
| --- | --- |
| 产品（PRD 负责人） | rubric 与预期结果的最终解释人；PRD 有歧义时负责仲裁，必要时回到 PRD 流程修订。本 Eval 不改 PRD |
| 测试负责人 | 把验收拆成 case，标注 P0 / P1 / P2，维护 AC↔case 映射与决策表，执行判定 |
| 安全复核 | 复核 B1、B2、B8 相关的 case 与结果 |
| 业务复核（运营代表） | 复核 B9（行业拒收）、B4～B7 相关 case 的期望值，确认不合格资产与状态推动的判定符合业务核对实际 |

**分阶段：**

- **启动**：产品与测试负责人对 120 条启动 case 逐条共同标注预期行为与禁止行为；回款状态决策表的期望值由产品逐行签认。D5 的 18 条 case 与 D3 的原因说明类 case，由产品与审校各自独立按 rubric 判定，分歧交产品负责人仲裁，仲裁理由写入 case 备注。
- **扩展**：新增 case 由测试负责人起草。产品抽查新增 case 的 20%（建议值），阻断项相关的 case 全部复核。
- **持续**：每次 release 后，D5 人工判定结果抽 10%（建议值）由第二人复判；复判不一致时，修 rubric 或补正反锚点。

**D5 二元 rubric**（每条判是或否，全部为“是”才通过）：

| 条目 | 级别 | 判定问题 | 正例锚点 | 反例锚点 |
| --- | --- | --- | --- | --- |
| R1 可区分 | P1 | 读取失败、无匹配、可见范围内无资产、上游未提供、暂无该项信息、暂时无法确认，用户能否分辨？ | 筛选读取失败显示“本次未能取得筛选结果，可重试”；补充信息整组没有显示“暂无该项信息” | 读取失败显示“无符合条件的资产”；L1 缺失显示为空白 |

| R5 名称与地址呈现 | P1 | 名称缩略保留开头与结尾并可查看完整名称；地址缩写保留大小写，复制得到完整地址？ | 超长债务人名称首尾保留，悬停或展开可看全名 | 只保留开头；复制得到缩写地址 |

## 5. 跑评频率

**分层节奏。** 以下都是建议节奏，只描述触发条件、责任与产物，不接入任何自动化。

| 层级与节奏 | 触发条件 | 范围 | 责任 | 产物 |
| --- | --- | --- | --- | --- |
| L1 确定性检查，每次 commit | M2 相关代码、上游对接或发行模块返回结果 / 机构关联的消费逻辑有改动 | 可在 mock 下快速判定的 code-based case：回款状态决策表全量；C2 金额异常不阻断与状态条件阻断的对照、提交前仅金额变化；C3 同批逐笔行业接收边界；唯一账户、金额截断与完整交接值；发起条件单项与组合；权限矩阵中的接口直连；“无权”与“不存在”响应比对；只入库字段与证件号码扫描；写接口拒绝；筛选匹配规则 | 研发 | 通过 / 失败清单；B 类失败直接阻止合入（建议） |

**L3 线上业务验证**（上线后，**只观察，不作为发布门槛**）。目的是区分“离线 case 全部通过”与“真实资产数据下确实判得对、用得顺”。

| 指标 | 口径（分子 ÷ 分母） | 用途 |
| --- | --- | --- |

关于 L3 指标：

- 比例指标按 Wilson 区间报告；
- 告警阈值与观察周期**待业务确认**；
- L3 的任何数值都不得反过来改写离线 case 的判定结果；
- L3 用真实流量统计，与第 2 节加重后的风险覆盖集分开解读。

**失败回流。** 来源有五类：线上工单、L3 异常、运营在业务核对中发现的资产信息或状态问题、安全告警、外部变化探索中发现的问题。处理流程：

1. 测试在约定时限内（**建议 3 个工作日，待确认**）脱敏并复现，确认属于 M2 行为问题，而不是上游数据本身错误；
2. 写成 case，放入“历史失败”类别，标注“真实”及来源编号，与合成 case 区分；
3. 涉及 B 类的问题，同时补一条绕过界面的变体；涉及回款状态的，同时补进决策表；
4. 确认是 PRD 规则缺口而不是实现缺陷时，交 PRD 负责人处理；本 Eval 不改 PRD。
