## 00. v1.5 —— 全局操作按钮对资产方常驻

### 00.1 问题是什么

需求方截图里那句"当前身份对本项目没有可用的全局操作"，出现在 **`FP-20260705-0018`（珠三角家电，明泰家电所有）** 上——它**不是本方项目**，`own === false`，所以服务端归属过滤（`AC-LS-06`）本来就不返回这三个动作。真正错的是**那句文案**：它写得像"按环节禁掉了"，让人误以为融资中就不能操作。

但顺着查下去确实有一个真问题：`availableActions()` 里三件全局操作被 `live`（`S-FP-1`～`S-FP-4`）整体包住，**项目一进终态（`S-FP-5 已关闭` / `S-FP-6 已结清`）整段就没了**——而终态恰恰是「提取已释放代币」最需要用的时候。

### 00.2 改了什么

| 场景 | v1.4 | v1.5 |
| --- | --- | --- |
| 本方项目 · 募集中 / 已报价 / 放款中 / 还款中 | 三件都在（其中解除质押可能被判定为 ⊘） | **三件都在且可点** |
| 本方项目 · **终态**（已关闭 / 已结清） | **整段消失** | 追加质押 ⊘ + 原因、关闭项目 ⊘ + 原因、**解除质押仍可用且为主操作** |
| 本方项目 · 解除质押上限为 0 | 按钮 ⊘，把入口藏在原因后面 | **按钮常在可点**，弹窗里给出可撤回上限、它怎么算出来的、为什么是 0、两条出路 |
| 本方项目 · 有存量业务时关闭 | 按钮 ⊘ | **按钮常在可点**，弹窗里给出具体原因 + 项目在途金额 / 项目融资余额 / 项目状态三个数，「确认关闭」不可提交 |
| **他方**企业主体的项目 | "当前身份对本项目没有可用的全局操作" | 讲清归属：「本项目属于另一个企业主体（XX）。追加质押、解除质押、关闭项目属于本方数据，按企业主体在服务端过滤（`AC-LS-06`）」 |
| 游客 | 只有「立即登录」 | 不变 |
| 资金方 | 本模块内只读 | 不变 |

**判定条款一条没动**：`D-FIN-48`（追加在 `S-FP-1`～`S-FP-4` 任何状态下都允许）、`AC-FIN-13` 视角 C / `INV-FIN-01`（可撤回上限 ＝ 可融金额 ÷ 质押率）、6.1（在途占用 / 未偿余额的关闭判定）、`D-FIN-57`（两段式释放）全部原样。变的只是**入口可见性**与**拒绝时的反馈形态**——从"把入口藏起来让用户猜"改成"入口常在 + 提交时权威判定 + 给出具体原因与当前数值"。

按钮上还常驻一行副文案，把量直接摆出来：非终态时是「本池当前可撤回上限 245,000.00 USD（＝可融金额 ÷ 80%）。已失效代币不受此限制。」

### 00.3 「除非项目失效」怎么落的

需求方原话是"除非项目失效"。按字面把终态的全局操作区整块拿掉会出事——`D-FIN-57` 的两段式里，**业务释放是即时的，链上提取由资产方自助发起、无时间限制**，未提取的代币还留在合约里。整块拿掉等于把资产方取回自己代币的唯一入口也拿掉了。

所以终态的形态是：**整区保留，逐项区分**。

- 追加质押 → `⊘` + 「项目已是终态（已结清），池内质押已全部释放，不能再追加。」
- 关闭项目 → `⊘` + 「项目已是终态（已结清）。」
- **解除质押 → 可用，且升为主操作**（终态下它是这一区唯一还能做的事）。
- 段末一整段说明承载两个 ⊘ 的共同理由 + 提取为什么还在：「业务释放在关闭 / 结清的同一时刻已完成，但代币仍停留在质押合约内，需您自行发起提取并自付 gas，**无时间限制、不过期**（`D-FIN-57`）。」

⚠️ **注意区分两种"失效"**：需求因覆盖不足**自动失效**（`AC-FIN-26`，对外状态落 `已失效／已关闭`）**不是项目终态**——项目仍是 `S-FP-2 募集中`，全局三件照常全在。原型里 `FP-20260416-0007` 就是这个样本。

### 00.4 补了一个终态样本

`REDEEMABLE` 里那 3 张「项目结清释放」的代币本来就写着 `from:'FP-20251103-0021'`，但这个项目此前**没有在 `PROJECTS` 里出现过**，导致终态下的全局操作区根本无从评审。

本轮补上 **`FP-20251103-0021` 华中冷链应收账款池（`S-FP-6` 已结清，晟远科技所有，池内 0 张）**，事件流从建池一路走到结清释放。它同时也是广场列表上「已放款」对外状态与终态详情页的样本。**只加了一条演示数据，没有改任何判定。**

### 00.5 终态下顺带修的三处文案

都是新样本暴露出来的、原来没人走到过的分支：

1. **质押代币清单的空态**原来写「创建时那笔质押最终链上失败，可重新质押后再发布」——那是空池草稿的话。终态改成「本池已空：质押在项目关闭 / 结清的同一时刻已全额业务释放。仍待链上提取的代币在「解除质押」弹窗内列出（`D-FIN-57`）。」
2. **统计区第 1 格**在 0 张时不再写「池内代币全部有效」，改「池内已无代币」。
3. **解除质押弹窗**在池子已空时不再讲"可撤回上限"（对空池没有意义），改成讲代币现在在哪、怎么拿回来。

### 00.6 一处请 PRD 补口径

**三档质押覆盖状态在终态项目上没有受众。** 按 `D-LS-17` 的判据，一个已结清、池内为空的项目会落在**「覆盖持平」**（`INV-FIN-01` 成立且可融金额 = 0）——判据上完全正确，但它的配套提示块写的是「追加质押可抬高融资上限并重新打开额度」，而终态下根本不能追加。

本轮处理：**pill 保留**（`FP-20-` 是派生字段，`D-FIN-56` 要求广场公开），**终态下不再渲染那段提示块**。判据、字段、pill 一个都没动。

**建议 PRD 在 5.3.1 补一句终态下的呈现口径**——是继续按判据显示、还是终态不适用。在那之前原型按上面这样处理。

## 0. v1.4 —— 五条（版式与信息取舍）

业务口径零变更，只动版式与信息取舍。两处"挪走/删掉时容易把定稿条款一起做没"的地方，处理方式写在各条里。

### 0.1 列表页「融资需求状态」列只留状态本身

去掉了状态 pill 下面四类副行：**锁定倒计时**（被谁锁定 · 已 N · 剩余 N）、**业务进度**（待放款 / 待放款确认）、**还款进度**（已还 X / 共 N 期）、**逾期天数**。`lockLine()` 与 `finLine()` 两个函数已整体删除。

**保留下来的两样，各有硬条款撑着：**

- **「已到期」** 改成与状态并列的第二个 pill，不是副行。L2 融资需求摘要把"已到期标记"列为必备字段（6.5.2），`D-FIN-43` 分支②/`D-FIN-47` 要求它按正常状态中性呈现。它是项目级并行标记，属于"状态本身"。
- **「已失效／已关闭」下面那行终结原因** 保留。`AC-LS-95` 原文：该标签**旁与详情页必须能看到终结原因**（自动失效 / 资产方撤下 / 项目关闭 / 业务终止），**不得只给一个合并标签**。删了就违规。

**状态取值同时换成了「融资需求对外状态」五值**，不再显示内部 `S-FP-*` 的档位名——见 §0.4 第 1 条。

### 0.2 详情页右栏只放操作项，锁定信息挪到左栏第一张卡

右栏现在只有一张「操作」卡（三段式）+ 深链说明。锁定信息整块搬到**质押代币清单上方**，成为左栏第一张卡。

**内容一项没减**（WS-325 `D-LS-20` / `AC-LS-97` 的四件事 + 两条出路）：

| 要求 | 落点 |
| --- | --- |
| 被谁锁定 | 左列第 1 行（机构企业主体全称） |
| 从什么时候开始 | 左列第 2 行「锁定起算」（报价提交时间 + 时区） |
| 已锁定多久 | 左列第 3 行 |
| **还剩多久** | 右列大号倒计时，小时级；不足 24 小时切分钟并转 warn 档 |
| 到期时刻 | 左列第 4 行 |
| 两条出路 | 右列底部 ①② 两行 |
| 「已锁定 + 剩余 ≡ 168 小时」可在屏幕上直接核 | 右列进度条下的刻度行 |

搬到宽栏后改用 `.ls-lock.wide` 的两列排布（左列事实、右列倒计时与出路），窄于 1180px 自动堆叠回单列。

### 0.3 在途报价与报价历史改列表，放在融资信息清单下方

原来是「键值块 + 时间线」两种形态混排，现在是**一张表、一行一笔报价**，在途与历史同表、用状态列区分，和「融资信息清单」用同一套表格语言。七列：融资业务编号 / 报价机构 / 报价金额 / 年化利率 / 结算币种与金额 / 报价提交时间 / 状态。

状态列承载终结方式与原因（`AC-LS-96` 的口径不变）：在途给「在途 · 剩余 N」+ 到期时刻；已拒绝给拒绝原因（对报价机构可见）；已失效给失效原因 + "系统事件，无原因可填"。

**倒计时不在这张表里重复**——它整块在左栏第一张「锁定信息」卡上，四项齐全。

### 0.4 按最新 PRD 复核（远端 `cly-V1.0.0`）

复核基线：WS-324 PRD **V9.0**（`1f67971`）+ WS-325 PRD **V5.0**（`1cef278`）。三处跟着改了：

1. **列表页的状态与筛选改用「融资需求对外状态」五值。** `AC-LS-93` 要求同一笔需求在**广场列表**、融资信息清单、我的控制台三处读到的对外状态一致，且**前端不得用 `S-FP-*`/`S-FD-*` 自行拼装**；WS-325 分册 6.4.1 ③ 进一步要求筛选按五值过滤、**不自建"可报价 / 已被锁定"这类第二套展示状态**。v1.3 的「项目状态（S-FP-\*）」与「是否可报价」两个筛选正好是被点名的那一套，**已删除**，合并成一个「融资需求状态」筛选。
2. **列表页未登录时只出「立即登录」。** WS-325 `D-LS-21`：卡片上的报价入口未登录时只出登录按钮，不再逐动作 `⊘`。已登录的四种不可点情形仍各给各的原因（`AC-LS-98`）。
3. **`⊘ 报价` 的短原因不再写内部状态名。** v1.3 里它会写成"融资中"这类 `S-FP-*` 档位名，现在改成该需求的对外状态（`AC-LS-93`）。

### 0.5 页头右上角「融资需求金额 + 有效期至」整块删除

金额与统计区第 3 格「融资需求」是同一个数，确实重复。

**有效期没有跟着一起丢。** `D-FIN-37`（有效期 = 首次发布日 + 1 年，系统生成、只读、不可编辑、不可延期）是定稿条款，`D-MC-107` 的结论也落在它身上；L2 融资需求摘要把"有效期至"列为必备字段。删掉那块之后，pill 行上只剩「有效期剩余 N 天」这个**相对**倒计时，绝对日期会没有落点。

处理：**绝对日期挪进页头 kick 行**，和发布日并列——`融资项目 · 发布于 2026-08-14 · 有效期至 2027-08-14 ［首次发布日 + 1 年 · 只读］ · 编号 … · UTC+8`。方括号里那条小注是虚线框的只读标记，把 `D-FIN-37` 的口径直接写在日期旁边。`AC-LS-02`「界面不得出现有效期输入框、日期选择器或修改入口」不受影响——它仍然是纯文本。

**为什么不加成第 6 个统计格**：`AC-LS-84` 明写统计区只呈现那 5 个数，加第 6 个就违规。

### 0.6 顺带修掉的两处视觉问题

- **统计区长数值被省略号截断**（`1,000,000.00 U…`）。币种改成小一号的 `<span class="cy">`，数值字号 clamp 上限从 30px 降到 27px，1280～1920 全区间不再截断（脚本断言：`scrollWidth > clientWidth` 的统计值个数 = 0）。

## 1. `D-LS-17` 质押覆盖状态 —— 按 PRD V9.0 的定稿走

**本轮开工时 `D-LS-17` 还是 PRD V8.0 里的唯一开放项，等设计师给标签。写到一半 PRD V9.0 落库（`1f67971`），需求分析师已经把它定稿了，并在分册 7.6 明确「这组是 PRD 术语，设计师按本 PRD 的标签走」。所以原型采用 PRD 的定稿，不用我自己那版。**

| | V8.0 旧名 | **V9.0 定稿（原型已采用）** |
| --- | --- | --- |
| 字段名 `FP-20` | 担保状态档位 | **Pledge coverage status ／ 质押覆盖状态** |
| 档位 ① | 正常 | **Ample ／ 覆盖有余** |
| 档位 ② | 额度用尽 | **At Capacity ／ 覆盖持平** |
| 档位 ③ | 担保不足预警 | **Insufficient ／ 覆盖不足** |
| 缺口 `FP-21` | 担保缺口 | **Coverage gap ／ 覆盖缺口** |
| 提醒 | 担保不足预警 | **Insufficient-coverage notice ／ 覆盖不足提醒** |

**判据一字未动**：③ 仍是「融资上限 < 项目融资余额」，② 仍是「可融金额 = 0 且 ① 成立」。原型里旧词根**零残留**（脚本断言：中英两个视图下全页 0 处「担保 / 抵押覆盖 / 不足预警 / 额度用尽」）。

**如实回报我原来的提案与差异**，供需求方判断是否还要调整：我给的是 **Collateral coverage ／ 抵押覆盖**，三档 `Sufficient 覆盖充足` / `Fully drawn 额度已用尽` / `Undercollateralised 覆盖不足`。两版**在同一个方向上**——都用「覆盖」做词根、都拒绝了 LTV 与 Health factor、都把「预警」降级。三处实质差异：

1. **`Pledge coverage` vs `Collateral coverage`。** PRD 用「质押」限定，和 `质押率`、`质押代币价值` 同族，模块内自洽性更好；我用 `Collateral` 是跟保理 / ABS 里 *collateral coverage ratio* 的现成叫法靠。两者都成立，**PRD 那版在本仓库内部更一致，采用它是对的**。
2. **档② `At Capacity` vs `Fully drawn`。** `At Capacity` 与另外两档同词根、可平行阅读，这是 PRD 的理由；`drawn / undrawn` 是授信业务里讲额度动用的现成说法，更直接说明「讲的是额度不是覆盖」。**这一处我仍然略偏好 `Fully drawn`**，但差别小于"平行阅读"的收益，按 PRD 走。
3. **档① `Ample` vs `Sufficient`。** `Ample`（有余）比 `Sufficient`（够）多一层"还有富余"的意思，正好对上判据里的「可融金额 > 0」——**PRD 这处比我准**。

**一处需要需求方注意的措辞风险**：`At Capacity` 在英文里既可读成"满负荷（正常）"也可读成"到顶了（受限）"，而档②恰恰是**不能再借**。原型已在统计区与提示块里用整句消歧（"There is 0.00 USD left to borrow, so no new commitment can be taken on… this is not an insufficient-coverage notice"），但如果将来要做纯标签的紧凑视图（比如通知列表），建议给它配一句固定副文案。

**本轮顺手修掉的一个真 bug（v1.2 起就在）**：公共 `shell.js` 的 `data-act` 事件委托**只挂在 `click` 上**，所以本模块此前所有 `<select>` 与 `<input>` 上的 `data-act` 从来没生效过——筛选下拉、项目名、需求金额三处输入实际是死的。WS-325 / 326 / 327 三个模块各自补过一段 `input` 委托，本模块漏了。现在按同样写法补上（只挂 `input`，不挂 `change`：按钮点击引起的 blur 会在同一拍里触发第二次重渲，把正在处理的节点换掉）。

## 8. 假设与遗留

1. **默认英文已落地，但正文英文是设计师产出的，不是评审过的译文。** `G` 表里的术语按 §1 的理由选定；长段口径说明的英文由本轮一并写出，**建议在实现前过一次业务方 review**——尤其是 `outstanding financing` / `committed demand` / `available to borrow` 三个映射，它们对应的中文是 `D-FIN-06` 明确点名的红线术语。
2. **代币符号是占位。** 分册 7.5.1 明确 WS-318 的代币符号配置本期仍为「待确认」且**不自造**，所以清单里显示 `[TBC] ／［待确认］`。等 WS-318 定了取值直接换 `TOKEN_SYM` 一处。
3. **`P-LS-90` 是原型侧内部页，PRD 未定义此页**：只承载草稿续做与本方台账，**不是 WS-328 我的控制台**。号段取 90 段是为了避让 `P-LS-04/05/06`（WS-325）、`P-LS-07/08`（WS-326）、`P-LS-09/10`（WS-327）。
4. **四环节的当前环节由前端按状态推导**，真实实现必须改为取服务端返回的当前环节与 `available_actions`（`AC-LS-87` 明令前端不得自行推断）。原型里这是演示便利，代码注释已标。
5. gas 预估为虚构值；链上超时 30 分钟为 PRD 标注的假设值，均待开发确认。
6. **`AC-LS-27` 池快照**：原型自 v1.1 起已整块移除（含数据字段），PRD 主册 6.5.2 的条款仍在，两边不一致，待 PRD 侧作废。
7. **自动失效后摘要区显示什么，PRD 没写。** `FP-20260416-0007` 的第 2 笔需求已按 `AC-FIN-26` 标成 `Void / closed ／ 已失效／已关闭` + 原因 `自动失效 · 覆盖不足`，与"判定即失效"对齐；但页头摘要区仍显示 200,000.00 USD 的需求金额（它是最后一次发布的金额，不是一笔还能被报价的要约）。这会让人以为还能报价——**建议 PRD 补一句"需求终结后摘要区金额如何呈现"**，在那之前原型保持现状并靠状态标签消歧。

**数据诚实性**：全部业务数据为演示数据，企业名带「（演示）／(demo)」后缀，编号 / 金额 / 哈希均为虚构。派生量由事件流按 PRD 公式算出，可在每张图的数据表里逐时点核对。

## 13. v1.8 —— 质押审核：先审核、后上链（跟 PRD V9.4）

需求方 2026-09-17 裁定「代币质押增加运营管理端审核环节，审核通过才是质押成功」。**运营端的审核界面不在本模块**（在 WS-337），本轮只改面客侧这一边。

### 13.1 链路从一步拆成两步

| | v1.7（改之前） | v1.8（本轮） |
| --- | --- | --- |
| 建池首笔 | 勾代币 → 链上费用二次确认 → 唤起 SDK 签名 → 入池 | 勾代币 → **提交质押申请**（零 gas）→ 审核 → 通过后回来 → 链上费用二次确认 → 签名 → 入池 |
| 追加质押 | 同上 | 同上 |
| 撤回 / 提取 | 不变 | **不变**（`D-FIN-83`：撤回不走审核，`AC-FIN-13` 的算法闸门更严且即时） |

提交那一刻**不唤起 SDK、不发起链上转入、不产生 gas**；代币留在资产方自己的地址里。

### 13.2 六条必须体现的，分别落在哪

| 条款 | 落点 |

### 13.3 新增了什么

- **质押审核卡**（详情页左栏首位，仅本方资产方可见——申请是本方数据，按企业主体服务端过滤）：在途申请逐条铺开，已结论的收进「审核历史」折叠。
- **五个申请态**：`审核中` / `审核通过 · 待入池` / `已驳回` / `结论已失效` / `结论已作废`（入池前复核未通过），外加 `已撤回`（**只在结论作出之前**可撤，与 `PA-05` 一致）与 `已入池`。
- **驳回原因原样透传**（`AC-LS-99`）：不截断、不改写，附「重新提交」，重新提交生成**新的申请编号**。
- **代币占用标记**：被在途申请占用的代币在两处可质押清单里**可见但不可选**（⊘ + 占用它的申请编号），防同一张进两份申请。
- **我的融资项目**页状态列带出在途申请（含入池有效期剩余），空池草稿区分「首笔质押申请审核中」与「首笔质押链上失败」。
- **覆盖不足提醒**里补一句「追加质押需先经平台审核，提交后不立即生效」——`R-LS-13` 记的就是这条自救路径变慢，文案不能让人以为提交即生效。
- **深链** `?action=enter_pool`：审核通过通知（`financing.pledge.review_approved`）的落点，直接把入池确认开在详情页上；非本方主体只落页面、不开层。
- 详情页补上**链上结果落点**（此前只有创建页有），入池成功 / 失败 / 超时 / 复核作废四类结果都落在这里。

### 13.4 没有做的

审核队列、审核动作、结论回写、审核人权限（`C-RV-01`～`C-RV-06`）都在运营端 WS-337，本模块只消费结论。原型里「通过 / 驳回」由演示数据给定，入池前复核在入池确认弹窗内用**结果模拟下拉**走通两条分支——与既有的链上结果模拟同一套写法。
