**关于 `category` 七值的定义表：本 PRD 里没有，也不会有。**

| 项 | 规则 |
| --- | --- |
| 定义在哪 | **`docs/notification-contract/接入指南.md` 4.1**。`fs` 组**逐字复用资产端那一组七个取值**，不新造、不改拼写、不改语义边界 |
| 为什么不在这里抄一份 | 抄一份就是分叉。**新造一组会立刻制造「同一个字符串在两个端语义不同」的隐患**，而那正是 WS-304 允许各端独立取值空间时最担心的失败模式 |
| 为什么正好是那七个 | 金融服务端面客侧与资产端**是同一类主体（面客用户）在同一类场景下**的分类需求——「流程走到哪一步」vs「钱发生了变化」、「运营内容」vs「平台技术状态」这两条分界线，在面客侧一字不差地成立 |
| 七个是否本期全用 | **全部先定义**。「先定义、后使用」是纯收益：分类筛选器**只渲染当前接收者实际拥有消息的分类**（`01` 7.3.2），定义了但没有消息的分类**不会在界面上产生空筛选项** |
| 待办的一个登记动作 | 接入指南 4.1 目前分「资产端」「管理端」两组，是两端时代的写法，**`fs` 组尚未增补**。改为按 `end` 分组并增补 `fs` 组，已登记为升级项 **`PMC-U-05`**（主文档 17.5），建议与本 PRD 同批执行 |

**`biz_type` 命名空间不重开**：全平台共用一套（接入指南 3.4「这是全平台唯一的 `biz_type` 登记处——四个端共用这一张表，不按平台分家」）。同一个 `biz_type` **可以出现在多行、分属不同 `end`**，那正是「一个业务事件在用户侧和运营侧各发一条」的正常形态。**本模块不申请新的一级域、不新建登记表。** 需要新的一级域时按接入指南 3.3 申请，改动落在共享登记表上，**不落在本 PRD 上**。

### 19.5 没来得及登记会怎样（**不会丢消息**）

| 环节 | 表现 |
| --- | --- |
| 服务端 | **照常接收并投递**，只记一次告警 |
| 前端 | 映射表里没有条目 → **不渲染跳转按钮**，**消息内容正常展示**（`01` 7.6.6 的降级） |
| 未读角标 | **仍然计入**（映射缺失不是失效） |
| 分类筛选 | 仍归入其 `category`，**不被过滤掉** |
| 监控 | 上报一次 `EV-F-MC-05`「未知业务类型」事件 |
| **唯一例外** | 保留段 `test` / `demo` / `tmp` → **直接拒收** |

> **登记滞后是流程问题，不该让用户承担。** 这也是为什么灰度期的映射缺失率不为 0 是预期的（`R-MC-06`），它应随各接入方登记完成而收敛到 0。

### 19.6 **增量登记自检**（硬性验收，`AC-F976`）

## 20. 双语文案模板规范

> **本章定的是规则，不是内容。** 每条消息叫什么、写什么，由你在**自己的 PRD** 里登记。**本章不含任何一条业务消息的文案。**
>
> （本模块自有界面的静态文案——按钮、标签、空态——在 [`01-页面与展示.md`](./01-页面与展示.md) 12.3，那是消息中心这个壳自己的文字，不是任何一条消息的文案。）

### 20.1 承载方式

| 方式 | 怎么填 | 什么时候用 |
| --- | --- | --- |
| **模板 key + 参数**（**面客侧默认，接入方须用这一种**） | `title_key` / `body_key` + `params` | 绝大多数业务消息 |
| 双语成品快照 | `title_snapshot_i18n` / `body_snapshot_i18n`，**中英各一份** | 仅限每条内容都不同、无法模板化的场景。**用快照必须在登记表里写明理由** |

**为什么面客侧更要坚持模板 key**：站内信在**展示时**按当前语言渲染；面客侧用户可随时切换中英，且历史消息会长期保留（本期不清理，`01` 7.9）。**快照做不到「改模板即对历史消息一并生效」**——一条用快照发出去的消息，译文错了就永远错在那里。

### 20.2 key 命名规则

| 规则 | 内容 |
| --- | --- |
| 形态 | `msg.<biz_type>.title` / `msg.<biz_type>.body`，**与 `biz_type` 三段式同源**，不另起一套命名 |
| 形态示意（**非登记项，不是任何真实业务**） | `biz_type = {domain}.{object}.{action}` → `msg.{domain}.{object}.{action}.title` / `msg.{domain}.{object}.{action}.body` |
| 成对 | `title_key` 与 `body_key` **必须成对提供**；只给其一视为接入错误（**服务端拒收**） |
| 大小写与分隔 | **全小写，点号分隔，多词用下划线**；与 `biz_type` 同规范 |
| **不得更名** | `biz_type` 一经登记不得更名，key 随之不得更名——**历史消息会一直带着当初的 key** |

### 20.3 占位符与参数约定

| 规则 | 内容 |
| --- | --- |
| 占位符形态 | **`{snake_case}`** |
| **时间** | 传 **UTC 原值**，**不得自己格式化**——展示层按接收者时区渲染并带时区标注（`01` 12.4） |
| **金额** | 传**数值 + 币种**，**不得拼成字符串**——展示层按平台统一格式渲染。跨境链融同时有法币与数币，**拼字符串必然在某一种下错格式** |
| **链上地址 / 哈希** | 按国际化基线第 5 章的缩略规则展示；**接入方传原值，不自己缩略** |
| **脱敏** | 完整邮箱、完整钱包地址、完整 IP、证件号**不得**进入 `params` 或正文。字段清单以 [`../v1.0-账户与登录/01-国际化基线.md`](../v1.0-账户与登录/01-国际化基线.md) 第 8 章为准（**本平台自己那份，不引 WS-302**） |
| **禁止句子片段** | ❌ **不得**把动词、状态、名词这类句子片段作为参数传进来再拼成一句话。**中英语序不同，片段拼接必然在某个语言下产生病句。** 需要不同措辞就用**不同的模板 key** |
| 富文本 | **不支持**。正文一律纯文本渲染并转义，HTML 标签不会生效 |

### 20.4 双语一致性要求（**三条**）

| # | 要求 | 为什么 |
| --- | --- | --- |
| **`T-1`** | **中英两份必须同时齐备**，缺任一份即视为翻译缺失，按 20.5 回落。**不得因为「界面默认英文」就只写英文** | 国际化基线 1 已定支持 `en` + `zh-CN` 两种语言，且「界面默认语言为英文**不改变文案工作量**，中英两份都必须齐备，变的只是默认呈现哪一份」 |
| **`T-2`** | **两份的占位符集合必须完全一致**（同名、同数量）。**构建期校验，不一致即报错** | 否则切一次语言就会出现「中文里有某个参数、英文里没有」的**静默信息丢失**——用户不会知道自己少看了一个数字 |
| **`T-3`** | **面客侧文案不得使用控制台侧术语**。国际化基线 0.2 差异 4 已把角色统一称「运营管理员 / Operations Administrator」——那是**运营端口径**，面客侧文案里不得出现 | 面客用户不知道也不该知道运营端的角色名 |

### 20.5 缺失回落（逐条沿用 WS-304 `02` 9.5.4，代入 `fs` 默认语言）

| 情况 | 表现 |
| --- | --- |
| 当前语言的翻译缺失 | 回落到 **`fs` 端默认语言 = `en`**（`D-F929`）；**构建期报告缺失项** |
| **`en` 也缺失** | 降级为「**分类标签 + 时间 + 通用标题**」的最小形态（通用标题取 `01` 12.3 的「通知 / Notification」）；详情页同样兜底 |
| **任何情况** | **绝不把文案 key 显示给用户** |
| `params` 缺某个变量 | 该占位符渲染为**空字符串**并去除多余空格，**不显示 `{xxx}` 原文**；服务端记一次告警 |
| 快照缺某一语言 | 展示 `en` 那一份 |
| **文案完全没提供** | **服务端拒收**——一条没有任何内容的消息不能进用户的列表 |
| 单条降级的影响范围 | 只影响该行 / 该条详情，**不影响同列表其他消息**（`AC-F921`） |

### 20.6 借贷广场业务消息的术语与必备变量（**V2.0 新增，对齐 WS-324 V9.0**）

> **本节只约束"怎么写"，不规定"写什么"。** 具体每条消息的标题与正文仍由接入方在自己的 PRD 里定义——本节加的是**用词与变量的四条硬约束**，防止同一件事在消息里和在页面上是两套说法。

#### 20.6.1 融资需求的状态一律用对外五值（`D-F933`）

| 项 | 规则 |
| --- | --- |
| 取值 | **`待报价` / `已报价待确认` / `放款中` / `已放款` / `已失效／已关闭`**，定义在 **WS-324 分册 6.9.1**（`D-LS-18` / `D-LS-19`） |
| 硬约束 | 凡消息标题、正文或列表摘要里要提「这笔需求现在什么状态」，**一律用这五个取值**，**不得自造第二套说法**（例如「已被锁定」「募集中」「已成交」「待接单」） |
| 不得做的事 | ❌ 在本 PRD 或消息文案里**重新定义**这五值；❌ 另立一套面向消息的展示状态；❌ 用内部状态机取值（`S-FP-*` / `S-FD-*`）直接出现在文案里 |
| 取值从哪来 | **服务端派生下发**（`AC-LS-93`）。接入方把它作为 `params` 变量传进模板，**不在模板里写死某一个状态词** |
| 本 PRD 不做的事 | **不复述五值 ↔ 内部状态的映射表**。映射是 WS-324 的内容，抄进来就是分叉 |

#### 20.6.2 融资类消息必带需求编号 `FP-28`（`D-F934`）

| 项 | 规则 |
| --- | --- |
| 规则 | 凡与某一笔融资需求相关的消息，`params` 里**必须带需求编号 `FP-28`**，并在标题或正文中展示 |
| 为什么 | **资产方在一个项目下可能先后发过多轮需求**。只给融资业务编号（`FD-01`）或还款计划编号（`RP-01`），收件人对不上是哪一轮——这是 WS-326 `D-LN-49` 与 WS-327 `D-RP-62` / `D-RP-66` 已经立下的要求，消息侧必须接住 |
| 形态 | `FP-28` = `项目编号 + 两位轮次序号`，**发布时生成、终身不变**（WS-324 `D-LS-13`） |
| 不得做的事 | ❌ **不得自造第二个需求标识**；❌ 不得只给业务编号就认为够了 |
| 与其他编号的关系 | `FP-28`（需求）/ `FD-01`（融资业务）/ `RP-01`（还款计划）是**三个并列编号**，按消息实际指向的对象带全，**不互相替代** |

#### 20.6.3 英文术语一律回 WS-324 分册 7.6 取词（`D-F935`）

| 项 | 规则 |
| --- | --- |
| 背景 | 面客端**默认英文**（WS-324 `D-LS-15`），本模块的消息正文对境外资金方而言**默认就是英文那一份** |
| 硬约束 | **中英术语一律以 WS-324 分册 7.6 的对照表与设计师 v1.3 产出为准，不自造英文。** 接入方新增模板时，凡涉及广场业务术语，**须回到 7.6 取词**，不得自行翻译 |
| 已定稿的一组（PRD 术语，设计师按 PRD 走） | `质押覆盖状态 / Pledge Coverage Status`，三档取值 `覆盖有余 Ample` / `覆盖持平 At Capacity` / `覆盖不足 Insufficient`（WS-324 `D-LS-17`） |
| 需要对照的术语清单 | 借贷广场、融资项目/资产池、融资需求、需求编号、质押代币数量/价值、代币有效·已失效、项目融资余额、质押率、质押覆盖状态与三档取值、追加质押、解除质押、关闭项目、融资需求/报价/确认/放款四环节、立即还款、立即登录（WS-324 分册 7.6） |
| 本 PRD 不做的事 | **不复制那张对照表**。它在 WS-324 分册 7.6，复制一份必然与之漂移（同 19.1 的理由） |
| 与 `T-1`～`T-3` 的关系 | 本条是 `T-1`（中英齐备）与 `T-3`（不用控制台术语）之上的**第三层约束**：齐备且不串端之后，**用词还必须与广场一致** |

#### 20.6.4 ⚠️ 「确认」是三件不同的事，**不得使用无限定词的单字「确认」**（`D-F936`）

> **这条在消息中心最致命**——三个「确认」会在**同一个消息列表里前后脚出现**，用户点进去才发现不是那件事。页面上有上下文兜底，消息列表里没有。

| 说法 | 实际是什么 | 发生时点 | 归属 |
| --- | --- | --- | --- |
| **「融资确认」环节**（需求方四环节展示名） | 资产方**接受 / 拒绝报价** | 放款**之前** | WS-325 |
| **「融资确认」**（附册 / WS-326 沿用的内部口径） | 资产方**确认收到放款** | 放款**之后**（`S-FD-4`） | WS-326 |
| **「还款确认」** | 资金方**确认收到还款** | 还款之后 | WS-327 |

**四条硬约束：**

| # | 约束 |
| --- | --- |
| 1 | 消息**标题与摘要不得出现无限定词的单字「确认」**。必须写全是哪一种确认——例如「确认收到放款」「确认收到还款」「接受/拒绝报价」 |
| 2 | 凡指需求方四环节的展示名处，**显式写作「融资确认环节（＝接受/拒绝报价）」**，与 WS-325 `D-LS-32` / WS-326 `D-LN-46` / WS-327 `D-RP-65` 同一处置 |
| 3 | **英文下三者不得共用一个词**。取词同样回 WS-324 分册 7.6（20.6.3） |
| 4 | **本模块不单方面改名。** 改名牵动 WS-325 / 326 / 327 与附册，属跨模块裁定，**等需求方拍板**；在拍板前按上面三条写限定词 |

> **为什么消息侧不能等改名**：改名是跨模块裁定、周期不定，而消息列表是这三件事唯一并排出现的地方。**限定词是零成本的止血**，且改名落地后仍然正确。
