## 18. 风险

| 编号 | 风险 | 影响 | 应对 |
| --- | --- | --- | --- |
| ~~R-TI-01~~ | ~~**数币地址的主体口径未定**（账号维度 vs 企业维度）~~ | — | **【V1.1 已关闭】** 需求方 2026-09-10 裁定**取企业维度——币归公司**，规则以 WS-313 `D-DS-05` 原文为唯一事实源，口径落在分册三 14.1a、分册一 8.1。**开发前阻塞项解除**，且**两端本就一致，不产生任何跨 issue 修订**。残留的取值实现风险转 `R-TI-12` |
| **R-TI-12【V1.1 改写】** | **上游取值实现走样，运营端发现不了。** 企业维度要求资产平台取「企业下最初完成企业认证的那位成员」的地址；一旦实现退化为「取任一已认证成员」「取最近登录成员」或「取提交人」，推来的地址就是错的——而**运营端无从判断**：报文里没有企业下的地址集合，运营端拿到什么用什么 | 代币铸到非预期地址，**不可逆、无法回收** | ① 取值正确性由资产平台侧保证，WS-313 `R-DS-04` 已把「不得退化为取任一已认证成员 / 取最近登录成员」写成实现约束并要求单测覆盖（`AC-DS-77`），**本模块依赖该约束、不重复定义**；② 本模块以 `D-TI-20` 实际收币地址与 `D-DS-05` 并列展示、不一致时高亮，作为事后可发现的兜底；③ 详情页固定标注「该地址为该资产方企业的统一收币地址」（分册一 10.3），让口径写在人看得见的地方 |
| **R-TI-14【V1.2 新增】** | **三套状态被读错。** 同一笔业务现在牵涉签发状态、代币状态、融资质押状态；其中两根在代币侧且**本期各只有一到两个取值**，容易被当成同一件事 | 对外应答给错结论；运营人员误判一枚代币还能不能用 | 分册一 9.12：`ST-01` **分页承载**（签发状态只在资产侧、代币两轴只在代币侧，本期不存在三者同页）、`ST-02` **三个字段一律带限定词，页面任何位置不出现无限定词的「状态」**、`ST-03` 三根轴互不写互不派生。与「两个交易哈希必须带限定词」是同一条原则 |
| **R-TI-15【V1.2 新增】** | **代币编号被误当成判重依据。** 它与来源资产 ID 严格 1:1，实现时容易顺手拿它做唯一约束 | 防超发的红线被绕过 | 分册三 14.2a 写死：代币编号**只用于展示与检索**，**不得**作为幂等键、唯一约束或重复铸造判定依据；防超发唯一约束仍是「来源资产 ID」（`AC-TI-40` 不变），并加反向验收 `AC-TI-70` |
| **R-TI-13【V1.1 新增】** | **两笔链上交易被混淆**：详情页同时有存证交易哈希与铸造交易哈希，运营人员对外应答时可能给错 | 对方拿哈希查不到预期内容，信任受损；排查成本高 | 分册一 10.5 的 `B-01`～`B-04`：两区块分开、标题明确、哈希字段**必须带限定词**、顺序与业务时序一致。反向验收 `AC-TI-60` |
| R-TI-02 | 汇率配错（多一个零、方向填反）导致铸造数量严重偏离 | 铸造不可逆，超发无法回收 | ① 新增/停用二次确认展示"当前值 → 新值"对照与影响面笔数；② 汇率值方向在表单上写死为 `1 <源币种> = X USD` 的句式，不给用户选方向；③ 换算过程整组快照 + 详情页展示，错误可被 J-4 应答时发现；④ 全部操作留痕可追责 |
| R-TI-03 | `S-TI-5` 被误当成失败而重试，造成**超发** | 同一资产铸两次，红线事故 | 【红线】`S-TI-5 → S-TI-2` 边不存在；界面不渲染重试按钮；服务端拒绝；补扫不处理 `S-TI-5`；反向验收 AC-TI-42 |
| R-TI-04 | 定时补扫自动重发已提交过交易的资产，造成超发 | 同上 | 【裁定】补扫**只处理从未提交过链上交易的资产**（分册一 11.2），链上类 `S-TI-4` 与 `S-TI-5` 一律不自动处理 |
| R-TI-05 | 合约 `decimals = 0`，2 位小数的换算结果无法铸造 | 签发全线失败 | DEP-TI-04 一句话确认即可；两种取值下页面结构与流程不变，只改一行取整规则 |
| R-TI-06 | **存量无地址资产**在本模块上线时仍存在，落入 `S-TI-6` 终态且运营端无处置手段 | 一批资产永久发不出去 | 主文档 3.4 的一次性数据体检作为**上线前置条件**；不变量由 AC-TI-44【红线】守住 |
| R-TI-07 | 汇率停用后大批资产被拦截，运营人员未察觉 | 资产滞留、资产方投诉 | 汇率列表顶部常驻「N 个币种无有效汇率，共 M 笔资产因此待签发」提示条；停用二次确认展示影响面；异常筛选覆盖。**本期不发站内信**（N-07），可见性靠页面承载 |
| R-TI-08 | 合并式下资产清单列数变多，可读性下降 | 使用效率下降 | 列表只放签发状态、原因、代币数量、重试次数四列；合约、链、哈希、地址、换算过程一律放详情页的独立区块 |
| R-TI-09 | 日后运营端取得代币生命周期职责（冻结/质押/赎回），需要把签发结果拆成独立实体 | 一次数据迁移 | 本期把 `D-TI-01`～`D-TI-20` 设计成**内聚的一组**，可整组迁出；且定论 10 显示职责正在离开运营端，风险方向与拆分预期相反 |
| R-TI-10 | 链上交易长时间无回执，`S-TI-5` 大量堆积，人工逐条查询成本高 | 运营负担 | 本期 `S-TI-5` 保留逐条人工查询（这是定论 9 的红线要求）；若上线后堆积明显，下一期再评估"批量查询链上状态"——**批量查询不等于批量重试**，不触碰红线 |

### 19.3 自动签发、重试与状态机

| 编号 | 验收项 |
| --- | --- |

| AC-TI-35 | 重试不限次数，每次累加重试次数并在时间线留痕；**补扫自动重发不计入重试次数**，但在时间线留痕 |

### 19.4 红线

| 编号 | 验收项 |
